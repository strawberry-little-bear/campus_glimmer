拾光校园（Campus Glimmer）是一个面向校园生活的二手交易与社区协作项目。它从“发布一件闲置、找到一个买家”的小闭环出发，逐步补齐校园交易中经常被忽略的细节：在哪里交付、如何沟通、预约是否有效、交易进行到哪一步、消息是否被看到、问题由谁处理，以及运营者如何了解站内真实需求。

项目不是一次性推倒重做的演示页面，而是按真实业务链路持续演进的 Django 项目。每次迭代尽量同时考虑数据模型、页面交互、权限边界、数据库迁移、后台运营和自动化测试，让新增能力能够自然地接入原有系统。

## 项目定位

校园二手交易和普通电商并不完全相同。校园用户通常在相对有限的地理范围内活动，交易更依赖当面沟通和时间协调；商品生命周期短，供需变化快；用户既是买家，也是卖家、内容参与者和社区成员。因此，项目将“商品列表”作为入口，但不把系统目标局限在商品 CRUD：

- 对用户，重点是降低从发现商品到完成交易的沟通成本；
- 对交易双方，重点是提供可追踪的预约、状态和交付确认；
- 对社区，重点是保留通知、举报、内容审核和争议处理的入口；
- 对运营者，重点是把搜索、浏览、收藏、预约和完成交易等行为整理成可解释的指标；
- 对项目本身，重点是用小步、可回溯的独立提交持续迭代，而不是一次性堆叠大量改动。

## 功能模块

### 1. 商品发布与校园地点

- 发布、编辑、删除商品，支持标题、描述、价格、分类、成色和多图上传；
- 商品状态覆盖“在售、已预订、已售出、已过期”等主要阶段；
- 支持“出售”“免费赠送”和“限期借用”三种交易方式，免费商品不会以 0 元伪装成普通商品，而是在列表、详情、领取申请和订单中使用明确的免费语义；
- 限期借用商品可以设置借用天数和押金记录，成交价固定为 0 元，交付确认后进入“借用中”，到期前和逾期后分别发送提醒；
- 借用归还需要借用者登记、发布者确认，双方完成确认后订单进入“已归还”，商品重新开放借用；同一件物品可以保留历史借用订单并再次进入新的借用周期；
- 免费赠送采用独立的领取申请队列：申请不会立即锁定商品，发布者可以查看申请说明和领取地点，选中一位同学后再生成正式订单，其余申请会收到结果通知；申请人也可以在发布者处理前撤回申请；
- 支持为商品设置可选的展示截止时间，到期后自动从公开商品流和推荐结果中隐藏，并由维护命令将商品状态更新为“已过期”；
- 卖家可以编辑已过期商品并设置新的未来截止时间，系统会自动重新上架，避免毕业季、短租和临时清仓商品长期占据列表；
- 商品可以绑定已配置的校园地点，包括校区、楼栋和更具体的交易说明；
- 支持按关键词、分类、地点、成色和价格区间组合筛选；
- 支持按最新发布、价格和相关度排序，并提供分页；
- 商品详情展示卖家资料、地点、留言、收藏状态、相近商品和可用的交易操作；
- 出售类商品会显示价格参考卡：基于近 180 天同类商品的价格分位数给出常见区间、中位数和参考可信度，并结合浏览、收藏和进行中预约展示需求热度；
- 价格参考使用可解释的站内统计，不自动改价、不承诺成交，也会在样本不足时降低提示强度；
- 用户可以收藏商品，也可以对暂时不可用的商品开启有货提醒；
- 首页提供分类入口、热门地点、最新商品和基于可解释信号的推荐；
- 校园地点可以标记为公共交付区域，并补充开放时间、照明、门禁等安全提示，供交付推荐使用。
- 管理员可以在运营看板查看按校园地点聚合的供需热力：当前在售、周期新增、有效求购、预约和完成交易会形成可解释的地点活跃度与供需压力，不采集用户实时位置。
- 管理员可以配置有开始和结束时间的校园专题，例如毕业季清仓、教材交换周；发布者可以在发布商品时加入已启用专题，用户从专题页集中浏览当前在售商品。
- 发布者可以在“我的商品”中批量将多件商品加入或移出专题，服务端只更新当前用户拥有的商品，并通过事务保证批量操作的一致性。
- 运营看板会按专题时间窗口聚合新增商品、当前在售、曝光、收藏、预约和完成交易，并给出浏览转预约、收藏转预约和预约完成率等转化指标；
- 对浏览较多但没有预约、或专题尚未形成供给的活动，系统会生成可解释的运营提示，帮助运营者决定是补充商品、优化描述，还是调整活动组织方式。

> 当前“就近”是基于校园地点数据的筛选，不依赖 GPS，也不会把用户实时位置上传到服务端。这样更适合校园内的固定交易点，也为后续增加距离、时间段或校区偏好留下扩展空间。

- 卖家可以在“我的商品”里看到每件商品的生命周期诊断，把“发布了多久”拆成新鲜在售、正常在售、关注放缓、沉底较久、即将到期、已下架或已成交几种状态；
- 诊断同时给出该商品的浏览、收藏、预约记录和距上次刷新的天数，卖家能判断问题是出在定价、图片还是商品已经沉到底部；
- 商品支持“刷新”操作，用于把仍在售的商品重新带回列表前排，刷新间隔和每月次数都有限制，避免靠频繁刷新长期霸占首页；
- 刷新节奏由后台按 24 小时最小间隔和每月 4 次上限控制，超出额度时页面会说明原因，而不是静默失败。
- 系统会定期把需要处理的商品合并成一条站内提醒发给卖家，未读时会在导航栏显示，不需要卖家记得主动去查；
- 提醒分两类：一类是商品进入“关注放缓 / 沉底较久 / 即将到期”需要决策，另一类是久未成交且价格高于同类常见区间时给出可参考的同类区间；
- 两类提醒按卖家合并，同一个卖家一次只会收到一条，列出条数有上限，其余折叠为“另有 N 件”；
- 提醒带冷却期，同类提醒在冷却期内不会重复发送；免打扰时段内只推迟发送，不会消耗冷却额度，也不会漏发；
- 价格提醒只引用真实存在的同类商品区间，没有足够样本时不给建议，也不会把“久未成交”直接等同于“应该降价”。

### 2. 搜索、保存与推荐

- 全局搜索支持关键词、分类、校园地点、成色和价格条件；
- 搜索框支持基于历史搜索、分类和地点的联想建议；
- 搜索词、筛选条件和结果数量会以结构化记录保存，用于分析供需缺口；
- 用户可以保存搜索条件，并在后续查看或启用、停用保存的搜索；
- 保存的搜索支持三种提醒节奏：即时提醒、每日汇总和每周汇总，无需重建关注即能切换；
- 汇总节奏会把缓冲区里的命中合并成一条通知，并可以限制单条最多列出几件商品，剩余命中以“另有 N 条未展示”提示；
- 汇总通知会写入命中原因（关键词、分类、地点、成色、价格），让用户知道为什么这条条件触发了提醒；
- 关注搜索支持设置临时静默时间，适合考试周或假期暂时不需要提醒；静默期间命中仍然会进入缓冲区，不会丢失；
- 关注搜索页会展示每条关注的待提醒数和当前命中数，方便判断是否需要放宽条件；
- 从汇总节奏切回即时提醒时，等待中的命中会立即补送一条，不会抄到下一次计划任务；
- 缓冲区使用“关注 + 商品”唯一约束，同一件商品重复发布不会产生重复命中记录；
- 推荐结果优先使用分类、地点、热度和新鲜度等可解释信号；
- 推荐反馈会被记录，便于后续判断推荐是否真正帮助用户发现商品；
- 搜索运营页可以查看热门搜索、去重用户数、无结果比例和可回到商品列表的跟进入口；
- 搜索洞察页会从同一用户的相邻搜索里挖出「同义词候选」：先搜 A 无结果、紧接着改搜 B 有结果，这种改口行为就是用户自己发现的等价说法，运营确认后即可变成同义词；
- 登录用户可以进入“校园互助机会”，查看平台根据自己仍可交易的商品和有效失物招领记录整理出的帮助机会；
- 用户可以在“互助贡献”页面查看累计积分、当前等级、下一等级进度、已解锁徽章和最近贡献事件；贡献记录只展示自己的可审计摘要，不公开交易对象和私密沟通内容。
- 互助贡献页提供“校园循环影响力”报告入口（`/contributions/impact/`），按最近 6 个月汇总已经完成或完成归还的流转记录；报告展示完成次数、不同物品数、协作同学数、分类 / 地点分布和月度趋势。
- 循环影响分采用公开且可解释的规则计算：完成出售计 8 分、免费赠送计 12 分、借用归还计 10 分；取消、待确认和仍在进行中的订单不会计入，页面也不展示交易金额或交易对象。
- 机会流会复用求购和失物招领的可解释匹配规则，展示匹配分数、分类 / 地点 / 关键词等依据，并提供查看求购、响应需求或查看匹配记录的入口；
- 同一条求购或失物记录只保留最有价值的一条推荐，过期记录、用户自己的求购和失物记录不会进入可响应机会。
- 用户可以对暂时不需要的机会执行“暂不展示”，系统只在推荐层记录 30 天的个性化忽略状态，不修改原始求购或失物招领数据；忽略到期后机会可以重新进入推荐。
- 求购响应和失物招领线索被确认后，发布者可以补充一次“互助完成反馈”，区分“已完成”和“暂未解决”，并选择“按约完成”“沟通顺畅”“信息有帮助”等轻量标签；它与交易星级评价分开，避免把非交易协作强行套进交易评分。
- 完成反馈会通知参与者，并在“已完成”时为帮助者生成幂等的校园互助贡献记录；未解决的反馈也会保留，方便后续运营统计和再次跟进，而不会被错误计入完成次数。

### 3. 失物招领与智能匹配

失物招领不是商品交易的附属页面，而是一条独立的校园协作链路。用户可以发布“我丢失了”或“我捡到了”的记录，平台在不公开敏感联系方式的前提下，帮助双方发现可能的对应关系。

- 记录支持丢失 / 拾到两种方向，并可填写标题、描述、分类、校园地点、发生时间、截止时间和辨识特征；
- 公开列表支持关键词、类型、分类、地点和时间排序筛选，过期记录会自动从公开入口隐藏；
- 系统会对丢失与拾到记录进行轻量规则匹配，综合比较分类、地点、发生时间和描述关键词；
- 匹配结果会展示分数和具体依据，例如“物品分类一致”“发生地点一致”“发生时间相差 3 天内”，避免只给出不可解释的推荐结论；
- 新记录发布后，会向已有高匹配度记录的发布者发送可去重的站内提醒；
- 用户可以向记录发布者提交私密线索，也可以关联自己发布的另一条相反类型记录；
- 记录发布者可以确认或暂不匹配线索，确认后双方记录进入“已匹配”，并通过站内通知继续沟通；
- 线索在确认前只对记录发布者可见，页面明确提示不要公开电话、宿舍号等敏感信息；
- 线索确认后，发布者可以记录互助结果和过程标签；反馈只展示必要的结果摘要，不公开私密联系方式，也不会替代失物归属的人工核验；
- 管理后台可以查看记录、线索、状态和处理时间，方便后续增加审核、举报和校园治理能力。

当前匹配采用可解释的规则评分，不宣称自动确认物品归属。这样既能快速形成实用闭环，也为后续接入更细的图像特征、时间窗口和人工审核留下边界。

### 4. 交易预约与订单状态

- 买家从商品详情发起交易预约；
- 预约创建时校验商品状态，并使用事务和行级锁尽量避免并发预约同一件商品；
- 买卖双方可以在订单详情中推进交易状态；
- 交易确认后可以提出交付时间、结束时间和校园地点，另一方可接受或暂不接受；
- 订单详情会根据商品发布地点、双方历史交付记录和地点使用情况推荐交付地点，并说明推荐依据和安全提示；
- 系统会从未来一周的校园日间时段中筛选双方均无预约冲突的候选时间，优先展示工作日课后和周末等更容易完成当面交付的时段；
- 推荐结果可以一键回填预约表单，但最终地点和时间仍由交易双方协商确认；
- 系统会检查买卖双方当前有效的交付安排，拦截重叠时间段，减少同一用户同时答应多笔交易的爽约风险；
- 每次交付安排都会留下提议人、回应人、时间和状态，重新协商时保留同一订单的可追溯链路；
- 接受交付安排后订单自动进入“待当面交付”，再由双方分别完成交付确认；
- 记录订单事件，保留状态变化和时间线，方便回看交易过程；
- 支持交付确认、评价和交易争议入口；
- 限期借用订单单独记录借用押金、预计归还时间、实际归还时间和双方归还确认状态；借用押金只作为双方线下约定的记录，不由平台代收或自动结算；
- 借用订单在双方完成交付确认后进入“借用中”，系统会发送归还前提醒和逾期提醒；借用者登记归还、发布者确认收到后，商品才会重新回到可借用状态；
- 借用逾期不会只发一条提醒就彻底沉默：逾期 1 天起进入三级催收阶梯，一级只提醒借用方，二级同时告知双方平台已开始记录，逾期满 7 天上报治理工作台；
- 催收阶梯按“逾期了多久”推导当前该在第几级，漏跑一次计划任务下一次会自动追上，不会因为一次故障永久落后一级；
- 同一笔订单两次催收之间至少隔一天，跳级追上来时会补发二级那一声（借出方在这一级才第一次被告知），但不会补播被跳过的一级；
- 平台在催收里只做记录和通知：不自动取消订单、不代扣押金、不给任何人打上失信标记，押金仍由两个同学线下结算；
- 双方确认归还后催收记录立即闭环，等级和升级次数保留下来供回看，但不再计入待办——同学之间的借用不该留下永久污点；
- 交易争议可以由买卖双方补充 JPG、PNG、WebP 或 PDF 证据，平台和交易参与人可以在受保护的下载入口中查看；
- 证据上传会写入订单事件时间线，并向另一方发送站内提醒，方便核实争议发生前后的过程。
- 通过管理命令处理临近超时提醒，并自动释放已经过期的预约；
- 订单详情提供交易安全卡，综合检查商品图片、同类价格、发布者历史履约、校园认证、公共交付地点、预约时段、交付确认码和已确认异常记录；
- 安全卡使用可解释的“提醒 / 注意 / 保障”信号，不阻断正常交易、不展示私密联系方式，只帮助双方在交付前完成必要核对；
- 订单相关通知会根据状态变化、提醒策略和用户通知偏好生成。

### 5. 私信、留言与通知中心

- 商品详情页支持公开留言；
- 用户之间可以围绕商品发送站内私信；
- 会话列表按最近消息聚合，展示最近一条消息、消息总数和未读数量；
- 支持按用户、商品或消息内容搜索会话，并可批量标记已读；
- 站内通知中心按通知类型、时间和已读状态组织消息；
- 顶部导航会定时刷新私信和站内通知未读数，页面切到后台时暂停刷新，重新回到前台后恢复；
- 活动中心会聚合交易、收藏、保存搜索、评价、审核和运营提醒等动态；
- 用户可以按类别关闭不需要的提醒，管理员还可以单独控制运营告警日报；
- 商品展示到期后会向发布者发送可关闭、可去重的站内通知，并保留商品详情作为重新编辑和上架入口；
- 免费领取申请的提交、选中、未选中和撤回状态会进入通知中心，并可在通知偏好中单独关闭；
- 新商品发布后会与有效求购按分类、地点、预算和关键词进行轻量匹配，并通过可关闭、可去重的站内通知提醒求购发布者；
- 商品发布者可以从匹配结果中一键响应求购，并补充成色、交付时间等说明；求购发布者可以查看匹配分数和依据，确认或拒绝响应，确认后再进入商品页完成正式交易；
- 求购响应会保留提交、确认、拒绝和撤回状态，避免把一次性的匹配提醒误认为已经完成交易；
- 失物招领的可能匹配、私密线索提交、确认和暂不匹配也会进入通知中心，并遵循独立的通知偏好；
- 互助机会页支持按日生成摘要通知：系统会汇总当前用户可响应的求购和失物招领机会，尊重个人通知偏好，并使用“日期 + 用户”幂等键避免重复提醒；
- 通知中心支持“稍后处理”：用户可以将未读事项延后 2 小时、24 小时或 3 天；延后期间不会计入顶部未读提醒，截止后自动重新出现，且保留原始通知和处理入口；
- 通知偏好支持免打扰时段：用户可以配置跨午夜的时间窗口，例如 22:00—08:00；时段内顶部未读提醒和动态未读汇总会暂时静默，但通知不会丢失，仍可从通知中心主动查看；
- 借用订单的即将到期、逾期、归还登记和双方完成归还确认也会进入通知中心，并遵循通知偏好和幂等发送规则；
- 借用逾期催收的第二级会同时通知借用方与出借方，第三级上报治理队列后不再继续向双方私域发消息，避免催收变成骚扰；
- 关注搜索的汇总提醒拥有独立的通知类型和偏好开关，关闭后不会再生成汇总，但缓冲区仍然会继续记录；
- 汇总提醒按“用户 + 周期”生成幂等键，每日汇总按日期去重，每周汇总按 ISO 周去重，重复运行计划任务不会重复推送；
- 每一条被标记为已读的通知都会记录阅读时间，用户侧可以对放置超过一周的未读事项看到温和提示，运营侧则能统计每类提醒真实的处理时效；

### 6. 社区治理与后台处理

- 用户可以举报商品，举报包含原因、补充说明和处理状态；
- 管理员可以在举报队列中查看、审核和记录处理备注；
- 私信和留言经过内容审核规则后，保留审核事件、命中规则、风险等级和复核状态；
- 交易争议有独立处理入口，避免把异常订单埋在普通订单列表中；
- 交付预约异常（未到场、严重迟到、现场安全问题）由任意一方提交，另一方不会看到提交动作本身；
- **治理工作台**把商品举报、交易争议、交付预约异常三类队列合并到同一页面，按队列、状态和统计周期筛选，最早超期的事项排在最前；
- **借用逾期催收的第三级不再只是一句“已上报”**：它作为第四类队列进入治理工作台，和三类传统队列放在同一张表里计算等待时长；
- **该队列的时限从三级催收发出那一刻起算**，而不是从第一级建行起算——那之前平台在走自己的阶梯，不该记在治理账上；
- 按队列、状态和统计周期筛选，最早超期的事项排在最前；
- 三类队列共用一套处理卡片，但处理时限不同：预约异常会阻塞一次线下交付，时限最短；交易争议涉及双方举证，时限最长；
- 预约异常此前只能在 Django 后台处理，现在工作台可以直接给出结论，处理人、处理时间、双方通知和订单时间线会一并写入；
- 每个队列都会统计周期内的处理时长（中位数、P90、最快/最慢）和时限内完成率，让"有多少"之外多一个"等了多久"的答案；
- 待处理清单不按统计周期过滤：周期开始前就超期的事项，恰恰是最不该被藏起来的那一件；
- 管理后台提供用户、商品、分类、校园地点、订单、通知和审核相关数据的维护入口；
- 治理操作尽量留下结构化记录，便于追责、复盘和后续运营分析。

### 7. 运营看板与运营告警

管理员可以按 7 天、30 天、90 天或 1 年查看运营数据，主要包括：

- 商品发布、浏览、收藏、预约、完成交易、搜索、新用户和举报数量；
- 有效求购数量、匹配通知量、被触达求购数和匹配通知阅读率，用来观察供需撮合是否真正产生回应；
- 求购匹配的“收到提醒 → 卖家响应 → 求购者确认”转化漏斗，并区分响应提交时间与确认处理时间；
- 求购响应总数、收到响应的求购数、确认/未采纳数量，以及按分类和期望地点拆分的响应确认率；
- “详情浏览 → 收藏 → 预约 → 完成交易”的去重转化漏斗；
- 每日趋势、订单状态、分类供给和校园地点供给；
- 校园供需热力：按配置地点展示供给、需求、预约和完成交易，并用“需求紧张 / 需求偏高 / 供需相对平衡 / 供给较充足”帮助运营人员定位补给机会；
- 校园需求雷达：将周期内的无结果搜索与有效求购按关键词、分类和校园地点聚合，输出“优先处理 / 值得补给 / 持续观察”分级；
- 需求雷达不会只显示一个无法解释的推荐分，而是同时展示无结果搜索次数、独立搜索用户、有效求购数、当前匹配供给和证据信号，并给出补充供给、关注地点、完善同义词或创建专题等建议；
- 需求机会分采用可解释规则：无结果搜索代表显性缺口，有效求购代表更强的主动意愿，当前供给不足会提高缺口优先级；结果只保留聚合统计，不暴露具体用户身份；
- 当需求雷达识别到高优先级缺口时，结果会进入运营提醒和运营告警日报，管理员可以从提醒直接回到对应统计周期，形成“发现缺口 → 触达运营 → 补充供给”的闭环；
- 治理队列处理时效：按队列展示周期内处理量、待处理、超期数量和中位/P90 耗时，并给出时限内完成率；
- 当任一治理队列出现超期事项时，运营告警会直接点名该队列和超期件数，交付预约异常按最高优先级提示，可以从告警一键进入治理工作台；
- 借用逾期催收超期只升到“需要关注”，而不是“优先处理”：它不阻塞一次线下交付，三件慢还的充电宝不该盖过一次约好的当面交付；
- 管理员可以直接从需求机会卡片建立跟进任务；任务会保存创建时的机会分、证据信号和建议动作，并通过“待跟进 → 跟进中 → 已完成 / 已忽略”记录运营处理过程，避免看板刷新后失去上下文；
- 需求跟进闭环效果：把「任务派出去之后缺口到底有没有被补上」单独做成一个面板，以任务创建时间为分界，对比同一主题在前后两个窗口的无结果搜索率，输出缺口收敛、基本持平、缺口扩大、样本不足和观察期未结束五种判定；
- 闭环判定不把变化和原因混为一谈：无结果率下降的同时可用供给增加，才判定为「供给动作生效」；率降但供给没涨，会提示排除季节性因素；率升且供给也没动，则明确记为任务未见效果；
- 基线期或观察期搜索量不足、以及观察期还没走完的任务单独标注，不计入命中率——用一次偶然的下降宣称成功，会让整个雷达失去可信度；
- 闭环命中率过低时会触发运营告警，提示该修的是机会分口径或补给动作是否对准真实需求，而不是继续加供给；
- 需求雷达命中率的学期纵向对比：跳学期趋势比的是相邻两个等长周期，而校园需求本身就顺常期节漂移：开学前两周搜教材和宿舍用品，考试周找复习资料，毕业季则是供给集中释放。现在把每个跟进任务按创建日归入学期阶段，只拿同一个阶段在相邻两个学期里相比，因为“这届考试周和上届考试周”才是唯一可比的那一对；
- 只在一个学期出现过的阶段不给方向：没有同类的早期阶段可减，而前三十天属于另一个季节，把它当成上个学期比会把季节性读成雷达在漂移；
- 每个阶段格子独立套用与整体相同的任务数门槛，不为了让表格好看而放宽：两周里只建了三个任务的阶段，命中率一步就是三分之一个台阶，在它上往方向说话只是算术；
- 早于第一个学期开始配置、或落在学期内未划分阶段的任务单独计数，不被丢掉——丢了就会缩小分母，让每个阶段的命中率安静地变大；
- 本模块只报告，不排序、不把阶段命中率回流到机会分、等级或状态：雷达学会按自己超长发挥的季节调整权重，比误报本身更糟；
- 校园专题表现：按专题自身开始、结束时间与统计周期的重叠部分计算，避免把活动之外的行为错误归因给专题；
- 专题分析同时保留汇总指标和逐专题漏斗，使用去重浏览记录和结构化订单记录，不暴露单个用户的行为明细。
- 学期节律与交易高峰：按学期日历把统计口径从“平均值”换成“当前处于学期的哪个阶段”，展示当前阶段与上一阶段的商品、求购、完成交易变化和搜索无结果率；
- 学期阶段通过偏移天数划分，管理员可以在后台调整开学两周、常规教学、考试周和毕业季的边界，不需要改代码就能适配不同学校的校历；
- 阶段对比同时给出“供给上升 / 供给回落 / 与上一阶段持平 / 基准阶段”的判断，帮助运营人员理解供给节律，而不是把阶段计数当成因果结论。
- 搜索同义词候选挖掘：同义词此前完全靠运营手工猜测「学生搜不到充电宝会不会改搜移动电源」，既低效又必然遗漏；现在把同一用户 30 分钟内的相邻搜索两两配对，只保留「前一次无结果、后一次有结果」的改口证据，按出现次数和涉及用户数排序；
- 候选只提议、不自动生效：同义词会改变此后每一次搜索的结果范围，配错一对（例如把 iPhone 和手机壳配到一起）会让所有人的搜索悄悄变差，所以每条候选都要运营在后台确认后写入；
- 已经启用为同义词的词对不再重复推荐，但停用后的同义词不会屏蔽候选——停用即不再影响搜索，改口证据重新出现时应当重新提醒运营；
- 搜索洞察页为每条候选提供「一键确认」入口，两个词直接预填进后台表单，运营只需要补一个是否启用的开关；候选也随 CSV 一起导出，便于转交同事批量处理。
- 同义词效果回流：同义词确认之后到底有没有用一直没人知道。现在把每条确认时间当成分界线，统计学生原本输入的搜索词在分界线两侧各四两周的无结果率；无结果率下降算生效，基本持平往往说明这两个词本来就不指同一类东西，上升则需要回头核对词对是否配错；
- 搜索趋势与筛选偏好：总量只能回答“搜索变多还是变少”，回答不了“是谁在变、筛选项有没有换口味”。现在按搜索词和按筛选项分别与上一个等长周期对比，看量的升降，以及无结果率、点击率的变化；
- 占比一律按同一类筛选项内部计算：全站搜索量上涨会推高每个取值的绝对次数，按次数比会让每个选项都“上升”而毫无信息量，所以分类占比上升只代表在用了分类筛选的搜索里它份额变大；
- 四类筛选项分别是成色、分类、地点和价格带；价格没有独立字段，由学生自己填的最低价 / 最高价落进哪个区间决定，两个价格都没填的搜索不计入任何价格带；
- 样本不足的搜索词和筛选项单独标注、不判方向：一个只被搜过两次的词足以让无结果率从 0% 跳到 50%，把噪声当趋势比承认“看不出来”更糟；
- 把“搜不到”和“搜到了不点”分成两类线索：前者是供给问题该补货，后者是排序、价格或标题问题，改搜索配置没有用，混在一张榜里会看错方向；
- 筛选组合的交叉对比：单维表只能回答“图书占比升了”和“50-200 元占比升了”，两者同时上升并不等于“50-200 元的图书”在升——这两个信号可能来自两群不相干的学生，把两个占比相加对一个没人测过的数字做算术；
- 组合占比一律在同一个分类内部计算：用全站搜索当分母会让占比随总量潮池般涨落，并且把不同分类的组合拿来互相比，那回答的就不再是“这个品类里学生更爱看哪个价位”；
- 只做分类×价格带二维交叉，不做三维：分类和价格带是学生能同时想着的两个因素，再去交上地点在校园搜索量下几乎每个格子都是空的，表格会变成一片破折号；
- 组合的样本门槛与单维筛选完全一致，一分不降：组合是交叉表的一个格子，证据比任一个单维都薄，单维那边算太薄的数据不能到组合表里突然变成“够薄所以够了”；本周期和上一周期都少于四次的组合只标为样本不足，只列出来、不判方向；
- 只在一个周期出现过的组合报为“本期新出现”，只在上个周期出现过的报为“本期已消失”，两者都不给占比差：没有上期的占比可减；
- 组合对比同样只报告、不改任何东西：不动门槛、不动价格带边界、不动分类，也不新建表和迁移，只读 `SearchQuery`。
- 候选门槛建议：出现次数门槛此前一直是个从没被回流数据校正过的常量，松了会让运营在噪声里挑词对，紧了会把低频但真实的等价挡在视野外。现在用已确认同义词的命中率反推这个门槛是松了还是紧了，在固定档位表（1–5 次）上只给出相邻的一档；
- 门槛只建议、不自动改：它决定运营能看到哪些候选，属于平台行为的开关，悄悄改掉它等于在没人看着的时候改掉平台照着行动的依据，因此模块从不写这个常量，改不改、什么时候改由运营决定；
- 词对大面积配错时不建议调门槛：若可判定的同义词里有超过四成让无结果率上升，问题出在词对本身，收紧门槛只会把这些配错的词对藏起来不给人看。这种情况单独标为「不是阈值问题」，并建议先回头核对；
- 每档的代价都算出来摆在一起：同一份搜索日志按 1–5 次各跑一遍，把候选总数和累计出现次数并列展示，运营在决定之前就能看到放宽一档会多出多少条待确认；
- 样本不足不给方向：可判定的同义词少于四条时命中率还是「一两条的观感」，此时只报告、不指方向，宁可维持现状。
- 候选否决与负向样本：候选列表此前只能「确认」不能「否决」，被运营看过并否掉的词对不留任何痕迹，下周原样回到列表里，运营只能把同一批噪声再读一遍；而门槛建议只读已确认的词，于是一个确认了两百条、也默默否掉两百条的候选池，和一个只确认了两百条的池子，在它眼里没有区别。现在每条候选行内都能直接否决，连同原因和备注一起落库，被否决的词对不再进入挖掘结果；
- 否决按出现次数加权，不按否决条数：一个出现四十次仍被否掉的词对和一个只出现两次的词对说的不是同一件事——前者是运营在说「平台的词汇表里这两个词确实不是一回事」，后者只是某位运营的个人口味。按条数计数会让否得多的运营看起来像面对着一个嘈杂的候选池，所以每条否决都带上它背后的改口频率一起呈现；
- 低于门槛的否决不进门槛判断：运营在候选列表之外否掉一个从未达到门槛的词对，说明不了门槛该松还是该紧——门槛从来不是他看见这个词对的原因。这类否决单独计数、单独展示，不混进门槛方向的样本里；
- 否决可撤销，且与确认互斥：运营三月否掉一个词对、十月改主意是常态，一个只能新增不能撤销的否决表会把一次误判永久变成一次误判；而同一个词对同时存在「已确认生效」和「仍在屏蔽候选」两条记录是自相矛盾的，矛盾必须由人来解开——词对后来被确认时否决标记为失效而不删除（保留「有人说过不」的痕迹），同义词被删掉时否决重新生效；
- 否决只是留痕，不是平台行为：它不扩大也不缩小任何搜索的结果范围，更不修改候选次数门槛本身。门槛方向由四个信号给出——样本不足、更像挖掘规则读错了（高频仍被判为不是同一个东西，收紧只会把它们藏起来）、支持收紧（否决集中在证据不足）、以及两类理由都不占多数时维持现状；
- 趋势对比只做对比，不改动同义词候选的出现次数阈值，也不重排需求雷达——阈值一动，平台照着行动的依据就变了，这个决定必须由运营来做；门槛建议一节虽然会给出方向，但同样只到建议为止，不碰常量本身。
- 统计只覆盖已确认的同义词，候选本身不落库，无法统计其确认率；已停用的同义词不参与判定，停用后的搜索变化属于市场而不属于这条配置。
- 通知处理时效与触达质量：区分“送达”与“被处理”，按通知类型统计已读率、平均 / 中位 / P90 处理时长，并把交易关键类通知单独汇总；
- 处理时长分布按“1 小时内 / 1 天内 / 3 天内 / 1 周内 / 1 周以上”分桶，避免只用一个平均值掩盖真实分布；
- 发送时段与处理时段对照，用来发现正好落在用户免打扰时段、始终没人处理的发送时间；
- 超出一周仍未处理的通知单独计数，并进入运营建议，防止未读数长期虚高；
- 当某类通知已读率低于 50% 或平均处理时长超过一周时，会标记为“需关注”并给出降低频率、改为摘要合并或调整发送时间等可执行建议；
- 订单全链路阶段时长：把“下单 → 卖家确认 → 当面交付 → 成交 / 借出 → 物品归还”的等待拆到每个阶段，用中位、P90、平均和最快 / 最慢分别描述，定位真正拖慢成交的那一段；
- 阶段耗时只统计相邻两个状态流转时间都齐全的订单；周期结束时仍在流程中的订单单独计入“进行中”，不把在途订单误判为超时；
- 瓶颈阶段会按中位耗时占比标出，并与分类、交付地点两个维度交叉拆分，回答“慢在哪一段、慢在哪些商品或地点”；
- 当某条流转记录的时间早于上一阶段时，该样本按异常剔除并计数，同时进入运营建议提示数据质量问题；
- 借用链与买卖链终点不同：买卖单走到“成交”，借用单还会继续统计“借出 → 物品归还”，因此两类订单的端到端口径分开呈现。
- 供给侧生命周期健康：把“发布过多少商品”换成“有多少商品还在被维护”，按生命周期等级统计当前在售商品、需要卖家决策的商品和发布超 45 天且无互动的商品；
- 卖家维护覆盖率只统计有在售商品的卖家，未发布过的用户不计入分母，避免用不相关的人群稀释真实维护情况；
- 按在管规模（1 件、2-3 件、4-8 件、9 件以上）分组展示卖家数、在售商品、待处理商品、无互动商品和刷新额度已用尽的卖家，用于区分“新手卖家”和“批量铺货后无人维护”；
- 统计周期内刷新次数、刷新卖家数、刷新额度已用尽的卖家和名下商品全部待处理的卖家，用来判断刷新机制是被正常使用还是已经被额度限制；
- 供给侧建议只在越过阈值时给出，没有对应问题时保持为空，不会为了填满看板而制造运营动作。
- 生命周期提醒触达与行动：把「提醒发出去之后卖家到底动没动手」单独做成一个面板，统计周期内被提醒的商品、通知被打开的比例、提醒后发生动作的比例，以及「看了但没动」的商品数量；
- 行动只认可可观测的写入点：刷新看主动刷新时间，成交看订单走到终态；编辑商品不算动作，因为任何保存都会改写更新时间，无法区分「卖家看过」和「别的东西改过这一行」；
- 按提醒类型分开展示行动率，且三个桶互斥：同时收到待处理提醒和价格参考提醒的商品单独成桶，否则同一个动作无法归因给任何一类，带证据的提醒是否更有效就答不了；
- 「看了但没动」和「完全没动作」的商品按发布天数排序逐条列出，而不是合并成一个数字，因为这类商品才是需要人工介入的那一批；
- 借用逾期催收阶梯：把“逾期之后平台还在做什么”做成可回看的台账，面板给出待催收数量、已上报治理队列数量、周期内升级与闭环数量，以及仍在跟进中的最长逾期天数；
- 催收看板只列出真正升级过的订单，迟还但从未催收的借用不填充列表，否则运营要读一堆不需要处理的行；
- 每一行都带当前等级、累计升级次数、最近升级时间和闭环时间，运营可以直接回答“这笔到底催到哪一步了、谁被告知过”；
- 台账不重复解释规则本身：三级阶梯的受众差异、跳级补发与归还即闭环的取舍写在看板脚注里，改规则只需要改模块常量。
- 借用逾期风险分层：按分类和押金档位分别聚合同一批借用单，给出每组的借用量、升级率、第三级率和平均闭环时长，第三级率高的组排在前面，用来回答「哪些品类天生更容易拖到第三级」；
- 分层口径在看板上写明：分母包含从未升级过的借用，样本少于 5 笔的组整行压暗并标注「样本不足」，闭环时长从真正发生的那一级催收起算。
- 借用逾期风险分层：催收阶梯和治理队列都回答不了「是一类物品本来就难还，还是一串不走运的同学」，把同一批借用单按分类和押金档位各聚合一遍，给出每组的借用量、升级率、第三级率和闭环时长，第三级率高的组排在前面；
- 分层的分母包含从未升级过的借用：只看升级过的订单会让每一组的升级率都变成 100%，分层就白做了；
- 样本少于 5 笔的组照常列出但标记为样本不足，并在看板里整行压暗——2 笔里 1 笔拖到第三级是 50%，这个数字不能拿去当结论，但直接藏起来会让人以为这个分类没有风险；
- 闭环时长从真正发生的那一级催收起算，而不是从到期日：在等级一等了一周的订单，不该被记成运营花了一周处理；
- 分层只做统计聚合，不会因为某个分类看起来更容易拖就提前催收它的借用方，也不据此调整押金或给任何人打标记——催收时机是「同学的东西最多能丢多久」的策略，不该被一个统计数字推着走。
- 定时任务健康度的跨周期趋势：健康面板回答的每一个问题都是关于单个周期的，而接下来的问题——这个月比上个月好还是坏——不能靠更轻的阅读单个窗口回答出来；
- 成功率按两个等长周期比较，趋势阈值与搜索趋势面板完全一致（超过 10 个百分点才算上升或下降），因为多个面板并排在同一张看板上，读者在一处学会“上升”的含义后不该在另一处重新学一个数；
- 耗时看中位数、最长一次和异常慢的次数，不看平均值：一个命令十一次四秒、一次四分钟，均值是三十五秒，而这个数字描述了没有任何一次真正发生过的运行；
- 一次运行按它开始的时刻归期，而不按结束时刻：按结束时刻归期会让卡在边界上的那次算进下一个周期，于是坏周期会报成“好周期之后跟着一个慢周期”；
- 任一周期运行次数少于 4 次时只报数值、不给方向：四次运行算出来的成功率一步一个五分之一，这样的差值是算术而不是证据；
- 运行次数永远不给方向：跑得更多只说明这个周期更忙，不代表更健康，把它叫“上升”会教会读者把量的变化读成质的变化；
- 命令耗时的分位分布：中位数回答“典型的一次有多久”，回答不了“最慢的那一档有多慢”——一个命令五十次四秒、一次四十秒，中位数在每个窗口里都是四秒，而调度窗口正是在被那一档悄悄吃掉；
- 三个分位各回答一个问题：P50 是典型的一次，P90 是偶尔等一回的那一次，P99 是吃掉调度窗口的那一次，只看中位数会把这三件读成同一件；
- 分位取最近秩，也就是某次真实发生过的运行，不取插值：插值 P90 会落在第九次和第十次之间，那是一次从未发生过的运行；
- 样本撑不起某个分位时就把它留空并标明样本不足：十次运行的最近秩 P99 就是最大值，贴上 P99 的标签是让读者以为尾巴被量过，其实只看见了一次运行；
- 失败运行不进分位：失败可能毫秒级退出，也可能挂到被调度器杀掉，算进去会让同一个数字同时描述“多常坏”和“好的时候多慢”，失败次数仍然列在旁边；
- 尾部倍数取已声称的最高分位与 P50 的差，样本不足 P99 时退到 P90：否则样本少一档的命令会被报成“没有尾巴”，而它恰好看得见的那一档正在变慢；
- 此处只报告，不拆分命令、不改调度配置、不把统计写回台账。
- 只报告，不改 `STALE_AFTER`、不重跑失败的命令、不改调度配置，也不把统计写回台账：一个能挥动调度的统计会把台账变成一个记录被它自己抠出来的形状的地方。
- 借用节奏与学期阶段交叉：把风险分层的结果与学期日历叠在一起看，围绕「考试周集中借出」还是「这个品类本身难还」分开：同样是第三级率，落在十四天的考试周和十四周的常规教学周里不是一回事；
- 阶段按学期进程排列而不是数据库返回顺序，跨学期的同一个阶段合并成一行：读者要比较的是「考试周是什么样」，不是「去年秋天那次考试周」；
- 日均口径的分母是阶段真正产生借用的那些天，而不是阶段的名义长度：报告窗口只覆盖阶段后半段时，用名义长度除会把日均压小好几倍，那看起来像个发现，其实是窗口切出来的假象；
- 阶段内占比的分母是所在阶段的借用总数，不是全站借用数：前者回答「这个阶段发生的事里有多少出了错」，后者会随总量涨落，回答的另外一个问题；
- 两个合成桶描述的是日历覆盖率而不是节奏：没配学期日历时发生的借用、落在阶段空隙里的借用，都单独计数并说出来，不参与「最忙阶段」的结论——静默丢掉会缩小分母，把每个阶段的占比悄悄放大；
- 交叉表的一个格子比任何一张父表都薄，因此门槛与风险分层完全一致（同一个 5），不因为表格变大就放容；样本不足的阶段和分类照常列出、整行压暗并标注，但不参与统计结论；
- 交叉只做统计聚合，不会把「考试周看起来集中借出」变成提前催收的许可；催收时机是「同学的东西最多能丢多久」的策略，不该被一个统计数字推着走。
- **借用催收的跨周期时效对比**：把「这个月是不是比上个月更糟了」做成看板上的一个确定答案，而不是靠人拿两张快照去目测。
- 当前周期与上一个等长周期用同一把时钟切分，周期边界取本地午夜，与搜索趋势面板共用同一个取界函数——同一笔借用在这张表里计入，在那张表里也必须计入。
- 分子分母都按同一笔借用归期：升级行属于哪一周是调度器决定的，借用属于哪一周是用户决定的，按升级行归期会让升级率随着调度节奏自己晃动。
- 升级率的分母包含从未升级过的借用。只看升级过的订单会让两个周期都落在 100%，差值恒为零，于是面板会在一个翻了三倍的队列上报完美稳定。
- 催收命令只走 120 天回看窗口，超出窗口的订单会永远留在分母里、表现成升级率偏低——这是面板唯一会低估一个周期的方向，也是运营承受得起的方向。
- 闭环时长从真正发生的那一级催收起算，不从到期日起算：在等级一坐了一周的订单不该被记成运营花了一周处理，否则队列越空、闭环时长越难看。
- 未闭环订单的逾期天数不参与跨周期对比。那是对着「今天」算出来的数，上一周期因此永远是更老的那个，这个指标只会自己往下掉——日历造出来的趋势，不是队列造出来的。
- 对比项同时覆盖比率与时长（升级率、第三级率、平均闭环时长、最慢闭环），只比率会漏掉「处理变慢」，只时长会漏掉「变频繁」。
- 任一周期少于 5 笔借用即标记样本不足，与借用风险分层同一个门槛：3 笔借用算出来的差值是噪声，面板不能成为隔壁表里算太薄、这里刚好够的那种地方。
- 方向词与阈值直接沿用搜索趋势（上升/下降/持平/本期新出现/本期已消失/样本不足，十分位），两块面板并排摆在同一张看板上，读者不该在两处各学一个数。
- 本模块只报告，不提前催收、不改动催收阶梯、不打标记借用人。
- 定时任务运行台账与健康统计：七个定时命令过去跑完就走，运行结果只存在于进程返回值里，看板既回答不了「上周的提醒到底发出去没有」，命令失败在项目内部也完全没有记录；现在每次运行都会落库一行记录，面板给出各命令的运行次数、失败次数、最近状态、静默天数和连续失败次数；
- 静默天数按最近一次<i>成功</i>运行计算，而不是最近一次任意运行：一直失败的命令同样每天都在跑，按任意运行计算会把它伪装成健康的；
- 台账只保存可横向比较的标量指标，不原样保存命令返回的任意结构，因此各命令才能摆进同一张表；`--dry-run` 单独标记且默认不计入成功率；
- 调度建议只在越过阈值时给出，并直接点名连续失败或长期静默的命令，不为了填满看板而制造运营动作。
- 当前周期与上一段同长度周期的变化对比；
- 基于发布、搜索、浏览、收藏、交易和私信行为的活跃用户分层；
- 基于新用户 cohort 的回访率，并明确统计样本口径；
- 无结果搜索比例、待处理举报队列和完成交易环比变化形成的运营提醒；
- 脱敏 CSV 导出，方便留档、复盘或交给外部分析工具继续处理。

管理员还可以通过管理命令发送运营告警日报。日报只投递给活跃管理员，尊重个人通知偏好，并使用“日期 + 统计周期”的幂等键避免同一日报重复刷屏。

### 8. 校园身份与可信交易

- 管理员可以在后台配置允许使用的校园邮箱域名，并单独启用或停用某个域名；
- 用户可以从个人资料发起校园邮箱认证，系统发送一次性验证链接；
- 验证链接默认 24 小时有效，重新发送会使之前的令牌失效；
- 认证成功后，商品详情的卖家信息会展示校园认证标识；
- 同一个校园邮箱不能绑定多个账号，认证状态与学校名称会保留在账户档案中；
- 用户拥有一个可公开访问的交易档案页，展示在售商品、评价和交易表现，但不会暴露邮箱、电话、微信等联系方式；
- 交易档案同时统计用户作为发布者和购买者的完成记录，并把完成交易数、履约率、评价均值和已确认交付异常拆开呈现；
- 信誉标签采用可解释的规则生成，例如“有完成交易记录”“交易履约稳定”和“评价表现良好”，不使用无法解释的单一信用分；
- 公开交易档案新增“校园互助贡献”模块：完成交易、完成借用归还等可验证行为会形成积分记录，并按“热心参与者”“可靠交易伙伴”“校园互助达人”等等级展示；
- 贡献积分采用独立的可审计记录和来源幂等键，同一笔交易重复提交或重复执行不会重复计分；
- 普通用户只看到积分、等级和脱敏后的贡献说明，不会看到订单编号、交易金额或其他参与人的联系方式；管理员可以在后台检索贡献类型、来源键和发生时间，用于复核和运营分析；
- 验证令牌只以哈希形式保存，认证完成后清空令牌哈希，不把明文令牌写入数据库。

> 校园认证只证明用户可以控制某个已配置的校园邮箱，不等同于平台对个人身份、商品质量或线下交易结果的担保。

## 典型业务流程

下面的流程图展示一条从发现商品到完成交易的完整链路。每个阶段都对应页面动作、业务约束和可回看的数据记录。

![校园交易闭环](docs/business-flow.svg)

### 用户视角

1. **发现**：用户从首页、分类、地点或搜索结果进入商品列表；
2. **筛选**：根据价格、成色、地点和状态缩小范围；
3. **了解**：查看图片、描述、卖家信息、地点和其他用户留言；
4. **沟通**：通过留言或私信确认商品细节、交付时间和交易地点；
5. **预约**：发起预约，系统校验商品是否仍可交易；
6. **推进**：双方更新订单状态，系统生成订单事件和必要通知；
7. **交付**：在线下完成交接后，由双方确认交付；
8. **反馈**：交易结束后评价，遇到异常时可以发起争议或举报。

### 系统视角

- 商品是交易入口，订单是状态主线；
- 私信和通知负责把状态变化传递给相关用户；
- 订单事件、浏览历史、搜索记录、评价和举报构成可回看的业务事实；
- 运营看板对这些事实做周期聚合，而不是直接修改交易数据；
- 管理员通知偏好和日报幂等键，保证运营提醒可控、可重复执行而不重复投递。

## 运营数据闭环

运营模块遵循“记录行为 → 聚合指标 → 识别问题 → 发送提醒 → 进入处理页面”的链路：

1. **记录行为**：保存搜索词、筛选条件、结果数量、浏览、收藏、预约、订单事件、私信和举报等结构化数据；
2. **聚合指标**：按统计周期计算供给、需求、活跃度、转化漏斗、回访率和治理队列；求购撮合还会关联匹配通知、卖家响应和求购确认，形成从触达到成交意向的独立漏斗；
   - 地点热力会进一步把供给、有效求购、周期预约和完成交易放到同一口径下，输出地点级供需压力，支持从“看见问题”进入“补充供给”的运营动作；
   - 专题分析会把“活动内容 → 商品曝光 → 收藏 → 预约 → 完成交易”串成专题级漏斗，并输出低转化提示，让运营数据能够反向影响下一轮活动策划；
3. **识别问题**：识别无结果搜索、待处理举报堆积、完成交易下降等运营告警；
4. **发送提醒**：管理员可以运行 `send_operations_digest`，将告警摘要写入站内通知中心；
5. **进入处理**：通知携带运营看板地址，管理员可以直接回到对应统计周期继续分析。

### 闭环的最后一环：动作有没有用

前五步只解决"发现问题并派人处理"，回答不了"处理完之后有没有好转"。一个只会报警、无法证明自己有用的雷达，很快会失去运营的信任。因此链路在"进入处理"之后补上第六步：

6. **验证效果**：以跟进任务的创建时间为分界，对比同一主题在前后两个窗口的无结果搜索率。

判定分五档，而不是简单二分：

| 判定 | 含义 | 运营该做什么 |
| --- | --- | --- |
| 缺口收敛 | 无结果率下降 | 若可用供给同时增加，说明补给动作对准了需求，可以复制到同类主题 |
| 基本持平 | 变化落在噪声区间 | 人工判断是否值得继续投入 |
| 缺口扩大 | 无结果率上升 | 核对是否补错了主题，或需求本身在增长 |
| 样本不足 | 两侧搜索量都太少 | 等待数据积累，不下结论 |
| 观察期未结束 | 任务刚建立不久 | 暂不判定，避免冤枉人 |

几条口径上的取舍：

- **分界线用任务创建时间，不用雷达行**。雷达行是滚动聚合，看板每刷新一次内容就变，不能当稳定边界；任务是一次有日期的决策。
- **变化和原因分开判**。无结果率下降但可用供给没涨，只记为"疑似收敛"并提示排除季节性因素；把两件事混在一起，会让运营误以为随便做点什么都能让数字变好。
- **样本不足不计入命中率**。用一次偶然的下降宣称成功，比不统计更糟。命中率只统计有完整证据的任务。
- **两侧窗口等长**。各取 14 天，避免单一季节波动伪装成收敛。
- **命中率过低会告警**。这通常意味着机会分口径或补给动作有问题，而不是该继续加供给。

日报是幂等的：同一个管理员、同一个日期、同一个统计周期只会生成一条对应通知。这样可以将命令接入系统计划任务，而不必担心重复执行造成通知刷屏。

## 学期日历与交易高峰

校园交易有明显的学期节律：开学两周集中在教材和宿舍用品，考试周转向复习资料，毕业季则是清仓供给集中释放。只看“最近 30 天平均值”会把这些变化抹平，因此项目引入学期日历，把统计口径切成阶段。

**阶段模型**

- `AcademicTerm`：一个学期，包含名称、标识、类型（春 / 秋 / 夏 / 冬）、起止日期和启用状态；停用后不再参与阶段计算，但历史数据保留；
- `AcademicPhase`：学期内的一个阶段，用「开始偏移天数 + 结束偏移天数」定位，偏移以学期开始日为第 0 天计算，超出学期长度时自动截断；
- `AcademicTermSnapshot`：阶段级统计快照，由管理命令刷新，看板可以直接读取缓存而不用每次重算全表。

**默认阶段计划**

| 阶段 | 偏移天数 | 典型特征 |
| --- | --- | --- |
| 开学周 | 0 – 13 | 教材和宿舍用品需求集中 |
| 常规教学周 | 14 – 97 | 以日常兴趣和小件为主 |
| 考试周 | 98 – 111 | 复习资料和陈旧资料需求上升 |
| 毕业季 | 112 – 125 | 清仓供给集中释放 |

偏移天数是可配置的，不是写死在代码里的常量：不同学校的校历长度不同，管理员在后台调整边界即可，代码和迁移都不需要改动。`AcademicPhase` 上还有唯一约束保证同一学期内偏移量不重叠。

**阶段感知的提醒内容**

关注搜索汇总和互助机会摘要会在通知尾部追加一句当前阶段说明，例如“当前处于秋季学期考试周：复习资料和陈旧资料需求上升。”，让用户理解为什么此刻收到这类提醒。没有配置学时会自动退化成原来的文案，不影响任何已有功能。

**维护命令**

```bash
python manage.py sync_academic_calendar
python manage.py sync_academic_calendar --ensure-phases
python manage.py sync_academic_calendar --refresh-snapshots
python manage.py sync_academic_calendar --term-slug autumn-2026
```

默认同时补齐阶段并刷新快照；`--term-slug` 可以只处理某个学期。命令会回报处理了多少学期、新增了多少阶段、刷新了多少条快照，适合接入系统计划任务。

**边界说明**

- 阶段对比说明的是供给节律，不代表单个用户的因果结论；
- 阶段统计复用现有的商品、求购、订单和搜索记录，不新增用户行为采集；
- 未配置学时时，看板会保留面板并提示如何录入，其余统计口径完全不变。

## 核心数据模型

项目使用 Django ORM 管理业务数据，当前模型可以按以下几组理解：

| 领域 | 主要模型 | 作用 |
| --- | --- | --- |
| 商品 | `Category`、`CampusLocation`、`Item`、`ItemImage` | 商品分类、校园地点、商品主体、交易方式、图片和可选展示截止时间 |
| 商品生命周期 | `Item.last_refreshed_at`、`Item.refresh_count`、`Item.attention_reminder_sent_at`、`Item.price_drop_reminder_sent_at` | 商品刷新时间与次数、待处理提醒和降价提醒的发送记录，用于生命周期诊断、刷新限流和供给侧统计 |
| 生命周期提醒效果 | `Item.attention_reminder_sent_at`、`Item.price_drop_reminder_sent_at`、`Notification.read_at`、`OrderEvent.created_at` | 提醒时间戳、通知是否被打开，以及订单何时走到终态；三者共同决定「提醒之后有没有动作」 |
| 校园活动 | `CampusCampaign` | 有起止时间的专题活动，以及专题与在售商品的可选关联 |
| 学期日历 | `AcademicTerm`、`AcademicPhase`、`AcademicTermSnapshot` | 学期起止日期、按偏移天数划分的阶段规则、阶段级统计快照 |
| 互动 | `Favorite`、`ItemAvailabilityWatch`、`Comment`、`PrivateMessage` | 收藏、有货提醒、公开留言和私信 |
| 交易 | `Order`、`OrderEvent`、`MeetingAppointment`、`DeliveryConfirmation`、`Rating` | 交易预约、交付时间协商、状态事件、双方确认和完成后的评价 |
| 订单阶段链路 | `OrderEvent`（状态流转事件） | 每次状态变化都会留下带时间戳的事件记录，运营看板据此还原“下单 → 确认 → 交付 → 成交 / 借出 → 归还”的阶段耗时 |
| 搜索 | `SearchQuery`、`SearchClick`、`SearchImpression`、`SavedSearch`、`SearchSynonym` | 搜索需求、点击、曝光、保存搜索和联想词；无结果搜索会进入需求雷达 |
| 需求撮合 | `DemandPost`、`DemandResponse` | 求购发布、商品响应、确认匹配和需求转化 |
| 通知 | `Notification`、`NotificationPreference` | 站内提醒、未读状态、阅读时间、通知偏好、求购关联、到期提醒和幂等键；通知类型包含商品生命周期提醒，可单独关闭 |
| 身份与信任 | `CampusDomain`、`CampusVerification`、`Rating` | 校园邮箱域名配置、身份认证和交易信誉摘要 |
| 治理 | `Report`、`ModerationEvent`、`OrderDispute`、`OrderDisputeEvidence` | 商品举报、内容审核、交易争议、证据和复核记录 |
| 运营 | 订单、浏览、搜索、收藏、求购等行为记录的聚合 | 看板、漏斗、用户分层、回访率、需求雷达、跟进任务和运营告警 |
| 需求跟进闭环 | `DemandOpportunityTask.created_at`、`DemandOpportunityTask.radar_key`、`DemandOpportunityTask.available_supply`、`SearchQuery.result_count` | 任务创建时间是唯一稳定的分界线（雷达行是滚动聚合，内容每次刷新都变），创建时的供给数用于判断「动作是否真的发生」，搜索结果数用于判断「需求是否被满足」 |
| 同义词候选 | `SearchQuery.user_id`、`SearchQuery.query`、`SearchQuery.result_count`、`SearchQuery.created_at`、`SearchSynonym.keyword` / `synonym` / `is_active` | 同一次会话内相邻两次搜索的改口证据；已启用同义词的两个方向都参与去重，停用同义词不屏蔽候选 |
| 同义词效果回流 | 不新增表，读 `SearchSynonym.created_at` + `SearchQuery` | 确认时间是唯一稳定的分界线；搜索词记录的是学生原本输入的那一串（扩展只发生在查询内部），按扩展词统计会成为自己和自己比、永远报成功 |
| 筛选组合对比 | 不新增表，读 `SearchQuery.category_id` + `min_price` / `max_price` | 组合占比的分母是同一个分类内部的搜索次数，因此分类总量上涨不会把每个组合都推成上升；价格带判据与单维表同一套，闭带需要两个界都设、开区间顶带只需下限 |
| 候选门槛建议 | 不新增表，读 `SearchSynonym` + `SearchQuery` | 命中率衡量的是「候选池 + 人工确认」整条链而非候选池本身，因此只作为调整门槛的参考；词对大面积配错时判定为配对问题而非阈值问题，收紧门槛只会把错误藏起来 |
| 候选否决分析 | 新增表 `SearchSynonymRejection` + 读 `SearchQuery` | 否决记录本身落库（否决候选不落库），归一化词对与排查器同一套，因此「充电宝」和「充电宝 」落到同一行；出现次数由同一份改口日志反汇，否决按次数加权而不按否决条数 |
| 定时任务台账 | `TaskRun` | 每个管理命令每次运行的起止时间、耗时、状态、固定指标和失败摘要，用于回答「调度是否健康」 |
| 定时任务失败原因分类 | 不新增表，读 `TaskRun.note` | 把周期内失败的运行按“失败长什么样”归成配置、数据状态、外部依赖、未归类四类，并统计每类的次数、涉及命令与最近一次备注；只描述不下结论 |
| 定时任务健康度的跨周期趋势 | 不新增表，读 `TaskRun.started_at` + `duration_ms` + `status` | 把同一批运行切成本周期与上一个等长周期，比较成功率方向与耗时趋势。一次运行按它开始的时刻归期，否则卡在边界上的那次会算进下一个周期；耗时给中位数、最长一次和异常慢的次数，不给平均值（一次跑了两小时的运行会把平均值抬成一个从未发生过的数字）；只报告，不改 stale 阈值、不自动重试。 |
| 借用逾期催收 | `BorrowReturnEscalation` | 一笔借用订单当前的催收等级、累计升级次数、最近升级时间、说明和归还闭环时间，用于回答「这笔到底催到哪一步了」 |
| 借用逾期风险分层 | 不新增表，读 `Order` + `BorrowReturnEscalation` | 按分类与押金档位聚合的借用量、升级率、第三级率与闭环时长，用来回答「哪些品类天生更容易拖到第三级」；只读聚合，不新增写入路径 |
| 借用节奏与学期阶段交叉 | 不新增表，读 `Order` + `BorrowReturnEscalation` + `AcademicTerm` / `AcademicPhase` | 把风险分层的同一批借用按学期阶段再聚合一遍，给出阶段日均借用、日均第三级与阶段内分类明细，用来区分「考试周集中借出」和「这个品类本身难还」；只读聚合，不新增写入路径 |
| 借用催收跨周期时效对比 | 不新增表，读 `Order` + `BorrowReturnEscalation` | 当前周期与上一等长周期逐项比较；分子分母按同一笔借用归期，逾期天数不参与对比 |
| 需求雷达命中率的跳周期趋势 | 整个 `DemandOpportunityTask` + `SearchQuery` | 同一个周期内的任务改变了多少，与上一周期比对命中率走向。取任务创建时刻作为归期，让刚刚建行的任务不会落入上一周期；只统计有证据的任务，只报告、不把命中率回流到任何字段。 |
| 需求雷达命中率的学期纵向对比 | 整个 `DemandOpportunityTask` 的 `created_at` + `AcademicTerm` / `AcademicPhase` + `SearchQuery` | 把同一个阶段在相邻两个学期里相比，而不是跟前三十天比。学期需求本身顺季节漂移，把上个月当成上个学期比会把季节性读成雷达在漂移；只在一个学期出现过的阶段不给方向，早于第一个学期配置的任务单独计数；只报告、不改加权。 |
| 需求雷达闭环的分层命中率 | 整个 `DemandOpportunityTask` 的 `category` / `location` + `SearchQuery` | 把同一周期的跟进任务按任务自己带的分类和地点切开，每个分层报自己的命中率。整体一个数字既可能是“每类都在 60% 左右”，也可能是“一类 95%、另一类 25%”，而这两者需要的回应相反。命中率只在层内读，不跟“该层占全部任务的比例”比；每层各自要过与整体相同的任务数门槛，门槛不为了表格好看而放开；任务数少的分层上的差值不算结论，这里不排序、不把命中率回流到机会分。 命中率只在层内读，不跟“该层占全部任务的比例”比；每层各自要过与整体相同的任务数门槛，门槛不为了表格好看而放开；任务数少的分层上的差值不算结论，这里不排序、不把命中率回流到机会分。 |

关键约束包括：

- 收藏、商品有货提醒等重复关系通过数据库约束或幂等逻辑避免重复；
- 订单创建在事务中校验并锁定商品，降低并发预约冲突；
- 通知读取、订单操作、评价、举报和运营数据访问均在服务端校验身份；
- 争议证据下载只允许订单买卖双方或管理员访问，不直接暴露原始 media 链接；
- 商品是否仍可预约由服务端的 `ItemQuerySet.available()` 和订单创建时的行级锁共同校验，不能只依赖前端按钮或定时任务是否及时运行；
- 搜索和运营数据尽量保存为结构化字段，便于重新计算和解释指标；
- 上传文件保存在 media 目录，数据库不直接保存二进制内容；
- 校园认证令牌只保存 Django 密码哈希，验证成功或重新发送后旧令牌不能继续使用；
- 校园邮箱域名由管理员显式配置，未配置或已停用的域名不能发起认证。
- 商品刷新按 24 小时最小间隔和每月 4 次上限控制，限流状态保存在商品上，刷新只改曝光排序，不改动商品内容和发布状态；
- 生命周期诊断在应用层计算，不回写商品状态，保证“待处理”只是一个可解释的运营口径而不是隐式过滤条件。
- 定时任务台账只保存可横向比较的标量指标，不原样保存命令返回的任意结构；失败记录写在独立短事务里，业务事务回滚也不会带走失败证据。

## 治理工作台

三类治理事项原本分散在三个页面，各自使用不同的词汇描述同一件事，而交付预约异常甚至没有前台处理入口，只能在 Django 后台里翻。治理工作台把它们收敛到一处，并补上三者都缺失的一个维度：**处理时长**。现在它同时照顾四类队列：商品举报、交易争议、交付预约异常，以及已经走过三级催收的逾期借用。

### 为什么是"等了多久"而不是"有多少"

积压数量只说明规模。10 件待处理举报可能件件都是当天提交，也可能第一件已经躺了半个月——这两种情况需要的动作完全不同。工作台对每个队列分别统计：

- 周期内处理量、已处理、待处理和超期件数；
- 处理时长中位数、P90 以及最快/最慢，按"处理人写进记录的那一刻"计算，打开队列页不算响应；
- 时限内完成率，衡量的是承诺有没有被守住，而不是事情有没有做完。

### 四类队列为什么时限不同

| 队列 | 处理时限 | 理由 |
| --- | --- | --- |
| 商品举报 | 2 天 | 离线复核，不阻塞交易本身 |
| 交易争议 | 3 天 | 需要双方举证，留给沟通的时间更长 |
| 交付预约异常 | 24 小时 | 阻塞一次已经约好的线下交付，拖延代价最高
| 借用逾期催收 | 7 天 | 已经走过三级催收，再给一周把最坏情况限制在逾期两周内 |

用一个共享时限要么让预约异常被埋进误报，要么让举报烂在队列里。超期判定同时设了一条 75% 的预警线，用来在真正超期前先露出"即将超期"的事项。

### 实现取舍

- **不建镜像表**：三类模型本身都有创建时间和关闭时间戳，聚合在应用层完成。镜像表只会多出一条写入路径和一次数据漂移的机会；代价是无法把聚合推给 SQL，而校园规模的治理队列本就只是几百件的量级。
- **待处理清单不受统计周期限制**：周期开始前就已超期的事项，恰恰是最不该被窗口藏起来的那一件。吞吐量按周期统计，待处理清单按实时状态统计，两者在页面上分开呈现。
- **同一事项只计一次**：一件举报可能同时落在"周期内"和"当前待处理"两个集合里，去重键用 `(队列, 主键)`，不能用 Python 对象的 `id()`——那是临时字典的地址，两次加载会得到两个不同的键，同一件举报就会被算成两件。
- **借用队列没有处理按钮**：平台只记录和通知，不取消订单、不代扣押金，因此这一类卡片只提供“查看订单时间线”，而不是一个假装能处置的实心按钮；
- **前台只下结论**：预约异常处理页只提供"已确认异常 / 已驳回"两种终态，不提供"转处理中"，与另外两个队列的流转规则保持一致。

## 权限与安全边界

### 普通用户

- 只能编辑、删除自己发布的商品；
- 只能查看和操作自己参与的订单、私信、通知和收藏；
- 只能修改自己的资料和通知偏好；
- 可以举报商品或内容，但不能直接改变审核结论；
- 可以发起校园邮箱认证，但不能自行把认证状态改为已认证。

### 管理员

- 可以访问运营看板、搜索洞察、举报队列、争议队列和内容审核队列；
- 可以处理举报、争议和审核事件，并留下处理记录；
- 可以接收运营告警日报，但是否接收由个人通知偏好控制；
- 不能绕过服务端权限检查直接代替普通用户完成交易操作。

### 部署注意事项

- 生产环境必须替换 `DJANGO_SECRET_KEY`；
- 不要提交生产数据库、上传文件、密钥或包含用户隐私的日志；
- 启用 HTTPS 后，应同步配置安全重定向、Session Cookie、CSRF Cookie 和可信来源；
- 面向真实用户时，应进一步配置反向代理、限流、备份、日志和媒体文件访问策略。

启动后访问 <http://127.0.0.1:8000/>。Docker 配置默认使用 SQLite，数据库和上传文件分别通过 `campus_data`、`campus_media` 数据卷持久化。停止容器后再次启动时，数据不会因为容器重建而自动消失。

如果要停止服务：

```bash
docker compose down
```

如果要连同数据卷一起清理，请确认其中没有需要保留的数据后再执行：

```bash
docker compose down -v
```

## 后台与定时任务

项目将需要周期执行的工作封装成 Django management command，便于接入 Windows 任务计划程序、cron、容器任务或其他调度系统。

### 预约超时处理

发送临近截止的提醒，并释放已经过期的预约：

```bash
python manage.py process_order_timeouts
python manage.py process_order_timeouts --reminder-hours 6
```

该命令同时检查限期借用订单：在预计归还时间临近时提醒借用双方，超过归还时间后发送逾期提醒；每个提醒阶段都带有幂等字段，重复运行不会重复刷屏。

同一次运行还会走一遍借用逾期催收阶梯：逾期满 1 天提醒借用方，满 3 天同时告知双方，满 7 天上报治理工作台。等级按「逾期了多久」推导，漏跑一次下一次会自动追上；同一笔订单两次催收至少隔一天；双方确认归还后记录立即闭环。

### 商品展示到期处理

将超过展示截止时间的在售商品自动下架，并向商品发布者发送一次到期提醒。该命令设计为幂等操作，可以安全地接入定时任务：

```bash
python manage.py expire_items
```

建议每天运行一次；即使命令没有及时执行，公开列表、推荐和创建订单时也会再次校验截止时间，避免过期商品继续被预约。

### 运营告警日报

按统计周期构建运营告警，并向符合条件的活跃管理员发送站内通知：

```bash
python manage.py send_operations_digest
python manage.py send_operations_digest --days 30
```

可选周期为 `7`、`30`、`90` 或 `365` 天。命令没有发现告警时不会生成空通知；同一天、同一周期重复运行时也不会向同一管理员重复投递。

### 互助机会摘要

向存在有效商品或失物招领记录、且当前确实有可响应机会的用户发送每日摘要：

```bash
python manage.py send_opportunity_digest
```

摘要只在存在匹配机会时生成，用户可以在通知偏好中关闭；同一用户在同一自然日重复运行命令不会收到重复通知。建议将命令接入每天一次的计划任务，并与站内通知未读提醒配合使用。

### 关注搜索汇总提醒

把缓冲区里的关注搜索命中合并成一条通知，按用户和周期去重：

```bash
python manage.py send_saved_search_digest
python manage.py send_saved_search_digest --frequency daily
python manage.py send_saved_search_digest --frequency weekly
```

命令会回归发送、跳过、无命中和静默中的关注数量；处于静默期的关注只统计不发送，命中记录仍然保留。建议每日运行一次（或按需分别运行日订任务与周订任务，两者彻底独立，不会互相干扰）；重复运行安全无偶给性。


提醒的触达与行动情况由运营看板的「生命周期提醒触达与行动」面板呈现，读取的是同一批时间戳，因此看板与命令回报天然一致。
### 商品生命周期提醒

把需要卖家处理的商品合并成一条站内通知，按冷却期控制节奏：

```bash
python manage.py send_lifecycle_reminders
python manage.py send_lifecycle_reminders --seller-id 12 --seller-id 34
python manage.py send_lifecycle_reminders --dry-run
```

命令会回报发送条数、两类提醒各覆盖多少卖家、回写了多少件商品的冷却时间，以及因关闭提醒、处于免打扰时段或缺少价格证据而跳过的卖家数。`--seller-id` 可重复传入，用于只补发某几个卖家；`--dry-run` 只统计不写入，适合上线前确认影响范围。

去重键按“通知类型 + 日期 + 卖家”构成，同一天重复运行不会发出第二条，也不会重复回写冷却时间，因此可以直接接入系统计划任务。建议每日运行一次，与运营告警日报错开时间，避免同一批卖家在同一天收到多条长文通知。

### 学期日历维护

学期日历本身不产生数据，它只是把已有记录按阶段重新聚合。因此只需要一个维护命令：

```bash
python manage.py sync_academic_calendar
```

命令做两件事：为启用中的学期补齐缺失的默认阶段，以及刷新各阶段的统计快照。默认两件事都做，也可以用 `--ensure-phases` 或 `--refresh-snapshots` 单独执行，或用 `--term-slug` 只处理某个学期。没有配置学时时命令会明确提示，不会静默失败。

建议在每学期开始前手工运行一次补齐阶段，之后按周刷新快照即可；阶段边界调整后同样需要重跑，否则看板仍会显示旧边界下的统计。

### 定时任务运行台账

七个定时命令过去都是「跑完就走」：各自打印一行摘要然后退出，发送了多少条、跳过了多少个卖家、有没有失败，只存在于进程返回值里。带来的两个后果是，看板回答不了「上周的提醒到底发出去没有」，而命令失败在项目内部也完全没有记录——只有调度器从退出码里知道出过事，排查一次漏跑只能去翻调度器日志。

现在每次运行都会留下一行 `TaskRun` 记录：

```bash
python manage.py send_lifecycle_reminders
python -X utf8 -c "from listings.models import TaskRun; [print(r.name, r.status, r.metrics, r.note) for r in TaskRun.objects.all()]"
```

接入方式对命令本身只增加一行上下文，返回值仍按原有方式打印，不影响任何现有输出：

```python
from listings.task_runs import normalise_metrics, record_task_run

with record_task_run('send_lifecycle_reminders') as run:
    result = send_lifecycle_reminders()
    run.metrics = normalise_metrics(result)
```

台账落库的数据进入运营看板的「定时任务运行台账与健康统计」面板，给出每个命令的运行次数、失败次数、最近状态、静默天数和连续失败次数，并汇总出需要优先处理的命令。

## 当前取舍与边界

- **先保证交易一致性，再扩展体验**：订单创建使用事务和锁，避免同一商品被并发预约；
- **先采用服务端渲染**：核心页面保持 Django 模板结构，降低部署和维护成本；
- **消息刷新保持轻量**：使用未读摘要接口和定时刷新，不引入 WebSocket 基础设施；
- **推荐保持可解释**：优先使用分类、地点、热度和新鲜度信号，不把黑盒模型作为交易判断依据；
- **价格参考不等于自动定价**：价格区间使用同类商品分位数和公开互动信号，样本不足时明确降低可信度，最终定价仍由发布者决定；
- **运营指标可重新计算**：行为记录和统计口径尽量清晰，避免只保存不可追溯的最终数字；
- **SQLite 只作为默认方案**：适合开发和轻量部署，不把当前容器配置当作大规模生产架构；
- **当前就近不是实时定位**：地点筛选不会推断用户位置，也不提供 GPS 距离承诺；交付地点推荐使用商品地点、历史交付和公开的地点使用统计，不采集实时位置；
- **地点热力只做运营聚合**：校园供需热力只统计已配置地点上的公开业务记录，采用周期聚合和去重计数，不把个人轨迹、实时位置或单个用户行为暴露给运营人员；
- **推荐不替代协商**：交付地点和时间推荐是可解释的规则建议，会避开已知预约冲突，但不会替用户自动确认预约；
- **安全提示不等于担保**：交易安全卡只基于平台已有的公开业务事实生成提醒，不对商品质量、个人身份或线下结果作保证，也不会因为出现提示而自动阻止交易；
- **治理时效是运营口径，不是考核指标**：处理时长按处理人写进记录的那一刻计算，衡量的是用户等待是否有回应，不用于评价具体处理人的工作量，也不因为它而给事项设置自动关单；
- **内容审核仍是可扩展基础**：已有审核事件和人工复核入口，敏感词策略、分级处置和更细的审计还可以继续完善。
- **通知时效只反映读取行为**：处理时长按「标记已读时间 − 通知创建时间」计算，衡量的是用户查看并处理提醒的快慢，不推断用户是否真正完成了背后的交易事项；
- **阶段时长只统计走完的链路**：周期结束时仍未走完所属流程的订单属于右删失样本，只计入“进行中”，不参与中位数和 P90 计算，避免把正常在途订单当成超时；
- **乱序事件按异常剔除**：流转时间早于上一阶段的记录不进入统计，但会保留计数并在建议中提示，避免用错误数据解释瓶颈；
- **借用与买卖终点不同**：买卖单的终点是“成交”，借用单还会继续统计“借出 → 物品归还”，因此两类订单的端到端耗时不可直接横向比较；
- **登记到场等动作事件不算里程碑**：状态没有发生变化的 `OrderEvent` 只用于交付记录，不参与阶段耗时计算；
- **时间差在 Python 侧计算**：SQLite 下对 datetime 字段直接相减会溢出，且不同数据库行为不一致，因此阶段耗时统一在应用层用带时区的时间对象计算，保证口径可移植。
- **刷新限流优先于首页公平性**：刷新用于让仍在售的商品重新可见，但如果允许无限刷新，首页会被少数卖家反复刷同几件商品占满，因此固定最小间隔和月度上限，超出时明确告知而不是静默拦截；
- **互动是弱信号，不作为下架依据**：“近 14 天无互动”只用于供给侧统计和卖家提醒，浏览、收藏、预约的缺失不能推出商品没有价值，也不会触发自动下架；
- **覆盖率分母只算有在售商品的卖家**：把从未发布商品的用户计入分母会让维护率看起来系统性偏低，掩盖真正需要关注的卖家群体；
- **生命周期等级与卖家端保持一致**：运营端和卖家端复用同一套等级和阈值，避免同一个商品在两处显示不同状态，也避免运营按另一套口径给卖家提建议。
- **提醒按卖家合并，不按商品合并**：一个卖家可能同时有多件商品需要处理，按商品发送会让活跃卖家一天收到好几条长通知，因此同一卖家一次只发一条，代价是单条通知更长、需要折叠展示；
- **冷却字段在通知落库后才回写**：如果先回写再发送，发送失败会静默吃掉一次提醒机会，卖家可能整月都等不到这条提醒；反过来，若通知已存在但回写失败，重复运行也只会补写字段，不会重复发送；
- **免打扰只推迟，不吞掉**：处于免打扰时段的卖家不计入发送成功，冷却字段保持原值，等时段过去后的第一次运行仍会收到，避免“夜里没收到，白天也不再发”；
- **价格建议必须能引用证据**：降价提醒只在同类商品区间存在且当前价格高于区间上限时给出，样本不足时明确标注“参考样本较少”，不把久未成交直接当成降价理由。
- **只报相关性，不报因果**：卖家完全可能在提醒之前就已经决定整理商品。面板能确认的只有「动作发生在提醒之后」，所有比例都按提醒时间戳切开计算，文案也写成观察值而不是归因结论；
- **动作只认可可观测的写入点**：刷新看 `last_refreshed_at`（只在卖家主动刷新时写入），成交看 `OrderEvent` 到达终态的时间。`Item.updated_at` 是 `auto_now`，任何一次保存都会改写它，拿它证明「卖家做过决策」不成立，因此一律不用；
- **受阻原因用当前值重算，并如实说明**：发送时的跳过计数只存在于命令返回值里，没有落库，看板无法回放当天的快照；因此偏好、免打扰和样本不足都按当前状态重算，面板脚注会写明这一点，不把重算值伪装成历史记录；
- **三个提醒类型桶互斥**：同时收到两类提醒的商品单独成桶。若让它同时计入两类，「带证据的提醒是否更有效」就无法回答，因为同一个动作不能归因给两个原因。
- **闭环分界线用任务创建时间，不用雷达行**：雷达行是滚动聚合，看板每刷新一次内容就变，用它当边界会让"动作之前"和"动作之后"随页面刷新而漂移；任务是一次有日期的决策，天然稳定。代价是每个任务都要按自己的 `radar_key` 重新反查一次搜索日志，而不能直接复用雷达已经算好的数字。
- **雷达标识从右往左解析**：标识由「搜索词|分类:ID|地点:ID」拼成，而搜索词是自由文本、本身可能含竖线，所以用 `rsplit('|', 2)`。从左切会把「A|B」这类词拆成两半，导致窗口匹配不到任何搜索。
- **收敛阈值取 10 个百分点**：低于这个幅度的变化更可能是噪声。阈值定得太低会让每个任务都"有效"，指标随之失去筛选能力；定得太高则会漏掉真实的温和改善。
- **观察期未结束与样本不足分开标注**：前者是"还没到能下结论的时候"，后者是"数据永远不够多"。混成一类会让运营对着刚建两天的任务判断失败，或者对着一个没人搜过的主题反复追问。
- **台账只记可比较的标量，不记任意 JSON**：七个命令返回的结构完全不同，原样存下来面板就没法把它们摆到同一张表里横向对比。因此这里固定一组指标字段（发送、跳过、失败、标记、下架、提醒），各命令把自己的结果映射过去，映射不上的键就留在命令自己的输出里；布尔值显式拒绝，因为 `True` 存成 1 会和真实的计数 1 混淆；
- **失败也必须落库，且异常继续上抛**：台账的价值全在异常行上，所以写入放在 `finally` 里，并使用独立短事务——依赖外层事务的话，恰恰是业务事务失败时最需要的那条记录会被一起回滚掉。异常按原样抛出，命令仍然大声失败，不会因为接了台账就被吞掉；
- **预演不算运行**：`--dry-run` 不发送任何通知，把它计入成功率会让「调度是否健康」这个问题无法回答，因此单独打标记，健康统计默认排除；如果一个命令只有预演记录，面板会显示无记录，因为它没有证明过任何事。
- **平台只记录和通知，不取消订单、不代扣押金、不打失信标记**：押金由两个同学线下结算，平台扣款会发明一个双方都没同意的金融关系；"失信"标记会把一次慢还变成比物品本身更持久的伤口。所以阶梯只回答「催到哪一步了、谁被告知过」，处置判断留给本来就有 SLA 的治理工作台；
- **三级阶梯换的是受众，不是同一句话说三遍**：对同一个用户重复催收不增加任何信息量，所以一级只问借用方，二级才让出借方知道平台已经开始记录，三级则必须离开双方私域。上限定在三级的理由不是"没想到第四级"，而是私域到这里已经证明无效；
- **跳级不回播，但跨级到第三级必须补发二级**：追着补三句话正是阶梯要避免的噪音；可宽口径的那一方（出借方）不能从头到尾被蒙在鼓里，否则上报治理队列对他就成了突然袭击；
- **按逾期时长推导等级，不按升级次数**：漏跑一次任务下一次自动追上，调度故障不会留下永久落后一级的订单。代价是等级偶尔一次跳两级，读表时要按"当前该在第几级"理解，而不是按"已经催过几次"；
- **归还即闭环，不是删除**：同学之间的借用靠信任，还清不该留污点。等级和升级次数保留在行里，时间线仍可回看，只是不再计入待办；
- **行只在真正达到某一级时才创建**：刚跨过截止线就建行会让看板把没人催过的订单算成待办，运营会去读一堆不需要处理的行；
- **台账只记一个汇总数**：三级分布留在命令输出里，映射不上的键不进 `METRIC_FIELDS`，否则"固定一组可横向比较的标量指标"这条就守不住了。

项目会围绕“更贴近校园场景、更完整的交易闭环、更可靠的社区治理”继续迭代，方向包括：

- **商品生命周期运营**：当前已支持卖家侧生命周期诊断、刷新限流、运营端供给侧健康统计，以及按卖家合并的生命周期提醒与冷却控制；后续可继续补充提醒发送后的处理率统计、跨学期的生命周期对比，以及按分类的调价参考聚合。
- **提醒效果评估**：当前已把提醒后的触达、阅读与行动纳入运营看板，可区分「没收到」「收到没看」「看了没动」三种情况；后续可继续补充跨周期的行动率对比，以及按分类、按卖家规模的行动率分层，用来判断提醒该加频还是该改文案。
- **调度可观测性**：七个定时命令已接入运行台账与健康统计，能回答「上次成功是什么时候、有没有在连续失败」；失败也已按“长什么样”分类聚合——配置与参数、数据状态、外部依赖、未归类，每类统计次数、涉及命令与最近一次备注，不用把九条几乎一样的行读一遍才发现其实是同一件事。跨周期的成功率对比也已落地：同一批运行切成本周期与上一个等长周期，趋势阈值与搜索趋势面板同一套，同时把耗时趋势补上——中位数、最长一次和异常慢的次数而不是一个均值，否则一次跑了两小时的运行会被平均掉。按命令分组的耗时分位统计也已落地：P50、P90、P99 各回答一个问题——典型的一次、偶尔等一回的那一次、以及吃掉调度窗口的那一次，只看中位数会把这三件读成同一件。中位数不动而 P99 从五秒涨到四十秒，正是上一轮那一组指标看不见的那类劣化。取最近秩而不是插值，因为插值 P90 会落在第九次和第十次之间，那是一次从未发生过的运行；样本撑不起某个分位时就把它留空，十次运行的最近秩 P99 就是最大值，贴上 P99 的标签是让读者以为尾巴被量过。后续可继续补充运行时长的按小时分布，以及失败原因在多个周期之间的变化。需要说清楚的边界是：分类只说明失败长什么样，不用来自动判定严重程度或自动重试——同一个 `CommandError` 既可能是致命的配置错误，也可能只是“今天没有到期订单”的正常提前返回，判断留给运营，行数据全部保留便于回去读原始备注。
- **搜索与供给**：同义词候选已经从「搜 A 无结果、随后改搜 B 有结果」的真实改写序列中挖掘出来，并由运营一键确认；已确认同义词的无结果率回流也已落地，可以区分“明显生效 / 基本持平 / 让搜索变差”，同义词挖掘不再是一条只能提议、无法自我校正的单向链路；命中率到候选门槛的反馈同样落地——用已确认同义词的命中率反推出现次数门槛该松还是该紧，在 1–5 次的固定档位表上只给出相邻一档，并把每一档会多出多少条待确认算出来摆在一起，门槛本身仍然只建议、不自动改，词对大面积配错时也只会提示先核对词对；搜索趋势与筛选偏好的跨周期对比也已上线，可以按搜索词看量的升降与无结果率、点击率的变化，按成色、分类、地点、价格带看筛选口味的迁移，并把“搜不到”和“搜到了不点”分成两类线索；筛选组合的跳周期交叉对比也已落地——分类×价格带两两交叉，占比在分类内部计算，因为单维信号同时动并不等于组合在动，而且稀疏门槛不会因为组合表格子多就下降；候选否决也已经落地：每条候选行内都能直接否决，原因和备注一起落库，被否掉的词对不再进入挖掘结果。否决按出现次数加权而不按否决条数，否得多的运营不会被读成面对着一个吹唧的候选池；低于门槛的否决单独计数、不进门槛判断，因为门槛从来不是运营看见那个词对的原因。否决可撤销，与确认互斥：词对后来被确认时否决标记为失效而不删除，同义词被删掉时否决重新生效。后续可继续补充按运营人员切分否决口径，以及被否决词对在更长周期里的回头率。
- **交易交付**：在现有确认码、预约异常和争议证据链基础上，继续完善爽约处置与交付后的售后协商；当前已支持基于历史地点、公共区域标记和预约冲突检查的安全交付推荐；
- **校园场景**：完善毕业季批量发布、借用物品归还协作、可循环借用、批量续期与学期模板，让短周期校园需求更容易被管理；
- **借用催收闭环**：三级阶梯已经能回答「催到哪一步了、谁被告知过」，第三级也已作为第四类队列进入治理工作台，时限从三级催收发出那一刻起算；按分类与押金档位的逾期风险分层也已经落地，可以回答「哪些品类天生更容易拖到第三级」，且分母包含从未升级过的借用、样本不足的组会明确标注；把风险分层的结果与学期节律叠在一起看的交叉表也已经落地：按学期阶段再聚合一遍，用日均口径让不等长的阶段可比，并按阶段展开分类明细，因为同样的第三级率落在十四天的考试周和十四周的常规教学周里不是一回事；跨周期的升级率与闭环时长对比，以及该队列自身的时效趋势也已经落在看板上：两块面板都只报告、不提前催收、不改动催收阶梯。
- **失物招领**：在现有可解释匹配和私密线索流转基础上，继续增加图片辅助、人工审核、认领凭证和异常举报；
- **校园供需运营**：地点热力、需求雷达与跟进闭环已经打通，可以回答「缺口在哪、派人去了没有、之后有没有好转」；命中率的跨周期趋势也已经落在看板上：同一批任务切成两个等长周期，把闭环命中率和中位收敛幅度放在一起看，因为两个周期可能命中率相同而一个把缺口补得深刻、另一个只补了边角。任务按创建时间归期而不按结果落地的周期归期，否则一个安静月会继承忙碌月的成绩；命中率也只统计有足够证据的任务，根本没人搜过的话题不让任何一边变得好看或难看。目前已做到跨周期对比与按分类、地点的闭环分层；后续可继续补充学期之间的纵向对比，让“雷达到底是否在变准”这个问题有更细的答案。
- **学期节律运营**：当前已支持学期日历、可配置的阶段偏移和阶段级对比，需求雷达命中率也已按阶段跳学期对比—同一个阶段只跟上一个学期的同一个阶段比，因为逆季节的需求本就不同；后续可继续补充阶段切换前的内容预热和按阶段调整的供给引导；
- **校园专题运营**：继续增加专题报名、活动目标、分阶段复盘和专题之间的转化对比，让校园活动从内容聚合逐步演进为可衡量、可复盘的运营闭环；
- **校园专题**：专题使用明确的起止时间和启用状态，过期专题不会继续出现在公开入口；商品与专题使用可选关联，不改变普通商品的浏览和交易流程。
- **循环价值**：继续完善校园循环影响力报告，增加学期对比、毕业季专题和更细的物品流转生命周期，但仍保持隐私安全和指标可解释；
- **信任体系**：继续完善校园认证、响应速度、交易安全卡和可解释的异常交易识别；
- **社区治理**：加入敏感词分级、举报优先级、审核工作台、申诉和处理结果反馈；
- **通知体验**：继续完善通知分组、批量操作、摘要投递和更及时的消息同步；当前关注搜索已支持即时、每日、每周三种节奏，汇总提醒按周期去重并限制单条列出条数，也支持临时静默和切回即时后补投。
- **供需匹配**：继续完善求购匹配评分、匹配解释、价格参考和响应后的预约转化统计；当前已支持卖家响应、求购者确认、响应状态通知和互助完成反馈，也提供了面向卖家的互助机会流，商品详情还提供基于样本的价格区间提示。
- **基础设施**：支持 PostgreSQL、缓存、对象存储、结构化日志、备份和更完整的生产部署；
- **体验完善**：优化移动端布局、无障碍、图片处理、校园配置和运营工具；
- **数据质量**：继续明确指标口径，增加异常行为识别和运营动作后的效果评估。

这些方向会继续拆成可以独立验证、独立回滚的功能提交，不以一次性重做为目标。

## 参与开发

欢迎提出具体的校园交易场景，也欢迎提交代码、测试、设计和文档改进。适合的贡献方向包括：

- 改进搜索、筛选、推荐和校园地点体验；
- 增加交易安全、交付确认和社区治理能力；
- 优化移动端页面、通知中心和无障碍细节；
- 补充模型、视图、权限和关键流程测试；
- 完善部署、监控、数据维护和运营分析；
- 根据真实校园使用经验调整分类、地点和交易流程。

建议按照以下方式提交改动：

1. 先说明要解决的使用场景和影响的业务链路；
2. 将一个独立功能的模型、页面、权限、测试和文档尽量放在同一组改动中；
3. 提交前运行本地检查和测试；
4. 使用清晰的中文提交信息，保持每个提交可独立理解和回溯；
5. 不提交本地数据库、上传文件、密钥或临时调试产物。
