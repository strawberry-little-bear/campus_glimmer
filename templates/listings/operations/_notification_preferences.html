三个数本应相等，现在它们相等了

站内通知中心上线到现在，Notification.KIND_CHOICES 上有 {{ notification_kind_coverage.current.kind_total }} 种已登记的类型，NotificationPreference 上有自己的布尔开关，NotificationPreferenceForm 里又另有一份字段列表。这三个数本应相等，或者只差免打扰那一组。它们一度不相等——而每个表各自都是自洽的，所以差额一直被「看起来像」吃掉了。两个方向的窟窿都已在「通知类型的两个窟窿补上」那一轮修掉，现在三张表是对齐的；要看见它，仍然得把三个数并排放，而不是各自数。本面板读的是三处代码事实：模型元数据、KIND_CHOICES、偏好表单字段，全部现读，不硬编码名单。

周期内没有发送记录，偏好状态需要先有通知发生。
只统计发过的类型：一个从没被发送过的类型，它的开关开着或关着都不产生任何后果。开关状态按发过通知的接收人统计，不按全站用户——一个从没收过这一类通知的用户，他的开关开着或关着都没有行为意义。不按用户报、不排名、不报任何人的用户名：「谁关了哪一类」是一份考勤表，不是一份看板。
这里只报告：不加迁移、不改 KIND_CHOICES、不改 NotificationPreference、不改表单字段列表。那两个窟窿已经在下一轮补上——一个补 KIND_CHOICES 里那一行名字，一个补表单字段里那一行暴露，两处都不改表结构，所以都没有迁移；补上之后差集变空，而这是修的结果，不是改口径改出来的。不报「偏好关闭让用户少收了多少条」：create_notification 在偏好关闭时直接 return None，被关掉的通知在库里一行都没有，那个数不存在。不把三个数的差解释成「设计疏漏」：为什么不等，代码里看不出来，只报差，不猜原因。

「关着却仍收到过」是这一节的观测对象。它只可能是窗口前收到的，或者汇总类通知（operations_digest / opportunity_digest / saved_search_digest）在另一个时刻生成。这一格很大，说明这个开关要么没接上、要么接的是一条用户没意识到的路径。「开着却没收到过」不是漏报——一个从没被预约过的用户开着 order_created 是天经地义。两格都只报人数，不报任何两格之间的比值。
这里只报告：不加迁移、不加字段、不改 create_notification 那句静默的 return None、不给任何人自动打开开关。开关名单从模型元数据现读，不硬编码——硬编码的名单会和代码走散，而那正是上一个面板要报的问题。不报「关掉之后通知少了多少」：被挡掉的通知一行都不建，分子在库里、分母不在，拿得到的那个数随窗口长短和用户活跃度漂移，不是开关的效果。关掉通知偏好是用户的私事：不列谁关了什么、不按用户排名、不输出用户名。
