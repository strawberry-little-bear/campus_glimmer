刷新额度为什么是一次性的

「本月刷新次数」这句话，和代码里真正生效的那条判据

_refresh_state 的第二条判据是 refresh_count >= MAX_REFRESH_PER_MONTH（{{ refresh_quota_drift.max_refresh_per_month }}），常量名、文案和 supply_lifecycle 的英文 docstring 都写着「monthly」。但 refresh_count 是从不清零的累计计数器——全仓没有任何一处把它写回 0。所以上限实际生效的口径是：这件商品发布至今最多刷新 {{ refresh_quota_drift.max_refresh_per_month }} 次，不是「本月」。

这个数是精确的，理由有点巧。限流判据是 >= {{ refresh_quota_drift.max_refresh_per_month }}，而 refresh_count 只会被加一，所以它最多到 {{ refresh_quota_drift.max_refresh_per_month }}、永远不可能到 {{ refresh_quota_drift.max_refresh_per_month|add:1 }}；于是 count 等于 {{ refresh_quota_drift.max_refresh_per_month }} 时，last_refreshed_at 就是撞墙那一刻，不需要一张刷新历史表。分母只收本周期刷新过的商品——一次都没刷过的商品不可能在本周期撞墙。

为什么先看板、后改口径

改口径要二选一：加一张刷新历史表，或给商品加一个「上次清零时间」字段——两条都要迁移。而且改完全部历史累计达 {{ refresh_quota_drift.max_refresh_per_month }} 的商品会同时获得一次刷新机会，上限对存量商品失效整整一轮，那正是刷屏最该防住的时候。所以先把这个差量量出来：如果只有个位数，改一句话就够；如果是成百上千件沉底商品，那它值得一张刷新历史表。

本模块只报告，不改 _refresh_state 的任何一条判据、不清零 refresh_count、不加刷新历史表、不动那条「本月刷新次数已达上限」的文案，也不把统计写回任何记录。supply_lifecycle 已经报过「刷新额度已用尽的卖家有多少位」，这里不复述那个数，只报额度这件事本身在商品层面差了多少。
