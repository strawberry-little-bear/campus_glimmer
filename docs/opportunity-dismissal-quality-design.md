# 用户按过「不再显示」的机会，第一次被运营读到

## 起点

`listings/opportunity_feed.py` 的 `build_opportunity_feed(user)` 是站内唯一一条个性化
推荐流，面向卖家：把他的在售商品和活跃的校园求购、失物招领记录做可解释匹配，给出一条
带理由的机会流。写入路径只有一处，在 `views.py` 的 `dismiss_opportunity`：用户在机会流
里点「暂不展示」，`OpportunityDismissal.objects.update_or_create` 落一行，带 `kind`
（`demand` / `lost_found`）、`demand` 或 `lost_found_post`、`expires_at` 和 `created_at`。

读路径也只有一处，就是机会流自己——`opportunity_feed.py` 里
`OpportunityDismissal.objects.filter(user=user, expires_at__gt=now)`，取出来做成两个 id
集合，把对应的机会 `exclude` 掉。除此之外的引用只有 `admin.py` 的注册和 `models.py`
的定义。

**也就是说，用户每一次「不再显示」都被完整记录下来，而平台从来不知道这些忽略到底意
味着什么。** 后台能列出这些忽略，看板上没有任何一个数字。

## 为什么这是真缺口

站内已有四个「量我们自己的打分 / 排序」的模块：

- `search_position_quality.py` 量搜索排序；
- `demand_match_quality.py` 量求购匹配打分；
- `recommendation_quality.py` 量首页八张推荐卡（上一轮刚做完）；
- `opportunity_feed` 是唯一一个**既带分数、又带理由、又带用户负反馈、却从未被量过的
  个性化排序**。

机会流的性质和前三个还不一样：它是站内唯一一条「平台主动告诉用户『你可以帮到别人』」
的推荐，用户对它按「不再显示」是一次明确的拒绝。一次拒绝比一次沉默信息量大得多——
沉默可能只是没看见，而「不再显示」是用户读完匹配理由之后做出的判断。

而机会流背后是两个已经上过看板的匹配器：`demand_matching._match_demand` 和
`lost_found_matching.score_lost_found_posts`。这两个函数的分数已经分别被
`demand_match_quality`（按求购人的接受 / 拒绝）和 `lost_found_lead_quality`（按线索
确认率）量过，但量的都是**被撮合的那一方**。机会流量的是**撮合的另一方**——卖家面对同
一个分数、同一句理由时的取舍。同一个分数在两个方向上的含义可能完全不同，而现在只能
看到一个方向。

四个答不上来的问题：

1. 忽略的规模有多大，求购和失物招领各占多少？
2. 分数高的机会是不是更不容易被忽略？如果不是，那两套匹配器的分数在机会流这个场景
   下不解释用户行为。
3. 哪一句理由在骗人？
4. 忽略之后有没有回来——静默期结束、同一条机会重新进入这个用户的候选池，用户是又忽
   略了一次，还是这次点了进去？

## 这个模块不报忽略率，因为分母不可得

这是本模块最重要的一条取舍，必须先说清楚。

`OpportunityDismissal` 只记「忽略」，不记「看过」。一条机会被 `build_opportunity_feed`
渲染出来、用户什么也没点，库里**一行都没有**。所以「窗口内被展示过的机会」这个数拿不
到，而它是忽略率的分母。

`recommendation_quality` 遇到过同样的问题，当时的解法是用 `BrowsingHistory` 反推分
母，并明确命名成**反馈率的下界**。机会流连这个近似都没有：机会流页面本身不产生任何
可反推的记录——「打开过机会流页」这件事不在任何表里，机会卡上的「去响应」按钮指向求
购详情页，那条浏览记录会被算成一次普通商品浏览，无法和机会流区分。

所以本模块**不报忽略率**。报一个「用页面构造当分母」的率（比如「进入机会流页的次数 ×
每页候选数」）是估算不是测量，而一个估算出来的率会让运营以为自己量过——那比没有数
字更糟。

具体报的是四个数，四个都只描述忽略本身：

1. **忽略的绝对规模与结构。** 总数、按 `kind` 拆、按用户拆（多少人在按、平均一人按
   几条）。
2. **按分数档拆的忽略分布。** 分子是忽略，分母也是忽略——这是忽略自己的形状，不是
   率。它能回答「分数高的机会是不是更不容易被忽略」，但答案只能是形状上的（高分档
   的忽略是不是更少），不能是「高分档的忽略率更低」。
3. **按理由拆的忽略分布。** 同理，这是哪一句理由在骗人的唯一线索。
4. **同一条机会被同一个人重复忽略了几次。** 见下一节，这是本模块最硬的证据。

## 重复忽略：本模块唯一能回答「忽略有没有用」的数

`OpportunityDismissal` 上有两个**无条件**唯一约束：`unique_opportunity_dismissal_demand`
是 `(user, demand)`，`unique_opportunity_dismissal_lost_found` 是
`(user, lost_found_post)`。而写入用的是 `update_or_create`，`defaults` 里只更
`expires_at`。

这两件事合起来意味着一个关键的实现事实：**同一个人对同一条机会的第二次「不再显示」不
会产生新行，只会把旧行的 `expires_at` 往后推 30 天。** `created_at` 是
`auto_now_add`，`update_or_create` 走到 update 分支时不会碰它，所以 `created_at` 停在
第一次忽略的时刻。

于是「重复忽略」在库里的形状是：一行，`created_at` 早于窗口起点，而它在窗口内被更
新过。判断它只能靠一个间接信号——`expires_at` 和 `created_at` 的距离。

第一次按下「不再显示」时，`expires_at = created_at + 30 天`（两次时钟读取相差毫秒）。
第二次按下时，`expires_at` 被推到「第二次的时刻 + 30 天」，于是
`expires_at - created_at > 30 天`。所以：

- `expires_at - created_at` 落在 30 天附近（取一个容差）的是**只忽略过一次**；
- 明显超过 30 天的是**忽略过不止一次**，超出的天数还能给出「第二次发生在多久之后」
  的下界。

这个判据是间接的，边界必须写进面板：它数不到「忽略过一次、30 天后到期、用户又重新看
到又忽略」的全部情形，因为第二次忽略也可能正好落在 `created_at + 30 天` 附近；它也
分不清「同一个人主动又按了一次」和「别的东西更新了这一行」——目前后者的写入路径不存
在，但这是一个需要守住的前提。**只报告，不改任何一行 `OpportunityDismissal`。**

## 分数怎么来：忽略时刻重算，不落库

`OpportunityDismissal` 不存分数，也不存理由。而分数和理由是每次请求重算的——同一条
机会在两个时间点上的分数可能完全不同：求购方改了预算、商品降了价、失物招领的
`occurred_at` 过了 7 天窗口，分数都会变。

所以分数必须在**忽略时刻**重算一次，走两个匹配器自己的函数，不能在运营模块里另写一
套：

- `kind == 'demand'`：`_match_demand(demand, item)`，需要知道用户当时拿哪件商品匹配的。
  `OpportunityDismissal` 没存 item，所以取这个用户名下在售商品里分数最高的那一次匹配
  ——这正是 `build_opportunity_feed` 的 `best_demands` 逻辑（同一条求购取分数最高的那
  件商品）。复算只读**当前在售**的商品，所以它还原的是「如果今天再进池，这条机会的
  分数是多少」，不是忽略那一刻的分数。这个近似必须写在面板上。
- `kind == 'lost_found'`：`score_lost_found_posts(source, candidate)`，同理取这个用户名
  下**活跃**失物招领记录里分数最高的那一次。

理由同样重算。求购侧的理由是 `_match_demand` 返回的第二个值；失物侧是
`score_lost_found_posts` 返回的第二个值拼起来的。按理由聚合的粒度和
`recommendation_quality` 一致：**按理由聚合，不按用户、不按商品。** 按用户是排名
（隐私，也不是运营射程），按商品让被忽略一万次和一次不可比。

## 规模门槛与噪声线

和其余模块同一个量级：

- 一个分数档要凑够 `MIN_BAND_SAMPLE = 12` 条忽略，才允许对它下「这一档的分数不解释
  行为」的判断；
- 一句理由要凑够 `MIN_REASON_SAMPLE = 12` 条忽略，才允许对它下「这句理由在骗人」的
  判断；
- 两个档 / 两句理由的占比相差不满 `NOISE_POINTS = 10` 个百分点，视为噪声。这里比的
  是**占比**（该档忽略数占全部忽略的比例），不是率——率的分母不可得，见上一节；
- 空平台不报 0%：一条忽略都没有的时候，所有占比都不存在，不是零。

## 不做什么

- **不报忽略率，不加曝光表。** 分母不可得，见上。也不为了这个面板给机会流页面加一次
  insert。
- **不改静默期。** 不把 30 天改成 7 天或 90 天，不缩短、不延长任何一行
  `OpportunityDismissal.expires_at`。
- **不删除任何忽略记录，不把忽略当成负样本回流到打分。** `_match_demand` 和
  `score_lost_found_posts` 的权重一个常数都不动。自己改自己权重会让看板量的不是机会
  流质量，而是它上周的输出。
- **不按用户排名，不报「谁最爱按不再显示」。** 那是一份指责清单，不是一份看板。
- **不判断忽略是否「正确」。** 平台没有能力判断一条机会对该用户是不是真的没用，只能
  记录他按了按钮。
- **不回填任何数据。** `created_at` 是用户第一次忽略的时刻，不改写。
