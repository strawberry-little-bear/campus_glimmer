# 用户建的心愿单分组，第一次被运营读到

## 起点

`FavoriteCollection` 和 `Favorite` 是站内最早的一批模型，心愿单分组的功能从那时候起就是建全的：

- `views.toggle_favorite` 在商品卡上收藏 / 取消收藏，写 `Favorite`；
- `views.favorite_list` 是读侧，列出这个用户名下的分组（带 `Count('favorites')` 计数）和收藏，支持 `?collection=<id>` 按分组筛选，`collection_id` 转 `int` 失败或分组不属于这个人时静默回落到「全部收藏」；
- `views.create_favorite_collection` 建分组，`FavoriteCollectionForm` 只校验名称非空且不超过 40 字，写入走 `get_or_create(user, name)`——同名分组不报错，只提示「已经存在」；
- `views.update_favorite_collection` 把一条收藏移进 / 移出某个分组，`collection_id` 为空表示移出（`Favorite.collection` 是 `on_delete=SET_NULL`，可以空），带 `next` 回跳并用 `url_has_allowed_host_and_scheme` 校验；
- `admin.py` 两个模型都注册了。

写路径一共四条（收藏、取消收藏、建分组、改分组），读路径一条半（心愿单页自己，`_favorite_ids` 给商品卡标星）。除此之外 `Favorite` 只在别处被顺带读过：`analytics.campus_pulse` 拿它算活跃用户，`recommendations` 拿它取分类偏好，运营看板的专题分析拿它算「浏览到收藏」的转化。

**也就是说，分组功能有完整的增删改查和 UI，而「有没有人用、建了分组之后收藏行为有没有变化」一条统计都没有。** 后台能按用户名列出分组，看板上没有任何一个数字。

## 为什么这是真缺口

站内已经有二十多个「量我们自己的功能」的模块，量过搜索排序、求购匹配、首页推荐、机会流负反馈、私信响应、评价质量、争议处理、借用风险、任务运行健康度。心愿单分组是少数几个**有完整 UI、有数据、但从来只被用户一个人看到**的功能。

它和前几轮做过的那些不一样：那些模块量的是「平台做了一个判断，这个判断准不准」；分组量的是「平台给了一个工具，这个工具好不好用」。前者是打分器的自我检验，后者是功能采用的度量。站内并不缺前者的样板，缺的是后者——绝大多数功能上线之后，除了页面上的点击数，再没有第二个数字。

四个答不上来的问题：

1. 有多少人在用心愿单分组？是个人人都用的功能，还是一个建完就再也想不起来的角落？
2. 分组被当成什么用——一个装几十条的收纳盒，还是一个装一两条的标签？这两种用法该有不同的引导。
3. 建了分组却一条都没放进去的有多少？其中有多少是早就建了、一直空着？
4. 大家给分组起的名字收敛吗？如果几百个人都在建「教材」「宿舍」「想买」，那平台应该把这几个名字做成预设分组，而不是让每个人都自己打一遍。

## 这个模块不报「先收藏后归类」，因为库里没有那个时刻

这是本模块最重要的一条取舍，先说清楚。

`FavoriteCollection` 有两个时间列，`Favorite` 有一个。乍看这个数据很富裕——「先收藏后归类还是收藏时就归类」这个问题，似乎能用 `Favorite.created_at` 和某个「归类时刻」的差来回答。但 `Favorite` **没有 `updated_at`**。

`views.update_favorite_collection` 把收藏移进分组走的是 `favorite.save(update_fields=['collection'])`。这一 save 只更新 `collection` 一列：`Favorite` 模型里没有任何 `auto_now` 字段，所以这次保存不刷新任何时间列。一条 60 天前收藏的商品，昨天被移进分组，它在这个库里的全部痕迹就是 `created_at = 60 天前`、`collection = 那个分组`——**它是什么时候被归类的，不存在。**

所以任何「窗口内新建的收藏里有多少条是直接就归了类的」这样的数都读不出来：一条窗口内新建的收藏，`collection` 是**今天读到的值**，不是它创建时的值。这个数会被读成「收藏时就归组率」，而它其实混着大量后来才移进去的收藏。报一个会被误读成另一个意思的数，比没有数字更糟——和上一轮不报忽略率是同一条规矩。本模块因此**不报任何和时间差有关的归类比例**，只报规模的切分。

同理不报的还有两件事：

**不报「分组被改名 / 被整理的频率」。** `FavoriteCollection` 有 `updated_at`（`auto_now`），但应用内没有改名路由：`create_favorite_collection` 走 `get_or_create`，同名时不写；`update_favorite_collection` 改的是 `Favorite.collection`，不是 `FavoriteCollection.name`。唯一的写入路径是 Django admin 的保存。所以 `updated_at != created_at` 只说明「有人在后台动过这条分组」，数不到改名，也分不清改名和别的字段变更。低频且不可归因，不报。

**不报「删分组之后收藏去哪了」。** `Favorite.collection` 是 `on_delete=SET_NULL`：删分组不删收藏，只把它们变成未分组。而删分组在应用里没有路由、没有视图，只走 admin。所以「删过分组的用户」这件事本身不留痕，删完的收藏和从来没归过类的收藏长得一模一样。不可报。

## 分母怎么切

这一轮和上一轮最大的区别：**分母全都有。** 机会流那边「被展示过的机会」拿不到，心愿单这边每一样东西的存量都是可数的。四类分母各自独立，不能混：

| 分母 | 是什么 | 用来报什么 |
| --- | --- | --- |
| 当前全部收藏 | `Favorite` 全表，不限时间 | 分组渗透率（已归组 / 全部） |
| 当前全部分组 | `FavoriteCollection` 全表，不限时间 | 分组大小分布、空分组率 |
| 当前有收藏的用户 | `Favorite.user_id` 去重 | 建过分组的人占多少 |
| 窗口内新建的收藏 / 分组 | 按 `created_at` 切 | 规模，不报比例 |

「当前」是一个快照，不是窗口。这一点必须写在面板上：分组可以被删（删完收藏变未分组），收藏可以被取消（`toggle_favorite` 的 `delete` 分支），所以快照和「窗口内发生过什么」是两件事。本模块同时报窗口内的新建规模（按 `created_at` 归期）和当前快照（渗透、分布），两者在面板上分开摆，不放进同一张表。

## 空分组要分「刚建」和「早就建了还空着」

空分组（一条收藏都没有）是「建了分组不会用」的信号，但它有一个明显的良性解释：这个分组是几秒钟前刚建的，用户还没来得及往里放东西。所以空分组要按 `FavoriteCollection.created_at` 拆一刀——建于 7 天前仍然是空的分组，才是真信号。7 天这个数没有理论依据，取的是「一个真心想用分组的人不会一周都想不起来往里放第一条」这个量级，写进常量并留注释。

## 分组名按用户数聚合，不按条数

分组名在同一个用户内唯一（`UniqueConstraint(fields=['user', 'name'])`），所以一个名字的计数天然就是「用过这个名字的用户数」，不需要另做去重。按名字聚合能回答「命名收敛吗」这个问题，但它有一个隐私边界：一个只被一个人用过的名字，报出来就等于报了一个人的个人命名。所以设 `MIN_NAME_SAMPLE`，只有被这么多个以上不同用户用过的名字才进榜单。这不是样本量问题，是隐私问题——和按用户聚合是排名是同一条线。

## 这个模块只报告

不新建分组、不合并分组、不改任何一条 `Favorite.collection`、不改任何分组名、不动 `FavoriteCollectionForm` 的任何校验、不给任何用户排名、不预设任何分组名。运营看到「教材」被很多人用，要动手做成预设分组，那是下一步的事——本模块只负责让这个数字第一次被看到。

总结起来，本模块报五块：分组的规模与人均、分组的大小分布（含空分组）、收藏的分组渗透、建过分组的人占多少、分组名的收敛形状。每一块都说清分母是什么、是什么的快照。凡是判据间接或分母不可得的地方，本模块选择不报，并把原因写在面板上。
