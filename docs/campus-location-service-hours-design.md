# 校园地点开放时段设计

## 要解决的问题

校园地点已经有档案、维护队列和交付推荐，但“这个地方什么时候适合交付”仍主要写在自由文本安全提示里。自由文本能提醒人，却不能参与时间判断：系统不知道图书馆门口晚上几点关门，也不知道门卫室是否只在工作日开放。

本轮要做的是给地点补充结构化的每周服务时段，并把它接到交付建议链路里。它不是门禁系统，也不承诺地点一定开放；它只把已登记的开放信息变成可解释的提示。

## 目标

- 为每个校园地点维护若干条每周重复的服务时段：
  - 星期，按周一到周日；
  - 开始时间；
  - 结束时间；
  - 启用状态。
- 支持跨午夜时段，例如 `22:00–次日 02:00`。
- 支持同一地点同一天多条时段，重叠或相邻时段按合并后的结果判断。
- 提供统一判断口径：
  - 某个时刻是否落在登记开放时段内；
  - 一个交付区间是否完整落在登记开放时段内。
- 在后台维护地点时可以直接编辑服务时段。
- 在订单详情的交付建议中展示地点的时段摘要：
  - 已登记时段的地点加分，并说明已登记；
  - 未登记时段的地点不扣分，提示双方自行确认；
  - 若已有交付安排，能解释当前安排是否落在开放时段内。
- 推荐时间结合当前交付地点做排序：
  - 落在登记开放时段内的候选时间加分；
  - 不在时段内的候选时间降低排序并说明原因；
  - 未登记时段的地点不惩罚，只提示自行确认。
- 提交交付安排时，如果所选时间不在登记开放时段内，保留提交能力，但用页面消息提醒双方自行确认临时开放、假期调整或现场门禁。

## 数据与判断口径

- 新增 `CampusLocationServiceWindow`：
  - `location`：所属校园地点；
  - `weekday`：1 到 7，对应周一到周日；
  - `start_time` / `end_time`：本地时间；
  - `is_active`：是否启用；
  - 时间戳。
- 同一地点、同一星期、同一开始时间只允许一条，避免重复配置。
- `start_time == end_time` 表示拒绝保存，不借用它表达“全天开放”；本轮不提供全天开关，避免用 `00:00–23:59` 伪装完整覆盖。
- 时段归属以开始日期的星期为准；跨午夜时段自动覆盖次日凌晨。
- 判断输入统一转换为当前时区的本地时间，再与每周时段比较。
- 一个预约区间必须被启用时段的并集完整覆盖，才算“落在开放时段内”；只覆盖一半时按“不在开放时段”处理。
- 没有启用时段的地点状态是“未登记”，不是“不开放”。

## 交互与推荐边界

- 地点推荐仍以商品地点、双方历史、近期使用和公共区域为主；服务时段只是新增的透明信号。
- 时间推荐未来一周、每天 9–21 点的基础扫描范围不变。
- 未登记时段不参与扣分，避免因为运营档案不完整而惩罚一个实际可用的地点。
- 已登记但不匹配的时间不会被强制隐藏，仍可能因为时间更近、周末或课后而出现在建议里，只是排序下降并写明原因。
- 不在开放时段内的交付安排可以提交，系统给警告，不代替双方协商，也不阻止假期临时调整。
- 地点详情和订单详情只展示时段文本，不展示管理员姓名或维护留痕。

## 明确不做

- 不记录用户实时位置、到达轨迹或行程画像。
- 不接入门禁、课表、校历或假期系统。
- 不自动改约、自动取消预约或自动停用地点。
- 不把“未登记时段”当成地点档案错误，也不在维护队列里自动生成修复任务。
- 不处理单日例外、法定假期、寒暑假特殊开放或临时关闭。
- 不向普通用户开放地点档案编辑权限。
- 不生成运营统计，不按地点输出个人交付时间分布。

## 验收口径

- 后台可以在地点编辑页维护多条启用时段。
- 同一地点同星期同开始时间的重复配置被数据库约束拒绝。
- 普通日间时段、跨午夜时段、重叠与相邻时段的覆盖判断准确。
- 未登记、已登记且开放、已登记但关闭三种状态在推荐理由中可区分。
- 未登记地点的推荐分数不因缺少时段下降。
- 时间推荐优先展示落在当前交付地点开放时段内的候选，并保留原因说明。
- 交付安排提交在时段外时仍可保存，但页面出现明确提醒。
- 不新增用户位置记录，不改变既有预约冲突校验和订单状态流转。

## 落地记录

- 已新增 `CampusLocationServiceWindow` 与迁移，后台地点编辑页支持行内维护多条时段。
- `campus_location_service_hours.py` 统一处理星期、跨午夜、重叠与相邻时段的覆盖判断。
- 地点推荐展示登记时段；时间推荐结合当前交付地点解释开放状态，未登记不扣分。
- 交付安排提交在时段外时仍按原流程保存，订单详情向双方展示提醒。
- 单日例外、假期日历和门禁接入仍未纳入本迭代。
