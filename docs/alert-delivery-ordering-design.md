# 告警投递的优先级、严格有序与升级通道设计

[按指标告警设计](metrics-alerting-design.md) 落地了带退避重试的 Webhook outbox。本设计在其上补齐三件事：critical 先投、同一规则内按入队序投、常规渠道耗尽后把 critical 送进独立的升级 Webhook。三者都发生在现有 outbox 这一张表里，不引入外部队列。

## 要解决的问题

- 严重度没有顺序：一条 info 的「共享未启用」可以排在 critical 的 5xx 前面被投出。
- 同一规则的事件可能乱序：firing 投递失败进入退避时，随后入队的 resolved 若被立即投出，外部系统会先看到「已恢复」再看到「出故障」。
- 常规渠道持续失败时没有第二渠道：critical 重试耗尽后只能等人翻台账。

## 不做什么

- 不做值班系统：没有轮班、静默、抑制与人工确认；升级通道只是「换个地址再喊一遍」。
- 不做跨规则的全局有序：不同规则之间只有优先级与到期时间两个序，不承诺先后语义。
- 不回填历史数据：升级部署后，旧行按默认「一般」档投递，不会按 payload 重算旧优先级。
- 升级不派生二级升级：升级行自身失败走正常退避，不会再喊第三遍。

## 设计

### 优先级

severity 在入队那一刻固定映射为三档 priority：critical 为零、warning 居中、info 最后，未知 severity 按 warning 处理。映射是模块常量而不是环境变量——它和规则本身的 severity 是同一份事实，不应该被部署单独改写。flush 按 priority、到期时间、id 排序；同档内保持原有的到期时间序。

### 同一规则的严格有序

闸门定义：每条规则取最早的一条未决常规行（pending，或租约未过期的 delivering）作为队首；队首未决时，同规则后面的行让位。具体行为：

- flush 每轮开始时用一条聚合查询取每条规则的队首 id；不是队首的行这一轮不投，计入 held。
- enqueue_and_deliver 的新行如果发现自己不是队首，不做立即投递，行带着租约留在表里等 flush 接手——resolved 不能越过退避中的 firing。
- 升级行自成一条流，不参与闸门，也不阻塞常规流。

这个保证是「同一规则内不乱序」，不是「不延迟」：队首退避时，同规则后续行会一起等。这是刻意的取舍——告警场景里错序比晚到难解释得多。

### 升级通道

critical 行在投递中标记 exhausted 时，若配置了 `DJANGO_ALERT_ESCALATION_WEBHOOK_URL`，向同一 outbox 追加一条升级行：payload 原样复制并加 `escalation: true`，去重键序列加 `escalated|` 前缀，行的 `escalated` 字段为 True。升级行立即用升级通知器投递一次，失败后进入与常规行相同的指数退避。升级 Webhook 的 URL、令牌与超时独立配置；URL 留空即整条通道关闭。warning 与 info 耗尽不产生升级行。

去重窗口两边各自独立：常规去重只看常规行，升级去重只看升级行，同一窗口内同一条已耗尽的行也不会重复派生升级。

## 运维口径

- 升级行与常规行共用 `/alerts/` 的状态计数和 `/metrics/` 的固定指标形状，不新增序列。
- `flush_alert_notifications` 的输出多了 held（本轮让位行数），其余键不变。
- 升级行的优先级继承原事件的 critical 档，会排在常规重试之前被 flush 处理。
