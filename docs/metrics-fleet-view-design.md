# 跨副本指标聚合设计

## 为什么先做需求

路线图里长期挂着一条：`/metrics/` 的计数器仍在进程内，多副本各算一份，跨副本聚合与按指标告警依然缺着。这句话的实际后果不是"少一个导出器"，而是监控数据在说谎：

- 生产是 Gunicorn 多 worker、多副本，而抓取目标通常只有一个地址。抓到哪个副本就看到哪个副本的数字，另外几个副本的流量被读成不存在。
- 更糟的是"抓到哪个副本"每天都不一样：负载均衡轮转、worker 重启、滚动发布都会让同一条曲线在两次抓取之间跳变，而看板上没有任何东西提示这是采样问题。
- "按 Prometheus 多目标模型部署"这条路在本项目不成立——单机小规模部署没有稳定的副本地址列表可写进 `scrape_configs`，为它引入一套服务发现属于为一个看板问题引入一套基础设施。

所以这一轮做的是：让 `/metrics/` 返回的是一整支舰队的合并视图，并让"这是几个实例合出来的"这件事在指标里可见。**按指标告警不在这一轮**，理由见文末边界。

## 目标

- 单目标抓取就能拿到整个服务的请求量、耗时和在途数，而不是其中一个副本的。
- 不引入新的外部依赖：共享载体就是默认缓存，生产里它已经是 Redis。
- 合并结果可解释：哪些副本进了视图、视图有多旧、有没有哪份因为格式不同被跳过，都要在指标里，而不是只存在于日志里。
- 共享存储出故障时降级而不是失效：监控端点自己 500 比数字旧一点更难排查。
- 禁用共享时也要诚实：有一个序列明说"你现在看到的是一个进程，不是整个服务"。

## 为什么共享载体是缓存，而不是消息队列

需要共享的只有一份几百行的快照，而 Redis 已经是生产的硬依赖（会话和缓存都指着它）。为它引入消息队列或专职聚合服务，等于为了一份快照多加一个要备份、要监控、要扩容的组件。

Django 缓存 API 没有可移植的 `scan`，所以实例名单是一张显式的名单，不是扫 key。两个副本同时发布时可能互相覆盖一次名单写入，最坏情况是某个实例在下一个发布周期重新出现；而快照本身带 TTL，不会留下"名字还在、数据没了"的鬼数据。名单读回来时会顺手做一次自清理，把已经过期的名字删掉。

## 为什么是周期全量快照，而不是增量 flush

三个候选方案里只有这个能同时满足"不重"和"不漏"：

- **抓到时顺手发布**：抓取目标只有一个地址，另外几个副本永远等不到被抓的那一刻，它们的计数就永远不进视图。等于把负载均衡今天的调度策略写进了监控口径。
- **增量 flush**：要在共享存储里做"读-改-写"，两次抓取之间可能丢增量，也可能因为重试把同一批增量算两遍。重不漏比丢更难实现，而丢一次增量没有任何信号。
- **周期全量快照**：每个实例每五秒把自己**整份**计数器写进去。无双重计数、无丢增量，"进不进视图"只取决于这个实例活没活，不取决于负载均衡今天把请求转给谁。

代价是每个周期多一次几百字节的写入和一次全量读取，对这份数据量来说可以忽略。

## 合并规则

| 维度 | 规则 | 为什么 |
| --- | --- | --- |
| 请求计数器 | 按 (路由, 方法, 状态类别) 相加 | "总共发生了多少次"的唯一算法 |
| 耗时直方图 | 只合并分桶布局相同的实例 | 混桶会算出从未发生过的分位数，比不合并更糟 |
| 在途请求 | 求和 | 每个副本此刻各自的数量，加起来才是服务此刻的数量 |
| 标签溢出标记 | 取并 | 任一副本触顶，整个视图的分桶就已经不全了 |
| 启动时间 | 取最早 | "这批实例是什么时候起来的"问的是最早那个 |
| 构建信息 | 按内容去重 | 滚动发布期间新老版本同时在线，两份都是事实 |
| 实例标识 | 只做存储键，不进标签 | 标签基数是要钱的东西，单目标抓取下"哪个副本"没有读者 |

`instance_id` 取 `hostname:pid`。带 PID 是因为一个容器里 Gunicorn 可能起多个 worker，它们各是一份计数器，同名会互相覆盖。

读取时必须排除自己的实例标识。这是整个合并里最容易犯的错：不排除的话，本进程那份计数会被算两遍，而症状只是"数字比日志里数出来的多一倍"——没有任何报错。

## 分桶不符时的取舍

`LATENCY_BUCKETS` 是代码里的常量，正常不会变；它变动的场景是滚动发布中新旧版本短暂同时在跑。此时新老两份直方图的分桶边界不同，直接相加会算出从未发生过的分位数——这比不合并更糟，因为它看起来是个合法的直方图。

所以分桶不同的实例只把请求计数器并进来，直方图整个丢掉，并由 `campus_glimmer_metrics_bucket_mismatch` 把跳过的实例数报出来。计数器的口径不受影响，受影响的只有 p95/p99 这一个视图，而且它是可见的。

## 失败路径：宁可少算，也要能抓到

共享存储读不动时（连接失败、缓存里躺着旧版本的畸形快照），本次抓取退化为本进程视图，并把失败次数记进 `campus_glimmer_metrics_shared_read_errors_total`，同时打一条 warning。

退化的前提是：一个 500 的监控端点比数字旧一点的监控端点更难排查。Prometheus 会记 `up == 0`，而看板上所有曲线一起消失，排查的人要先分辨"是服务挂了还是抓取挂了"。

合并也放在同一个 try 里。畸形快照让 `merge_fleet` 抛异常时，走的是同一条降级路径，而不是让端点 500。

发布线程同理：`publish_safely` 吞掉存储异常，线程继续活着。存储恢复之后它还得发布，否则舰队视图会一直停在死前那一刻。日志只在状态翻转时记一行——共享存储每五秒抖一次，每周期一行同样的警告会把真正要看的东西从日志里冲掉。

## 开关与默认值

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `DJANGO_METRICS_SHARED` | 按缓存后端判断 | 三态开关。留空时 LocMem 判为关、跨进程后端判为开；显式设置优先。拼错的值直接让启动失败 |
| `DJANGO_METRICS_SHARE_INTERVAL` | `5.0` | 快照发布间隔（秒） |
| `DJANGO_METRICS_SHARE_TTL` | `30.0` | 快照存活时间（秒） |

LocMem 默认关是有意的：它是进程内的，多 worker 下各存各的，开了只会给出"只有我自己"的假象——比不开更糟，因为看板上会多一个写着 1 的实例数。

TTL 取间隔的六倍，是为了让连续六次发布失败才让一个实例从视图里消失：一次 GC 停顿或一次重启不该让实例数抖一下。启动时就校验 `TTL > 间隔 > 0`，因为 TTL 小于等于间隔时，一个活着的实例也会在两次发布之间过期，症状是看板上的实例数来回跳，而没有任何东西指向这个配置项。

## 覆盖范围

`campus_glimmer/test_metrics_fleet.py` 共 30 项，分六组：

- **共享开关与发布节奏（5 项）**：LocMem 默认关、跨进程缓存默认开、显式设置覆盖后端猜测、拼错的开关值和倒挂的 TTL/间隔都必须让启动失败。
- **快照形状（3 项）**：字段齐全、可 JSON 往返、实例标识稳定且能区分同一容器内的多个 worker。
- **合并语义（7 项）**：计数器与直方图相加、在途求和、溢出取并、启动取最早、构建信息去重、分桶不符时只跳直方图。
- **共享存储（6 项）**：发布读回往返、排除自身、鬼条目自清理、坏快照降级、读失败降级并计数、TTL 下限兜底。
- **发布线程（4 项）**：单次发布可读回、能按需停止、存储故障带不走线程、日志只在状态翻转时记。
- **暴露面（5 项）**：五个新序列齐全且 TYPE 行唯一、两副本端到端合并、抓取不计入自身、未配令牌仍 404、关共享时报单实例。

新增的五个序列：`campus_glimmer_metrics_shared_enabled`、`campus_glimmer_metrics_instances`、`campus_glimmer_metrics_view_age_seconds`、`campus_glimmer_metrics_bucket_mismatch`、`campus_glimmer_metrics_shared_read_errors_total`。既有序列名与标签完全不变，现有看板和告警规则不需要跟着改。

`process_start_time_seconds` 的语义在这一轮扩展了：共享开启时它是"视图内最早启动的实例"的启动时间，不是本进程的。这是唯一一处既有序列的语义变化，`node_time_seconds - process_start_time_seconds` 这类表达式算出来的会是舰队里最长寿的那个实例的存活时长。

## 边界

这一轮**没有**做的部分，需要如实说明：

- **按指标告警不在范围内。** 聚合只是把数字凑齐了，"哪个指标超过什么阈值该通知谁"仍然是空的，仍然写在外层监控系统里。路线图里那条待办只结掉一半。
- 共享存储是尽力而为的名单，不是强一致的服务注册表。两个副本同时发布可能互相覆盖一次名单写入，后果是某个实例晚一个周期才出现在视图里。
- 不覆盖跨主机的指标保留与可视化。本机制只负责"一次抓取拿到整个服务此刻的样子"，长期存储、降采样、看板仍然在外层。
- 没有压测。五秒间隔、几十字节量级的设计没有实测过多副本下的写入放大；生产副本数上去之后应该实际看一眼缓存 QPS。
- 没有覆盖共享存储被写进脏数据之后的自愈。读失败会计数并降级，但不会尝试修复或告警到人。

## 运维上必须知道的一件事

启用共享之后，**只能把一个抓取目标指向 `/metrics/`**。每个副本返回的都是同一份合并视图，配两个抓取目标会把总量按副本数翻倍——而且翻倍出来的数字看起来完全正常，没有任何东西会提示你重复抓了。这是这套设计对部署方式提出的唯一要求，也是它最容易用错的地方。
