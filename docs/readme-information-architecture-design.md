# README 信息架构与阅读路径设计

## 背景

README 已经承担了四个角色：项目首页、功能手册、工程结构说明和运营口径档案。随着功能持续增加，单页长度超过 5000 行。虽然功能模块内部已有折叠块，但目录、章节和文档清单仍然把所有信息平铺在首页，新读者第一眼看到的是密集文本，而不是可以按需进入的阅读路径。

本次调整不是重写项目介绍，也不是弱化长期迭代积累，而是把已有内容按读者任务分层，让 README 回到“短首页 + 深文档”的正常长期项目结构。

## 目标

1. README 首页保留项目定位、核心能力、快速开始、测试、部署和当前概览。
2. 为不同读者提供明确路径：第一次了解、本地运行、看功能、看代码、看运营数据、看规划。
3. 将长篇内容拆分为可独立维护的文档：
   - `docs/feature-handbook.md`：八条业务链路的完整功能说明。
   - `docs/module-map.md`：项目结构、业务模块、测试模块和设计文档索引。
   - `docs/product-boundaries.md`：当前取舍、边界和实现纪律。
   - `docs/roadmap.md`：后续路线图和拆分方向。
4. 保留原有细节，不在拆分过程中删除长期积累的口径。
5. 首页所有深链接指向正确文档；被移动章节内部的架构图链接按新文档位置修正。
6. 文档语言保持中文，叙述口径保持“持续迭代”，避免表达成临时重做或一次性改造。

## 非目标

- 不改业务代码、数据模型和页面行为。
- 不删除历史设计说明、指标口径或测试说明。
- 不把 README 简化成营销页；工程细节仍必须可追溯。
- 不引入新的文档生成工具，继续使用 GitHub 可直接渲染的 Markdown。
- 不修改本地数据库、上传文件或运行数据。

## 阅读路径设计

### 第一次了解

首页按顺序提供：项目定位、系统概览、功能速览、典型业务流程和当前概览。读者不需要进入 3000 行功能手册即可判断项目是否与自己的场景相关。

### 想运行项目

首页保留依赖、虚拟环境、初始化、开发服务器、Docker 和配置说明，并在本地运行前后补充测试与部署注意事项。

### 想看完整功能

首页提供八个模块的短摘要表，并链接到 `docs/feature-handbook.md` 对应章节。详细折叠块、业务规则和边缘情况在手册中维护。

### 想看代码结构

首页保留一级目录概览，模块、测试和设计文档索引链接到 `docs/module-map.md`。后续新增文件时只需更新索引文档，不需要拉长 README。

### 想看运营口径

功能手册中的运营看板章节保留完整指标解释。首页只保留“数据闭环”的摘要和进入链接，避免首页被大量口径细节淹没。

### 想看边界和规划

首页提供当前边界的短摘要，详细取舍链接到 `docs/product-boundaries.md`；路线图只保留分组概览，详细方向链接到 `docs/roadmap.md`。

## README 目标结构

1. 标题、徽章、一句话定位。
2. 阅读指南：按读者任务给出入口。
3. 项目定位。
4. 系统概览与技术栈。
5. 功能速览与八个模块的摘要地图。
6. 典型业务流程。
7. 运营数据闭环摘要。
8. 核心数据模型概览。
9. 权限与安全边界。
10. 本地运行、配置、Docker。
11. 后台与定时任务。
12. 测试与持续集成。
13. 当前取舍摘要。
14. 路线图摘要。
15. 参与开发、License 和链路图。

## 内容迁移规则

- 原文整段迁移，不在迁移时顺手改业务描述。
- 被迁移章节如果引用 `docs/architecture.svg`、`docs/end-to-end.svg` 等相对路径，迁入 `docs/` 后改为同目录文件名。
- README 中不再直接指向旧锚点，而是指向新文档锚点或文档开头。
- 每个新文档开头补充一句维护说明，说明它来自 README 的长期资料拆分，用于避免后续重复堆叠。
- 手册章节编号保持 1-8，方便历史讨论继续对齐。

## 验收标准

1. README 首页显著缩短，第一屏能读到定位和阅读指南。
2. 八个功能模块、结构清单、详细边界和详细路线图仍可从首页两次点击内到达。
3. 不出现孤儿章节：被移动的每个一级章节在新文档中都有对应标题。
4. Markdown 内链目标存在，图片路径可解析。
5. `git diff --check` 通过。
6. 文档提交与实现提交分离，便于回溯本次拆分。
