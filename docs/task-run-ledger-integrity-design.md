# 定时任务台账完整性审计设计

## 为什么这轮先做需求

`TaskRun` 已经撑起一组调度面板：健康度看它算成功率和连续失败，耗时面板看它算分位，小时负载看它算拥塞，失败原因看它读备注，自我重叠看它用开始时间与耗时拼出真实重叠。可是这组面板都有同一个前提——**台账行本身是可信的**。此前没有任何面板先回答这个问题。

正常写入路径确实比较稳：`record_task_run` 用单调时钟算耗时、只写成功 / 失败两种状态、失败备注来自异常文本、成功指标经过 `normalise_metrics` 过滤。但这个模型也在 Django admin 里可编辑；将来还可能有回填脚本、迁移辅助命令或人工排障写入。数据库层并不会完整执行 Django 的表单校验，`CharField` 里可以出现未知状态，JSON 指标里可以出现嵌套对象、布尔值或负数。调度统计一旦吃进这些行，问题会被包装成“成功率下降”或“耗时变长”，而真正该看到的是“这一行台账不可读”。

所以这一轮不新增调度能力，而是给台账补一层**读数前的完整性审计**：先告诉运营这批行的形状能不能支撑后面的结论。

## 要回答的问题

- 周期内的台账行里，有多少行时间戳自洽？
- 成功且非 dry-run 的行，有多少行带有可比的标量指标？
- 失败行是否留下可供失败原因分类的备注？
- 有没有未知命令名、未知状态或明显不可能的耗时？
- 问题行集中在哪些命令、哪些问题类型？

## 统计口径

### 1. 窗口与归期

审计周期默认 30 天，非法或小于 1 的天数回落到 30。窗口按本地午夜切开，从周期起点到调用时的 `now`，与其他运营面板保持同一套日期边界。`now` 可以注入，测试能钉住时间。

一行只按 `started_at` 归入周期。跨过周期边界的运行留给开始它的那个周期；这不影响本模块，因为审计的是行自身，不比较周期。

### 2. 时间完整性

一行出现以下情况计入问题：

- `started_at` 或 `finished_at` 在 `now` 之后，并留出 60 秒时钟余量；
- `finished_at` 早于 `started_at`；
- `duration_ms` 小于 0。

`duration_ms` 与两个时间戳差值的一致性只审**严重不一致**：差异超过 `max(2000ms, 时间戳间隔的 10%)` 才计入。原因写在设计里，也要写进面板：`duration_ms` 来自单调时钟，时间戳来自墙钟，两套钟本来就不保证同速；NTP 校时、宿主机暂停、容器恢复都会让它们出现小差异。把毫秒级差异当脏数据，会把正常行误报成坏行。

### 3. 状态与失败证据

状态只允许 `succeeded` / `failed`。其他值说明这行不是当前写入路径写出来的，进入问题行。

`failed` 行必须有备注。失败原因分类已经把备注当作输入，空备注的失败行不是“更干净的失败”，而是让下游只能归到未归类，本身需要被看见。`succeeded` 行的备注不要求为空：将来写入路径可能写正常说明，不能把合法扩展提前判成错误。

`dry-run` 由备注精确等于 `dry-run` 判断，与既有健康度口径一致。dry-run 是有效台账行，单独计数；但它没有发送东西，不参与“成功行是否带指标”的要求。

### 4. 指标形状

指标形状与 `task_runs.normalise_metrics` 同一套契约：

- 只接受 `sent`、`skipped`、`failed`、`marked`、`expired`、`reminded`；
- 值必须是数字标量；
- 布尔值不算数字；
- 负数不算次数；
- 嵌套对象、列表、字符串都算形状问题。

一条成功且非 dry-run 的行至少要有一个合法指标键，才算“指标可读”。失败行不要求指标：异常可能发生在返回结果之前，这正是不该伪造结果的地方。dry-run 也不要求指标：它本来就不承诺发送。

未知指标键单独计数，但不让整行进入问题清单；这相当于 `normalise_metrics` 的过滤行为——新命令先带一个新键时，应该提醒维护者扩展字段清单，而不是把已经可读的其他指标一并判坏。

### 5. 命令名

已知命令复用调度健康面板的名单。未知命令单独列出，不计为问题行：名单是当前调度契约，不是数据库约束；一个新命令接入时会先出现在台账里，正确动作是补充名单，而不是把它的历史行全部标成脏数据。

## 输出形状

模块返回四层：

1. **摘要**：总行数、成功 / 失败 / dry-run、已知 / 未知命令、问题行数、干净行数、问题行占比、成功且非 dry-run 行的指标可读占比。没有台账行时占比为 `None`，不是 0%。
2. **问题类型表**：每类问题的行数和涉及命令数，固定顺序，方便页面与 CSV 对齐。
3. **命令表**：每个命令的运行数、问题数、时间问题数、指标问题数、失败备注问题数、未知键数、未知命令标记。
4. **问题行清单**：行 ID、命令、开始时间、问题标签，最多 12 条，隐藏数单独给出。清单按问题数和开始时间排序，只输出结构化字段，**不输出原始备注**。

## 边界

- 只报告，不修复台账、不回填指标、不删除未知命令、不改 `record_task_run`。
- 不判断调度是否完整，那属于健康度面板的职责。
- 不读 crontab，也不从耗时反推调度配置。
- 不输出失败备注原文；备注可能带异常参数、路径或外部系统信息，页面只说“缺备注”或“形状异常”。
- 不按用户、机器或调度器聚合；台账里本来就没有这些字段，不能编造责任方。
- 不把未知命令、未知指标键或 dry-run 自动等同于错误。

## 验收

- 空台账返回固定结构，比例字段为空；
- 正常成功、失败、dry-run 行不误报；
- 结束早于开始、未来时间、负耗时、严重耗时不一致各自可被识别；
- 未知状态、空备注失败、布尔 / 负数 / 嵌套指标可被识别；
- 未知命令与未知指标键只单列，不进入问题行；
- 指标可读率的分母只包含成功且非 dry-run 的行；
- 问题清单截断不影响汇总，隐藏数可见；
- 构建过程只读；
- 运营看板页面与 CSV 导出同名呈现，并带同样的口径说明。
