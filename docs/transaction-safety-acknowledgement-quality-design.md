# 交易安全卡确认质量运营面板设计

## 起点

交易安全卡已经接入买卖双方确认：每个角色对「订单 + 安全卡指纹」只落一条 `OrderSafetyAcknowledgement`，关键提醒变化后需要重新确认，历史记录保留用于审计。

这条链路的读取路径目前只有两处：

- 订单详情页给交易双方看当前版本是否确认；
- Django 后台给管理员翻原始记录。

运营侧仍然答不了四个问题：

1. 本期还在可确认阶段的订单里，买家、卖家、双方各自确认到什么程度；
2. 从下单到确认通常隔多久，双方补齐是否明显更慢；
3. 有多少订单真的发生过「确认过后信号变化、需要重新确认」；
4. 哪些还挂着的订单缺哪一侧确认，挂了多久。

也就是说，确认数据已经能审计单笔订单，但还不能观察整条交易链路的确认质量。

## 目标

新增一个只读运营面板和 CSV 导出，用同一套产品侧安全卡计算逻辑回答上述问题。它只报告，不改订单、不改确认记录、不发提醒、不生成告警。

## 需求口径

### 1. 观察窗口与分母

主分母按订单创建时间切窗口，只收：

- 创建时间在统计周期内；
- 当前状态仍为 `pending`、`confirmed` 或 `meeting` 的订单。

这三个状态与安全卡确认入口一致。已完成、已取消、借用中或已归还的订单不能补确认，把它们放进当前覆盖率分母会把「流程已经不允许动作」读成「用户没做动作」。

周期外的长期挂单不在覆盖率分母里，但待确认清单可以跨周期展示，因为它回答的是「现在该看哪几单」，不是「本期新订单表现如何」。

### 2. 当前版本必须在服务端重算

面板不能信任页面曾经显示过的历史指纹，必须对每笔订单：

1. 调用产品侧 `build_transaction_safety(order)`；
2. 用同一个 `transaction_safety_fingerprint(summary)` 得到当前指纹；
3. 只把匹配当前指纹的确认记录视为当前确认。

这样交付地点、商品图片、预约状态等关键信号变化后，旧确认只进入版本历史，不会冒充当前确认。

### 3. 覆盖率按角色拆开

对主分母报告：

- 双方都已确认；
- 仅买家确认；
- 仅卖家确认；
- 双方未确认；
- 买家确认率、卖家确认率、双方确认率。

零样本平台也保留分母和四档状态，不给编造的方向。

### 4. 确认时延只统计已完成的链路

从订单创建时间计算：

- 第一位确认出现的时间；
- 买家和卖家都确认当前版本的时间。

仍缺任一侧确认的订单是右删失样本，只计入未完成规模，不进入中位数和分档。

分档使用固定边界：1 小时内、1-6 小时、当天、隔天到 3 天、3 天以上。小时级以下不再细拆，因为安全卡核对发生在用户打开订单的自然节奏里，分钟级抖动没有运营含义。

### 5. 版本变化只报可观察下界

历史确认表只知道「哪些指纹曾被确认过」，不知道每一个安全卡版本第一次出现的时刻，也没有保存每次信号变化事件。因此：

- 可以统计一笔订单曾被确认过的指纹数量；
- 可以识别当前版本之前最近一次确认过的指纹；
- 不能统计「安全卡一共变化过几次」；
- 不能计算每个历史版本的完整确认率。

所有版本变化指标都标为观察下界，不用推测值补齐。

### 6. 待确认清单服务当下动作

清单只收仍处于可确认状态的订单，按以下顺序排序：

1. 缺两侧确认优先于缺一侧；
2. 创建时间更早者优先。

每行只展示订单号、商品、状态、缺少的角色和订单年龄，不展示用户名，不按用户汇总，不生成负责人。清单最多展示 20 条，但总数照实报告。

### 7. 只读与隐私边界

本面板：

- 不写 `OrderSafetyAcknowledgement`；
- 不改订单状态或商品状态；
- 不发送站内通知，不把确认变成催办；
- 不生成运营告警；
- 不记录或读取 IP、User-Agent、设备信息；
- 不按用户统计、不排名、不输出用户名；
- 不把确认率与订单结局做因果判断。

确认只表示用户核对过当前安全提醒，不等于平台担保，也不等于线下交付一定会顺利完成。

## 验收

- 空数据时面板可渲染，分母为 0，不显示编造比例；
- 买家、卖家、双方确认的当前覆盖率按角色拆开；
- 安全卡指纹变化后，旧确认不再计入当前覆盖率；
- 仍在可确认状态的订单会进入待确认清单，已完结订单不进入；
- 确认时延只统计双方已确认的完整链路，缺一侧的只报规模；
- 历史版本数量按确认过的指纹数报告，并明确是观察下界；
- 清单不输出用户名，截断时保留总数；
- 管理员可访问面板和 CSV，普通用户无权访问；
- 迁移检查与相关测试通过。
