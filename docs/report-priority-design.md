# 商品举报优先级设计

## 要解决的问题

商品举报队列已经能按状态和时间展示待处理事项，治理工作台也能按各队列的处理时限提醒超期风险。但不同举报本身的危害并不相同：一条仍在售商品上的疑似诈骗举报，和一条已经下架商品上的重复广告举报，不应该只因为提交时间更晚就排在后面。

这个设计补的是一个可解释的只读优先级口径：它不替管理员下结论，也不自动处理举报，只把“为什么这一条应该先看”写清楚，并在举报队列和治理工作台里呈现。

## 事实来源

- 只读 `Report.reason`、`Report.status`、`Report.created_at`、`Item.status` 和 `Item.expires_at`。
- 不新增表、不新增字段、不回填历史。
- 优先级在请求时计算，代表“此刻队列里的处理建议”；同一历史举报在商品状态变化后重新进入队列时，优先级可以变化，这正是因为风险仍在暴露，而不是历史事实被改写。
- 未知举报原因按普通优先级处理并显示原值，不让脏数据把队列弄崩。

## 优先级口径

优先级只有三档，避免把人工判断做成伪精确分数。

1. **优先处理**：疑似诈骗举报，且被举报商品此刻仍处于在售且未过期状态。诈骗类举报同时威胁交易资金和平台信任，商品仍可见意味着风险还在继续曝光。
2. **较高关注**：满足以下任一条件：
   - 疑似诈骗举报，但商品已经不在售或已经过期；
   - 不当内容举报，且商品仍在售且未过期；
   - 同一件商品当前有至少两条待审核 / 审核中的举报。`Report` 已有同商品同举报人的唯一约束，因此这个数字代表不同举报人的交叉信号，只报人数，不展示举报人。
3. **常规处理**：重复发布或广告引流、其他问题，以及没有命中上述风险的未知原因。

多条信号同时命中时取最高档，不累加分数。优先级标签旁边列出命中的信号，例如“疑似诈骗”“商品仍在售”“多人举报同一商品”，让管理员能复核规则本身。

## 排序与展示

- 举报队列默认先按状态组排序：待审核 / 审核中在前，已处理 / 已驳回在后。
- 同一状态组内按优先级、提交时间排序：优先处理、较高关注、常规处理；同档新提交的在前。
- 状态筛选不改变优先级规则；已结束举报可以保留标签，但排序始终在后，避免历史事项挤占当前队列。
- 治理工作台继续以“是否超期”和等待时长作为跨队列主排序，不让举报原因挤掉交付预约异常这类更短时限的队列。举报行只展示优先级标签和信号，用于同队列内的辅助判断。
- 队列页显示当前优先级分布：优先处理、较高关注、常规处理各多少条，只统计待审核 / 审核中事项。

## 只读与隐私边界

- 不自动确认举报、不自动下架商品、不通知卖家、不给举报人或卖家打标签。
- “多人举报同一商品”只输出数量，不输出用户名，也不生成反复被举报商品榜。
- 不读取举报补充说明来判断真假；说明文本仍只给管理员人工审核。
- 不把优先级写入数据库，不进入运营日报的自动处置建议。
- 优先级不是违规结论，页面文案必须保留“建议先看”的语义。

## 输出形态

- 举报队列：优先级分布卡、每条举报的优先级标签和命中的信号说明。
- 治理工作台：商品举报行增加同一个优先级标签，跨队列排序规则保持不变。
- 详情页：显示该举报当前的优先级和信号，方便复核时理解它为什么被排前。

## 非目标

- 不做机器学习风险评分，不引入黑盒分。
- 不按举报人信誉加权，不惩罚第一次举报的同学。
- 不改变治理工作台现有 SLA：商品举报仍是两天，交付预约异常仍按更短时限处理。
- 不处理敏感词分级和申诉，它们是后续独立迭代。
