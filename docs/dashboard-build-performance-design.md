# 运营看板自身构建耗时的观测口径

状态：设计稿（请求内观测，不新增表和字段）
计划模块：`listings/dashboard_build_performance.py`
计划接入：`listings/views.py`、运营看板页面与 CSV 导出
计划面板：运营看板「看板自身构建耗时」

## 1. 要回答的问题

运营看板已经从一份核心统计扩成几十个独立面板。页面和 CSV 导出各自维护了一份几乎相同的构建器列表，带来三个实际问题：

1. 同一个面板在页面里被写两次时，现有代码不会报错，只会重复查询并覆盖前一次结果；
2. 页面与导出如果有一处漏改，测试需要逐个面板才能发现；
3. 看板慢的时候，运营只能感知整页慢，不知道时间花在哪一组构建器上。

本迭代只回答一个工程问题：**这一次请求里，运营看板的共享构建器各自花了多少时间，形状是否正常。** 它不评价任何业务指标，也不替代业务面板。

## 2. 需求与验收

### R1 共享构建器只组装一次

页面视图和 CSV 导出必须调用同一个共享组装函数。该函数负责：

- 构建运营看板核心统计；
- 按同一份固定面板注册表构建所有共享面板；
- 返回带性能报告的同一个 `dashboard` 字典。

页面特有的待办计数、需求跟进任务和状态筛选，以及 CSV 特有的序列化，不属于共享组装范围，也不伪装进同一份数字。

验收：`operations_dashboard` 与 `operations_dashboard_export` 不再各自手写共享面板列表；页面中同一个共享构建器不会被调用两次。

### R2 计时是请求内的，不落库

每次请求用 `time.perf_counter()` 记录：

- 核心看板构建；
- 每个共享面板构建器。

计时结果只放在当前请求上下文里，请求结束即丢弃。不写 `TaskRun`，不写新表，不写日志，不做跨请求平均。

验收：新增模块不产生迁移；同一请求能看到每个构建器的毫秒级耗时；重复请求不会累积历史。

### R3 输出总数、分位与排序，不输出查询数

报告固定输出：

- 共享构建器数量；
- 计入的构建耗时总数；
- P50、P90（最近秩，不插值）；
- 最慢构建器；
- 每个构建器的耗时、占比与累计占比；
- 重复 key 数量。

不输出 SQL 查询数。项目运行时未强制开启 Django `DEBUG`，拿不到可靠的连接查询数；为了面板好看而临时打开 `DEBUG`，会改变被观测系统的行为。

验收：P50/P90 与输入排序无关；样本不足的分位保持 `None`；累计占比按耗时从慢到快计算。

### R4 一次、零次和重复都要可读

- 一个构建器：P50 和 P90 都取这一条，不编造第二个样本；
- 零个构建器：报告空态，不把总耗时报成 0 毫秒的业务结论；
- 重复 key：单列数量，不在报告里自动覆盖或静默合并。

验收：零样本、单样本、多样本和重复 key 均有单元测试。

### R5 页面与 CSV 使用同一口径

页面显示「看板自身构建耗时」，CSV 导出必须有同名节和同构表头。两者都只显示构建器标签、耗时和占比，不输出用户、请求头、IP、SQL 或异常堆栈。

验收：staff 访问页面和 CSV 均为 200；两个出口的标题和关键表头一致。

### R6 只观测，不自动优化

慢不等于错：首次请求可能有连接池预热，测试库与生产库的数据量不同，导出序列化也不在本报告范围内。因此报告不自动：

- 缓存面板结果；
- 合并或删除面板；
- 调整数据库索引；
- 给构建器标成「有问题」。

验收：本迭代不改任何业务查询，不新增缓存，不改变面板结果。

## 3. 输出形状

```python
{
    "has_data": True,
    "summary": "...",
    "metrics": {
        "builder_total": 48,
        "total_elapsed_ms": 123.4,
        "p50_ms": ...,
        "p90_ms": ...,
        "slowest_key": "...",
        "slowest_label": "...",
        "duplicate_key_total": 0,
    },
    "rows": [...],
    "note": "...",
}
```

`rows` 按耗时降序排列，字段固定为：

- `key`：构建器结果在 dashboard 里的键；
- `label`：给人看的面板名；
- `elapsed_ms`：本次耗时；
- `share_percent`：占计入耗时的比例；
- `cumulative_percent`：从最慢开始的累计占比；
- `is_slowest`：是否最慢。

## 4. 边界与隐私

- 观测范围只包含共享组装，不包含页面渲染、CSV 序列化、浏览器下载和中间件；
- 请求参数筛选后的需求跟进结果不进入共享计时，避免页面和 CSV 看到不同口径；
- 标签使用固定中文面板名，不拼接请求路径、用户输入或异常文本；
- 面板仅管理员可见；
- 不采集用户身份，不把某个管理员的访问速度公开成个人效率指标。

## 5. 为什么先做请求内观测

跨请求平均需要持久化存储和统一时钟，容易把开发环境、CI 空库和生产流量混在一起；APM 依赖部署形态，也会把一个教学项目的运行复杂度抬高一档。请求内耗时已经足以回答「这一次到底慢在共享构建的哪一段」，也能先守住页面与导出共享同一组装路径的工程契约。

等这组形状被看懂后，再决定是否需要持久化采样或更细的 SQL 级观测；在那之前不做。
