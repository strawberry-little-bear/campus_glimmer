# 同一个标题，屏幕和下载件不能是两句话

## 起点

`test_dashboard_export_columns` 有三个存量失败，全指向同一处：

```
('通知偏好开关：25 个开关各自的形状', '0 个开关逐个看', [...], 'no header row at all')
```

`test_every_panel_table_has_a_recognisable_header_in_the_export`、
`test_every_panel_subheading_stays_inside_its_section`、
`test_the_same_holds_once_the_panels_have_rows` 三条，说的是同一个事实的三个侧面。

## 事实

模板 `operations_dashboard.html:1082`：

```django
<h3 class="h6 mb-3 mt-2">{{ notification_preference_usage.rows|length }} 个开关逐个看</h3>
```

导出 `views.py:3479`：

```python
writer.writerow(['25 个开关逐个看', '分组', '开着', '关掉', ...])
```

**面板的标题是算出来的，导出的标题是写死的。** 空平台（一条偏好行都没有）时
`rows` 是空列表，`|length` 给 0，面板渲染成「0 个开关逐个看」；导出那边照样写
「25 个开关逐个看」。

于是同一个对象，在屏幕和下载件里是两个名字。测试要的是「导出的每一张表都认得出
自己的表头」，它拿面板的子标题去导出里找，找不到——这就是失败。

## 为什么这是一个真问题，不是测试太严

三种读法都会撞上它：

1. **运营对照着屏幕和 Excel 看**。屏幕上这一节叫「0 个开关逐个看」，下载回去叫
   「25 个开关逐个看」，第一反应是「这两份数据是不是不同步的」。看板的所有口径
   都建立在「屏幕和下载是同一份数据」这个默认上，一个标题不一致就够把这个默认
   打掉。
2. **空平台是常态，不是边角**。一个新部署、或者刚清过测试数据的站点，打开看板就是
   空态。空态下最容易发现「这两个名字不一样」，而空态恰恰是运营第一次认识这个
   面板的时候。
3. **硬编码的 25 会走散**。模块自己的文档字符串第一节就写着「开关名单从模型元数据
   现读，不硬编码——硬编码的名单会和代码走散，而那正是 `notification_kind_coverage`
   要报的问题」。现在导出的标题硬编码 25，等于在一个「反对硬编码」的模块里留下了
   一个硬编码。哪天 `NotificationPreference` 加一个开关，面板标题会自己变成 26，
   导出还写 25——而那正是本模块存在的意义所要报的那类偏差。

## 修法：让两边问同一个问题

修的方向只有一条——**导出的标题必须和面板的 `<h3>` 是同一个字符串**。至于这个字符串
由哪个数生成，第一版选错了，下面记下选错的原因和最后的选法。

## 先走错的一步，以及为什么走错

第一版修法是把导出改成 `f"{usage['field_total']} 个开关逐个看"`，理由是「模块自己
说开关名单从模型元数据现读，导出不该写字面量」。跑测试，三个失败一个都没少。

原因在于**这两个数本来就不是一个数**：

- `usage['field_total']` 是 `len(fields)`，模型上有多少个布尔开关，恒为 25；
- 模板的 `rows|length` 是 `len(usage['rows'])`，**当前有几行可以逐个看**，空平台是 0。

面板标题问的是「这一节现在有几行可看」，导出用 `field_total` 问的是「这个面板一共
讲多少个开关」。把导出从写死的 25 换成算出来的 25，两边照样对不上——数字的来源
变了，语义没变。这是本轮真正学到的：**对齐两个字符串之前，先确认它们问的是同一个
问题。**

## 真正的修法

让导出跟着 `rows` 走，和模板的 `rows|length` 同一个数：

1. `views.py` 的导出里，`'25 个开关逐个看'` 改成 `f"{len(usage['rows'])} 个开关逐个看"`；
2. 节标题 `'通知偏好开关：25 个开关各自的形状'` 改成 `f"通知偏好开关：{usage['field_total']} 个开关各自的形状"`——它也是写死的，同一个问题。这一处**保留
   `field_total`**：模板 `operations_dashboard.html:1052` 的 `<h2>` 本来就写死 25，
   而节标题讲的是「这个面板讲多少个开关」，`field_total` 正是这个意思，两边天然一致；
3. 冒烟测试补一条：空平台时，面板的 `<h3>` 文本必须出现在导出里。之前空平台那条只
   断言了空态文案存在，没有断言两边标题对齐，所以这个偏差一直没被抓住。

第 3 条是这一轮真正的产出。测试已经把这个 bug 抓出来过三次（三个失败指向同一处），
但**没有任何一条测试能单独证明它被修好了**——`test_dashboard_export_columns` 是拿
面板反查导出，方向对，但它是通用比对，报错信息里看不出「这是空态特有的」。补的这条
直接从空态那一侧盯标题对齐，回归时第一个炸的就是它。

验证方式是反向的：把导出临时改回写死的 `25`，确认新断言失败（`'0 个开关逐个看'
not found in ...`），再改回 `len(usage['rows'])`。确认过这条线是真的，不是碰巧绿的。

## 不做什么

- **不改这个模块的任何口径**。25 个开关、四格、四组、`min_preference_rows` 门槛，
  全部不动。这一轮只修「同一个标题在两个地方是两句话」。
- **不改模板**。模板用 `rows|length` 是对的——它报的是「当前有几行可看」，空平台给 0
  是事实。要改的是导出，不是面板。
- **不把节标题也改成 `len(rows)`**。节标题讲的是「这个面板讲多少个开关」，`field_total`
   正是这个意思，模板的 `<h2>` 也写死 25，两边天然一致。子标题讲的是「现在有几行可看」，
   才跟着 `rows` 走。同一个面板里两个标题问两个问题，各自的算法要跟各自的问题对齐。
- **不为了迁就测试去放宽断言**。测试的 docstring 写着「这里只做比对，不改写看板、
   不改写导出，也不为了让某个列名对上而调整任何一边的文案」——但那一句针对的是
   「列名不同」（面板窄卡片用短名、导出用全名，本来就该不同）。标题不一致不是
   列名不同，是同一个字符串在两处不一致，属于要修的那类。
