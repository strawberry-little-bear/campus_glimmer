# 备份脚本边界设计

<p align="right"><a href="../README.md">返回项目主页</a> · <a href="README.md">完整手册</a></p>

## 为什么先做需求

`docker/backup.py` 是生产恢复的唯一入口，却是仓库里少数没有测试的模块。它的分支一年可能只执行一次，而"备份能创建"和"备份能恢复"之间隔着五类边界：校验、路径、版本、保留期、异地镜像。这些边界一旦悄悄退化，症状不是测试变红，而是某次事故里恢复失败——那时候已经没有时间修 bug 了。

已经踩过的两个真实例子说明这不是假想：

- 镜像里是 PostgreSQL 17 客户端、生产库是 16，dump 能生成、清单校验也通过，但目标库拒绝恢复。现在的版本护栏就是那次事故的产物。
- 备份脚本的 manifest 路径如果允许 `../`，一个被篡改或写错的清单就能让校验读到备份目录之外的文件。

路线图里另一条长期挂着的缺口是「数据库 dump 的隔离恢复没有进 CI」。这一轮先把脚本自身的边界钉住，恢复演练仍然按[备份与恢复](backup-restore.md)的口径人工执行——当时挡路的理由是 CI runner 自带的 PostgreSQL 客户端主版本与生产不一致，硬塞一个 16 客户端进去只会把任务变成版本管理任务。

这条理由后来不再成立：runner 的客户端版本可以由 apt 包名钉死。于是有了独立的 `backup-restore` CI 任务——装 PostgreSQL 16 客户端、真实 dump、灌进隔离库逐表比对，并用一个假 17 客户端验证版本护栏真的会拦，见[备份与恢复](backup-restore.md)的「CI 恢复演练」。

## 目标

- 备份脚本的每条失败分支都有用例，且不需要 PostgreSQL、MinIO 或网络。
- 校验失败必须一次性说完全部问题，而不是修一个再撞下一个。
- 异地镜像必须是"读回比对过"的副本：上传返回 200 不等于备份成功，字节不符或 key 缺项都必须让这次备份失败。
- 失败路径必须留下干净的工作区：staging 目录被清空，不出现"看起来可用"的半成品。
- 保留期清理必须对单个坏 manifest 免疫：一份读不懂的清单不该让其它过期备份永远留着。

## 覆盖范围

`campus_glimmer/test_backup_script.py` 共 52 项，分十三组：

- **URL 解析（2 项）**：非 PostgreSQL scheme、缺主机、缺库名显式失败；省略端口时落到 5432。
- **校验和（1 项）**：`sha256_file` 跨 1 MiB 分块边界仍与 `hashlib` 一致。
- **清单路径（2 项）**：`../`、绝对路径、空路径和穿越目录都被拒绝；目录内的相对路径可以解析。
- **备份校验（7 项）**：一致归档通过；大小不符、SHA-256 不符、清单版本不受支持、清单不可读、路径越权、对象数量不符分别报错；多个问题用 `；` 汇总成一条。
- **保留期（5 项）**：保留天数小于 1 不动手；目录不存在不报错；只删过期的 `backup-` 目录，普通目录和同名文件不受影响；naive 时间戳按 UTC 解释；坏 manifest 跳过且不阻塞其他清理。
- **对象前缀（1 项）**：`object_listing_prefix` 把空串、`/`、`media`、`media/`、`/media/` 统一收敛成目录作用域，列对象时不会把整个桶当成一个扁平命名空间。
- **版本护栏（4 项）**：客户端与服务端主版本解析成功、解析失败分别的返回与报错；`psql` 命令行里不出现密码。
- **dump 命令（1 项）**：`pg_dump` 的命令行里不出现密码，密码只经 `PGPASSWORD` 环境变量传递，`sslmode` 透到 `PGSSLMODE`。
- **创建与运行（7 项）**：缺 URL 或缺 bucket 直接失败；成功时生成 `backup-<时间戳>` 且 manifest 不写密码；时间戳撞车时追加随机后缀；dump 或下载失败时 staging 被清空；`run_once` 按环境变量调用创建与清理，缺省值符合文档。
- **异地配置（7 项）**：未配置返回 `None`；只填其中几项（有其它变量但没有端点、缺 bucket、缺任一凭证、保留期不是整数）必须报错，不静默跳过；保留期缺省时沿用 `BACKUP_RETENTION_DAYS`。
- **异地镜像（6 项）**：镜像前先跑本地 `verify_backup`；上传后按 manifest 的 SHA-256 读回逐字节比对，截断或篡改都会被发现；远端 key 集合缺项、多项都要失败；镜像不包含 `manifest.json` 同样失败。
- **异地保留期（6 项）**：保留天数小于 1 不动手；只删各自 `manifest.json` 里读到的创建时间已过期的归档；缺 manifest、manifest 读不动、时间不可解析都跳过不删；未过期的归档一个不碰。
- **失败传播（3 项）**：镜像失败时 `run_once` 必须向上抛，不让本地备份成功伪装成整次任务成功；未配置异地时 `--mirror` / `--prune-offsite` 直接以非零码退出。

## 为什么用 mock 而不是起真服务

`_dump_database`、`_download_objects` 和 S3 客户端在测试里被替换，因此这 52 项在任何机器上都是毫秒级，也不需要 Docker Hub。mock 的位置选在"脚本与外部世界的接缝"上：被替换的是子进程和客户端，被测的是脚本对它们下达的指令和对结果的处理。真正不能 mock 的是恢复语义——dump 灌回 PostgreSQL、对象按原 key 写回桶里——那部分由 `object-storage` 任务和人工演练负责。

## 顺带修掉的问题

`prune_backups` 原来只捕获 `OSError/ValueError/KeyError`。manifest 里 `created_at` 写成了数字时，`datetime.fromisoformat` 抛的是 `TypeError`，会中断整个清理循环，导致保留期形同虚设。现在坏 manifest 一律跳过，并有用例钉住。

## 边界

这一轮**没有**覆盖的部分，需要如实说明：

- **没有验证 dump 能被 `pg_restore` 读回。** 脚本不再生成不可恢复的归档（版本护栏）；「能读回」由 `backup-restore` CI 任务对一次性数据库验证，正式环境的恢复演练仍要按文档人工执行。
- **没有覆盖真实 S3 的分页、截断与 multipart。** `_download_objects` 只按 paginator 返回的对象逐一下载。
- **没有覆盖守护进程模式的循环与失败重试。** `main()` 的 while 循环不进入测试，只测它调用的 `run_once`。
- **没有覆盖真实异地端点的网络分区、跨账号密钥轮换与加密。** 异地镜像的上传、读回比对与保留期由内存里的 `FakeOffsiteClient` 钉住，换不成对第二个真实端点、断点续传和密钥轮换的单测；备份目录权限同理属于部署方案。
- **读回比对是按整个对象载入内存的。** `mirror_backup` 用 `get_object` 一次读完整份字节再算 SHA-256，没有做分块流式比对；对象体积涨到需要流式之前，这条边界不用改，但要知道它在哪儿。
