# 毕业季批量发布：发布后的补图工作队列

## 起点

批量发布第一刀把商品事实一次性建好，第二刀又让 UTF-8 CSV 可以先解析成可编辑预览。两刀都刻意不处理图片：二十个文件对应二十件商品的映射、失败重试和部分成功语义，不能混在商品创建事务里顺手做。

但“发布后再补图”不能只停留在一句提示。毕业季卖家发布完一箱闲置后，最需要的是一个很短的下一步：哪些商品还没有图、去哪里补、已经补完几件。本设计补这条卖家侧工作队列，不把媒体处理伪装成已经支持批量上传。

## 产品形状

### 队列从哪里来

批量发布事务提交并完成匹配通知后，服务端把本批次商品 ID 写入当前用户 session 中的短期补图队列，然后跳转到“本批次补图”页面。

队列只保存服务端生成的最小事实：

- 归属卖家 ID，用于防止同一浏览器换账号后串队列；
- 本批次商品 ID 列表，最多 20 个；
- 批次发布时间，用于页面说明。

不新增批次表、不新增商品批次字段、不生成迁移。session 过期后队列自然消失；下一次批量发布会覆盖上一份队列，避免长期保留卖家已经不关心的任务。

### 页面回答什么

“本批次补图”页面只回答三个问题：

1. 本批次一共发布了几件。
2. 还有几件值得补图。
3. 下一件去哪里编辑。

页面展示待补图商品的标题、交易方式、价格或押金口径、状态和发布时间，并提供跳转到现有单件编辑页的按钮。每补一张图后回到队列，对应商品会从待办中消失，完成数增加。

“值得补图”的规则保持保守：商品仍属于当前卖家、仍然没有图片、状态仍在售或已预订、且展示未过期。已售出、已过期或被删除的商品不再出现在待办里，但计入“不需要继续处理”；如果商品已经有图，则计入已完成。

## 与现有能力的关系

- 单件编辑页仍是唯一的图片上传入口，沿用最多五张图、体积治理、方向修正、压缩和缩略图生成规则。
- 补图队列不提供多文件上传，不理解“这二十个文件分别属于谁”。
- “我的商品”继续承载长期管理；本队列只服务刚发布的这一批，不在商品列表里制造新的持久状态。
- 不改变商品排序、刷新时间、曝光权重和推荐分数。补图影响的是商品自己的展示质量，不是一次营销动作。
- 不发送站内通知、邮件或每日提醒。卖家发布后已经被重定向到队列，重复催促没有必要。

## 隐私与运营边界

- 队列只对当前登录卖家可见，读取时始终按 `seller` 和 ID 列表双重过滤。
- 不展示其他卖家的无图商品，不做全站无图率排行。
- 不把补图速度用于信用、徽章或卖家标签。
- 不把队列写入运营看板；运营侧已有的商品图片覆盖度统计继续承担全局观察职责。
- session 中的商品 ID 不暴露给页面或 URL，页面只渲染当前卖家有权看到的商品事实。

## 明确不做的事

- 不做批量图片上传。
- 不做拖拽文件与商品行的自动匹配。
- 不做异步图片任务或失败重试队列。
- 不做跨批次累计待办、补图排行榜或催促通知。
- 不为队列新建模型、迁移或后台任务。

## 验收口径

- 批量发布成功后写入本批次补图队列，并进入队列页面。
- 队列只显示当前卖家、无图、仍可展示或已预订的商品。
- 有图商品不出现在待办里，并计入完成进度。
- 已售出、已过期或删除的商品不再要求补图，也不造成权限泄漏。
- 换账号登录后看不到上一个卖家的队列。
- session 失效或下一次批量发布会按规则替代旧队列。
- 匿名访问队列页被登录保护拦截。
- 全链路不新增模型、不新增迁移、不触发额外通知。
