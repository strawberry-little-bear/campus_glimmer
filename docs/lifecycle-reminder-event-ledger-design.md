# 生命周期提醒事件台账设计

## 背景

商品生命周期提醒目前有两类事实没有分开保存：

1. **商品上的冷却时间戳**：`Item.attention_reminder_sent_at` 和 `Item.price_drop_reminder_sent_at` 只保留每个商品每种提醒的最近一次发送时间。
2. **合并通知**：一次任务会按卖家合并成一条 `lifecycle_reminder` 通知，通知本身不逐件展开。

这两个字段足够回答“最近一次有没有提醒”，也能支撑滚动周期的提醒效果面板；但跨学期对比需要稳定的历史事件流。时间戳会被下一次提醒覆盖，通知又无法可靠还原每一件商品进入了哪一类提醒。如果把当前字段直接当成历史台账，旧学期会被系统性低估。

## 目标

新增 `LifecycleReminderEvent` 事件台账，在真实发送事务内为每件商品的每类提醒落一行事件：

- `item`：被提醒的商品；
- `seller`：收到提醒的卖家；
- `kind`：`attention`（待处理提醒）或 `price`（价格参考提醒）；
- `sent_at`：发送时间；
- `notification`：对应合并通知，通知以后被清理时置空，事件仍保留。

事件是**实际发送事实**，不是候选清单。预演、偏好关闭、免打扰、去重命中都不写事件。

## 写入口径

`send_lifecycle_reminders` 继续按卖家合并通知，不改变用户体验。通知创建成功后，在同一事务内：

1. 为本批 `attention_items` 写入 `attention` 事件；
2. 为本批 `price_items` 写入 `price` 事件；
3. 回写商品上的两个冷却时间戳。

一件商品同时进入两类候选时写两行事件，对应两个不同问题；一条通知覆盖多件商品时写多行事件，并指向同一条通知。任何一步失败，整个事务回滚，避免出现“通知存在但事件缺失”或“冷却时间被消耗但没有通知”的半状态。

唯一键使用 `(item, kind, sent_at)`，并建立商品、卖家与发送时间的查询索引。唯一键不是为了把同一秒重复调用解释成两次触达，而是保证事务重放不会把同一发送事实写两遍。

## 读路径

现有「生命周期提醒触达与行动」面板先改造为混合来源：

- 周期内有事件台账的商品和提醒类型，优先读事件；
- 旧数据只有商品时间戳时，继续按旧口径回退；
- 同一商品同一类型同时出现事件与时间戳时，只保留事件，避免双计；
- 面板单独报告事件覆盖数与旧时间戳回退数，让运营知道这期结果里有多少是稳定事件口径。

事件台账不回填。没有事件的旧提醒只能继续作为回退样本，不伪造成历史事件。

## 边界

- 不改变提醒频率、文案、合并粒度或冷却规则；
- 不根据事件自动调整频次、给卖家打标签或发送新通知；
- 不把事件面板单独暴露商品标题、描述或卖家名单；
- 不把“动作发生在提醒之后”解释为因果；
- 未来做跨学期对比时，只比较同一 `phase_key`，且只纳入观察窗口已经关闭的阶段；进行中阶段先报不完整，不提前判方向。

## 验收

- 真实发送：通知、事件、冷却时间戳同事务落库；
- 两类提醒：同一商品写两行，`kind` 不混；
- 一条合并通知：多件商品事件共享同一通知外键；
- 预演、偏好关闭、免打扰、去重命中：不写事件；
- 效果面板：优先事件、回退时间戳、不双计，并输出来源覆盖；
- 迁移检查、专项测试、模板解析与导出契约通过。

## 后续演进

事件台账稳定运行后，跨学期生命周期对比才有可比分母。下一步可以按学期阶段聚合“发送、打开、动作”三层，并把旧时间戳回退比例作为数据可信度边界单独展示。
