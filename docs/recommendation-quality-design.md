# 首页那八张推荐卡，第一次被运营读到

## 起点

`listings/recommendations.py` 的 `RecommendationService` 给每个登录用户算八件商品，
按一个可解释的分数排下来，首页「为你挑选」一栏渲染出来。分数由五部分组成：新鲜度
（最多 4 分）、被收藏数（最多 8 分）、用户标过「想看看」（+10）、分类匹配（+8）、
地点匹配（+5）。每一件推荐都带一句人话理由——「你标记过想看，优先为你保留」「符合
你的分类与交易地点偏好」「就在你关注过的校园地点附近」「校园用户正在关注」。

写入路径有一条，是 `RecommendationFeedback`：用户在推荐卡上点「想看看」或「不感兴趣」，
`views.recommendation_feedback` 用 `update_or_create` 落一行，带 `action`、`created_at`
和 `updated_at`，`(user, item)` 上有唯一约束。

读路径也只有一条，就是推荐服务自己——`_load_preferences` 把这两类反馈读回来，
「想看看」的商品 +10 分，「不感兴趣」的商品直接从候选里 `exclude` 掉。

**除此之外，零。** `RecommendationFeedback` 是全站唯一一个「用户对推荐结果本人表态、
而平台从来不知道这个表态准不准」的字段。后台能列出这些反馈，看板上没有任何一个数字。

## 为什么这是真缺口

站内已经有三个「量我们自己的排序/打分」的模块，推荐的打分是唯一一个没被量过的。

- `search_position_quality.py` 量搜索排序：点击落在第几位、点击的商品是不是排得比曝
  光的商品高、整体点击率低的时候点击是堆在前面还是散在后面——因为平台自己出了一套
  相关性排序，就得知道它有没有用；
- `demand_match_quality.py` 量匹配打分：按分档统计求购人的真实决定（接受/拒绝），看
  单调性，看高分是不是被过度承诺——因为匹配分数要拿去影响运营的撮合动作；
- `item_lifecycle.py` / `price_insights.py` 也都只报数不改权重。

推荐打分的性质比这两个更严重：它**直接决定每个用户打开首页看到什么**，而首页是全站
流量最大的页面。一个新鲜度权重写错的推荐服务，会让每个用户的第一屏都是刚上架四小时
内的商品，运营从任何现有面板上都看不出这件事——搜索面板量的是搜索，供给面板量的是
商品，两个都不碰「用户看到的那八张卡是什么」。

而 `RecommendationFeedback` 已经在收集判断推荐好坏的证据了，只是没人读：

- 用户点「想看看」，说明这件商品值得优先保留——这是**正样本**；
- 用户点「不感兴趣」，说明这件商品不该被推给他——这是**负样本**；
- 两件事都发生在推荐卡上，而推荐卡是按那个分数排出来的。

也就是说，**打分、证据、和证据所对应的那个分数，三样东西都在库里，只是从没被放在
同一张表里。**

## 这个模块要回答什么

一个登录用户打开首页，看到八件商品，每件带一句理由。他点了一件「想看看」、三件「不
感兴趣」，其余四件没有任何表示。运营要回答的问题是：

**这套打分挑出来的东西，用户认不认？不认的话，是哪个理由在骗人？**

拆开是四个问题，四个分母：

1. **推荐卡收到了多少反馈。** 反馈率本身是第一个数字——首页推荐对登录用户展示，
   一张卡被展示过多少次（用 `BrowsingHistory` 里被推荐商品的浏览反推，见下面的口径说
   明），其中有多少次换来了一个「想看看」或「不感兴趣」。零反馈不是「用户满意」，
   是这套卡没有引起任何反应，两种情况在运营眼里完全不同。
2. **正负反馈的比例。** 「想看看」除以全部反馈。这个数高说明推荐的方向对，低说明
   用户在大量划掉不该看的东西。分母只收有过反馈的推荐，不收展示数——拿展示数当分母
   会把「没人看」混进「看了不喜欢」。
3. **按理由拆。** 每一句理由是一个可解释的分数组成部分。按理由统计正负比例，就能
   知道是哪一句在骗人：「你标记过想看，优先为你保留」如果负反馈占多数，说明 +10 分
   这个权重把用户自己点过「想看看」的商品推得太频繁，用户当时想看、现在不想看了；
   「校园用户正在关注」如果负反馈占多数，说明收藏数这个 0.8 的乘子在校园场景下是个
   噪声——一件商品被十个人收藏可能只是便宜，不是好。
4. **反馈之后用户做了什么。** 「想看看」之后有没有真的去看这件商品（`BrowsingHistory`
   有没有在反馈之后新增一次浏览）、有没有真的下单；「不感兴趣」之后是不是还在被推荐
   给同一个人（`RecommendationFeedback` 的 `action` 是唯一的，`update_or_create` 会把
   旧的「想看看」改成「不感兴趣」，所以同一对 (user, item) 只有一行——但如果用户在
   另一件同分类商品上继续点「不感兴趣」，说明这个理由整类都在失效）。

## 口径上的取舍

### 展示数从浏览历史反推，不从推荐服务重放

推荐服务每次请求都会重算八件商品，没有一行「这次推荐展示了什么」的记录。要拿到展示
数，有两条路：新加一张 `RecommendationExposure` 表，或者用已有的
`BrowsingHistory` 反推。

选反推，不加表。理由有两条。一是**推荐卡上的商品被点开详情页这件事本身已经被记录
了**——`views.item_detail` 第 466 行 `BrowsingHistory.objects.get_or_create`，只要用户
登录且不是卖家本人。反推的逻辑是：一件商品出现在某个用户的推荐卡上（分数够高），
这个用户之后浏览了它，这条浏览就是一个「推荐 → 点开」的完整证据链。二是**新加一张
曝光表会让首页变慢**：首页现在没有任何写路径之外的额外查询，加一张表意味着每次首页
请求多一次 insert，而这个 insert 要写在渲染八张卡的事务里，失败就会让首页打不开——
一个运营面板不该让首页承担这个风险。

反推的代价必须明说，而且比上面说的更严重：**它既数不到「展示了但没点开」的那部分，
也会把「点了但和推荐无关」的那部分算进来。** 一件商品被推荐给一个用户而那个用户从未
点开，反推看不见它；反过来，一件商品是用户从搜索点进去的，它占了分母却没有推荐卡可
点。所以本模块报的「反馈率」分母是**窗口内全部被点开过的 (用户, 商品) 对**，直接数
`BrowsingHistory`，不和反馈取交集。

这个分母只低不高，所以反馈率报出来的是**下界**。取交集是更诱人的写法——「被推荐且被
点开且表过态」听起来最严格——但那样分母只剩几件，反馈率恒为 100%，这个数字就不存在
了。宁可报一个偏低的下界，也不报一个恒等于 100% 的假数。

### 一条推荐是一个 (用户, 商品, 理由) 三元组，理由取反馈时刻的理由

`RecommendationFeedback` 只存 `(user, item, action)`，不存这件商品当时是因为哪句话被
推到这个用户面前的。而理由是由分数决定的，分数是每次请求重算的——同一条反馈在两个
月前可能是「校园用户正在关注」，今天再算可能就是「符合你的分类与交易地点偏好」（因为
这个用户后来收藏了同分类的东西）。

所以理由必须**在反馈时刻重算一次**，不能查库。做法是：对每一条反馈，用模块自己的
一份轻量复算（读同样的五个输入）算出当时的理由。这份复算必须是 `recommendations.py`
的一个导出函数，不能在运营模块里另写一套——两套打分逻辑算出两个理由，比没有理由更
糟。

这里的边界是：**反馈时刻重算的理由不等于推荐当时的理由**，因为用户的收藏、浏览、订
单在反馈之前又变了。本模块报的是「用户在看到这句话的时候点下了按钮」，而那句话是他
点按钮之前最近一次看到的。这是一个近似，但它是唯一不用改表、不用加曝光日志就能拿到
的近似。把它和「真正的推荐当时的理由」混为一谈是错的，所以面板上每一行都带一句说明：
理由是按下按钮时重算的，用户在那之后又收藏或浏览过的东西会改变它。

五个输入里只有一个需要额外定口径：`feedback_match` 取**改过口**，不取「这件商品现在
还在不在想看看集合里」。

改过口的行，第一次表态已经把商品写进了「想看看」集合，用户第二次点按钮时「你标记过
想看，优先为你保留」那句话是生效的，按钮就是被它推动的。只表过一次态的行，点击本身
就是入集合的那个动作，那句话在点击那一刻还没出现。若按「现在还想看」读，所有
interested 反馈都会落进 `feedback_match` 桶、所有 dismiss 都不落，按理由拆开的正负比例
就退化成恒等式（interested 100%、dismiss 0%），第 3 问永远问不出东西。

### 「想看看」改「不感兴趣」是一次改口，不是两条记录

`update_or_create` 保证同一对 `(user, item)` 只有一行。所以一个用户先点「想看看」、
后点「不感兴趣」，库里有**一行**，`action='dismiss'`，`updated_at` 是改口的时刻，
`created_at` 是第一次表态的时刻。

这两列都要读。改口本身是一个信号：用户当时想看，现在不想看了。按 `updated_at` 归期
统计当前态度，同时把「改口过」的条数单独数出来——它是「推荐可能推得太频繁」最直接
的证据，比任何比例都硬。

判据不能直接写 `created_at != updated_at`。`created_at` 是 `auto_now_add`、
`updated_at` 是 `auto_now`，一次 `create()` 里两列各取一次时钟，实测相差几微秒到一毫
秒。直接比相等会把**每一条**首次反馈都误判成改口，改口数恒等于反馈总数，第 4 问直接作
废。所以判据是两列的时刻差超过 60 秒：真实用户两次表态之间至少隔着一次页面往返，而
同一次写入的两列差不出这个量级。

### 正负比例的分母只收有过反馈的推荐

反馈率的分母是「被推荐且被点开」，正负比例的分母是「有过反馈」。两个分母不能混：

- 拿展示数当正负比例的分母，会把「没人看」算成「看了不喜欢」——零反馈的商品会把比
  例推向 0，让运营以为用户在大量拒绝，其实用户根本没看；
- 拿反馈数当反馈率的分母，会让反馈率恒为 100%，这个数字就不存在了。

所以两个比例分开报，各自带自己的分母和门槛。

### 按用户不聚合，按商品也不聚合

推荐服务是**按用户**跑的，反馈也是**按用户**落的。按用户聚合成「这个用户的推荐命中
率」是排名，不是运营面板该有的东西——它会让运营去盯某几个用户。按商品聚合成「这件
商品的推荐命中率」同样没用：一件商品被推荐给一万个人和被推荐给一个人，命中率不可比。

本模块按**理由**聚合，因为理由是打分的可解释输出，也是运营唯一能动手改的东西
（改权重、改文案）。按用户和按商品的切分都不做，理由切分是唯一能指向一个具体改动的
切分。

### 只报告，不改权重

这是本项目所有「量自己」模块的共同边界，这个模块尤其要守住，因为它的输出直接指向
`recommendations.py` 里的四个常数。模块**不**调 `+10`、**不**调 `0.8`、**不**调
`+8`、**不**改任何一句理由文案、**不**把负反馈的商品加进任何黑名单、
**不**给用户重算推荐。

理由很直接：一个自己改自己权重的推荐服务，会让推荐结果变成「运营上周在看板上看到
的那个形状」，而运营看到的是用户上周的行为。两件事必须分开，否则看板量的就不是推荐
质量，而是它自己上周的输出。

## 不做什么

- **不加曝光表。** 见上，首页不该为一个运营面板多一次 insert。
- **不做协同过滤。** 现在没有用户-商品评分矩阵，也没有证据支持。
- **不按用户排名。** 那是隐私问题，也不是运营面板的射程。
- **不把「想看看」当成成交信号。** 它只是一个表态，和下单之间还隔着一次预约、一次
  见面。模块只报「表态之后有没有去看」，不去报「表态之后有没有买」当成推荐质量。
- **不回填任何数据。** 反馈行的 `action` 是用户自己按的，不改写。

## 落地顺序

1. `listings/recommendations.py`：导出一个 `recommendation_reason_for(item, user)`，
   把 `RecommendationService.get()` 里算理由的那段抽成可复用的纯函数，服务自己和运营
   模块共用同一份。**这一步必须先做**，否则运营模块会另写一套打分。
2. `listings/recommendation_quality.py`：读 `RecommendationFeedback` +
   `BrowsingHistory` + `Favorite` + `Order`，按理由统计反馈率、正负比例、改口数和反馈
   后的动作，给出每一条理由的样本门槛。
3. 接进 `build_operations_dashboard()`，放在 `chat_response_trend` 之后。
4. 看板加面板：四个数字一组，按理由一张表，每行带门槛说明。
5. CSV 导出加同名节。
6. 测试覆盖：反馈率分母只收点开过的、正负比例分母只收有反馈的、按理由拆的正确性、
   改口单独计数、样本不足不给方向、空平台不报 0、复算理由与服务本身一致。
