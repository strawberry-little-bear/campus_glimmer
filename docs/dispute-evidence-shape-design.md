# 证据文件的形状：争议双方实际传了什么、有多大

## 起点

`OrderDisputeEvidence` 是交易争议的附件表，四个业务字段加两个审计字段：

- `dispute` —— 挂在哪条争议下，`ForeignKey`，一条争议可以有多份证据。
- `uploaded_by` —— 谁传的，`ForeignKey`。
- `attachment` —— 证据文件，`FileField`，`upload_to='dispute_evidence/%Y/%m/'`。
- `note` —— 证据说明，`CharField(300)`，可空。
- `created_at` / `updated_at`。

写入路径只有一处：`add_dispute_evidence`（双方均可，要求争议还在 `open` / `reviewing`）。入口上挂着
`validate_dispute_evidence`，它限死了两件事：**文件不能超过 5 MB**、**扩展名只能是 jpg / jpeg /
png / webp / pdf 四种**。这是站内唯一一个带校验器的文件字段，也是唯一一处把「治理侧要能审阅」
写成了代码的产品规则。

## 为什么这是真缺口

`dispute_resolution_quality.py` 是争议域唯一的读者，它读 `created_at`、`note` 的长度、`dispute`
自己的 `reason` / `status` / `resolved_at` / `resolution_note`，报驳回率、证据到达时刻、发起方向、
处理意见填写率。它对 `attachment` 只做一件事：数条数。`evidence_count`、`attachment_count`
这两个数字在它那里出现，而 `attachment.name` 和 `attachment.size` **一次都没有被读过**。它有一个
测试就叫 `test_attachment_count_is_reported_but_not_used_as_sufficiency`——刻意只报规模、不把
条数当成证据充分性。

也就是说，这套格式规则现在是个黑箱：

1. **运营不知道争议双方实际传的是什么格式。** 四种允许格式各自有多少份、占比多少，没有一个数。
   如果 PDF 占比极低，说明四种格式里有一种是规则允许、现实里从没被用过的——那要么是产品提示没
   写清，要么是这一种本来就不该出现在列表里。这件事从条数上完全看不出来。
2. **运营不知道文件有多大。** 手机截图普遍一两百 KB，实物照片可能三四 MB。如果九成证据是
   200 KB 的截图，那 5 MB 上限形同虚设，它防住的不是正常用户，而是极少数真的会传大文件的人；
   反过来，如果大量文件贴着上限走，说明上限可能真的在挡人，而处理人会看到一堆「传不上来」。
3. **「有没有附件」和「附件长什么样」是两个问题。** 前者已经在报（`with_evidence_count` /
   `without_evidence_count`），后者没有。一笔争议带三张 150 KB 的截图和一笔争议带一份 4.8 MB
   的扫描件，在条数上差三倍，在审阅成本上是两件不同的事。

前两个问题的共同点是：**它们都是产品决策的效果，而这个决策的效果从来没有被度量过。**
站内其它带校验器的字段几乎都有读者——`borrow_days` 有 `borrow_days_shape`，押金档有
`borrow_risk`，求购匹配分有 `demand_match_quality`。唯独这一处格式规则，上线之后没有任何一个
数字回答过「它拦下了什么、放过了什么、用户实际交上来的是什么」。

## 口径上的取舍

### 扩展名分布：四种格式各报，另设「其它」

按 `attachment.name` 的扩展名分档报份数与占比，四种允许格式各自一档，另设「其它」一档兜住
校验允许范围之外的扩展名。

**「其它」理论上应该是 0**——入口上挂着 `validate_dispute_evidence`，不合规的根本存不进来。但它
仍然单列，不合并、不省略：直接入库、历史数据、命令行造数、或者校验器将来被绕过，都会让这一档
变成非 0。一个恒为 0 的格子是有信息的——它说明校验在生效。把它省掉，这个信息就没了。

**不因为「PDF 没人用」就建议下掉 PDF。** 格式规则是治理侧的可审阅性要求，不是使用频率的函数。
PDF 占比低可能只是用户手上没有扫描件，不代表它不该被允许。本模块只把现状读出来。

### 大小分档：取规则里的原值，不取分位数

按 5 MB 上限和几个运营能认出来的整数分档：100 KB、1 MB、3 MB，再加一档「贴上限」单独数接近
5 MB 的（≥ 4.5 MB）。

**档位取规则里的原值，不取分位数。** 理由和 `borrow_days_shape` 的期限档一样：运营看表时要能
认出自己在表单上见过的那几个数。5 MB 是写在校验器里的数，4.5 MB 是它的九成；一个每月都会移动
的分位边界什么也说明不了，而这个数要能回答「上限是不是该调」——只有固定档能回答这个问题。
档位互斥、左闭右开、全列，包括 0 样本档。

**「贴上限」单独数一档。** 这是本模块唯一一个运营能直接动作的数：如果一批文件反复撞上限，
说明上限在挡人，该调；如果一个都没有，说明上限宽松，甚至可以收紧。它和「4.5 MB 到 5 MB 之间
有多少份」的区别在于，前者是一个阈值观察，后者只是一格分布。运营问的是前者。

### 每笔争议的附件数与总大小

一笔争议带几份、总大小多少，和它的结案状态做交叉。

**不判「证据够不够」。** 平台没有能力判断一段聊天记录能不能证明「商品与描述不符」，这个判断
只有处理人能做。`dispute_resolution_quality` 已经用一条测试守住这条线，本模块不越过它——报
「一笔争议平均带几份、总大小中位多少」，不报「几份才算充分」。

**不读文件内容。** 不 OCR、不解码、不看图片尺寸、不判断这份截图是不是真的和这笔订单有关。
本模块只读 `attachment.name`（路径字符串）和 `attachment.size`（存储返回的字节数），这两个都
是存储层的元数据，不是内容。

### 与 `dispute_resolution_quality` 的分工

它报「有没有附件」，本模块报「附件长什么样」。两个面板并排读，不重复：

| 模块 | 回答什么 |
| --- | --- |
| `dispute_resolution_quality` | 争议进来得多晚、有没有附件、按 reason 的驳回率、发起方向、处理意见写没写 |
| 本模块 | 附件是什么格式、有多大、一笔争议带几份、有没有人在撞 5 MB 上限 |

**不重复它的窗口口径**：它按争议发起时刻切窗口（一条窗口外发起、窗口内结案的争议不计入），
本模块按证据上传时刻切窗口（一份窗口外上传、窗口内才被争议引用的附件不计入）。两个窗口不
同是有原因的——它问的是「本期的争议处理得怎么样」，本模块问的是「本期交上来的材料长什么样」，
两个问题的分母不是同一批记录。这一点必须在面板上写明，否则读者会拿两边的「附件数」对账。

### 不报「上传失败过几次」

`validate_dispute_evidence` 在表单层抛 `ValidationError`，**失败不留任何记录**。所以「有多少次
上传因为超过 5 MB 被拒」这个数，库里没有，本模块不知道，不编。这是全站一贯的底线：数据不可知
不等于样本不足，必须明确说「这个数不知道」，不能拿一个近似值顶上去。

### 空文件与缺失大小

`attachment.size` 由存储后端返回。一个 0 字节的文件是「传了一个空文件」，一个读不到大小的
文件是「存储层出了问题」——**这两件事不是一回事**，分开报。0 字节的文件进大小分档的「0 KB」
一格，读不到大小的单独数出规模，不摊派到任何档位，也不进任何分母。

## 明确不做的事

- 不加迁移、不加字段、不改模型。只读 `attachment.name` 与 `attachment.size`。
- 不改 `validate_dispute_evidence` 的 5 MB 上限，不改它的四种扩展名集合。上限与格式是产品
  决策，本模块只把现状读出来。改不改、怎么改，是运营拿着这些数字另外做的决定。
- 不读文件内容、不 OCR、不看图片尺寸、不判断「这份证据是否充分」。
- 不报「上传失败过几次」——校验在表单层拦下，失败不留记录，这个数不知道，不编。
- 不按用户排名、不输出用户名、不按 `uploaded_by` 拆。谁传的附件本身不带方向，拆开只会得到
  两个同样没有解释力的数，这是 `dispute_resolution_quality` 已经论证过的口径。
- 不读 `note`。它是自由文本，可能写着电话、微信、楼栋号。
- 不列证据文件名。文件名是用户上传时的原始名，可能带着真名、身份证号、订单号。
- 不因为「PDF 没人用」就建议下掉 PDF，也不因为「贴上限的很多」就自动放宽上限。格式规则是
  治理侧的可审阅性要求，不是使用频率的函数。
- 不重复 `dispute_resolution_quality` 的口径。它报「有没有附件」，本模块报「长什么样」，
  窗口口径也不同，见上。

## 门槛

- `MIN_EVIDENCE_SAMPLE = 5`：要给某一格式或某一大小档一个占比方向，至少 5 份附件。争议是低频
  事件，附件比争议还少，门槛和 `borrow_risk.MIN_SAMPLE_SIZE` 同一量级。
- 空分母报 `None`，模板显示「—」，不报 0。分子 0、分母存在时报 `0.0`，两者不是一回事。
- 百分点差值不满 `NOISE_POINTS = 8` 视为噪声，不给方向。全站同一套。
- 窗口默认 `DEFAULT_LOOKBACK_DAYS = 30`，与 `dispute_resolution_quality` 的默认周期一致，
  两个模块的看板入口在同一个下拉里，读同一段时间才有可比性。
