# 校园地点单日开放例外设计

## 要解决的问题

校园地点已经可以登记每周重复的开放时段，交付地点与时间推荐也会解释当前安排是否落在时段内。但校园真实运行并不完全按周重复：法定假期闭馆、考试周延长开放、雨天临时关闭、设备检修暂停一天，都是“只改某一天”的安排。

如果继续把这些信息写进自由文本，系统仍会在假期当天推荐一个按周规则看似开放的地点；如果要求运营删除再重建每周时段，又会把长期规则改坏。因此本轮补充一层日期级例外，让长期规则和临时调整分开维护。

## 目标

- 为每个地点按日期维护单日开放例外：
  - `closed`：当天临时关闭；
  - `replacement`：当天用一组指定时段替代每周规则。
- 一个例外日期可以有多个替换时段，支持例如“上午 09:00–12:00，下午 14:00–18:00”。
- 例外必须填写原因，供后台维护人员理解这行配置为什么存在。
- 关闭例外覆盖当天全部每周时段，包括前一天跨午夜延伸到当天的时段。
- 替换例外完全替代当天的每周时段，不用“每周时段 + 增减片段”表达，避免同一日期出现两套口径叠加。
- 交付安排、地点推荐和时间推荐都读取同一套例外判断结果。
- 订单页在当前安排被例外关闭或替换到时段外时继续提醒，但不阻止双方协商提交。

## 数据与判断口径

- 新增 `CampusLocationServiceException`：
  - `location`：所属地点；
  - `effective_date`：例外日期；
  - `exception_type`：`closed` 或 `replacement`；
  - `reason`：配置原因；
  - `is_active`：是否启用；
  - 时间戳。
- 新增 `CampusLocationServiceExceptionWindow`：
  - 属于某个单日例外；
  - `start_time` / `end_time`；
  - 只允许当天内的开始时间早于结束时间，不支持跨午夜。
- 同一地点同一日期只允许一条启用的例外头，避免“关闭”和“替换”同时生效。
- 同一例外下同一开始时间只允许一条替换时段。
- 例外只调整已有每周时段的地点；没有每周时段的地点仍按“未登记每周开放时段”处理，不用一次性例外伪装长期档案完整。
- 生成可判断区间时：
  - 若日期没有启用例外，沿用每周时段；
  - 若日期启用关闭例外，该日期不生成开放区间；
  - 若日期启用替换例外，只生成该日期的替换时段；
  - 替换时段仍可多条、重叠或相邻，判断前合并。
- 区间覆盖规则沿用每周时段：预约必须完整落在开放区间并集内，半开边界、跨午夜周规则和相邻时段合并逻辑不变。
- 汇要同时能说明每周规则和影响判断日期的例外，避免用户只看到“关闭”却不知道是假期或检修。

## 交互与推荐边界

- 后台将单日例外作为独立维护入口，并在例外编辑页维护替换时段。
- 地点推荐在传入目标交付时间时：
  - 落在例外后的开放区间内，说明“当天例外开放”；
  - 遇到关闭例外或替换后不在开放区间，降低排序并提示核对；
  - 没有目标时间时仍只展示每周规则，不用未来所有例外干扰当前排序。
- 时间推荐结合当前地点的目标日期：
  - 优先给出例外替换后的开放区间；
  - 关闭日的候选降低排序但不隐藏，因为双方仍可能改地点或线下另行确认；
  - 未登记每周规则的地点不惩罚。
- 提交预约时，例外关闭或替换时段外仍允许保存，并显示含原因的警告。
- 订单详情同步展示当前安排的例外状态和原因。

## 明确不做

- 不导入校历、法定假期或门禁系统。
- 不支持跨多天的例外区间；连续假期按多个日期维护，保证每一天的原因和类型都能单独追溯。
- 不自动生成假期例外，也不根据异常预约自动关闭地点。
- 不让普通用户编辑例外；这是地点档案运营配置。
- 不记录用户位置，不输出个人到访轨迹。
- 不用单日例外替代每周档案治理；地点长期没有每周时段时仍是未登记状态。

## 验收口径

- 同一地点同一日期无法创建第二条启用例外头。
- 替换时段支持多条、重叠和相邻合并；开始时间大于或等于结束时间被拒绝。
- 关闭例外覆盖当天每周时段，也覆盖前一天跨午夜延伸到当天的部分。
- 替换例外替代当天每周时段，不与每周时段叠加。
- 停用例外头后恢复每周规则。
- 地点推荐、时间推荐、预约表单和订单详情使用同一判断结果。
- 例外外的时间提交仍可保存，并出现带原因的提醒。
- 既有每周时段测试保持通过，迁移检查和系统检查通过。
