# 通知聚合的质量：合并掉的是打扰，还是信息

## 起点

`create_notification` 收到一个 `dedupe_key` 之后，会先找一条**同接收人、同类型、同键、还没读**
的行，在 `dedupe_window_seconds` 窗口内找到就合并：`occurrence_count += 1`、
`last_occurred_at = now`，并且**覆盖** `actor`、`message`、`target_url`，`title` 不动。
`dedupe_forever=True` 时连「未读」这个条件都不要，永远往第一条上叠。

这是通知系统里唯一一条**写入时合并**的路径，13 处调用点都在用它：求购匹配、
商品生命周期提醒、运营日报、互助机会摘要、关注搜索汇总、有货提醒，以及 `views.py` 里七处
手工构造的键。

而读它的地方只有一个：`analytics.py` 里的 `compression_rate`——
`(event_count - row_count) / event_count`，即「多少条事件被合并掉了」。这个数在看板上
孤零零地挂着，回答不了任何问题：

- 合并到底是**帮了用户**（少收 9 条打扰）还是**害了用户**（一条未读行下面压着 9 件事，
  用户当噪音跳过）？
- 一条被合并了 9 次的通知，第一次和最后一次**隔了多久**？是半小时内的连击，
  还是横跨了三天，最后那次才是用户真正要看的那次？
- 被聚合过的行，用户**真的去读了吗**？和从没被聚合过的行比，阅读率差多少？
- 按类型拆，**哪一类在反复响**？

`notification_response.py` 把 `occurrence_count` 和 `last_occurred_at` 放进了 `PERIOD_FIELDS`，
但拿它们只做了一件事：什么也没做。**这两个字段被写了，被拉了，没有被算过。**

本模块把这两个字段和阅读行为连起来，第一次回答「合并到底发生了什么」。

## 为什么之前没被看见

因为 `compression_rate` 是一个**比例**，而比例天生看不出样本。一个「合并率 60%」既可以
是「同一件事在两分钟内响了三次」，也可以是「同一个提醒拖了四天、用户一次都没点开」。
前者是聚拢，后者是堆积——**两种完全相反的含义，在看板上是同一个数字。**

再看读取侧的现状：

- `occurrence_count` 的真实读者：只有 `analytics.py` 的 `Sum` 聚合；
- `last_occurred_at` 的真实读者：`notifications.py` 自己的去重窗口条件，以及
  `notification_response` 的 `PERIOD_FIELDS`（拉了不算）。

**没有任何一处把「这一行被合并过」和「这一行后来被读了」放在一起看过。**
而这两件事，恰恰是判断合并好不好的唯一依据。

## 报什么

### 口径一：聚合的规模与跨度

周期内所有带 `dedupe_key` 的通知（`dedupe_key != ''`），按 `occurrence_count` 分档：

| 档 | 含义 |
| --- | --- |
| 1 次 | 从未被合并过——键设了，窗口内没有第二次 |
| 2–3 次 | 轻度聚合 |
| 4–8 次 | 中度聚合 |
| 9 次及以上 | 重度聚合 |

每档报行数、被读行数、阅读率。

**跨度**另算：`last_occurred_at - created_at`，即「第一条到最后一条隔了多久」。
跨度分桶（分钟级、小时级、天级、跨天以上）。**跨度和次数是两个独立的维度**：
9 次里 8 次发生在 10 分钟内，和 9 次摊在 5 天里，是两件不同的事。

聚合率本身（`event_count - row_count`）也报，但**只作为分母说明**，不单独成榜——
它已经在 `analytics.py` 里了，重复报一遍只会让人以为这里有新信息。

### 口径二：聚合过的行 vs 从没被聚合过的行

本模块最硬的一个数，两组对照：

| 指标 | `occurrence_count = 1` | `occurrence_count > 1` |
| --- | --- | --- |
| 行数 | | |
| 阅读率 | | |
| 平均处理时长（已读样本） | | |
| 未读行数（右删失） | | |

**这是本模块的核心叙事**：压缩率高可能是好事（少打扰），也可能是坏事（一条未读行下面压着
9 件事，用户直接当噪音跳过）。这个对照第一次让两种可能分开。

**不给因果。** 只说「被聚合过的行阅读率更低」，不说「聚合导致了阅读率更低」——
被聚合的类型（求购匹配、关注搜索汇总）本身就可能比单次通知更容易被跳过。
两组之间还差着**类型的构成**，而这个构成在本模块里不做控制。

**未读行单独数，不并进时长统计。** 一条还没被读的通知，它的处理时长此刻不存在，
不是零；把它当 0 会凭空拉低均值。`notification_response` 已经在守这条线，本模块沿用。

**已读要求 `read_at` 有值。** `is_read=True` 而 `read_at IS NULL` 的是阅读时间上线之前的
老数据，`notification_kind_coverage` 已经如实漏过这一档，本模块同样处理。

### 口径三：按类型拆聚合

每个类型：周期内发送的事件数、行数、聚合率、平均每行合并次数、被聚合行的阅读率。

只报**周期内真的发过**的类型。空平台不报 0 条、不报 0%。

**不按用户报、不排名用户。** 「谁的合并最多」是一份考勤表，不是一份看板。

### 口径四：合并行的结构与最后一次事件

合并会覆盖 `message` 和 `target_url`，而 `title` 停留在第一次。用户点进去看到的东西，
和标题说的可能不是一件事。

**只报结构，不判定是 bug**：

- 周期内被合并过的行里，`target_url` 为空的行数与比例——没有落点的通知，用户读完了
  也无处可去；
- 不读 `message` 内容，不比较「标题和正文是不是一回事」——那要解析自然语言，
  超出本模块的口径。

## 判据与门槛

- 一个类型的规模至少要 `MIN_BUCKET_SAMPLE = 12` 条，才允许对它下「这一类在反复响」
  的判断。和通知类型版图、搜索位置质量、求购匹配质量同一个量级；
- 对照组两侧任一侧少于 12 行，**只报数不下判**——两组阅读率的差距在小样本上是噪声；
- 空平台（一条通知都没有）不报 0 条、不报 0%，报 `None`；
- 拿不到的分母（没有任何带键的通知）报 `None`，不报 0；
- 不按用户排名，不报任何人的用户名，不列任何一条通知的原文。

## 不做什么

**不改 `create_notification`、不改 `dedupe_window_seconds` 的默认值（300 秒）、
不加迁移、不改 `Notification` 模型。** 合并是写入路径，本模块只读不改。
「窗口是不是太短」「`dedupe_forever` 是不是该收敛」是另一个决定，需要先有数据，
而本模块正是提供数据的那一个。

**不自动拆分聚合行、不自动标记已读。** 一条压着 9 件事的未读通知，拆开还是合着，
是产品决定；本模块只把「它压着 9 件事」这个事实报出来。

**不把低阅读率归因给聚合。** 两组对照里差着类型构成、差着通知本身的重要程度、
差着用户此刻在不在站内。本模块只报「低」，不报「因为低」。

**不读 `message` 的语义。** 标题与正文是否描述同一件事，要解析自然语言；本模块只报
`target_url` 的空值比例这个结构事实。

**不统计 `dedupe_forever` 分支的效果差异。** 库里的行看不出它当初是哪条路径写进去的
（`dedupe_forever` 只影响查询条件，不落字段），报不出来，如实不报。

## 交付之后

运营第一次能回答三个问题：

1. 合并到底是省了打扰还是堆了噪音——两组阅读率与处理时长对照；
2. 一条被合并多次的通知，事件摊了多长时间——跨度分布；
3. 哪一类在反复响——按类型拆聚合率。

`analytics.py` 的 `compression_rate` 从一个孤立的比例，变成有对照、有跨度、有类型拆解的
一组数。
