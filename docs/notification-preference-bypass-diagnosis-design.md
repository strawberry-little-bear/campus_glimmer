# 通知偏好关闭后异常链路诊断设计

## 起点

通知偏好使用面板已经能看到每个开关的“关着却仍收到过”那一格。那一格变大时，运营只知道规模异常，不知道应该往哪里查：

- 是用户先收到通知、后来才关闭开关，窗口内留下的正常残留；
- 还是开关关闭之后，某条写入路径仍然创建或更新了通知；
- 或者是偏好行本身缺失，让默认开关与历史通知混在同一个分母里。

现有模型只保存 `NotificationPreference.updated_at`，没有每个开关各自的关闭时刻，也没有偏好变更流水。因此不能把所有“关着却仍收到过”都判成故障，也不能反推出用户当时的选择。

## 目标

新增一个只读诊断面板和 CSV 导出，把“关着却仍收到过”拆成可解释的口径：

1. 当前关着、周期内有通知、且最近一次发生时间不晚于偏好行最后写入：先归为“与后关一致”，表示时间顺序允许它是旧通知残留；
2. 当前关着、周期内有通知、且最近一次发生时间晚于偏好行最后写入：标为“偏好写入后仍出现”，这是需要检查写入链路的可疑下界；
3. 收到过通知但没有偏好行：单列为默认开关覆盖，不并入任何一方；
4. 开关名单、通知类型和写入路径说明同屏展示，方便从异常类型跳到对应实现。

面板只做诊断线索，不自动改偏好、不发提醒、不生成催办工单。

## 口径

### 1. 观察窗口

诊断沿用运营看板当前周期，按通知的“最近发生时间”切窗口。优先使用 `Notification.last_occurred_at`，为空时回退到 `created_at`：

- 普通通知一次写入后两者基本一致；
- 聚合通知的 `last_occurred_at` 表示同一行最近一次发生的时间；
- 直接创建且未填该字段的旧数据不能因为字段为空就消失，所以回退到行创建时间。

窗口外的通知不进入异常计数。它可能只是很久以前收到、后来才关掉，把它留在当前周期里会让正常残留永远清不完。

### 2. 可疑下界，不是可疑总量

对每个当前关闭的开关，取该用户周期内此类型通知的最新发生时间：

- 最新发生时间 `<= NotificationPreference.updated_at`：时间顺序允许“先通知、后关开关”，归为“与后关一致”；
- 最新发生时间 `> NotificationPreference.updated_at`：偏好行最后一次写入之后仍出现该类型，归为“偏好写入后仍出现”。

第二类是**观察下界**，不是完整总量。原因有四个：

1. `updated_at` 是整行偏好最后写入时间，不是该开关的关闭时间；用户后来改过其他开关，会把 `updated_at` 推到更晚，从而掩盖更早的异常；
2. 偏好没有历史流水，无法知道每个开关曾经何时开启或关闭；
3. 数据导入、后台手工修正或时钟异常也可能造成时间顺序失真；
4. 聚合通知的最近发生时间只记录已经落库的更新，被开关挡掉的重复事件不会留下痕迹。

所以面板不输出“绕过率”，也不把两类相除。比值会把缺失的分母伪装成已测量结果。

### 3. 与后关一致也不是免责证明

“与后关一致”只说明当前可见时间顺序不冲突，不证明开关一定生效：

- 用户可能先收到通知，之后关闭开关；
- 也可能关闭开关后发生过异常，但之后又保存过其他偏好，使 `updated_at` 晚于异常时间；
- 还可能通知行创建时偏好尚不存在，后来用户才第一次保存偏好。

这一类的作用是减少误报，帮助运营把注意力集中到时间顺序明显冲突的类型。

### 4. 没有偏好行单列

`NotificationPreference` 不是注册时创建的。没有偏好行的用户在行为上等同默认全开，收到通知并不异常。把他们并入“开着”会掩盖设置页覆盖度，并入“关着”则会制造假故障。诊断只报告：

- 有偏好行的用户数；
- 收到过通知但没有偏好行的用户数。

### 5. 写入路径说明

面板为每个类型标注当前已知路径：

- **统一写入**：经过 `create_notification`，在写入或更新前读取对应开关；
- **汇总写入**：先构造汇总，再经各自开关闸门后写入；
- **默认开关**：没有偏好行时按模型默认值处理。

路径标签只说明代码意图，不证明某一行通知当时走了该路径。异常类型需要回到对应模块检查调度和数据导入历史。

### 6. 只读与隐私边界

本面板：

- 不改 `NotificationPreference`，不自动打开任何开关；
- 不改 `create_notification` 和三个汇总任务；
- 不读取通知标题与正文，只使用时间、类型、接收人外键和偏好布尔值；
- 不输出用户名，不按用户汇总，不排“谁关了还收”的名单；
- 不发送站内通知，不生成告警或催办；
- 不把诊断结果用于自动风控、信誉或排名。

“关了什么通知”属于用户隐私，运营需要的是链路是否接对，而不是个人偏好清单。

## 展示

面板包含三层：

1. **总览**：本期仍出现且当前关着的用户数、偏好写入后仍出现的用户数、通知行数下界、无偏好行用户数；
2. **逐类型表**：类型、已知路径、关着且周期内出现的人数、与后关一致、偏好写入后仍出现、可疑通知行数下界；
3. **边界说明**：明确 `updated_at` 不是逐开关时间戳，空分母不报 0%，缺失历史无法补齐。

表格按模型中的开关顺序输出，不按可疑人数排序。排序会把运营面板变成类型排行榜，而小样本类型一旦排到第一位，最需要的信息反而是样本量。

## 验收

- 空平台可渲染，并明确没有偏好行时不下结论；
- 所有通知类型开关逐个输出，一个不漏；
- 通知发生在偏好最后写入之后时，进入“偏好写入后仍出现”；
- 通知不晚于偏好最后写入时，进入“与后关一致”，不被写成故障；
- 窗口外通知不进入本期诊断；
- `last_occurred_at` 为空时回退 `created_at`；
- 没有偏好行的通知接收人不进入异常，而进入覆盖口径；
- 面板和 CSV 标题一致，导出包含同一套列；
- 不输出用户名，不按用户排名；
- 管理员可访问，普通用户无权访问；
- 迁移检查与相关测试通过。
