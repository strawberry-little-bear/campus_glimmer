# 通知类型、偏好开关与用户手上的那一栏

> 本文保留修复当时的版图快照：24 种通知、26 个布尔开关、27 个表单字段。当前已扩展到 27 种通知、28 个布尔开关、30 个表单字段；模块与测试仍从代码现读三张表，不依赖本文数字。

## 起点

站内通知中心上线到现在，`Notification` 上已经长出 **24 种**通知类型（`KIND_CHOICES`），
`NotificationPreference` 上有 **26 个**布尔开关，`NotificationPreferenceForm` 里**摆出来
27 个字段**。这三个数本应相等，或者只差免打扰那一组。

它们不相等。

`notification_response.py` 从上线那天起就在按 `kind` 分桶，读 `Notification.KIND_CHOICES`
当标签表；`notification_snooze_return.py` 上一轮接着读同一张表。两处都是同一句：
`kind_labels.get(kind, kind)`——查不到就用英文键名顶上。**这句 fallback 从来没有被触发过**，
因为两个模块都只统计库里有的通知，而库里的通知类型全都来自发送路径，发送路径用的 kind 全都
在 `KIND_CHOICES` 里……除了一个。

## 两个窟窿，都不是「bug 报不出来」的那种

### 窟窿一：`mutual_aid_feedback` 是一个没有名字的类型

`NotificationPreference` 上有一个 `mutual_aid_feedback` 开关（「互助完成反馈」，
help_text 写着「互助发布者确认响应结果后提醒参与者」）。它在 `views.py` 的两处被真正发送：

- `views.py:7436`——求购侧的互助结果反馈；
- `views.py:7838`——失物招领侧的互助结果反馈。

而 `Notification.KIND_CHOICES` 的 24 个值里**没有 `mutual_aid_feedback`**。

后果不止是看板上显示英文。`notification_list` 的类型筛选器是这么构造的：

```python
allowed_kinds = {value for value, _ in Notification.KIND_CHOICES}
if kind_filter not in allowed_kinds:
    kind_filter = ''
```

**互助完成反馈的通知，用户在自己的通知中心里筛不出来。** 它照样进来、照样进角标、
照样能被点开，但类型下拉里没有它，按类型筛的时候它会整批消失。偏好页面上那个开关也
因此变成一个谜：用户关掉了一个在看板上叫 `mutual_aid_feedback` 的东西。

这是本轮要报的第一个数：**一个正在被发送、正在被接收、正在被关掉的通知类型，
在用户界面上没有名字。**

### 窟窿二：`meeting_incident` 是一个用户关不掉的开关

反方向也有一个。`NotificationPreference` 上有 `meeting_incident`（「交付预约异常」），
模型上有、默认开着、`views.py:1213` 和 `views.py:1224` 真的在发。而
`NotificationPreferenceForm.Meta.fields` 的 27 个字段里**没有它**。

模板 `notification_preferences.html` 是 `{% for field in form.visible_fields %}`，
表单里没有的字段，页面上就没有那一行。所以：**交付预约异常的提醒，用户收到了，
但偏好页面上没有任何一个开关能关掉它。** 旁边 26 个类型全都有开关，唯独这一类的用户
只能被动接收。

这不是「默认开着所以不用管」。其余 23 个类型的开关全都在页面上，用户形成的心智是
「这一页能管我的通知」。一个 Silent 的例外破坏的是这个心智本身。

## 为什么这两个窟窿之前没被看见

因为三个表各自都是自洽的：

- `KIND_CHOICES` 有 24 个，`notification_response` 拿它当标签表，够用；
- `NotificationPreference` 有 26 个布尔，比 24 多两个，看起来像「多了免打扰」；
- 表单有 27 个字段，比 26 多一个，看起来像「多了免打扰的开关」。

多出来的那个被「看起来像」吃掉了。**要看见它，得把三个数并排放，而不是各自数。**

## 报什么

### 口径一：类型版图的三张表对齐情况

一张表，24 行，每行一个通知类型，四列：

| 列 | 含义 |
| --- | --- |
| 在 `KIND_CHOICES` 里 | 有没有中文名 |
| 有偏好开关 | 模型上有没有这一列 |
| 开关在偏好表单里 | 用户手上能不能改 |
| 周期内真的发过 | 库里有没有 |

四列都是二值。**这一列不是为了报「有几个对得上」，是为了让「对不上的那几行」
自己浮出来。** 空平台报 `None` 不报 0——一个通知都没发过的平台，说不出它的类型版图
齐不齐。

### 口径二：没有名字的类型，规模有多大

`mutual_aid_feedback` 这一行：周期内发了几条、被读了几条、占全部通知的多少。
只报聚合，不列清单——通知标题和内容是收发双方的私域内容。

**不报「这个类型的处理时效」。** 看板上它显示成英文键名，但这不是一个可以跟其他类型
并列比较的样本：它是唯一一个没有中文名的，把它排进 `notification_response` 的 kind 榜单
等于逼着运营去理解一个 UI 层的命名缺口。规模就够了，规模说明的是「有多少用户收到过
一条在看板上没有名字的通知」。

### 口径三：关不掉的开关，规模有多大

反方向：周期内 `meeting_incident` 发了几条、被读了几条。同样只报聚合。

这一列的问法和第二列不一样：第二列问「用户收到的东西有没有名字」，这一列问
「用户能不能对自己的通知说不」。其余 23 个类型的开关都在偏好页面上，这一类的用户
只能收着——报出规模，运营才知道这个例外影响了多少人。

### 口径四：偏好的实际状态，按类型

周期内**真的发过**的类型，逐个读 `NotificationPreference` 上对应的开关：

- 开着（默认值）——用户没碰过，或者明确留着；
- 关着——用户明确关掉了这一类。

**只统计发过的类型。** 一个从没被发送过的类型，它的开关开着或关着都不产生任何后果，
报出来是一堆没有行为支撑的数字。

关掉的比例按类型报。**不按用户报**——「谁关了哪一类」是一份考勤表，不是一份看板。
也不报「关闭导致了少收多少条」：`create_notification` 在偏好关闭时直接 `return None`，
库里一行都没有，那个数不存在（详见「不做什么」）。

### 现在这一刻

版图对齐情况是关于代码的，不按周期过滤。规模与阅读情况是回顾性的，按 `created_at`
落在周期内筛——和 `notification_snooze_return` 同一个口径。

## 判据与门槛

- 一个类型的规模至少要 `MIN_BUCKET_SAMPLE = 12` 条，才允许对它下「这一类触达不足」
  的判断。和其余模块同一个量级；
- 空平台不报 0 条、不报 0%：一条通知都没有的时候，这些数都不存在，不是零；
- 「在 `KIND_CHOICES` 里」「有偏好开关」「开关在偏好表单里」三列是**代码事实**，
  不是统计量——它们不随周期变化，也不需要样本门槛。

## 不做什么

**不加迁移、不改 `KIND_CHOICES`、不改 `NotificationPreference`、不改表单字段列表。**
这两个窟窿的修法各是一行代码（往 `KIND_CHOICES` 里加一个元组、往表单里加一个字段名），
但那是**修复**，不是**度量**。本模块只报告：把「有一个类型没有名字」「有一个开关用户
关不掉」这两个事实搬到运营眼前，修不修、什么时候修，是另一个决定。

**不报「偏好关闭让用户少收了多少条通知」。** `create_notification` 第一件事就是
`if not getattr(preference, kind, True): return None`——被关掉的通知在库里一行都没有，
连「被关掉」这个事实都不存在。`lifecycle_reminders` 和 `saved_search_digest` 有
`result['skipped_preference']` 计数，但它只活在命令返回值里，没有落库。报一个拿不到的
数，比不报更糟。

**不把三个数的差解释成「设计疏漏」。** 24、26、27 三个数不相等是事实，为什么不等——
是某一次加类型时忘了同步，还是有意留的余地——代码里看不出来。只报差，不猜原因。

**不按用户聚合、不排名、不报任何人的用户名。** 偏好是用户私域，按用户聚合成
「这一类通知有多少人关掉了」就已经是上限，不能再往下走到人。

**不列任何一条通知的原文。** 和 `notification_response`、`notification_snooze_return`
守的是同一条线。

## 交付之后

`build_notification_kind_coverage(days=30, now=None)` 的返回值里有五块：

- `landscape`：类型版图的三张表对齐情况，24 行，四列二值；
- `unnamed_rows`：没有名字（不在 `KIND_CHOICES` 里）的类型，规模与阅读情况；
- `unreachable_rows`：用户关不掉的开关（不在表单里）的类型，规模与阅读情况；
- `preference_rows`：发过的类型上，偏好的实际状态；
- `current`：此刻这三类各有多少，不按周期过滤的是版图本身。

面板挂在「延后的通知，延了之后回来了吗」旁边——两个面板读的是同一批通知，一个问
「用户说现在不方便之后怎么样了」，一个问「这些通知在用户界面上到底齐不齐」。CSV 导出
加同名的节。测试同时钉住计算正确性与面板 / 导出呈现，包括「`mutual_aid_feedback` 不在
`KIND_CHOICES` 里所以标签回退成键名」和「`meeting_incident` 不在表单里所以用户关不掉」
这两条边界。
