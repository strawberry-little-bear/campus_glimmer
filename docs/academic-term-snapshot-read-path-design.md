# 学期阶段快照，从「只被写」变成「真的被读」

## 起点

上一轮量了 `AcademicTermSnapshot` 自己：这张表自迁移 0052 起就存在，`refresh_academic_term_snapshots` 每周由调度器往里写数，admin 里注册了，`refreshed_at` 还是只读字段——**而它从头到尾没有任何一条读路径**。`build_academic_calendar` 是学期日历唯一的消费方，它一次都没读过这张表，每次渲染都拿 `AcademicPhase` 的日期区间实时聚合 `Item`、`DemandPost`、`Order`、`SearchQuery`。

上一轮把这件事报上了看板，并留下一句明明白白的边界：**本模块不报快照数与实时数的偏差**。理由是「拿一个没人读的缓存和实时值比大小，得出的是这个缓存不准，而它不准的根源恰恰是没人读」。

这一轮做的正是那句话指出的下一步：**给它一条读路径。** 这是功能改动，不是度量，所以要单独一轮，并且要独立回答度量模块回答不了的问题。

## 为什么现在可以做

实时计算的代价是实的。`build_academic_calendar` 每次渲染要做 `3 个学期 x 4 个阶段 x 7 个计数 = 84` 次 `COUNT` 查询，每次看板请求都重算一遍全部学期的全部阶段。而其中绝大部分行**永远不会再变**：`Item.created_at`、`DemandPost.created_at`、`Order.created_at`、`SearchQuery.created_at` 全是 `auto_now_add=True`，仓库里没有任何一条写入路径会回头改它们。一个 9 月结束的阶段，它的七个计数从 9 月最后一天起就是定值，之后每周一次的刷新算出来的是同一个数。

所以真正的问题不是「快照准不准」，而是「**哪些行可以安全地读，哪些行不能**」。这一轮要回答的就是这个切分。

## 一条阶段什么时候可以安全地读快照

判据不是 `refreshed_at`。上一轮已经查证：`update_or_create` 会把 `auto_now` 字段无条件补进 `update_fields`，所以每次刷新都推进它，十个计数一个都没变也照推。拿它当「这一行还新鲜吗」的判据，会把一条两个月前就结束的阶段读成刚刚更新。

真正的判据是**这一行的计数是否已经封闭**。一条阶段满足下面两条，它的七个计数就是定值：

1. 阶段的结束日期已经过去（`end_date < 今天`）；
2. 这一行确实存在，且它的 `(phase_key, start_date, end_date)` 与当前 `AcademicPhase` 算出来的区间一致。

第 1 条保证没有新的 `Item` / `DemandPost` / `Order` / `SearchQuery` 还能落进这个区间——所有四个 `created_at` 都是 `auto_now_add`，写完不改。第 2 条保证读到的这一行描述的确实是当前配置的那个阶段，而不是改 `starts_on` 之后被旁置的孤儿行（孤儿行的区间和当前阶段对不上，读它等于读一个已经不存在的阶段）。

反过来，**当前进行中的阶段永远实时算**，不读快照。理由很直接：进行中的阶段每小时都在长出新商品、新搜索，快照最多是上周的，把它读出来会让运营看着一个正在变化的数字以为是新鲜的。而当前阶段恰好是看板上唯一有人盯着的那一行。

这个切分还有一个好处：它让「快照有没有在按时刷新」这件事从仪表问题变成正确性问题。以前刷新中断了，看板照样显示正确的数字（因为实时算），没人会发现命令挂了。现在进行中的阶段实时算、已结束的阶段读快照，一旦某个已结束阶段缺行，看板就必须说出来，而不是悄悄退回实时计算——那会把一次真实的刷新中断藏起来。

## 不缺行时的行为

一个已结束阶段在快照表里找不到匹配行，有三种可能：命令从来没跑过、这个阶段是新配的、命令中断了。这三种情况对运营的含义完全不同，但不该由 `build_academic_calendar` 自己去猜。本模块的做法是**逐行标记来源**，让面板和导出能区分「这一行读的是快照」还是「这一行是实时算的」，并在汇总处给出快照行的占比。缺行不静默退回实时计算后假装无事发生，而是照常算实时值、但把 `source` 标成 `live`——数字仍然正确，来源可查。

## 不做什么

**不改 `refresh_academic_term_snapshots` 的写入逻辑。** 它按周刷新全部启用中学期的全部阶段，这一轮不动它。快照的刷新策略是「每周一次」，与「已结束阶段不再变」正好相容：一个阶段结束后的第一次周刷新就会把它定下来。

**不加缓存层、不引入 Redis、不改 `AcademicTermSnapshot` 的字段或约束、不加迁移。** 这一轮只加一条读路径，读的是已经存在的数据。

**不让 `refreshed_at` 参与任何判据。** 上一轮查证的事实在这一轮依然成立，且现在有了新的后果：既然不能拿它判断新鲜度，那么「已结束阶段读快照」的安全性就必须完全建立在「计数已封闭」上，而这一点由 `end_date` 和区间匹配两条保证，与刷新时间无关。

**不因为读了快照就让面板上的数字变旧。** 运营看板上最敏感的是当前阶段，它实时算；已结束阶段的数字本来就是定值，读快照和实时算在数值上应当完全一致。这一点由测试钉住：同一个阶段，两条路径算出来的七个计数必须相等。

## 只报告，不改写

本模块不改任何快照行、不删孤儿行、不触发刷新、不改 `AcademicTermSnapshot` 的唯一约束、不动 `refresh_academic_term_snapshots` 的任何逻辑。它只决定**渲染时读哪一份数据**，以及把「这一行读的是哪一份」如实地标出来。

总结起来，这一轮回答三个问题：哪些阶段可以安全地读快照（结束且区间匹配）、哪些必须实时算（进行中、缺行）、以及读到的这一行到底来自哪里（`snapshot` 还是 `live`）。凡是判据间接的地方，把这些判据为什么间接写在面板上。

## 交付之后

`build_academic_calendar` 的返回值里多了一个 `source` 块：`snapshot_row_total`、`live_row_total`、`row_total`、`snapshot_share`。占比的分母是**实际渲染出来的阶段行数**，不是快照表的行数——拿后者当分母，孤儿行会被算成已覆盖。快照表全空时占比报 `None` 而不报 `0%`：0% 会被读成「刷过了但一行都没命中」，而空值的含义只是「快照表还没有可用数据」。

每一行还多三个键：`source`（`snapshot` / `live`）、`source_label`（面板上的中文标签）和 `source_note`（这一行为什么读这份数据）。三个键两条路径都必须给——`_snapshot_payload` 最初漏了 `source_note`，是「两条路径给出同一套键」这条测试抓出来的。形状不一致的后果很具体：模板和 CSV 导出得为快照行单独写一条分支，而那正是这条读路径要避免的事。

面板在学期表格的阶段列挂了徽标，表格上方加了一行汇总说明；CSV 导出多了「数据来源」和「来源说明」两列，以及一块「数据来源汇总」。**算出来了就必须被读**——上一轮把这张表报成「只被写、从未被读」，这一轮如果让读路径的结论只停在函数返回值里，就是把同一个错误原样再犯一遍。为此补了三个测试：面板要出现汇总文案和「读快照」徽标、CSV 每一行都要带来源列、空占比要说清它与 0% 的区别。
