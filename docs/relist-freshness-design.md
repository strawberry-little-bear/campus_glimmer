# 重新上架的那件商品，为什么一回来就沉底

状态：已实现（只报告，不改任何写入路径）
模块：`listings/relist_freshness.py`
面板：`relist-freshness-panel`，标题逐字「重新上架的那件商品，为什么一回来就沉底」

## 1. 来龙去脉

商品可以设一个可选的展示截止时间。到期后 `expire_items` 把状态改成 `expired`
并通知发布者；卖家编辑商品、把截止时间改到未来，`edit_item` 会把状态改回
`available`，并提示「商品已重新上架」。

问题出在紧接着的下一步。卖家看到「重新上架」四个字，会预期这件商品像新发布
一样回到列表前排。实际上它回来之后，生命周期诊断给出的第一句话是「距上次发布
或刷新已 90 天，在售列表里基本已经沉底」。

运营一开始会以为诊断坏了。诊断没坏，它说的是事实。

## 2. 事实链

`Item.freshness_age_days` 的实现是：

```python
last_active_at = self.last_refreshed_at or self.created_at
delta = timezone.now() - self.last_active_at
return max(0, delta.days)
```

`last_refreshed_at` 只在 `refresh_item` 里被写入。`edit_item` 的重新上架分支只做
两件事：把 `status` 改回 `available`，然后 `save(update_fields=['status',
'updated_at'])`。它不碰 `last_refreshed_at`，也不碰 `refresh_count`。

所以重新上架这件动作，在系统里**没有留下任何时间戳**。新鲜度仍然是发布那一刻
算起的，一件上学期发布、这学期重新上架的商品，一回到在售列表就带着整个假期的
新鲜度欠账。

## 3. 为什么这件事值得单独看

供给侧看板已经报了「发布超 45 天无互动」的总量，但把三种完全不同的情况混在了
一个数字里：

- 发布时就没运营好，一直沉底；
- 重新上架过，卖家以为给过它一次机会；
- 发布时设了很长的截止时间，从没到期过。

第三种根本不需要运营介入，前两种需要的动作完全不同。更关键的是，这批商品恰好
是**刷新额度最充裕**的那批：`refresh_count == 0` 意味着 4 次额度一次没用过，
24 小时间隔也没占着。也就是说，问题最好解决的一批商品，恰好也是系统最没提醒过
的那批。

而系统给卖家的提示是矛盾的：一句「已重新上架」，紧跟着一句「已沉底 90 天」。

## 4. 判据

一条纯字段比较，不做任何推断：

```
status == 'available'
且 expires_at 存在且晚于当前时刻
且 freshness_age_days >= STALE_DAYS（45）
且 refresh_count == 0
```

含义是精确的：这件商品从发布起一次都没刷新过，已经沉底，但仍带着一个未来的
截止时间在售。

这里刻意没有去推断「它是否重新上架过」。理由是做不到：重新上架不留时间戳，
而 `expires_at` 在未来这个信号新发布的商品也会有（发布时就可以设一个未来的
截止时间）。所以本模块报的是**新鲜度欠账**这个可观测量，不是重新上架这个
不可观测量。凡是需要「重新上架过几次」才能回答的问题，一律留给下一轮加字段
之后再做。

`STALE_DAYS`、`MAX_REFRESH_PER_MONTH`、`_level_for`、`_refresh_state` 全部从
`lifecycle_diagnostics` 导入，判据只允许有一份。

## 5. 看板回答什么

- 在售商品里有多少件带着新鲜度欠账，占在售多少；
- 这批商品欠了多少天：按欠账分档（45 天以上、90 天以上、180 天以上、更久），
  档位上界与相邻模块保持一致；
- 它们现在处于什么生命周期等级，复用 `_level_for`；
- 刷新额度对它们是不是空的（`refresh_count` 分布），用来证明「问题最好解决的
  一批恰好最没被提醒」；
- 欠账商品里有多少件已经彻底没有互动（无浏览、无收藏、无订单），这部分连刷新
  都救不回来，需要的是重新拍照或降价；
- 清单给出商品、欠账天数、刷新次数与等级，不带用户名、不列自由文本原文。

## 6. 口径

- 空分母报 `None`，不报 0。在售商品不足 `MIN_MEASURED_ITEMS`（12）件时占比只
  报数字不给方向。
- 「无互动」指浏览、收藏、订单三者皆零，且订单只数未取消的。
- 已下架、已成交、已过期的商品不进分母：额度对它们没有意义，混进来会把「问题
  好解决」这个结论冲淡。
- 周期参数只影响周期量。新鲜度是当前状态，不按周期切。
- 不按卖家排名，不报用户名，不把商品标题以外的自由文本带进面板。

## 7. 不做什么

- 不在重新上架时重置 `last_refreshed_at`，不给重新上架记时间戳，不加字段。
  改这一处会让所有重新上架过的商品同时获得一次免费的「回到前排」，等于给存量
  商品开一个排序后门，而且它和 `refresh_count` 额度之间的关系需要先想清楚。
- 不改 `_level_for` 的等级判据，不让「重新上架过」单独成为一档。
- 不自动帮卖家刷新。
- 不做「上学期同期」对比：历史快照表里没有新鲜度欠账这个量，硬做会伪造分母。

## 8. 先看板后改规则的理由

改口径有三条路，每条都有代价：

1. 重新上架时重置 `last_refreshed_at`——等价于送一次刷新，且绕过
   `MAX_REFRESH_PER_MONTH` 的额度，排序后门；
2. 加一个 `relisted_at` 字段，新鲜度改读它——要迁移，且所有历史商品的
   `relisted_at` 都是 NULL，得先决定 NULL 时回落到哪；
3. 让 `_level_for` 认「expires_at 在未来但发布很久」这一档——改的是等级语义，
  供给侧看板的「发布超 45 天无互动」计数会跟着变，运营手里的历史数字对不上。

三条路都值得做，但先得知道规模。如果只有十几件，改一句文案、或者在卖家编辑
页加一句「重新上架不会让商品回到前排，需要刷新」就够；如果是成百上千件，那它
值得一个字段。这就是先看板的理由。
