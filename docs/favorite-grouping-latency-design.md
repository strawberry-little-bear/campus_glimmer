# 心愿单分组：把「先收藏后归类」这个报不了的数变成可测

## 起点

`favorite-collection-quality-design.md` 做完之后，看板上心愿单分组这一组有了七张
表：规模分布、大小形状、空分组、渗透、命名收敛。它们回答的是「分组这个功能有没
有人在用、被当成什么用」。

有一个数被明确留白了，模块 docstring 里专门写了四段解释为什么不报：

> **本模块不报「先收藏后归类」，因为库里没有那个时刻。**
> `Favorite` 没有 `updated_at`。`views.update_favorite_collection` 走的是
> `favorite.save(update_fields=['collection'])`，模型里也没有任何 `auto_now`
> 字段，所以这次保存不刷新任何时间列。

README 的路线图里也留了同一句话，并写明了代价：

> 后续若要报这个比例，需要在 `Favorite` 上加一个 `grouped_at` 列并在
> `update_favorite_collection` 里显式写——那是一次迁移加一条写入路径，要一并想清楚值
> 是不值得。

本轮就是那个决定。做，因为这不只是补一个数。

## 为什么值得一次迁移

「先收藏后归类」不是一个孤立的数，它是**这个功能唯一的行为指标**。

渗透率、大小分布、空分组、命名收敛，量的全是**存量**：现在有多少条收藏归了类、
现在有多少个分组是空的。它们能告诉你分组功能被使用了，但告诉不了你**用户是怎么
用它的**——而「先收藏后归类」正好是这两种用法的分界线：

- 一条收藏在**收藏的那一刻**就归了类，说明用户心里已经想好了「这东西属于哪一类」；
- 一条收藏过了很久才被归类，说明分组是**事后整理**的工具，用户先囤后理。

这两种用法对应完全不同的产品判断。前者说明分组该在收藏动作的当场就出现（商品卡
上直接选分组），后者说明分组该有一个「批量整理」的入口。现在这两个判断都只能猜。

站内已经有了一条同形状的先例：`RecommendationImpression` 和
`OpportunityImpression` 都是为了把一个「下界」变成真实比例而加的表。那两次加的是
新表，这次加的是一个字段——但动机是同一条：**一个被误读成另一个意思的数，比没有
数字更糟**。当前窗口内新建的收藏读出来的 `collection` 是今天读到的值，报出去会被读
成「收藏时就归组率」，而它其实混着大量后来才移进去的收藏。

## 口径：一个字段不够，要三个状态

直接加一个 `grouped_at` 时间列，只能回答「归过类的收藏里，多少条是当场归的」。但
真正该问的是三分，不是两分：

| 状态 | 判据 | 它说明什么 |
| --- | --- | --- |
| 当场归类 | `grouped_at` 与 `created_at` 同一次操作内写下 | 收藏时心里已有分类 |
| 事后归类 | `grouped_at` 明显晚于 `created_at` | 先囤后理 |
| 从未归类 | `collection` 为空，`grouped_at` 也为空 | 分组功能没覆盖到它 |
| 归过类又取消 | `collection` 为空，但 `grouped_at` 不为空 | 试过分组又退回去 |

最后那一类最容易漏。`update_favorite_collection` 支持把 `collection_id` 传空，也就是
**把一条收藏移出分组**。如果只记「归过类」，这批人会被算进「从未归类」，而他们其实
是「用过又不用了」——那是比「从未归类」更强的信号，说明分组对他们没有价值。

所以 `grouped_at` 的语义必须钉死：**它记录的是这条收藏的分组最后一次发生变化的时
刻，不论变化是归进去还是移出来。** 它不是「首次归类的时刻」，也不是「当前分组的
归属时刻」。这个区别要写进字段的 help_text 和模块 docstring，因为下一个读到
`grouped_at` 的人一定会以为是前者。

### 当场与事后的分界

「同一次操作内」在 HTTP 层面对应不上——收藏走 `toggle_favorite`，归类走
`update_favorite_collection`，是两个请求。真正的判据只能是**两个时间戳的距离**。

取多少？这里借 `EMPTY_GROUP_GRACE_DAYS = 7` 的同一条理由：一个真心想当场归组的用
户，不会在收藏之后还想一周才想起来。但比 7 天更该问的是「这个阈值会不会把一批正常
的延时归类误判成事后」——所以阈值必须**可配置地报出来**，而不是硬编码在判据里。面
板上要写出这一档用的是多少天，否则运营读不出「当场」和「事后」的分界在哪。

新增 `INSTANT_GROUPING_GRACE_MINUTES = 60`：一小时内算当场。取一小时而不是一天，
理由是用户可以合理地在「看到商品 → 收藏 → 去心愿单整理」这条路径上花掉几分钟到半
小时，但不太可能花掉大半天还想得起刚才那条收藏该归哪。**这个数没有理论依据，所以
它必须出现在面板上。**

## 写入路径：两条，都要接

`Favorite.collection` 有两条写入路径，只接一条会让字段在另一条路径上腐烂成假数据：

1. `views.update_favorite_collection`——应用内唯一一条，`save(update_fields=
   ['collection'])`。要加上 `'grouped_at'`。
2. Django admin 的 `FavoriteAdmin`——`Favorite` 在后台注册了，默认 change 表单
   能改 `collection`。这条路径**不能靠改 view 接上**，只能靠 `Favorite.save()`
   自己判断。

所以 `grouped_at` 的写入放在模型层，不放在视图层：覆写 `Favorite.save()`，当
`collection` 发生变化时把 `grouped_at` 设成 `now`。这样两条路径都覆盖，而且将来
谁再加第三条路径也不用记得改。

代价是 `toggle_favorite` 删除再重建时：`get_or_create` 新建的 `Favorite`
`collection` 是 `None`，`grouped_at` 也是 `None`，一致。取消收藏走 `delete()`，
不涉及 `save()`，无影响。

### 为什么不用 `auto_now`

`auto_now` 会在**每次** `save()` 时刷新，包括 `save(update_fields=['collection'])`
之外任何一次保存——而 `Favorite` 目前只有这一处保存。更关键的是 `auto_now` 没法表达「只有当 collection 变化时才更新」：它无条件
刷新，那么一条收藏因为任何别的原因被保存（将来加字段时），`grouped_at` 都会被推
到当前时刻，**事后归类会被误判成当场归类**。所以必须是显式覆写 `save()`，比较
`collection_id` 的旧值和新值。

`update_fields` 要能拿到：覆写后的 `save()` 在检测到变化时把 `'grouped_at'` 追加进
`update_fields`，否则调用方显式列了字段时这一列不会被写。

## 存量数据怎么办

加列之后，**所有已有的收藏 `grouped_at` 都是 `None`**，包括那些 `collection` 已经
有值的。这是一个必须摆在面板上的事实，不能悄悄算进去：

- 存量已归组的收藏，`grouped_at` 为空，说明「归过类但不知道什么时候归的」；
- 它们既不能算「当场」也不能算「事后」，只能单列一类：**「迁移前归组」**。

这一类随时间自然消亡，但它会存在很久（校园平台的收藏是长期累积的）。如果把它算进
分母，「事后归类」的占比会被一批不知道时刻的收藏稀释；如果不算，面板上就少一类。
选单列——**分母里没有它的位置，面板上有它的一行**。这不是样本不足，是数据不可知，
两种事的处理方式不同：样本不足照实报数字但压淡，数据不可知必须明确说「这个数不知
道」。

同类先例：`demand_task_aging` 对「期限距建任务超过 180 天」的处理，以及各模块的
右删失样本单独数规模。

## 修完之后要守住的东西

- 新增一条测试钉住 `grouped_at` 的语义：移出分组也要更新它（否则「归过类又取消」
  这一类永远读不出来）。
- 新增一条测试钉住 admin 路径：直接 `favorite.collection = x; favorite.save()` 也
  要写下 `grouped_at`（否则后台改一条收藏就在库里造一个假数据）。
- 新增一条测试钉住 `update_fields`：调用方只列 `['collection']` 时 `grouped_at`
  照样落库。
- 模块的三分表要能在真 bug 出现时红：把 `update_favorite_collection` 里的
  `grouped_at` 写死成一个常量，测试会红。

## 不做什么

- 不加 `Favorite.updated_at`。`grouped_at` 只记分组变化，不记别的——一个通用的
  `updated_at` 会让下一次有人改 `Favorite` 任何字段时把它一起刷新，而这个字段的
  全部价值就在于它只在这一种变化上动。
- 不改 `update_favorite_collection` 的任何行为、校验、跳转。
- 不给任何用户排名、不输出用户名、不读任何自由文本。
- 不动 `favorite_collection_quality` 现有的任何一张表和任何一个阈值——新表是新增
  的，不是改出来的。
- 不做「批量整理」功能。那是产品决策，本轮只把数据立起来。
