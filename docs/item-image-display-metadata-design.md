# 商品图片展示尺寸与懒加载设计

## 背景

上一轮已经为 `ItemImage` 生成最长边 480 像素的列表缩略图，并让商品卡片、搜索结果、表格和详情缩略条优先读取小图。但浏览器侧仍缺两层信息：

1. 图片标签没有内在宽高，浏览器只能在图片下载后才知道比例；虽然主要卡片由 CSS 固定高度，但小图场景和弱网下的重排仍有机会发生。
2. 列表图片全部立即解码，页面商品越多，首屏外的图片越会抢占网络和解码资源。

上一轮设计曾把 `srcset`、懒加载和 CDN 留作后续单独评估。本设计先处理前两项中不依赖新流量数据、也不改变图片资产形态的部分。

## 目标

1. 为原图和缩略图分别记录应用 EXIF 方向后的内在宽高。
2. 商品列表、搜索、表格、公开档案、私信预览、详情缩略条和同类商品输出 `width`、`height`。
3. 非首屏语义明显的列表图片输出 `loading="lazy"` 与 `decoding="async"`。
4. 历史数据可通过现有 `backfill_item_thumbnails` 命令补齐缩略图和宽高档案，保持幂等、可分批。
5. 宽高缺失时模板不输出无效属性，图片仍按原路径回退展示。
6. 保持任务台账可回答：检查多少、更新多少、失败多少、跳过多少、剩余多少。

## 为什么暂不做 `srcset`

当前只有 480 像素缩略图和最长边 1600 像素原图两个候选。商品卡片、搜索卡片和小表格的显示宽度都明显小于 480 CSS 像素；若把 1600 原图放进 `srcset`，高 DPI 设备可能重新选择原图，抵消列表页体积收益。

在引入真实展示宽度和多档缩略图之前，强行拼一个两档 `srcset` 看似响应式，实际会扩大带宽不确定性。因此本轮只输出准确的内在宽高与懒加载语义，不做 `srcset`。

## 数据口径

`ItemImage` 增加四个不可编辑字段：

- `image_width`、`image_height`：原图应用 EXIF 方向后的宽高。
- `thumbnail_width`、`thumbnail_height`：列表缩略图宽高。

新图生成缩略图时一次性写入四项。替换原图时四项随缩略图一起重建；生成失败时删除旧缩略图，宽高不伪装成已知。

历史行按以下规则补齐：

- 缩略图缺失：生成缩略图并写四项。
- 缩略图已存在但任一宽高缺失：读取现有文件补宽高，不重复生成文件。
- 原图任一宽高缺失：读取原图并补齐。
- 文件不存在或无法解码：该行计入失败并继续，不影响后续行。

## 页面口径

- 商品卡片与搜索结果：输出小图 URL、宽高、`loading="lazy"`、`decoding="async"`。
- 我的商品、公开档案、私信预览、详情缩略条、同类商品：输出小图 URL与宽高；滚动后才可见的场景使用懒加载。
- 详情页主图保持立即加载，不添加 `loading="lazy"`，避免影响用户正在查看的商品主体。
- 无图占位图只补充异步解码，不伪装商品图片尺寸。
- CSS 仍负责最终显示大小；`width` 和 `height` 用于让浏览器提前计算比例。

## 非目标

- 不新增 960 像素等中间缩略图档位。
- 不引入 CDN、图片服务或客户端懒加载库。
- 不修改上传体积上限、压缩策略和缩略图规格。
- 不把宽高覆盖率加入运营看板；回填进度由命令输出和任务台账回答。
- 不自动修复缺失文件，只报告失败类型。

## 验收标准

1. 新上传图片保存后，原图与缩略图宽高同时入库。
2. 替换图片后，旧宽高不会保留到新图。
3. `list_image_width` / `list_image_height` 优先使用缩略图尺寸，缩略图缺失时回退原图尺寸。
4. 商品列表模板输出懒加载、异步解码和宽高属性。
5. 已有缩略图但缺宽高的历史行能被命令补齐，且不会重复生成同名缩略图文件。
6. 坏图不阻断批次，任务台账指标完整。
7. 相关模型、命令和模板测试通过，迁移检查通过。
