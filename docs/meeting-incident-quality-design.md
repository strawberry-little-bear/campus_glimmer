# 交付预约异常处理得公不公平

## 起点

`MeetingIncident` 是站内唯一一条「约好了见面，其中一方在现场出了状况」的记录：买家或卖家
在交付时间安排上点「报告异常」，选一个类型、写一段情况说明，这条记录就进队列等审核。它是
`governance_sla` 里四条治理队列之一，也是站内**唯一一条由交易一方对另一方发起、且直指
线下人身安全**的申诉。

而它此前被读到的程度，比 `Report` 还浅：

| 模块 | 读了 `MeetingIncident` 的什么 |
| --- | --- |
| `governance_sla` | 处理时长、超期清单、时限内完成率 |
| `analytics` | 周期内新增多少条 |
| `meeting_attendance` | `reason == 'no_show'` 这一类，和另一方的到场登记做对照 |
| `dispute_resolution_quality` | 什么都没读——它只服务 `OrderDispute` |
| `report_resolution_quality` | 什么都没读——它只服务 `Report` |

`reason`、`status`、`reviewer`、`resolution_note`、`reported_by`、`accused` 六个字段里，
`resolution_note` 的全部读者只有两处：`forms.py` 的表单字段和 `views.py:1727` 的写入路径。
**一个字段被写、被表单收集，从来没被统计过。**

`meeting_attendance` 的到场对照只做了 `no_show` 一类，而且它的目的是「这条工单该不该被
当成矛盾去核实」，列的是具体工单、用户名和商品名——那是一张给运营逐条处理的清单。本模块
问的是另一个问题：**这条队列整体的处理倾向**。两者不重叠，也互不替代。

## 为什么之前没被看见

因为 `MeetingIncident` 看起来一直是「有数的」：`analytics` 有新增计数，`governance_sla`
有时效。两个模块各自都自洽，都回答了「这条队列忙不忙、快不快」。而「处理得公不公平」这个
问题，需要把 `reason`、`status`、`resolution_note`、`reported_by`、`accused` 五个字段
**连起来看**——单看任何一个字段都问不出这个问题。

更隐蔽的一层：`MeetingIncident` 上有一个 `OneToOneField(appointment)`。一次交付安排只能
产生一条异常。所以「同一场约会里双方各报一次异常」在这个模型上**结构上不可能**，而
「同一个人反复报异常」是完全可能的——因为一个人可以和多笔不同的订单对面。这个约束把
「这人是不是在刷异常」这个问题换了一个形状，而换过之后的形状此前没有人看过。

## 报什么

### 口径一：驳回率按异常类型拆

四种异常类型的举证难度完全不是一回事：

| 类型 | 提交人要证明什么 |
| --- | --- |
| 对方未到场 | 对方没有出现在约定地点 |
| 对方严重迟到 | 对方出现了，但晚了很多 |
| 现场安全问题 | 现场有威胁、纠缠或其他不安状况 |
| 其他预约异常 | —— |

「未到场」有系统里的到场登记可以对照，是四种里唯一有客观证据的；「安全问题」几乎不可能
有系统证据，全凭提交人陈述。把它们平均成一个总驳回率，这个数一旦波动，运营第一反应是去
查处理人，而不是去查是哪一类异常在涨。

**已完结的才算进分母。** 分母只收 `status` 为 `resolved` 或 `dismissed` 的。还挂在
`open` / `reviewing` 的是右删失样本：异常还没判，谈不上被确认还是被驳回。这和争议模块、
举报模块守的是同一条线。

### 口径二：处理意见写了没有、写了多长

`resolution_note` 报两件事：填写率，和长度分档。

**一个字符内容都不读。** 它是处理人写给双方的一段自由文本，可能写着电话、微信、楼栋号。
这个模块只关心一件事：这段结论有没有被写下来。

**按结局拆填写率。** 被驳回的异常如果普遍不写意见，提交人收到的是一个没有理由的驳回——
这是这套治理里最伤人的一种体验，而它此前没有任何数字。注意这一条比 `Report` 更重：
异常的另一半是**指控对方**，一条没有理由的驳回，会让提交人觉得自己被反过来罚了一次。

**不报「长度和驳回率的关系」。** 长意见是不是更难被申诉，观测数据里分不开。只报形状，
不给方向。

### 口径三：提交方向——谁在报谁

`reported_by` 与 `accused` 在每一条异常里都是一对，而这对人的身份可以由 `Order` 的
`buyer` / `seller` 推出来。报：周期内已完结的异常里，买家报卖家的有多少条、卖家报买家
的有多少条，两侧各自的驳回率。

**这不构成「哪一方更常被驳」的结论。** 买家报卖家和卖家报买家，各自的总量、各自面对的
异常类型构成都可能完全不同。两侧都过样本门槛时只报数字与差值，且必须同时把两侧的
总量一起报出来——一个 100% 对 100% 的差值，如果两侧各只有 1 条，是没有信息量的。

**不按用户排名、不报任何人的用户名。** 把「谁被报得最多」做成一张排行榜，平台就从仲裁者
变成了一个记录谁难相处的小本子。

### 口径四：异常的人是不是同一批人

按 `reported_by` 聚合：周期内发过异常的用户里，有多少只发了一条、多少发了多条、最多发了
几条。

**不排名、不报用户名。** 报的是分布形状：绝大多数人只报过一次，说明这条通道是**应急**
性质的；有一批人反复在用，说明它是某些用户的**常规**手段。两种形状对应完全不同的治理
动作——后者要看的不是「谁在报」，而是「这些订单为什么反复走到要报异常这一步」。

**受 `OneToOneField(appointment)` 限制，不报「同一场约会里双方各报一次」**——那个数
结构上恒为 0，报出来是一个永远为 0 的常数。

## 判据与门槛

- 一个异常类型的已完结样本至少要 `MIN_BUCKET_SAMPLE = 12` 条，才允许对它下「这一类
  更容易被驳回」的判断。和举报处理质量、争议处理质量、通知类型版图同一个量级；
- 填写率对照两侧（已确认 / 已驳回）各至少 12 条才给方向，差值不满 `NOISE_POINTS = 8`
  个百分点视为噪声；
- 提交方向两侧各至少 12 条才给方向，且必须同时报两侧的总量；
- 空平台（一条异常都没有）不报 0 条、不报 0%，报 `None`；
- 拿不到的分母报 `None`，不报 0。

## 不做什么

**不加迁移、不改 `MeetingIncident`、不改审核表单、不改 `views.py:1727` 的写入路径。**
`resolution_note` 没有设为必填是一个产品决定，本模块只报「实际有多少人填了」，不把填写率
变成强制。

**不判定任何一条异常成立或不成立。** 平台没有能力从现有字段判断一次异常是不是恶意指控，
本模块只报「它被驳回了」这个既成事实。

**不把驳回率和处理人挂钩。** 按 `reviewer` 拆驳回率是一份考官成绩单，本模块不报。

**不读 `detail` 和 `resolution_note` 的任何内容。** 两处都是自由文本，可能写着电话、
微信、楼栋号。

**不重复 `meeting_attendance` 的到场对照。** 那个模块对照的是 `no_show` 一类里
「提交人说的」和「系统里另一方的到场登记」，列的是具体工单。本模块只读聚合数字，
不读任何一条工单、不列用户名、不列商品名。

**不把「异常多」读成「用户爱找茬」。** 异常是站内唯一一条直指线下安全的申诉，用得多
可能说明用户信任这条通道。本模块只报形状，不做人物评价。

## 交付之后

运营第一次能回答四个问题：

1. 哪一类异常更容易被驳回——按异常类型拆的驳回率；
2. 被驳回的提交人收到了有理由的驳回吗——按结局拆的处理意见填写率与长度；
3. 是谁在报谁、两侧的驳回率差多少——提交方向分布（只报数字，不判谁更常被驳）；
4. 这条通道是应急用的还是常规用的——提交人的分布形状。

`MeetingIncident` 从一条「只有计数和时效」的队列，变成一条**质量可读**的治理队列。它和
`dispute_resolution_quality`、`report_resolution_quality` 并排放在看板上，站内三条用户
申诉通道第一次用同一套口径被读。
