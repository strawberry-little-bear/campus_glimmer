# 贡献里程碑事件覆盖审计设计

## 1. 背景

贡献等级与徽章现在已经有了 `ContributionMilestoneEvent` 事实台账：在线写入在贡献创建后记录首次跨越，历史数据按 `occurred_at`、`id` 稳定重放。下一步如果直接做跨周期达成节奏对比，前提是先知道这张台账和贡献流水能不能对上。

因此这一轮只做覆盖审计，不做跨周期方向：

> 每一条应该发生的首次跨越，台账里有没有？台账里的每一行，能不能指回同一条真实贡献？

面板只读，不补事件、不删事件、不重跑迁移、不触发任何用户可见产品动作。

## 2. 对账口径

审计分两层，避免把「规则演进」和「数据坏了」混成一个问题。

### 2.1 事实行一致性

逐行读取既有里程碑事件，只核对可以由当前行和它指向的贡献直接证明的事实：

- 事件用户与触发贡献用户一致；
- `reached_at` 等于触发贡献的 `occurred_at`；
- `previous_value < threshold <= reached_value` 仍成立；
- 事件保存的门槛、跨越前后指标与按贡献流水稳定重放得到的该次跨越一致。

这些字段是台账自身的承诺。任何一处不一致都单列为「事实不一致」，需要人工核对，不自动修复。

### 2.2 覆盖一致性

把全部 `CommunityContribution` 按用户、`occurred_at`、`id` 稳定重放，得到当前规则下的应有里程碑集合。事件主键是：

`用户 + milestone_type + milestone_code`

应有集合与实际集合比较后分三类：

- **已覆盖**：应有且已有；
- **缺失**：应有但没有，只能报数量与所在里程碑，不输出用户；
- **多余**：有但当前重放没有，只能报数量与所在里程碑，不输出用户。

如果已覆盖事件的门槛或标题与当前规则不同，单列为「规则快照差异」。它说明事件保存的是达成当时的规则解释，当前产品规则已经改变；这不是自动修复项，更不能因此改历史事件。

## 3. 报告形状

- 顶部给总事件数、覆盖用户数、回填事件数、在线事件数、缺失数、多余数和事实不一致数；
- 按里程碑类型汇总等级与徽章的覆盖情况；
- 按 `milestone_code` 列出应有、已有、缺失、多余、回填与在线数量；
- 单独给出规则快照差异和触发贡献归属不一致、时间不一致的行数；
- 空贡献流水与空事件表各自说明，不把「没有事实」伪装成「覆盖率为 0」；
- 不按统计周期过滤，因为台账审计问的是全量事实是否对齐，周期切分属于后续达成节奏分析。

## 4. 隐私与解读边界

- 不输出用户名、贡献标题、描述或来源幂等键；
- 缺失和多余只聚合到里程碑代码，不做个人清单；
- 在线与回填只说明写入来源，不用「回填多」判断运营效果；
- 覆盖不完整时不给等级或徽章的方向性结论；
- 面板不发通知、不补事件、不重建迁移、不改贡献流水，也不触发庆祝、弹窗或额外积分。

## 5. 测试与验收

- 完整在线流水得到 100% 覆盖，并能区分回填与在线事件；
- 删除一条事件后只增加对应缺失计数；
- 构造当前重放不存在的事件后只增加多余计数；
- 修改事件指向、达成时间或跨越前后指标后进入事实不一致，不与缺失、多余混算；
- 门槛或标题快照差异单列，不改变覆盖计数；
- 页面与 CSV 导出使用同一构建器，均不暴露用户级信息；
- 不修改贡献流水和事件表。
