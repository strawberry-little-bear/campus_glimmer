# 专题摘要的形状 · 设计说明

`listings/campaign_digest_shape.py`。这个模块读的是用户在专题页亲手拨的两个开关，和这两个开关驱动出来的缓冲池。它只报告：不加迁移、不加字段、不改频率选项、不改发送边界、不取消任何命中、不补发任何摘要、不按频率做任何自动处置。

## 为什么要有这个模块

专题关注提醒这条链路早就通了：`CampaignRegistration.notify_updates` 和 `update_frequency` 是用户的两个开关，`campaign_updates.py` 里的 `queue_campaign_update_matches` 入队、`send_campaign_update_digest` 送达或取消、`set_campaign_update_preference` 在关闭订阅时批量取消。写入路径完整、有测试、有幂等约束。

但读者只有 `campaign_analytics` 汇总里的三个原始计数：当前摘要订阅、待发送命中、周期摘要。三个数回答不了运营真正要问的事：

- **有多少人真的开着摘要。** 加入专题和订阅摘要是两次独立同意，报名数永远大于订阅数。这两个数之间的落差、每日与每周各自的落差，此前没有任何一张表读过。
- **缓冲池的条目都去了哪里。** 入队之后只有三种结局：送达、取消、还挂着。`CampaignUpdateMatch.cancelled_at` 有三条写入路径（退出订阅、专题结束、商品不可投递），读者数为零——这些条目一条都没被数过。
- **摘要到底快不快。** 每日摘要的周期是一天，每周是七天。缓冲三天的条目在每周那一档是提前送达，在每日那一档是拖了三倍。绝对等待时长分不清这件事，必须除以各自频率的周期。

## 四节口径

### 一、从加入到订阅

此刻的快照，**不按统计窗口切**。参与中的报名是分母，其中开启摘要的是分子，订阅率问的是「还在参与的人里多少人开着摘要」。

- **已退出的报名单列，不进分母。** 把已退出的人并进分母只会把订阅率稀释掉，而他们本来就已经用「退出」投过一次票了。
- **加入和订阅是两次独立同意**，两个数的落差就是这条链路的第一个漏点。
- 「全局偏好关着」「没有偏好行」「此刻免打扰」是三件不同的事，分开三列：前者是发送端第一道门拦下的，中者发送端会补一行默认开启的所以照样送达，后者只压顶部角标、不挡摘要入库。
- 频率取值落在 `daily` / `weekly` 之外的单独一行，只在真有的时候出现，不静默并进任何一档。

### 二、缓冲池的三种结局

窗口按 `matched_at` 切，不按 `notified_at` 切：要数的是「这段时间里入队的条目分别去了哪里」，而「什么时候送到」是第三节的事。

- 四列互斥：入队 = 已送达 + 已取消 + 仍未送达。
- **取消只数从未送达的那些。** 送达过又取消的条目结局已经定了，再算一次取消会让两列都虚高。
- 「仍未送达」只数窗口内入队的那些；第四节数的是此刻全部挂着的，两个数不一样，面板上必须写明。
- 库里只写 `cancelled_at`，**没有取消原因字段**，所以「为什么取消」不知道，这里不编。
- 频率取报名行**当前**的值，不是入队那一刻的值：`CampaignUpdateMatch` 自己没有频率字段，一个把每日改成每周的用户会把老条目带到每周那一行去。这是数据模型决定的，面板上必须写明。

### 三、从入队到送达，相对各自频率的周期

只收 `notified_at` 非空的条目。分档按「等待时长 ÷ 该频率自己的周期」的倍数切，不按绝对时长切。

四档互斥、左闭右开、全列，包括 0 样本档：

| 档位 | 倍数 | 说明 |
| --- | --- | --- |
| 周期内 | ≤ 1 | 在自己那一档的周期里送达 |
| 一到两倍 | ≤ 2 | 超过一个周期，但还在两个周期以内 |
| 两到四倍 | ≤ 4 | 已经拖到两个周期以上 |
| 超过四倍 | 其余 | 拖过四个周期，这一档的合并已经没有节奏可言 |

- **恰好等于一个周期算「周期内」。** 踩着周期线送达的那一条是准点的，把它推到下一档会让「周期内」这一列系统性少算一条，而那一列正是本节唯一要报的数。
- 表外频率没有周期，除不出倍数来，两个档位都报空，**不把整组扫进「已超周期」**——那是拿一个不存在的分母下结论。
- 等待时长在导出里按秒报，页面上换算成最贴近的单位。中位与 P90 比均值更要紧：一个被单条死条目拖偏的均值会让人以为整档都慢。
- 一档的已送达样本不足 `MIN_SAMPLE`（12）条时打「只作参考」标，几十条上几个百分点的差距是噪声。

### 四、当前仍挂着的

右删失样本，**此刻全量快照，不看窗口**：所有仍未送达且未取消的命中，含窗口之前入队的。

- 「其中仍可投递」用发送端自己的边界函数 `_eligible_item` 复算，不另写一份条件：报名仍活跃、订阅仍开着、专题仍在进行、商品仍归属该专题且当前可售。两份条件一旦漂移，这个数就会从「还能送」悄悄变成「送不出去」。
- 仍可投递不足全部的那部分是审计尚未扫到的死条目，会由下一轮发送的兜底取消处理，本模块不代劳。
- 「周期内 / 已超周期」按该频率的周期切，表外频率没有周期，两列报空。
- 最老一条已等待按秒、分、时、天报。这个模块报的是一天到一周尺度的量，报「平均等待 259200 秒」会让运营以为这是秒级流程。

## 隐私与只读边界

- 不输出用户名、商品标题、订单号或任何名单，不按用户排名。
- 不读 `bio` 一类的自由文本，不读取消原因（库里也没有这个字段）。
- 不写任何表。第三节和第四节都只做聚合和算术。
- 摘要阅读率已由 `campaign_analytics` 报，本模块不重复：那边报的是触达，这里报的是节奏。

## 面板与导出的同构

`operations_dashboard_export` 里「专题摘要的形状」一节与模板面板逐节对应：四个 `<h3>` 子标题在两边逐字相同，每张面板表格在导出里都有一张认得出表头的表。键值摘要行只挂在显式的口径子标题底下。导出的列名可以比面板宽（面板的列名要塞进窄卡片），但不会更窄。
