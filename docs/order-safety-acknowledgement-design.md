# 交易安全卡双方确认的设计

## 起点

订单页已经有「交易安全卡」：它会提醒商品缺少图片、价格明显低于同类、交付地点不是公共区域、预约尚未双方确认等信息。安全卡只基于当前订单状态即时计算，页面刷新后仍然能看到，但系统没有记录双方是否读过并确认过这些提醒。

这带来两个问题：

- 用户侧：一方说自己看过安全提醒，另一方和平台都无法核对。
- 运营侧：如果线下交付出现问题，争议处理人只能推断双方可能看过订单页，不能知道安全卡在交易前处于什么状态、哪一方确认过。

## 目标

给交易安全卡增加一个轻量的双方确认闭环：

1. 买家和卖家可以分别确认当前安全卡；
2. 确认记录绑定安全卡当时的信号集合；
3. 交付地点、预约状态、商品图片等关键信号变化后，旧确认不再被当成当前确认；
4. 历史确认保留，方便争议处理时回看；
5. 确认只作提醒和审计，不阻断订单，也不自动改变订单状态。

## 需求口径

### 1. 每个角色一条当前确认

新增订单安全确认记录，按「订单 + 角色 + 安全卡指纹」唯一：

- 角色只有买家和卖家，不用自由用户外键，避免把无关用户写进交易确认；
- 安全卡指纹由当前提醒标题和行动建议生成，同一张安全卡重复确认不产生新记录；
- 商品图片、预约、交付地点等状态变化导致信号集合变化时，指纹变化，双方需要重新确认；
- 数值型说明的变化不触发重新确认，例如同类均价从 47% 变为 48%，因为用户需要执行的行动没有变化。

### 2. 确认动作必须幂等且并发安全

- 只有订单买家或卖家可以确认；
- 只有 `pending`、`confirmed`、`meeting` 状态允许确认，交易完成、取消、借用中或归还后不再补确认；
- 请求必须使用 POST；
- 服务端在事务中锁定订单并重新校验状态；
- 同一角色、同一指纹重复提交只保留一条记录；
- 不写订单状态事件，避免把“看过安全提醒”伪装成订单业务状态变化。

### 3. 页面展示当前口径

订单安全卡展示：

- 买家是否已确认当前安全卡；
- 卖家是否已确认当前安全卡；
- 当前用户可确认时提供确认按钮；
- 双方都确认后显示完成状态。

页面只显示当前指纹下的确认，不把历史确认混入当前状态。

### 4. 不制造通知噪音

确认安全卡是用户自己的风险认知动作，不是对方的待办：

- 不给对方发送站内通知；
- 不生成运营告警；
- 对方打开订单页时自然能看到确认状态；
- 确认按钮不暗示平台已担保交易安全。

### 5. 隐私与边界

- 只记录角色、指纹和确认时间，不记录 IP、User-Agent 或设备信息；
- 不把确认记录用于用户信誉、排名或自动风控判定；
- 不阻止双方继续交易；
- 争议处理时只作为“当时看到过哪组提醒并确认过”的审计证据，不替代双方举证。

## 验收

- 买家确认后，订单页显示买家已确认、卖家未确认；
- 卖家确认同一张安全卡后，显示双方已确认；
- 同一角色重复确认不生成重复记录；
- 安全卡信号集合变化后，旧确认不再显示为当前确认，允许并要求重新确认；
- 无关用户、已完结订单和 GET 请求不能写入确认；
- 迁移检查与相关测试通过。
