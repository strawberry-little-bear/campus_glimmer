# 通知中心批量稍后处理与恢复

## 起点

通知中心已经支持按类型、状态和关键词筛选，支持逐条标记已读、勾选批量已读，也支持把
单条未读通知延后 2 小时、24 小时或 3 天。延后期间它不会占用顶部未读角标，到期后
`actionable_unread_q` 会让它重新回到待处理列表。

但当前操作粒度只有两个极端：

- 一条一条点“延后处理”；
- 对全部或所选通知直接标记已读。

当用户一次性收到多条同类提醒时，批量已读会永久消掉提醒，逐条延后又太慢。已延后列表
目前也只有查看，没有“恢复到现在”的入口，用户误点延后或临时改变安排时，只能等待到期，
或者直接标记已读。这个迭代补齐这两段操作。

## 用户问题

用户打开通知中心时，面对的是三种不同意图：

1. **现在能处理**：进入详情，处理后再让系统按既有规则标记已读；
2. **今天不想做，但不想丢**：把一组通知统一延后；
3. **原计划以后处理，现在提前有空**：把已延后的通知恢复为当前未读。

第三种尤其重要。延后不是删除，也不是已读；用户应该能撤销自己的时间安排。

## 本轮范围

新增两个 POST 动作：

- **批量稍后处理**：把所选“当前可处理且未读”的通知统一延后 2 小时、24 小时或 3 天；
- **批量恢复**：把所选“仍在延后中的未读通知”恢复为当前可处理状态。

同时调整通知中心工具栏：

- 选中状态跨多个批量按钮共用；
- 当前页可勾选未读通知并选择延后时长；
- 在“仅看已延后”筛选下提供“恢复所选”；
- 操作结果用消息条明确报告成功数和因状态变化跳过的数量；
- 按钮文案和禁用状态继续由同一段轻量 JavaScript 管理，不引入前端依赖。

## 状态语义

### 可批量延后

只有满足以下条件的通知会被更新：

```text
recipient = 当前用户
is_read = false
snoozed_until is null OR snoozed_until <= now
```

一次性写入同一个 `now + duration`。已经在未来延后中的记录不会被覆盖，避免“批量延后”
把用户先前的安排无意中推得更远；已读记录也不会被重新变成未读。

### 可批量恢复

只有满足以下条件的通知会被更新：

```text
recipient = 当前用户
is_read = false
snoozed_until > now
```

恢复只把 `snoozed_until` 置空，不修改 `is_read`、`read_at`、创建时间和聚合次数。记录会立刻
重新计入顶部未读角标，用户仍可通过原有入口处理。到期但尚未读的通知本来就可处理，不需要
“恢复”，因此不在此动作的更新集合中。

### 状态漂移

用户打开页面后，通知可能被另一标签页标记已读、延后或恢复。服务端不信任页面里的状态，
每条批量动作都在数据库查询里重新限定当前状态：

- 条件仍满足：更新；
- 条件已变化：跳过，并在反馈里报出跳过数；
- 不属于当前用户或不存在：跳过，不泄露记录是否存在；
- 重复 ID：先去重，再统计；
- 异常输入和非整数 ID：忽略；
- 单次最多处理 200 条有效 ID，既覆盖分页批量操作，也限制恶意请求的查询规模。

## 页面交互

通知中心继续使用一个批量表单，页面上的复选框通过 `form` 属性关联到它。不同按钮使用
`formaction` 指向各自端点，避免复制多份选择状态。

工具栏按当前筛选提供动作：

| 当前视图 | 标记已读 | 批量延后 | 恢复所选 |
| --- | --- | --- | --- |
| 全部 / 仅看未读 | 可用 | 可用 | 不显示 |
| 仅看已延后 | 可用 | 不显示 | 可用 |
| 仅看已读 | 不显示选择列 | 不显示 | 不显示 |

“全选本页”继续只选择当前页可勾选的行，不跨页积累隐藏 ID。操作完成后回到当前筛选 URL，
保留 `kind`、`status`、`q` 和页码解析结果。

## 安全和一致性

- 两个端点都要求登录且只接受 POST，GET 返回 405；
- 所有查询都以 `recipient=request.user` 为硬边界；
- 重定向继续使用项目的站内地址校验，拒绝外部 `next`；
- 延后时长使用固定白名单，非法值不执行更新；
- 使用单条 `UPDATE` 批量写入，不逐条 `save()`，避免一次操作产生 N 次写查询；
- 不新增数据库字段、不新增迁移、不发送通知、不改变通知偏好；
- 批量恢复不等于已读，批量延后也不等于已读，两个动作都不会伪装成“处理完成”。

## 不做什么

- 不做批量恢复“全部到期通知”，没有明确选择就不改状态；
- 不做跨页全选，避免用户以为只处理当前筛选，实际修改了整个收件箱；
- 不把延后自动变成服务端队列或异步任务；到期可见性仍由读取时的 `snoozed_until` 判断；
- 不新增通知类型，不改单条延后的现有三档时长；
- 不把延后次数写回模型，本轮没有新的运营口径需求，避免为了统计而增加写入字段。

## 验收

测试需要覆盖：

1. 批量延后只更新当前用户的、当前可处理的未读通知；
2. 已读、未来已延后、他人和非法 ID 不更新；
3. 三类固定时长都能写入，非法时长不更新；
4. 批量恢复只清空当前用户仍在延后中的未读通知；
5. 恢复后通知重新进入 `active_unread_notifications`；
6. 重复 ID 只计算一次，超过 200 条时只处理前 200 个有效 ID；
7. 外部重定向被替换为通知中心；
8. GET 请求返回 405；
9. 通知中心按筛选渲染对应批量按钮，并保留筛选查询串；
10. 回归单条延后、批量已读、顶部未读统计和通知筛选。

## 落地方式

本轮只修改通知工具函数、通知视图、URL、通知中心模板、样式、测试和文档。设计点先独立
提交；实现完成并通过定向测试、通知相关回归、`manage.py check` 和迁移检查后，再提交功能。
这样页面体验、批量写入和状态口径可以作为一个完整迭代独立回滚。
