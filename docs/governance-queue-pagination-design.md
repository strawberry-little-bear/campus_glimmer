# 举报与争议队列分页设计

## 要解决的问题

商品举报和交易争议原先一次性读取全部记录，再在页面上逐条排序、装饰和渲染。数据量小的时候，这种写法足够直接；进入生产运行后，页面体积、查询结果和模板循环都会随历史记录线性增长，而运营真正需要的只是“当前筛选下最该先看的一页”。

本迭代把两条人工治理队列改为服务端分页，并把举报的既有优先级口径完整下沉到数据库排序。它不改变举报或争议的状态流，不增加自动处置，也不把统计写入业务表。

## 商品举报队列

### 每页 10 条，优先级在 SQL 中排序

举报卡片包含原因、补充说明、商品状态、优先级信号和处理入口，10 条足以保留值班上下文。`rank_report_queryset()` 使用 `Case / When`、相关子查询和聚合生成排序字段，数据库只返回当前页；`build_report_rows()` 只装饰当前页记录，不再把完整积压加载进 Python。

数据库排序与 `build_report_priority()` 的人工规则保持一一对应：

1. 待审核、审核中的举报排在已处理、已驳回之前；
2. 同一状态组内按“优先处理、较高关注、常规处理”排序；
3. 同档按 `created_at` 倒序，再以 `pk` 倒序保证结果稳定；
4. 疑似诈骗且商品仍曝光为最高档；诈骗已下架、不当内容仍曝光、同一商品至少两条开放举报为较高档；
5. 商品是否曝光以 `available` 和 `expires_at > 当前时间` 为准。

“同一商品开放举报数”通过子查询统计，只输出数量，不读取或展示举报人身份。优先级字段只存在于查询注解中，不落库、不回填历史。

### 全量统计不随筛选和页码变化

页面顶部的优先处理、较高关注、常规处理和待处理总数，只统计全量开放举报。即使正在查看“已解决”或第 2 页，这些数字仍代表此刻整个开放积压，避免运营把筛选后的局部数字误读为总体压力。

分页区域显示当前记录区间与筛选后的总数；只有一页时隐藏分页。非法页码回到第一页，超出总页数时收敛到末页。有效状态筛选会写入翻页链接，并在页码变化时继续生效。

## 交易争议队列

### 每页 12 条，固定处理顺序

争议卡片需要同时展示订单、双方、原因、说明和处理入口，因此每页取 12 条。排序由明确的队列层级决定：

1. `open` 待处理；
2. `reviewing` 处理中；
3. 已解决与已驳回；
4. 同状态内按 `created_at`、`pk` 倒序。

关闭状态使用同一层级而不是依赖状态字母序，保证 `rejected` 不会因为字典顺序被排到 `resolved` 前面。页面提供全部、待处理、处理中、已解决和已驳回筛选，翻页时保留有效状态参数。

### 待处理总数始终按全量计算

争议页顶部“待处理或处理中”的总数始终由 `open + reviewing` 全量记录计算，不受当前状态筛选和页码影响。列表区间和结果总数则描述当前筛选，两者使用不同标签，避免把“当前页数量”“筛选结果”和“全量待办”混成一个数。

## 只读边界

- 不自动确认举报、不自动下架商品、不自动改判争议；
- 不更改举报、订单或争议的状态机与权限；
- 不新增模型字段、迁移或历史回填；
- 不在分页统计中读取举报说明、争议说明或用户隐私；
- 新记录插入可能让动态队列的后续页内容移动，这是“按当前风险排序”的预期行为。

## 验证

自动化测试覆盖：

- SQL 优先级与可解释 Python 规则一致；
- 开放举报先于关闭举报，跨页顺序稳定；
- 举报每页 10 条、争议每页 12 条；
- 全量待办统计不受状态筛选和页码影响；
- 状态筛选在翻页链接中保留；
- 非法与越界页码安全收敛；
- 单页隐藏分页条；
- 非工作人员访问返回 `403`。
