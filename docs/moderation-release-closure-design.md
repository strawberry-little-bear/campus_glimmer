# 内容审核误判放行的闭环设计

## 起点

内容审核队列已经能拦截留言和私信，也能由运营人员把一条命中规则的内容标记为「误判放行」。但这个词现在只描述审核结论，不描述业务结果：

- 留言被拦截时没有创建 `Comment`，复核为误判后也不会补创建；
- 私信被拦截时没有创建 `PrivateMessage`，复核为误判后同样不会补发送；
- 审核记录里甚至没有保存私信接收人，事后想补发送也不知道该发给谁。

也就是说，运营按下「误判放行」后，作者收到一条写着「内容已放行」的通知，内容本身却永远消失了。这既伤害用户，也让审核数据失去公信力：`dismissed` 是队列里的终态，却不是业务上的恢复。

## 目标

把「误判放行」从一个人工标签补成一条可审计的业务闭环：运营判定误判后，内容按原渠道恢复发布，恢复动作和审核结论同事务落库，队列能看出每条 `dismissed` 记录到底有没有真的放行。

## 需求口径

### 1. 拦截时就保存足够的恢复材料

- 商品留言：继续保存 `author` 与 `item`，二者足以恢复一条 `Comment`。
- 私信：新增可空的 `receiver` 外键，两条私信写入路径在创建审核记录时都写入接收人。
- 审核内容必须完整保存，不能先截断再放行；否则「放行」出来的内容不是用户原本提交的内容。

历史审核记录没有 `receiver`，不猜测、不回填、不自动补发。它们在队列里明确显示为缺少恢复材料。

### 2. 误判放行必须恢复原渠道

在同一次事务中：

1. 锁定仍为 `pending` 的审核记录；
2. 写入 `dismissed`、复核人、复核时间；
3. 留言补创建 `Comment`，私信补创建 `PrivateMessage`；
4. 写入 `released_at`，作为「这条内容真的回来了」的审计证据。

`confirmed` 不创建任何内容；仍为 `pending` 或已完结的记录不能被二次处理，因此不会重复发布。

### 3. 恢复后的通知分开发

- 作者仍收到内容审核结果通知；
- 被放行的留言按原路径通知商品卖家；
- 被放行的私信按原路径通知接收人。

作者通知与接收方通知是两件事：前者说明复核结论，后者说明有新内容需要处理。

### 4. 不能恢复的历史数据要显式暴露

缺少作者、商品或私信接收人的 `dismissed` 记录可以保留人工结论，但 `released_at` 必须为空。队列和后台展示这组事实，不用一条「已放行」的文案掩盖。

### 5. 不改变规则判断

本迭代不改四条规则、不改权重、不改风险分档、不自动复核、不自动放行。系统只修复「人工已经判定误判之后，内容没有回来」的闭环。

## 验收

- 命中规则的留言与私信在拦截时保存完整恢复材料；
- 复核为误判后，原内容分别出现在留言表和私信表；
- 私信接收人收到新私信通知，作者收到审核结果通知；
- 确认违规不恢复内容；
- 重复提交复核不会重复发布；
- 历史私信记录缺少接收人时不崩溃、不伪称已放行；
- 迁移检查、内容审核相关测试和全量本地测试通过。
