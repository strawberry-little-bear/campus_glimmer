# 机会流的忽略率，第一次是一个测量的数

状态：已实现（只报告，不改机会流任何写入路径）
模块：`listings/opportunity_dismissal_quality.py`
新增表：`OpportunityImpression`（迁移 `0060_opportunityimpression`）
写入点：`views.opportunity_feed`
面板：`opportunity-dismissal-panel`，同上一块「机会流上被按「不再显示」的机会」

## 1. 来龙去脉

`opportunity_feed.build_opportunity_feed` 是站内唯一一条个性化推荐流：把卖家的
在售商品和活跃的校园求购、失物招领记录做可解释匹配，给出一条带理由的机会流。
用户点「暂不展示」，`views.dismiss_opportunity` 落一行 `OpportunityDismissal`。

`opportunity_dismissal_quality` 上线时报了四组数：规模与结构、按分数档拆的忽略
分布、按理由拆的忽略分布、重复忽略。前两组的分子是忽略、分母也是忽略——那是
忽略自己的形状，不是率。当时的结论写得很硬：**本模块不报忽略率，因为分母不可得。**

分母指的是「被展示过的机会」。`OpportunityDismissal` 只记忽略、不记看过：一条
机会被渲染出来、用户什么也没点，库里一行都没有。机会流页面本身也不产生任何可
反推的记录——「打开过机会流页」不在任何表里，机会卡上的「去响应」按钮指向求购
详情页，那条浏览记录会被算成一次普通商品浏览，无法和机会流区分。

于是有一个很具体的报数方式被明确否掉：用页面构造当分母（「进入机会流页的次数
× 每页候选数」）。那是估算不是测量，而一个估算出来的率会让运营以为自己量过
——那比没有数字更糟。

本轮就是那个「先想清楚值不值得」的结论：值得，而且办法很直接——把「被看见」
这件事本身落库。

## 2. 事实链

写入点只有一处，`views.opportunity_feed`：

```python
feed = build_opportunity_feed(request.user)
_record_opportunity_impressions(request.user, feed['opportunities'])
return render(request, 'listings/opportunity_feed.html', ...)
```

`_record_opportunity_impressions` 把这一屏的机会转成 `OpportunityImpression` 行，
一次 `bulk_create(rows, batch_size=32)`。一屏最多 12 条（`build_opportunity_feed`
的 `limit=12`），所以一次渲染就是一次 round-trip，不随用户名下在售商品数增长。

字段：`user`、`kind`（`demand` / `lost_found`）、`demand`、`lost_found_post`、
`shown_at`（有索引）。`kind` 与 `OpportunityDismissal.KIND_CHOICES` 是同一套，
两条表在口径上是对偶的：一条记「看见了」，一条记「不看了」。

## 3. 口径（四条，逐条都是取舍）

### 3.1 不设 `(user, target)` 唯一约束

`OpportunityDismissal` 上有两个无条件唯一约束 `(user, demand)` 和
`(user, lost_found_post)`，因为忽略该折叠：同一个人第二次按「不再显示」只是把
静默期往后推。**展示不该折叠。** 同一条机会在不同时刻被渲染给同一个人是两次独立
的展示，去重会让分母变小、忽略率虚高。

去重只发生在算「第一次被看见」的那一刻，见 `_first_seen_keys`。

### 3.2 分母只数窗口内第一次被看见的 (用户, 机会) 对

一条机会在窗口外就被看见过、窗口内又被看见，它的分母会被计两次以上，而分子
（忽略行）只可能在窗口内产生一条。分母重复计、分子不重复计，率会虚低。

所以分母只认「这一次是窗口内第一次看见它」。这也顺带回答了「一条机会被展示了
多少次」——那个数单独报，见 `_build_rate_rows` 的 `shown_count`。

### 3.3 分子要求「该机会在窗口内至少被展示过一次」

一条忽略若来自窗口外的展示（用户先看到、过了几天才按按钮），它没有窗口内的分母。
把它算进分子会让率虚高，所以分子规则是「这条忽略对应的机会在窗口内至少被展示过
一次」。见 `_dismissed_keys` 与 `_build_dismissal_rate`。

### 3.4 忽略率仍报下界，只低不高

上面两条已经让率偏低；还有第三种偏低来源：一条机会在窗口内被看见、用户在窗口
内才按按钮，但按钮的动机来自窗口外那次看见。这种情形分子算不到、分母照算。

方向是可接受的，理由说三遍都不亏：**虚高的忽略率会让运营以为机会流在惹恼用户，
虚低只会让人保守。**

空分母报 `None`，不报 0——一周一条都没展示过，忽略率不存在，不是零。

分母门槛 `MIN_IMPRESSIONS = 24`。上一轮唯一敢报的比例是重复忽略占比，门槛挂在
「12 条忽略」上；这一轮门槛改挂在展示上，因为现在分母的量级是展示不是忽略。

## 4. 按分数档的忽略率

分数档这一层是真正的新东西。上一轮只能报「这一档占全部可打分忽略的比例」，那
完全可以由展示结构决定——如果整个平台一周只展示了 20 条机会、高分档本来就少，
高分档忽略少可能只是因为高分档展示得少。有分母之后，「高分档忽略率 8%、低分档
41%」才是一句能拿去改权重的话。

每一行报四个数：

- `shown_count`：这一档在窗口内第一次被看见的次数（分母）；
- `dismissal_count`：其中被忽略的次数（分子）；
- `dismissal_rate`：两者之比，空分母是 `None` 不是 0；
- `repeat_show_count`：这一档里被渲染过不止一次的次数。

`repeat_show_count` 和重复忽略是一对正交读数：一条机会被展示了 5 次只忽略 1 次，
那是用户在忍；展示了 5 次忽略 3 次，那是静默期对该用户无效。上一轮判重复忽略只
能靠 `expires_at - created_at` 的距离，这是第二个读数，两个互相校验。

### 4.1 「今天已匹配不上」这一行

分数算不出来的展示（用户今天已经没有在售商品 / 活跃记录能匹配上）不进任何分数
档。但**它仍然要单独报一行**：它确实被看见过，丢掉会让分母偏小、忽略率虚高。

少了这一行，「被看见了 5 次、但用户今天已经没有在售商品能匹配上」的展示会从分母
里整个消失，而它正是最可能被忽略的那批。它的 `dismissal_rate` 恒为 `None`——没有
分数就无从分档，也无从和一个「应该」的率比较；报的是 `shown_count`。

### 4.2 比的是率，不是占比

`_build_rate_shape` 按 kind 分别比最高与最低分数档的**忽略率**，相差不满
`NOISE_POINTS` 个百分点视为噪声。两个 kind 分开读：求购和失物的分值域不同
（2-11 对 30-100），混在一张表里比等于比两个不同的刻度。

## 5. 看板回答什么

- 窗口内有多少条机会第一次被看见，其中多少条被按了「不再显示」；
- 忽略率是多少，方向明说（下界、只低不高）；
- 按分数档的忽略率，回答「分数高的机会是不是更不容易被忽略」；
- 有多少机会被渲染过不止一次，和重复忽略对照着读；
- 上一轮那四组数一个没少：规模与结构、按分数档的忽略分布、按理由的忽略分布、
  重复忽略。

## 6. 口径汇总

- 渲染路径只多一次 `bulk_create`，不多任何一次 select；
- 没有机会可渲染时一次 insert 都不发；
- 写不进去不致命：页面照常渲染，只是这一次展示进不了分母；
- 不回填历史数据，曝光表自上线起才开始积累，此前周期的忽略率仍是 `None`；
- 分子分母两个方向都只数窗口内产生的行，归期按 `shown_at` / `created_at`；
- 分数在忽略时刻重算，走 `_match_demand` 与 `score_lost_found_posts` 自己；
- 不按用户排名，不判断忽略是否「正确」。

## 7. 不做什么

- **不用页面构造当分母**，不引入「进页次数 × 每页条数」。这条是本模块早期被明确
  否掉的方案，重申一次：估算是估不出来测量该有的样子。
- **不给 `OpportunityImpression` 设 `(user, target)` 唯一约束**，见 3.1。
- **不改静默期，不动任何一行 `expires_at`。**
- **不回填历史数据。** 回填需要伪造 `shown_at`，而伪造出来的分母比没有分母更糟。
- **不把忽略回流成负样本。** `_match_demand` 与 `score_lost_found_posts` 的权重
  一个常数都不动。忽略率是给运营看的读数，不是给匹配器看的训练信号——这条项目里
  的推荐类模块一律如此。
- **不按用户排名**，不报用户名，不判断忽略是否「正确」。用户忽略一条机会可能只是
  「我这周不想卖这个」，本模块没有资格判定。
- **不做曝光去重表。** 「这条机会累计被看见过几次」这种跨周期的问题是另一个模块的
  事，本模块只回答窗口内。

## 8. 先看板后改规则的理由

忽略率一旦可测，紧接着的问题一定是「那要不要改匹配器的权重」。不改的理由是现在
还读不出方向：分母自上线起才开始积累，第一个月的样本大概率够不到
`MIN_IMPRESSIONS`。而虚高的率会推着人去动权重——这正是 3.4 把方向钉成「只低不高」
的原因：让这个数在证据不足时保持保守，比让它吓人更安全。

先看板，是因为「高分档忽略率 8%、低分档 41%」这句话要等分母积累够才说得出口。
在那之前，看板上已经有的按分数档占比、按理由占比、重复忽略，足够运营开始动手了。
