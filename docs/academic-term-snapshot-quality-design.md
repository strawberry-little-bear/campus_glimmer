# 学期阶段统计快照，第一次被运营读到

## 起点

`AcademicTermSnapshot` 是站内最安静的一张表。它从迁移 0052 起就存在，`refresh_academic_term_snapshots` 按学期阶段一行一行往里写，`sync_academic_calendar` 每周由调度器跑一次把它刷出来，admin 里也规规矩矩注册了，`refreshed_at` 还是只读字段。

**但它从头到尾没有任何一条读路径。**

`academic_calendar.build_academic_calendar` 是学期日历唯一的消费方，而它一次都没有读过这张表：它是拿 `AcademicPhase` 的日期区间，在渲染的那一刻实时聚合 `Item`、`DemandPost`、`Order`、`SearchQuery` 得出每个阶段的数字（`_phase_stat_payload`）。全仓库搜 `AcademicTermSnapshot` 只有四处——模型定义、admin 注册、`refresh_academic_term_snapshots` 里的 `update_or_create`，以及测试。模板里连 snapshot 这个词都没有。

也就是说，`refresh_academic_term_snapshots` **每周都在往一张没人看的表里写数**。它每跑一次，数据库就多几条精确到秒的写入，而这份写入的唯一作用是把 `refreshed_at` 往前推。数据是真的，口径是真的，存储是真的，只是从来没有人读过它一眼。

README 的「后台与定时任务」一节写着「建议每学期开始前手工运行一次补齐阶段，之后按周刷新快照即可」。按周刷新，意味着库里本该存着一条清晰的、每周一次的刷新轨迹。既然没人读过，也就没人知道这条轨迹在不在。

## 为什么这是真缺口

站内已有二十多个「量我们自己的功能」的模块，量过搜索排序、求购匹配、首页推荐、机会流负反馈、私信响应、评价质量、争议处理、借用风险、任务运行健康度。它们量的是「平台做了一个判断，这个判断准不准」或「平台给了一个工具，这个工具好不好用」。

这一轮量的是第三种东西：**一个已经存在很久的持久化设施，它到底还在不在工作。**

这是一个和前面几轮都不同的缺口。`sync_academic_calendar` 自己已经接了 `record_task_run`，台账会记下「上次成功是什么时候」，所以「命令有没有跑」这件事是有答案的。但台账答不了另外四个问题：

1. 快照的**内容**对不对？`update_or_create` 的匹配键是 `(term, phase_key, start_date)`，而 `start_date` 是 `AcademicPhase` 算出来的属性（`term.starts_on + start_offset`）。改一次学期开始日期，`start_date` 就整体平移，于是旧行**不会被更新，而是变成孤儿**，同时新键下再插入一批新行。台账只看到「刷新 4 条」，看不到一次平移留下的成倍行数。
2. 有多少快照其实早就**过期**了？一条阶段上学期就结束了，`refreshed_at` 还停在那时——它现在显示的还是那批数。
3. 阶段被删了之后，快照会怎么样？`AcademicTermSnapshot` 没有到 `AcademicPhase` 的外键（只有到 `AcademicTerm` 的），删阶段不会带走任何快照。
4. 这个表既然没人读，那**删掉它**是不是更好的选择？这是本模块要回答的最后一个问题，也是最该问的那一个。

## 最关键的一条事实：这张表的写入是无条件的

本模块所有判据都建立在一条从 Django 源码里查证的事实上，先说清楚。

`refresh_academic_term_snapshots` 走 `AcademicTermSnapshot.objects.update_or_create(...)`。乍看 `refreshed_at` 能不能反映「数据变了」，取决于 `update_or_create` 在值没变时会不会跳过保存——如果会跳过，`refreshed_at` 就是一个干净的「内容上次变化时刻」，判据会强得多。

**它不会跳过。** Django 的 `update_or_create`（`django/db/models/query.py` 第 1002-1014 行）在拿到已存在的对象后，会把 `defaults` 里每个字段 `setattr` 上去，然后构造 `update_fields`；在确认 `update_fields` 全是实体字段之后，**显式地把 `pre_save` 不是默认实现的所有字段补进 `update_fields`**，注释写得很直白：「Add fields which are set on pre_save(), e.g. auto_now fields」，理由是向后兼容。`refreshed_at` 正是 `auto_now=True`。

结论：**每次调用 `update_or_create`，不管十个计数有没有一个发生变化，`refreshed_at` 都会被推进到当下。**

这条事实决定了本模块报什么、不报什么：

- `refreshed_at` 只能回答**「命令上次写到这一行是什么时候」**，回答不了「这一行的内容上次变化是什么时候」。这两个意思差得很远——一条阶段两个月前就结束了、商品再也不会新增，它的十个计数从此再也不变，但每周一次的刷新照样把 `refreshed_at` 推着走，于是它看起来永远「新鲜」。
- 所以本模块**不报「内容陈旧度」**，只报**「刷新陈旧度」**，并且在面板和 docstring 里都把这句话写明。把刷新时间当成内容时间报出去，会让一条早就不会再变的阶段一直显示为刚刚更新——这比没有数字更糟。
- 同理，本模块**不报「数据漂移」**。想看「库里存的快照数」和「现在实时算出来的数」差多少，理论上可以把两者都算一遍再相比，但那是拿一个已知没人读的缓存和实时值比大小，得出的是「这个缓存确实不准」——而它不准的原因恰恰是没人读。报一个没有消费方受害者的偏差，只是在给一个已经没人用的缓存做体检。

## 分母怎么切

四个分母，各自独立，不能混。这是本模块和上一轮心愿单分组最像的地方。

| 分母 | 是什么 | 用来报什么 |
| --- | --- | --- |
| 启用中学期的应有阶段 | `is_active=True` 的学期及其全部 `AcademicPhase` | 快照覆盖率 |
| 快照表实际行数 | `AcademicTermSnapshot` 全表 | 规模、多余行 |
| 快照表的行（按学期分组） | 同一学期下的快照行 | 孤儿阶段、刷新中断 |
| `TaskRun` 里该命令的运行 | 台账里 `sync_academic_calendar` 的行 | 命令是否还在跑 |

「应有」这个词要格外小心，因为它有两层：`refresh_academic_term_snapshots` 遍历的是 `is_active=True` 的学期和它们的全部阶段，所以应有行数 = 启用中的学期数 x 它们的阶段数。但**多余行不属于任何当前阶段**，所以「实际行数 >= 应有行数」是常态，`实际 - 应有` 的那部分就是孤儿和学期停用残留的合计。这个减法本身不区分两者，要分开必须再按匹配键分组——本模块两个都报，且报的是两个不同的数。

**学期停用留下的行不是孤儿。** `AcademicTerm.is_active` 的 help_text 写着「停用后该学期不再参与阶段计算，但历史数据保留」，所以一个已停用学期下面的快照行是**设计如此**的残留，不是故障。把它们算进孤儿会把一条被写死的行为报成异常。孤儿只指：学期还启用着，但这一行的 `(phase_key, start_date)` 在当前阶段集合里找不到对应——那才是匹配键失效的证据。

## 孤儿行：改一次学期开始日期就会成倍留下

这是本模块最具体、最能落地的一个发现，单独说。

`AcademicPhase.start_date` 不是数据库列，是模型上的 `@property`：

```python
@property
def start_date(self):
    return self.term.starts_on + timedelta(days=self.start_offset)
```

而快照的唯一约束是 `UniqueConstraint(fields=['term', 'phase_key', 'start_date'])`。于是：运营把某学期的 `starts_on` 从 9 月 1 日改到 9 月 8 日，四个阶段的 `start_date` 全部平移 7 天，匹配键全部失配。`update_or_create` 找不到旧行，走 create 分支插入四条新行；旧的四条**没有任何东西会去删它们**——`AcademicTermSnapshot` 的外键只到 `AcademicTerm`，删阶段删不掉它们，改学期开始日期也删不掉它们。

台账里这次运行显示「刷新阶段快照 4 条」，和上学期一模一样。而表里从这一刻起是 8 条。

本模块把这类行定义为「孤儿阶段」：它所属的学期还启用着，但它的 `(phase_key, start_date)` 在当前阶段集合里找不到对应。孤儿行本身不可怕，可怕的是它**不报错、不告警、不显眼**，只会安静地让表变大。报出来的目的不是让人去删，而是让人知道这个表的行数不能当口径用。

## 过期快照：一条阶段的数字停在多久以前

一条快照过期不过期，不能只看 `refreshed_at`，因为 `refreshed_at` 每周都在动（见上面那条事实）。真正该问的是：**这个阶段的结束日期已经过去多久了。**

一条阶段上周才结束，`refreshed_at` 是昨天，数字是准的。一条阶段上学期就结束了，`refreshed_at` 也是昨天，数字也是「准的」——但它准在三个月前，之后这条阶段再也不会变。这两种情况在 `refreshed_at` 上完全一样，只有 `end_date` 能分开。

所以过期判据取**「阶段结束日期距今年数」**，门槛 `STALE_PHASE_DAYS`。一条阶段结束超过这个天数，本模块报它为过期。这个判据和 `refreshed_at` 完全无关，因此不受「刷新无条件推进 `refreshed_at`」这条事实的影响——这是它唯一的可用之处。

反过来，**「刷新中断」**才该看 `refreshed_at`：台账里明明有很多次 `sync_academic_calendar` 的成功运行，但某一行快照的 `refreshed_at` 远早于最近一次成功运行，说明这一行没有被刷到——它对应的阶段在最近一次刷新时已经不在启用中的学期里了。这是一个和孤儿行互相印证、但角度不同的信号：孤儿行是「表里有当前不存在的阶段」，刷新中断是「当前存在的阶段没被刷到」。两者都报，都只报告。

## 这个模块不报什么

**不报快照数和实时数的偏差。** 理由见上：一个没人读的缓存和实时值比大小，得出的结论是「这个缓存不准」，而它不准的根源是没人读。要做这个对比，正确做法是先给它一个读路径（让 `build_academic_calendar` 读快照而不是实时算），那是一个功能改动，不是一次度量。

**不报「内容陈旧度」，只报「刷新陈旧度」。** 因为 `refreshed_at` 每周都会被推进，它和内容变化无关。

**不报每个阶段十个计数的业务含义。** 那属于学期日历面板自己的事，本模块只量「这张表健不健康」，不重复发布已经在实时算的数字。

**不因为孤儿行多就建议删表。** 表里有多少多余行、命令还在不在跑，这是事实；这张表该不该存在，取决于「要不要让 `build_academic_calendar` 改读快照」这个还没做的决定。本模块把决定需要的材料摆齐，不替运营做这个决定。

## 这个模块只报告

不刷新任何快照、不删任何孤儿行、不改任何 `AcademicTerm.starts_on`、不删任何 `AcademicPhase`、不动 `refresh_academic_term_snapshots` 的任何逻辑、不改唯一约束、不建新表、不加迁移、不碰 `build_academic_calendar` 的实时计算路径。运营看到孤儿行要去清理，那是下一步的事——本模块只负责让这个表的真实状态第一次被看到。

总结起来，本模块报四块：这张表到底有多大、应有阶段被覆盖了多少、有多少孤儿行和刷新中断的行、命令本身还在不在跑。凡是判据间接的地方，本模块把判据为什么间接写在面板上。
