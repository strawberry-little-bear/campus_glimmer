# 求购响应确认之后，交易如何接上

## 起点

`DemandPost` 是站内唯一一条「反向商品」：一个学生写清楚自己要什么、预算多少、在哪个校区等，
`DemandResponse` 是卖家拿自己的一件在售商品去接这条需求。关键写入路径四条，都在 `views.py`：

1. `respond_to_demand`（POST）—— 只有商品发布者本人能响应。响应前会重新跑一次 `_match_demand`，
   分类、地点、预算、关键词四项都过了才允许建行。建行时把 `match_score` 和 `match_reason`
   一起写进去，并发一条站内通知给求购发布者。
2. `review_demand_response`（POST，`accept` / `reject`）—— 只有求购发布者本人。`accept` 写入 `accepted_at`、
   给响应人记一次贡献、把求购改成 `fulfilled`，并把同一条求购下其余 `pending` 的响应改成 `deferred`
   并逐一通知。`deferred` 表示暂时停用；发布者显式拒绝才进入 `rejected`。
3. `reopen_demand_response`（POST）—— 发布者在已确认商品失效时显式重新开放求购，详见下一节。
4. `submit_demand_feedback`（POST）—— 求购发布者对一条 `accepted` 的响应提交 `MutualAidFeedback`，
   一条响应只能提交一次，`outcome` 是 `completed` / `unresolved` 二选一。

`accept` 之后给响应人的通知说明：求购发布者会继续完成预约或领取申请。求购发布者在已确认响应卡片上
直接看到「继续预约」/「继续借用」/「申请领取」，入口携带 `demand_response=<id>`。

## 确认之后怎样接上交易

`create_order` 接受可选的 `demand_response` 查询参数，并在表单里作为隐藏字段继续传递。只有满足
以下条件才放行：

- 当前用户是 `response.demand.requester`，也就是求购发布者；
- 响应状态是 `accepted`；
- 响应的商品与订单入口中的商品一致。

进入写入事务后会再次锁住响应和商品并复验，防止确认状态或可用性在页面打开后变化。出售与借用创建
`Order`；免费赠送创建 `GiftApplication`。两者都保存来源响应。免费商品仍走申请队列，发布者选中
申请人时再把 `GiftApplication.demand_response` 复制到新订单。

同一响应再次打开或提交时，系统先找关联订单，再找关联领取申请：已有订单就回到订单详情，已有待处理
领取申请就回到「我的领取申请」。因此刷新、重复 POST 或两次并发提交不会制造第二笔交易。

响应卡片同时承担状态提示：已创建订单时显示「查看交易」；免费申请尚未选中时显示等待状态；商品已经
不可预约且仍满足重新选择条件时，显示「重新选择响应」入口。状态判断只帮助用户找到下一处，不自动改变
响应、求购或商品状态。

## 为什么需要显式来源

一件商品可以响应两条不同求购，并且两条都可能被各自发布者确认。`UniqueConstraint` 只挡
`(demand, item)`，不能保证一件商品只有一条已确认响应。只看「商品相同 + 同一下单人 + 下单晚于确认」
会让一笔订单同时算作两条响应的转化。

`Order.demand_response` 与 `GiftApplication.demand_response` 是这条关联的事实地基。新订单从入口
带上来的响应写入外键，转化统计只认这个 ID。迁移前没有来源字段的旧订单才回退到三条推断：商品相同、
买家是求购发布者、下单不早于确认时刻。

响应里的 `responder` 是商品卖家，买家是 `response.demand.requester`。这个方向必须固定：把响应人当
买家会把真正的求购发布者下单排除在外，也会把卖家自己对商品的订单误算成转化。

## 确认商品失效后重新选择

已确认只说明双方选中了这次匹配，订单或领取申请仍由求购发布者主动创建。如果页面打开后商品下架、过期、
售出或被另一笔进行中的订单占用，原入口会停止，发布者可能被卡在一条已经没有可用交易的求购里。
`reopen_demand_response` 提供显式恢复路径，只有同时满足以下条件才放行：

- 当前用户是求购发布者，响应是这条求购当前唯一的 `accepted` 记录；
- 求购仍是 `fulfilled` 且未超过截止时间；
- 响应商品当前不可用；
- 这条响应还没有关联 `Order` 或 `GiftApplication`。

事务内会锁住求购、响应和商品并按上述条件复验。成功后，旧响应改为 `superseded` 并写入
`superseded_at`，求购回到 `active`，`reopen_count` 和 `last_reopened_at` 记录这次重新选择。原来的
`deferred` 响应只有商品仍可用时才恢复为 `pending`；`rejected` 和 `withdrawn` 保持原状态，不会被一次
重新开放悄悄翻案。重复提交旧入口会提示已经处理过，不会重复通知或重复增加次数。

重新开放需要发布者明确点击，系统不会因为商品失效自动改状态。已有订单或领取申请时也不允许改选，避免
把已有交易改挂到另一条响应上。

### 重新选择后的响应闭环

`DemandReopenEvent` 是每次显式重新选择的不可变事实记录。它与响应状态变更在同一个事务内写入，保存求购、
被替代响应、原商品标题与交易方式快照、原确认时刻、重新选择时刻、累计重开次数和来源。事件写入失败时，
旧的 `accepted` 响应不会变成 `superseded`，求购也不会重新开放。唯一约束 `(demand, reopen_count_after)`
阻止同一次重开被记两遍，服务端仍以锁住的求购状态完成幂等判断。

运行时事件按 `reopened_at` 切窗，每次重新选择都是独立样本；看板同时报告事件数和受影响求购数，不能用其中
一个替代另一个。一次事件的后续确认只匹配同一求购在事件之后、该求购下一次重开之前的首次有效确认；
确认发生在重开之前，或已经跨过下一次重开边界，都不能倒挂到这一次事件。订单优先于领取申请，领取申请
仍不等于订单转化。

漏斗守恒关系是：`再次确认事件数 = 订单事件数 + 未发起交易入口事件数`。订单再分成已成交、已取消和仍进行中；
没有交易入口的再按领取申请、商品不可交易、求购结束和仍可推进但未发起交易归类。两段时延分别为
「重新选择 → 首次再次确认」和「再次确认 → 最早交易入口」，没有明确时间戳时不补造样本。

迁移会从旧 `superseded` 的 `superseded_at` 兼容重建历史事件，并把来源标成 `backfill`。这些记录用于披露
旧轨迹，不进入精确事件分母、再次确认、订单和时延漏斗。漏斗不推荐响应人、不自动催办、不替发布者选择
领取人，也不根据停在某一步推断任何用户的责任。

趋势只取三个严格相邻、右开的时间窗口：较早为 `[period_start - 2d, period_start - d)`，上一周期为
`[period_start - d, period_start)`，当前周期为 `[period_start, now]`。再次确认率的分母是运行时事件数，
订单转化率的分母是再次确认数；两项各自要求每个周期至少有 12 个分母，不能互相借样本。

两项比例都分别比较较早到上一、上一到当前两段变化。只有连续两次各下降至少 8 个百分点才写入运营提醒与日报；
判断使用未取整比例，当前恢复、只下降一次或任一周期的对应分母不足都不告警。`source=backfill` 只披露数量，
不参与趋势、告警或阶段方向。提醒携带 `ops-reopen-funnel` 锚点，供运营回到面板人工核对，不自动改任何业务状态。

## 五个要回答的问题

1. 确认了求购响应之后，到底有多少真的变成了订单？
2. 从确认到创建交易申请隔了多久？
3. 变成了订单的那些，最后成交了吗？
4. 确认之后没有订单的，是已经发起了免费领取申请，还是响应商品不可用了、求购被关闭了，
   或者仍可推进但完全没有发起交易？
5. 发布者重新选择之后，需求有没有再次确认并接上订单或领取申请；事件数、受影响求购数、阶段和时延
   分别是什么？
6. 确认响应形成订单之后，预约、到场和双方交付确认各走到了哪一步？

## 口径取舍

### 一个订单算不算「这条响应带来的」

新订单有 `demand_response` 时，只拿外键比较。没有来源的旧订单才使用下面三条同时满足的兼容推断：

- 订单的 `item` 等于响应的 `item`；
- 订单的 `buyer` 等于 `response.demand.requester`；
- `Order.created_at` 不早于响应的确认时刻。

显式来源让同一商品上的多条已确认响应可以准确分开。没有来源的旧记录仍可能遇到无法区分的历史重叠，
不把兼容推断伪装成精确关联，也不为了消除不确定性而回填一个平台无法确认的外键。

### 领取申请算不算交易转化

领取申请不算订单转化。`GiftApplication` 只证明求购发布者已经从一条确认响应进入免费领取队列；
真正的订单转化仍只由 `Order` 决定。预览和 CSV 会先展示领取阶段，再展示没有订单的剩余阶段，
避免把“等待卖家选择”误写成“双方都没动”。

`GiftApplication.demand_response` 是领取阶段的显式来源。新记录只按这个外键归属；迁移前没有来源的
旧记录必须同时满足商品相同、申请人是求购发布者、申请不早于确认，才进入兼容推断。同一件商品有多条
兼容确认时，旧申请归到确认时刻离申请最近的一条；一份申请只归一条响应，显式来源优先。

### 订单结局与成交

分母是**窗口内已确认的响应数**，不是求购数、也不是全部响应数。

- 订单结局里 `completed` 和 `returned` 都算成交——借用订单走到 `returned` 是一次完整的闭环。
- `cancelled` 独立一类，不算成交也不算没有订单：它是一次发生在确认之后的真实失败。
- 只报规模，不猜责任。取消可能是卖家反悔、买家反悔，也可能是双方谈崩；订单事件里的 `actor`
  只说明谁按了按钮，不等于谁造成了结果。
- 分母包含 `accepted` 和 `superseded`，排除 `withdrawn`。撤回没有进入发布者的确认决策；
  `superseded` 则是曾进入决策、后来因重新选择留下历史确认，必须继续计入窗口内的确认事实。

### 从确认到交易创建隔了多久

按订单的 `created_at` 减响应的 `accepted_at`。重新选择会刷新 `updated_at` 并写入 `superseded_at`，
但不会覆盖原确认时刻；因此 `accepted_at` 才能稳定回答“这条响应是哪次确认带来的”。迁移前没有
`accepted_at` 的旧记录才回退到 `updated_at`。

- 分档按小时起步（一小时内 / 一到二十四小时 / 一到七天 / 超过七天），不按分钟也不按天起步。
  用户从确认走到表单需要一点时间；同时「当天」这档不应被整日粒度吞掉。
- 只报有订单的响应。没有订单的响应属于领取与阶段表，不进入时延分布。
- 中位数之外报 P90 和平均。平均会被长尾带偏，运营需要同时看到「大多数人多久走完」和「最慢的人拖多久」。

### 确认响应后的预约与交付漏斗

确认响应形成的订单，继续看这条只读漏斗：

```text
已确认响应 → 去重来源订单 → 提出过预约 → 预约已确认
→ 已结束 → 双方到场 → 双方确认交付
```

响应转化漏斗仍以确认响应数为入口分母；到这里以后改用**去重来源订单数**。迁移前的兼容归因可能让多条响应
同时看见一笔旧订单，直接沿用响应数会把一个真实订单在预约和到场里重复计数。没有订单的响应留在转化阶段表，
不进入交付漏斗。

每笔来源订单只落在预约阶段表的一档：

- 订单仍是 `pending` 且没有预约：订单待卖家确认，尚未提出预约；
- 订单处于 `confirmed` / `meeting` / `borrowed` 且没有预约：已进入可预约阶段，尚未提出预约；
- 订单处于 `completed` / `returned` / `cancelled` 且没有预约：订单已结束且无预约记录。这个事实不能反推
  “先取消还是先没约成”，不排先后；
- 已有预约时，按当前状态分为等待确认、对方未接受、已取消、已确认未结束和已确认已结束；未知状态单独披露。

到场只统计 `status=confirmed` 且 `end_at <= now` 的预约，分母是这些已经结束的确认预约，再拆成双方到场、仅买家、
仅卖家、双方都未到场。尚未结束的确认预约作为右删失样本单列，不能提前算进“双方都未到场”。到场不等于交付完成。

交付确认按订单拆成双方已确认、仅买家确认、仅卖家确认、双方尚未确认。只有买卖双方都留下确认时间才计入双方交付
确认；比例以全部去重来源订单为分母，描述当前走到哪一步。单方到场或单方确认不补造另一方缺失的事实，也不把未完成
订单标记为失败或“疑似爽约”。

`MeetingAppointment` 继续保存每个订单的当前安排，供当前阶段漏斗使用；上线后的首次提议、改期、接受、拒绝和订单取消同时写入
不可变的 `MeetingAppointmentEvent`，保存每次提议的时间、地点、发起角色及回应快照。只有从首条 `proposed` 开始的事件链算作完整
历史，可用于精确响应和改期统计；上线前旧预约不回填事件，旧订单备注只作为兼容下界并单列，不与完整链混算。

### 确认之后没有订单，走到了哪一步

分母是确认之后没有订单的响应。按下面顺序判，命中即停：

1. 已有领取申请时，按申请状态归为「等待卖家选择」「未选中」「已撤回」「已选中但缺订单」
   或未知状态。明确的业务事实优先于服务端推断。
2. 没有领取申请，且响应商品已经不可交易（`is_available_now` 为假）——商品下架、卖出、过期，
   或被另一笔进行中的订单占着。
3. 没有领取申请，且求购已经 `closed` / `expired`。这一档只报规模，不给方向：可能是发布者已经找到，
   也可能是忘记回来结束，平台分不清。
4. 以上都不命中，归「商品和求购仍可推进，尚未发起交易」。只有这一类才表示完全没有订单和领取申请。

`fulfilled` 不算第三类，因为 `accept` 当时就会写入它。把它算进来，所有没有后续订单的响应都会落入
「求购不重要了」，真正尚未发起交易的一类会失去意义。

总数始终守恒：`订单转化数 + 没有订单的响应数 = 周期内确认响应数`；没有订单的部分再拆成领取申请、
商品不可交易、求购已结束和尚未发起交易四类。「已选中但缺订单」正常不该出现；单独展示是为了让历史
缺链或写入异常可见，不自动补造订单。

## 规模门槛与隐私

- 窗口内已确认响应少于 12 条时，转化率只报数字不给方向。
- 「有交易」和「没有交易」两组做维度对照时，差值不满 8 个百分点视为噪声。
- `DemandResponse.message` 是自由文本，只报填写率和长度分档，一个字符都不读——里面可能写着电话、
  微信、宿舍号。
- 阶段清单只带商品标题、求购标题、确认时刻和阶段，不输出用户名，也不做个人排名。

## 不做什么

- 不自动建订单，也不自动替免费商品挑选申请人。确认只代表双方选中这次匹配，交易仍由用户主动创建。
- 不因商品失效自动重新选择响应；只有发布者明确提交后，才重新开放求购并恢复仍可交易的暂时停用响应。
- 不催响应人或求购发布者，也不把 `DemandPost.status='fulfilled'` 推迟到订单完成。否则已经选中的
  需求会继续进入机会流，被反复推荐给其他卖家。
- 不为旧记录强行回填来源。兼容推断用于历史统计，不写回业务数据，也不声称精确。
- 不做「疑似放鸽子」检测。确认后没有继续交易可能有多种正常解释，把无法证实的原因变成个人标签会伤害
  校园互助中的信任。
- 不把求购响应和失物招领线索的转化并起来报。两者难度和流程不同，合并会互相稀释。
