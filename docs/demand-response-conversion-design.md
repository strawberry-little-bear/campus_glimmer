# 确认了求购响应之后，交易真的发生了吗

## 起点

`DemandPost` 是站内唯一一条「反向商品」：一个学生写清楚自己要什么、预算多少、在哪个校区等，
`DemandResponse` 是卖家拿自己的一件在售商品去接这条需求。写入路径三条，都在 `views.py`：

1. `respond_to_demand`（POST）—— 只有商品发布者本人能响应。响应前会重新跑一次 `_match_demand`，
   分类、地点、预算、关键词四项都过了才允许建行。建行时把 `match_score` 和 `match_reason`
   一起写进去，并发一条站内通知给求购发布者。
2. `review_demand_response`（POST，`accept` / `reject`）—— 只有求购发布者本人。`accept` 做四件事：
   这条响应改成 `accepted`、`record_demand_response_contribution` 给响应人记一次贡献、
   求购改成 `fulfilled`、同一条求购下其余 `pending` 的响应全部批量改成 `rejected` 并逐一通知。
3. `submit_demand_feedback`（POST）—— 求购发布者对一条 `accepted` 的响应提交 `MutualAidFeedback`，
   一条响应只能提交一次，`outcome` 是 `completed` / `unresolved` 二选一。

`accept` 之后给响应人的通知原文是：「"xxx"已确认使用你的商品"yyy"，请继续进入商品详情完成
预约或领取申请。」

## 为什么这是真缺口

**确认之后没有任何东西把这次确认和一笔订单连起来。**

`Order` 模型里没有一个字段指向 `DemandResponse`，也没有一个字段指向 `DemandPost`。`create_order`
是从商品详情页发起的普通预约：校验 `is_available_now`、校验没有进行中的订单、校验借用/免费的
分支，然后建 `Order`。这条路径上没有任何一处问过「这个买家是不是刚刚确认了某个求购响应」。
从确认到下单，中间全靠用户自己记住、自己摸回商品详情页、自己再走一遍预约。

于是站内现在同时住着两个关于「这条求购成了没有」的说法，而且它们互相不知道：

- `DemandPost.status` 在 `accept` 那一刻就变成了 `fulfilled`。此后这条求购从所有「寻找中」的
  列表里消失，从需求雷达的候选池里消失，从搜索的求购筛选里消失。
- `Order` 那边什么都没有发生。交易可能十分钟后就成了，也可能再也没有发生——卖家卖给了别人、
  买家在详情页看到「已有一笔进行中的交易预约」然后走掉、两个人根本没再说过话。

**`fulfilled` 这个词现在描述的是「有人点了确认」，不是「有人买到了」。** 而全站唯一一个按
`DemandPost.status` 做的漏斗（`analytics.py` 的 `_build_demand_match_insights`）把响应数、
处理数、确认响应数一级一级报下来，到「确认」这一级就是终点了。运营看到的是一个确认率，
看不到确认之后有多少真的变成了订单。确认率高而成交低，说明的是流程断在中段；这两个数现在
分居两处，谁也说不清。

已经存在的两个统计都只摸到了这个缺口的一侧，都没有跨过去：

- `demand_match_quality.py` 回答「平台自己打的匹配分准不准」，拿 `match_score` 和求购发布者的
  接受/拒绝做对照。它不关心接受之后发生了什么。
- `analytics.py` 的互助反馈统计回答「确认之后发布者说这次算不算完成」，但它把求购响应和失物
  招领线索并成一个总数报，而且只有提交了反馈的那些才进得来——**没有提交反馈的那一批，
  恰恰是最可能断在中段的那一批。**

## 四个答不上来的问题

1. 确认了求购响应之后，到底有多少真的变成了订单？这是这个模块存在的首要理由。
2. 从确认到下单隔了多久？确认之后那段路是用户自己摸回去的，走多久完全是用户的事，
   但走多久本身能说明「那段路好不好走」。
3. 变成了订单的那些，最后成交了吗？确认之后下单、下单之后取消，是两种完全不同的失败。
4. 确认之后没有订单的，是响应人那边出了问题（商品下架了、被买走了），还是求购这边出了问题
   （求购其实已经不需要了）？

## 口径取舍

### 一个订单算不算「这条响应带来的」

没有任何外键，只能用字段比对回推：订单的 `item` 等于响应的 `item`、订单的 `buyer` 等于响应的
`responder`、订单的 `created_at` 不早于响应的确认时刻。三条同时满足才算。

- **商品相同是硬条件。** 一件商品只能有一条 `accepted` 响应吗？不能，`UniqueConstraint` 只挡
  `(demand, item)`。同一个人可以拿同一件商品响应两条求购，两条都被确认（不同发布者），于是
  一件商品上可能挂着两条已确认响应。这时「同一件商品 + 同一个买家」会同时命中两条响应。
- **解决办法是按响应逐条判定，不按订单归属。** 一条响应只要能找到满足条件的订单就算转化，
  一条订单可以同时算作两条响应的转化。这个口径会让「转化响应数」和「有订单的响应数」在
  极少数重叠场景下不一致，**宁可重复计数也不假装能分清**：把两笔说不清的成交硬派给其中一条，
  会让另一条的转化率凭空变成零，而它是真的转化了。
- 反过来，**不能用 `Order.buyer` 之外的东西近似**。`Order` 没有 `demand` 字段，将来加了也要等
  数据积累，现在补不了历史。

### 成交看什么状态

`Order.status` 里 `completed` 是交易完成，`returned` 是借用归还。借用订单走到 `returned`
是一次完整的闭环，和 `completed` 等价。**`cancelled` 单独一类，不算成交也不算未成交之外的事**
——它是一次真的失败，而且失败在确认之后，比「没有订单」更值得被看见。

只报规模不猜原因：取消可能是卖家反悔、可能是买家反悔、可能是两个人谈崩了。订单事件时间线里
有 `actor`，但一次取消的 `actor` 是操作按钮的那个人，不等于「谁造成的」，这个判断平台做不了。

### 转化率的分母

分母是**已确认的响应数**，不是求购数、不是响应数。

- 一条求购被确认过一次就 `fulfilled`，之后再也不会有第二条被确认（`respond_to_demand` 直接
  挡掉非 `active` 的求购）。所以「求购数」在确认率那一层就已经收敛了，用它当分母等于把每个
  求购强制折算成一次转化，看不出批量放弃。
- 分母里**排除 `withdrawn` 的响应**。撤回是响应人自己撤的，它没有进入过发布者的决策，
  既不是转化也不是流失，把它算进任何一边都会让分母说一件没发生的事。
- 已确认的响应按 `demand` 聚合去重之后再报一次「多少条求购真的成交了」：同一条求购只会确认
  一条，所以这两个数在正常情况下相等，不相等就说明有并发确认，那本身就是要看见的信号。

### 从确认到下单隔了多久

按 `Order.created_at` 减响应的 `updated_at`。`accept` 分支 `save(update_fields=[... 'updated_at'])`
带的 `auto_now`，所以 `updated_at` 就是确认时刻，**不需要另建字段**。

- 分档按小时起步（一小时内 / 一到二十四小时 / 一到七天 / 超过七天），不按分钟：确认之后那段路
  是用户自己走的，分钟级的抖动没有运营含义。**也不按天起步**：确认当天就下单和隔天下单是两件
  不同的事，按天起步会把「当天」这档撑得很大，而这档恰恰是最该被单独看见的。
- 只报有订单的那些。没有订单的响应谈不上「隔了多久」，它是另一张表。
- 中位数之外报 P90 和平均。平均数在长尾上会被一条隔了三周的订单带偏，运营要看的是
  「绝大多数人多久走完那段路」。

### 确认之后没有订单的，卡在哪

这是本模块唯一一张清单，也是唯一一处要读业务字段做判断的地方。按下面顺序判，命中即停：

1. 响应商品已经不可交易（`is_available_now` 为假）—— 响应人这边出了问题。商品下架、卖出、
   过期，或者被另一笔进行中的订单占着。这是最干净的一类：卖家侧有动作，而且动作可查。
2. 求购那边已经不重要了。`DemandPost.status` 是 `closed` / `expired`。**这一档只报规模，
   不给方向**——一条关闭了的求购对应的未成交响应，可能是发布者自己找到了，也可能是他忘了
   回来关，平台分不清。`fulfilled` 不算这一类：它是 `accept` 当场写的，人人如此，把它算进来
   会让每一条未成交的响应都落进「求购那边已经不重要了」，而第三类「还在路上」一条都数不到。
3. 以上都不命中，归「还在路上」。这一类是真正要运营看一眼的：商品在、求购在、两边都没动，
   那次确认就这样悬着。

### 不做什么

- 不自动建订单、不自动跳转、不改 `accept` 之后的任何通知文案。
  自动建订单会发明一次双方都没有点过「确认」的交易，那是这套系统最不该有的东西。
- 不催响应人下单、不催求购发布者回来收尾、不改 `DemandPost.status` 的写入时机。
  把 `fulfilled` 改成等订单完成再写，会让这条求购在成交前一直占着需求雷达的候选池，
  把「已经解决的需求」反复推荐给卖家。
- 不按用户聚合、不排名、不报任何人的用户名。清单里出现的是商品标题和求购标题，
  不是「谁答应了没做到」。
- 不做「疑似放鸽子」检测。一次确认之后没有订单，在校园场景里有太多种正常解释：
  卖家反悔了不好意思说、买家自己找到了、两个人线下一句话就解决了。平台没有能力把这些和
  真的放鸽子分开，把它做成一个标签会直接毁掉这条本来建立在信任上的链路。
- 不把求购响应和失物招领线索的转化并起来报。两者难度天差地别，合并会互相稀释。

## 规模门槛与噪声线

- 已确认响应少于 12 条时，转化率只报数字不给方向。十二条上一个转化是八个百分点，
  和抛硬币差不多。
- 「有订单」和「没有订单」两组的某维度对比（如是否带说明文字）差值不满 8 个百分点视为噪声，
  同互助反馈补充说明的既有口径。
- `DemandResponse.message` 是自由文本，只报填写率和长度分档，一个字符都不读——里面可能写着
  电话、微信、宿舍号。
