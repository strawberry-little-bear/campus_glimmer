# 求购响应确认之后，交易如何接上

## 起点

`DemandPost` 是站内唯一一条「反向商品」：一个学生写清楚自己要什么、预算多少、在哪个校区等，
`DemandResponse` 是卖家拿自己的一件在售商品去接这条需求。写入路径三条，都在 `views.py`：

1. `respond_to_demand`（POST）—— 只有商品发布者本人能响应。响应前会重新跑一次 `_match_demand`，
   分类、地点、预算、关键词四项都过了才允许建行。建行时把 `match_score` 和 `match_reason`
   一起写进去，并发一条站内通知给求购发布者。
2. `review_demand_response`（POST，`accept` / `reject`）—— 只有求购发布者本人。`accept` 做四件事：
   这条响应改成 `accepted`、`record_demand_response_contribution` 给响应人记一次贡献、
   求购改成 `fulfilled`、同一条求购下其余 `pending` 的响应全部批量改成 `rejected` 并逐一通知。
3. `submit_demand_feedback`（POST）—— 求购发布者对一条 `accepted` 的响应提交 `MutualAidFeedback`，
   一条响应只能提交一次，`outcome` 是 `completed` / `unresolved` 二选一。

`accept` 之后给响应人的通知说明：求购发布者会继续完成预约或领取申请。求购发布者在已确认响应卡片上
直接看到「继续预约」/「继续借用」/「申请领取」，入口携带 `demand_response=<id>`。

## 确认之后怎样接上交易

`create_order` 接受可选的 `demand_response` 查询参数，并在表单里作为隐藏字段继续传递。只有满足
以下条件才放行：

- 当前用户是 `response.demand.requester`，也就是求购发布者；
- 响应状态是 `accepted`；
- 响应的商品与订单入口中的商品一致。

进入写入事务后会再次锁住响应和商品并复验，防止确认状态或可用性在页面打开后变化。出售与借用创建
`Order`；免费赠送创建 `GiftApplication`。两者都保存来源响应。免费商品仍走申请队列，发布者选中
申请人时再把 `GiftApplication.demand_response` 复制到新订单。

同一响应再次打开或提交时，系统先找关联订单，再找关联领取申请：已有订单就回到订单详情，已有待处理
领取申请就回到「我的领取申请」。因此刷新、重复 POST 或两次并发提交不会制造第二笔交易。

响应卡片同时承担状态提示：已创建订单时显示「查看交易」；免费申请尚未选中时显示等待状态；商品已经
不可预约时不再给出继续入口。状态判断只帮助用户找到下一处，不自动改变响应、求购或商品状态。

## 为什么需要显式来源

一件商品可以响应两条不同求购，并且两条都可能被各自发布者确认。`UniqueConstraint` 只挡
`(demand, item)`，不能保证一件商品只有一条已确认响应。只看「商品相同 + 同一下单人 + 下单晚于确认」
会让一笔订单同时算作两条响应的转化。

`Order.demand_response` 与 `GiftApplication.demand_response` 是这条关联的事实地基。新订单从入口
带上来的响应写入外键，转化统计只认这个 ID。迁移前没有来源字段的旧订单才回退到三条推断：商品相同、
买家是求购发布者、下单不早于确认时刻。

响应里的 `responder` 是商品卖家，买家是 `response.demand.requester`。这个方向必须固定：把响应人当
买家会把真正的求购发布者下单排除在外，也会把卖家自己对商品的订单误算成转化。

## 四个要回答的问题

1. 确认了求购响应之后，到底有多少真的变成了订单？
2. 从确认到创建交易申请隔了多久？
3. 变成了订单的那些，最后成交了吗？
4. 确认之后没有订单的，是响应商品不可用了，求购被关闭了，还是两边都还在但没有继续？

## 口径取舍

### 一个订单算不算「这条响应带来的」

新订单有 `demand_response` 时，只拿外键比较。没有来源的旧订单才使用下面三条同时满足的兼容推断：

- 订单的 `item` 等于响应的 `item`；
- 订单的 `buyer` 等于 `response.demand.requester`；
- `Order.created_at` 不早于响应的确认时刻。

显式来源让同一商品上的多条已确认响应可以准确分开。没有来源的旧记录仍可能遇到无法区分的历史重叠，
不把兼容推断伪装成精确关联，也不为了消除不确定性而回填一个平台无法确认的外键。

### 订单结局与成交

分母是**窗口内已确认的响应数**，不是求购数、也不是全部响应数。

- 订单结局里 `completed` 和 `returned` 都算成交——借用订单走到 `returned` 是一次完整的闭环。
- `cancelled` 独立一类，不算成交也不算没有订单：它是一次发生在确认之后的真实失败。
- 只报规模，不猜责任。取消可能是卖家反悔、买家反悔，也可能是双方谈崩；订单事件里的 `actor`
  只说明谁按了按钮，不等于谁造成了结果。
- 分母里排除 `withdrawn` 的响应。撤回没有进入发布者的确认决策，把它算进任何一边都会让分母
  说一件没发生的事。

### 从确认到交易创建隔了多久

按订单的 `created_at` 减响应的 `updated_at`。`accept` 分支用 `save(update_fields=[... 'updated_at'])`
触发 `auto_now`，所以 `updated_at` 就是确认时刻，不需要另建字段。

- 分档按小时起步（一小时内 / 一到二十四小时 / 一到七天 / 超过七天），不按分钟也不按天起步。
  用户从确认走到表单需要一点时间；同时「当天」这档不应被整日粒度吞掉。
- 只报有交易的响应。没有交易的响应属于卡点表，不进入时延分布。
- 中位数之外报 P90 和平均。平均会被长尾带偏，运营需要同时看到「大多数人多久走完」和「最慢的人拖多久」。

### 确认之后没有交易，卡在哪

这是本模块唯一读业务字段做判断的清单。按下面顺序判，命中即停：

1. 响应商品已经不可交易（`is_available_now` 为假）——商品下架、卖出、过期，或被另一笔进行中的
   订单占着。这是响应商品一侧已经发生动作的证据。
2. 求购已经 `closed` / `expired`。这一档只报规模，不给方向：可能是发布者已经找到，也可能是忘记
   回来结束，平台分不清。
3. 以上都不命中，归「还在路上」。商品在、求购仍在，确认后的交易还没有创建，这一类才是运营要看的
   跟进对象。

`fulfilled` 不算第二类，因为 `accept` 当时就会写入它。把它算进来，所有没有后续交易的响应都会落入
「求购不重要了」，第三类会失去意义。

## 规模门槛与隐私

- 窗口内已确认响应少于 12 条时，转化率只报数字不给方向。
- 「有交易」和「没有交易」两组做维度对照时，差值不满 8 个百分点视为噪声。
- `DemandResponse.message` 是自由文本，只报填写率和长度分档，一个字符都不读——里面可能写着电话、
  微信、宿舍号。
- 卡点清单只带商品标题、求购标题、确认时刻和卡点类别，不输出用户名，也不做个人排名。

## 不做什么

- 不自动建订单，也不自动替免费商品挑选申请人。确认只代表双方选中这次匹配，交易仍由用户主动创建。
- 不催响应人或求购发布者，也不把 `DemandPost.status='fulfilled'` 推迟到订单完成。否则已经选中的
  需求会继续进入机会流，被反复推荐给其他卖家。
- 不为旧记录强行回填来源。兼容推断用于历史统计，不写回业务数据，也不声称精确。
- 不做「疑似放鸽子」检测。确认后没有继续交易可能有多种正常解释，把无法证实的原因变成个人标签会伤害
  校园互助中的信任。
- 不把求购响应和失物招领线索的转化并起来报。两者难度和流程不同，合并会互相稀释。
