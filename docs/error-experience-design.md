# 品牌化错误体验设计

## 问题

错误页通常只在出问题时出现，但恰恰是用户最需要明确下一步的时候。此前项目没有自定义错误模板：关闭 `DEBUG` 后回落到 Django 默认页面，视觉与站内不一致，CSRF 失败也不解释“操作没有执行”和“如何安全重试”。如果直接让错误页继承完整站点外壳，500 又可能因为数据库、会话或上下文处理器故障再次失败。

## 本轮范围

覆盖五条实际会遇到的错误路径：

- `400.html`：请求格式或参数无法识别；
- `403.html`：账号缺少受保护页面所需权限；
- `403_csrf.html`：CSRF 校验未通过；
- `404.html`：地址失效或内容已下线；
- `500.html`：未处理的服务端异常。

这些模板共用 `errors/base_error.html` 和 `static/css/error-pages.css`，但外壳是独立的静态 HTML：

- 不依赖全站导航中的用户信息、未读计数或数据库查询；
- 不输出异常字符串、堆栈、SQL、请求参数或账号数据；
- 保留状态码、问题原因、可执行的返回入口和反馈所需信息；
- 首页与发现页使用固定站内路径，避免错误处理时再次依赖复杂上下文；
- 页面支持键盘跳转、清晰焦点、语义化标题和 `prefers-reduced-motion`。

## 恢复路径

| 错误 | 用户看到的核心信息 | 推荐动作 |
| --- | --- | --- |
| 400 | 请求没有被识别 | 返回上一页，从站内入口重新发起 |
| 403 | 当前账号没有权限 | 确认账号身份，或返回公开页面 |
| CSRF 403 | 安全校验失败且操作未继续 | 返回上一页刷新后重新提交；登录状态变化时重新登录 |
| 404 | 地址变更或内容已移除 | 检查地址，或从发现页重新查找 |
| 500 | 服务端请求未完成 | 稍后重试；提交类操作先确认结果，避免重复执行 |

## 不做什么

- 不展示“技术支持编号”或自动重试按钮：当前没有可供用户查询的错误追踪系统，伪造编号没有价值；自动重试也可能重复提交交易动作。
- 不在错误页放联系表单：500 时后端可能不可用，表单本身会再次失败。
- 不替换健康检查的 `503` 响应：`/healthz/` 与 `/readyz/` 面向编排系统，继续使用机器可读的 JSON 和状态码。
- 不记录用户输入到错误页面，也不把异常对象直接渲染进模板。

## 验证

- 覆盖 400、403、CSRF 403、404、500 的真实 Django handler；
- 断言页面包含品牌、状态码和站内返回入口；
- 断言受保护异常文本不会进入响应；
- 使用无头 Chrome 在 1424px 与真实 390px 设备模拟下检查；
- 390px 下 `document.documentElement.scrollWidth` 与视口宽度一致，无横向溢出。
