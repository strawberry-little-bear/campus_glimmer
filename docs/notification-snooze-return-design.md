# 延后的通知，延了之后回来了吗

## 起点

`Notification.snoozed_until` 从通知中心上线那天起就在表上。`snooze_notification` 给用户三档——
2 小时、24 小时、3 天——点一下，这条通知就从顶部未读提醒里消失，到期后自己回来。这条链路上
已经有度量：`notification_response.py` 读 `read_at`，报每类通知的已读率和处理时长；
`handoff_code_usage.py` 的文档字符串里甚至已经承认，用户关掉通知会让重新生成的数字变成下界。

但**运营侧一条关于「延后」的统计都没有**。

`notification_response.py` 的 `PERIOD_FIELDS` 是六个字段：`kind`、`is_read`、`read_at`、
`created_at`、`occurrence_count`、`last_occurred_at`。里面没有 `snoozed_until`。它的
`response_seconds` 从上线到现在都是同一个式子：`read_at - created_at`。

## 一个被忽略的事实：延后把「处理慢」拆成了两半

一条通知 3 月 1 日创建，用户当天点了「延后 3 天」，3 月 4 日到期，3 月 4 日当天被读。

`notification_response` 读出来：处理时长 3 天。

用户实际的动作：到期当天就处理了。零天。

这 3 天不是平台慢，是用户自己说「现在不方便」。把它记在「处理时长」的账上，会让一类通知
显得难处理——而真相可能只是这类通知总在不方便的时刻到来，延后功能工作得很好。

反方向同样成立。一条从未被延后、放了 5 天才被读的通知，`response_seconds` 是 5 天，这 5 天是
实打实的沉默。两个 5 天落在同一个指标里，而它们需要完全不同的回应：前者该改发送时机，
后者该改提醒方式。

**所以本轮要做的第一件事，是把延后期从处理时长里拆出来。** 拆开之后会看到一个等式：

```
read_at - snoozed_until  ==  (read_at - created_at) - (snoozed_until - created_at)
   扣掉延期的处理时长          含延期的处理时长            用户主动要求的等待
```

左边那一项，正是「这条通知到期之后，隔了多久被读」。它和 `notification_response` 的口径不是
竞争关系，是它的一个分量：`snoozed_until - created_at` 那一段是用户自己安排的等待，剩下的
才是平台该负责的那部分。

## 为什么不能拿延后当已处理，也不能把延后并进未读

延后是用户主动说「现在不方便」。它和「未读」是两种完全不同的沉默。

未读是提醒没被看见。延后是提醒被看见了、被明确地推到以后。把延后并进未读，会让未读率虚高——
一批用户已经明确处置过的事项挂在角标上。把延后当成已处理，又会漏掉一批真的被搁置的事：
到期之后它回来了，而它可能永远不再被读。

**延后到点之后回来了吗**，这是本轮的核心问题。`actionable_unread_q` 的条件是
`snoozed_until__isnull=True OR snoozed_until__lte=now`——到点的通知重新变成 actionable
unread，重新计入顶部角标。它后来被读了吗？从到点算起隔了多久？至今没读的有多少、最久的等了
多久？

## 报什么

### 口径一：延后的规模与六种结局

周期内创建的通知，按「有没有被延后过」分成两半，被延后过的那一半再按当前状态分成五种结局：

| 结局 | 条件 | 含义 |
| --- | --- | --- |
| 还在延后中 | `is_read=False` 且 `snoozed_until > now` | 用户说「现在不方便」，还没到回来的时刻 |
| 延后期间就被读了 | `is_read=True`、`read_at` 有值且 `read_at <= snoozed_until` | 不等了，提前回来处理 |
| 到点之后才被读 | `is_read=True`、`read_at` 有值且 `read_at > snoozed_until` | 回来了，而且读了 |
| 到点之后仍未读 | `is_read=False` 且 `snoozed_until <= now` | 回来了，然后继续沉默 |
| 已读但没有阅读时刻 | `is_read=True` 且 `read_at IS NULL` | `read_at` 上线之前标记的老数据 |

第五行是数据本身的窟窿，如实报出来、不猜、不并进任何一档。

**「到点之后仍未读」是本模块最硬的一个数。** 它不问「等了多久」，只问「到期了，还没读」——
这是一个可以直接去改的通知类型清单。

### 口径二：回来之后多久被读

对「到点之后才被读」的样本，报 `read_at - snoozed_until`：从到期到被读隔了多久。分档按天切
（当天 / 1-3 天 / 4-7 天 / 7 天以上 / 至今没读），至今没读的是右删失样本，单独数、不丢不混——
和会面出席、交接码使用、归还握手三个模块守的是同一条线。

同时报中位数和 P90。时长本身带噪声，只报一个中位数会把「偶尔等一回的那一次」藏起来。

### 口径三：把延后期从处理时长里拆出来

同一批样本上摆三个数：

- 含延期的处理时长 `read_at - created_at`——`notification_response` 的口径；
- 扣掉延期的处理时长 `read_at - snoozed_until`——口径二的中位数；
- 两者之差 `snoozed_until - created_at`——用户主动要求的等待。

三个数摆在一起，「这类通知处理慢」才有机会被读成「这类通知总是在不方便的时刻到来」。
**但差本身不精确**：`snoozed_until` 每次延后都被覆盖，一条被延后三次的通知，库里只留得下
第三次的时刻，所以这一差是下界——前面两次延掉的等待不在里面。

### 口径四：延后过 vs 从没延后过

两组阅读率对照：

- 延后过的一组，只收「已经有结论」的（已读，或到期未读）；还在延后中的不计入分母——一条
  还没到期的通知说不出它会不会被读；
- 从没延后过的一组，全部计入。

两组都要过样本门槛，差值在噪声带内不给方向。**只做对照不给因果**：愿意延后的用户本来就是
更谨慎的那批，这个差值描述的是人，不是通知。

### 现在这一刻

规模与结局是回顾性的（按 `created_at` 落在周期内筛）。但「此刻还有多少通知被延后着」
「此刻有多少到点未读」是关于现在的，不按周期过滤——一个三个月前到期、至今没人读的通知，
恰恰是最不该被藏起来的一件。这条沿用跟进任务停留时长和治理队列待处理清单的既有口径。

## 判据与门槛

- 一组至少要 `MIN_BUCKET_SAMPLE = 12` 条，才允许对它下「这一组读得更少」的判断；
- 两组阅读率相差小于 `NOISE_POINTS = 8` 个百分点视为噪声，只报数字不给方向；
- 时长分档的噪声线取 `NOISE_DAYS = 3` 天；
- 空平台不报 0 条、不报 0 天：一条通知都没有的时候，这些数都不存在，不是零。

## 不做什么

**不加迁移、不加字段、不改任何写入路径。** `snoozed_until` 每次延后都被覆盖，所以「延后过
几次」「最初延到什么时候」在库里不存在。本轮只报「当前有没有被延后」，不报次数——报一个库里
没有的数，比不报更糟。

**不把「延后期间就被读了」当成「用户会提前回来处理」。** 这一组混着两种来源：用户点单条
「标记已读」（`mark_read`，语义干净），和一键全部已读 / 批量勾选已读
（`Notification.objects.filter(...).update(is_read=True, read_at=now)`，**不清
`snoozed_until`**）。后者的 `read_at` 是批量那一刻，于是一条还在延后中的通知也会落进这一组。
本模块如实报这一组的规模，但不对它下「用户会提前回来」的结论——那是一份把清空收件箱读成
积极处理的误读。

**不列逐条通知。** 通知的标题和内容是收发双方的私域内容，运营看板是全站运营读的。把一条通知
的标题搬上看板，等于把两个用户之间的一句话搬到第三方眼前。所以按通知类型聚合，不列清单——
这和 `notification_response` 的既有做法一致。

**不改写入路径、不自动取消延后、不自动标记已读。** 只报告。

**不按用户排名，不报「谁最爱延后」。** 那是一份考勤表，不是一份看板。

**不把三个时长数字相加或相减。** 含延期的处理时长是上界（延后次数不可知），扣掉延期的是
精确值（到期时刻是写下来的），它们的差是下界。三个数各有各的可信度，摆在一起看，不加。

## 交付之后

`build_notification_snooze_return(days=30, now=None)` 的返回值里有六块：

- `totals`：延后过的规模与六种结局分布；
- `return_lag`：回来之后多久被读的分档、中位数与 P90；
- `decomposed`：含延期、扣掉延期、用户要求的等待三个数；
- `contrast`：延后过 vs 从没延后过的阅读率对照；
- `kind_rows`：按通知类型的延后规模、到点未读与扣掉延期的中位时长；
- `current`：此刻的延后中与到点未读，不按周期过滤。

面板挂在「通知处理时效与触达质量」旁边——两个面板读的是同一批通知，一个问「多久被处理」，
一个问「用户说现在不方便之后怎么样了」。CSV 导出加同名的节。测试同时钉住计算正确性与面板 /
导出呈现，包括「到点未读不按周期过滤」和「批量标记已读不清 `snoozed_until`」这两条边界。
