# 内容审核申诉闭环设计

## 要解决的问题

内容审核现在已经有拦截、人工复核、分级节奏和误判放行，但用户收到「确认违规」后只有一个通知入口，缺少表达不同意见的正式路径。运营侧也无法区分「维持原判」和「复核后改判」，更无法确认一次改判是否真的把内容恢复到了原渠道。

这轮迭代补一条最小但完整的申诉链路：

- 被确认违规的内容作者可以提交一次申诉；
- 运营在内容审核队列中单独筛选待处理申诉；
- 申诉可以维持原判，也可以改判为误判；
- 改判必须复用既有误判放行事务，内容能恢复就恢复，缺材料就显式暴露；
- 原复核人与原复核时间在申诉中留痕，不因改判被覆盖。

申诉是对结论的二次复核，不是重新发布通道，也不改变自动拦截规则。

## 用户侧口径

新增「我的内容申诉」页面，只显示当前登录用户自己提交过的留言或私信审核记录。

可申诉记录必须同时满足：

- 审核事件状态为 `confirmed`；
- 当前用户是该事件的作者；
- 该事件还没有申诉。

每条 `ModerationEvent` 最多一条申诉。首次申诉包含：

- 申诉原因：
  - `not_violation`：内容不违规；
  - `missing_context`：缺少语境；
  - `other`：其他需要补充的情况。
- 申诉说明：必填，最多 1000 字。

页面展示被拦截内容、命中规则、原复核时间和申诉结果。作者只能看到自己的记录，不能通过 URL 查看或申诉他人的事件。

首次迭代不做申诉时效窗口、多次申诉、匿名申诉或附件材料。历史已确认记录只要仍满足作者与状态条件，同样可以申诉。

## 运营处理口径

内容审核队列新增申诉状态筛选：

- `pending`：待处理申诉；
- `upheld`：维持原判；
- `accepted`：申诉成立并恢复内容；
- `accepted_without_restore`：申诉成立但缺少恢复材料。

待处理申诉是用户明确请求复核的记录，应排在普通待复核记录之前。处理完成后仍回到原分级排序，便于复盘。

运营只能提交两种决定：

- `upheld`：维持原判；
- `accepted`：改判为误判。

如果选择改判，系统在同一事务内执行：

1. 保存申诉处理人、处理时间和说明；
2. 把审核事件改为 `dismissed`；
3. 复用 `_release_moderated_content` 恢复原内容；
4. 恢复成功则申诉结果为 `accepted`；
5. 缺作者、商品或私信接收人时，申诉结果为 `accepted_without_restore`，不伪装成已恢复；
6. 通知内容作者处理结果。

申诉处理说明对作者可见，用于解释结论；不进入自动处置或规则调整。

## 数据与留痕

新增 `ModerationAppeal`：

- `event`：一对一关联 `ModerationEvent`；
- `appellant`：申诉用户，写入时必须等于事件作者；
- `reason`：申诉原因；
- `statement`：申诉说明；
- `submitted_at`：提交时间；
- `status`：待处理或三种终态；
- `original_reviewed_by`：提交申诉时的原复核人快照；
- `original_reviewed_at`：提交申诉时的原复核时间快照；
- `resolved_by`：申诉处理人；
- `resolved_at`：申诉处理时间；
- `resolution_note`：处理说明。

原审核事件仍保留现有 `reviewed_by` / `reviewed_at` 作为当前结论口径；改判后它们更新为申诉处理事实。申诉表保存首次确认违规时的复核快照，避免历史判断被覆盖后不可追溯。

申诉表不复制正文、命中规则或风险分级，读取时关联审核事件，避免同一事实出现两份可编辑副本。

## 通知与安全边界

- 申诉提交后进入队列计数，不给所有管理员逐个发通知，避免一次申诉造成批量打扰。
- 申诉处理完成后通知事件作者，仍使用 `moderation_update` 通知类型。
- 运营不能处理自己发出的内容对应的申诉时无需特殊拦截：申诉人不是运营，复核人是运营；后续如出现自己申诉自己的异常数据，以权限和留痕暴露，不做静默改写。
- 申诉不接受新的交易、联系方式或外部链接材料；说明按原文保存，只用于人工复核。
- 申诉不自动改风险分级、不自动修改规则、不自动封禁或解封账号。
- Django Admin 对申诉只读展示，处理写路径统一放在审核队列，避免后台直接改终态绕过恢复事务。

## 非目标

- 不做申诉率、胜诉率等运营统计；先保证单条链路可信。
- 不做多级复审或仲裁。
- 不做申诉催办和升级提醒。
- 不改 `risk_score`、`risk_level`、`risk_tier` 的口径。
- 不改现有初次复核流程。

## 验收

- 只有确认违规事件的作者能提交一次申诉。
- 我的申诉页面不泄露他人记录。
- 队列能筛选待处理申诉，并把它排在普通待复核事件之前。
- 维持原判不改变审核事件状态和原复核事实。
- 申诉成立时，审核事件改判为误判，内容恢复成功则回到原渠道并通知接收方。
- 历史材料缺失时，申诉结果显式记录为成立但未恢复，不写入恢复时间。
- 原复核快照、申诉说明、处理说明和处理时间完整保存。
- Django Admin 申诉信息只读。
- 数据库迁移、系统检查、迁移检查和相关审核测试通过。
