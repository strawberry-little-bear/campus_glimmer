# 免费领取的申请队列，第一次被运营读到

## 起点

`listings.GiftApplication` 是站内唯一一条「多人竞争、平台只记录不排序」的队列：一件免费商品可以被任意多的人同时申请，卖家在后台看到一列 `pending`，选定一个，其余的人由系统在同一笔事务里置成 `rejected`。

它有三个字段一直在被写，但读路径只有后台那一列：

- `applicant_note`（TextField，申请说明）——唯一的写路径是 `views.py:626` 的 `applicant_note=form.cleaned_data.get('buyer_note', '')`，唯一的读路径是 `admin.py:86` 的 `search_fields`。**运营侧一条统计都没有。**
- `decided_at`（DateTimeField）——三处写路径：`views.py:786`（卖家选定申请人）、`views.py:797`（其余的人置 `rejected`）、`views.py:832`（申请人自己撤回）。读路径只有 `admin.py` 的 `list_display` / `list_filter` / `readonly_fields`。
- `meeting_location`（ForeignKey）——创建时写入，同样只有 admin 在读。

卖家选定申请人之后，`views.py:755-798` 会用这条申请创建真实的 `Order`，`buyer_note` 取的是 `locked_application.applicant_note`——说明文字是申请人唯一一次自由表达，它会被原样带进订单。

而判断依据缺失的代价是实的：**运营现在分不出一件免费商品是「没人要」还是「有 8 个人要、卖家还没决定」**。前者该去改免费商品的曝光位置，后者该去催卖家决定——两件事的处置方式完全相反，而后台把两者显示成同一个样子：一列 `pending`。

`applicant_note` 写了什么、写没写，也从来没有人读过。它是唯一一条自由文本，是申请人在这个队列里唯一的表达。

## 口径上的取舍

### 分母只收已经处理完的申请

`selected` / `rejected` / `withdrawn` 三种状态都带 `decided_at`，有明确的起止两点，算得出「从申请到处理隔了多久」。`pending` 没有处理时刻——它是右删失样本，单独数出来，不丢也不混。

把 `pending` 算进任何等待分布都会让「平均处理时长」偏短：一个刚提交两分钟的申请和一个提交了三周的申请，在分母里是同一条，而前者压根还没有开始被等。

### 撤回单独一档，不和「未选中」混在一起

`withdrawn` 是申请人自己点的撤回（`views.py:832`）。它可能是买家改主意了，也可能是等太久等不住了——**平台没有能力区分这两者**。而 `rejected` 是卖家做的决定。把两者合成一个「没成」的档，会让「撤回率」变成一个说不清是什么的数。

所以撤回单独一档，并且**只报规模，不给方向**：撤回率高了可能是商品吸引力不够，也可能是卖家回得太慢，平台分不出是哪一种，也就不该替任何一种下结论。

### 申请说明的填写率，和「填了 vs 没填」的选中率对照

`applicant_note` 是 TextField、`blank=True`，不填也能提交。这个字段唯一能回答的问题是「写说明的人是不是更容易被选中」，所以报两件事：

1. 填写率——有多少申请真的写了字；
2. 填了说明和没填说明两组的选中率对照。

对照只在两组各自至少 12 条时才给方向，差值不满 8 个百分点视为噪声。**愿意写一段说明的申请人可能本来就是更认真、更想要的那批人，平台没有能力把「说明起了作用」和「这个人本来就更容易被选中」分开。** 这是这个字段的固有边界，报数字，不裁断。

说明的正文本身不进任何统计模块。它是自由文本，可能写着电话、微信、楼栋号——本模块只读长度和填没填，一个字符都不往外拼、不做词频、不进任何榜单。

### 队列长度按商品聚合，选中率按申请聚合

一件商品收到多少份申请，是商品维度的事实；一份申请有没有被选中，是申请维度的事实。两者不能混在一个数里。

队列长度单独报分布：0 份（没人要）、1 份（独一份，谈不上竞争）、2-4 份、5 份以上。**1 份的那一档要单独列出来**——一份申请的「选中率」必然是 100%，把它和 8 份申请的选中率混在一起平均，会得到一件压根不存在的商品。

选中率的分母只收已经处理完的申请，和等待时长同一个分母。

### 按分类和是否免费礼物分组

按 `Item.category` 分组，运营能看出「哪一类免费商品问的人多、哪一类没人问」。免费商品的分类结构和付费商品不同，混在一起报会让两类都被稀释。

### 处理时长按小时和天分档，不按分钟

从提交申请到卖家处理，时间尺度是小时到天。报「平均等了 4 小时 23 分」会让运营以为这是小时级的流程，而真正要动作的对象是「卖家隔了多久才打开后台」。分档按「当天内 / 一到三天 / 三到七天 / 超过七天」走，每一档对应一个可动作的判断。

## 不做什么

- **不给卖家排序、不替卖家推荐申请人。** 队列现在是按 `status, created_at` 排的（`models.py` 的 `Meta.ordering`），先来后到，一目了然。任何「更该被选中」的排序都是平台在替一个具体的人做决定，而这个决定会直接决定另一个人能不能拿到东西。
- **不改任何申请状态、不催卖家、不给申请人发提醒。** 这是全项目统计模块一致的边界：统计模块只读，动作归动作。
- **不读说明正文、不做词频、不进任何榜单。** 理由见上。
- **不把选中率做成「商品热度分」。** 选中率高不等于商品好——一件没人申请的免费商品和一件 8 个人抢的免费商品，选中率一个是 100%（如果它被处理了）一个是 12.5%，而这个 100% 说明的恰恰是「没人要」。单看选中率会读反。
- **不写 `withdrawn` 之外的新状态。** 加一个只读模块不会替任何流程发明写路径。
