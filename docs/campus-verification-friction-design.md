# 校园身份认证的最后一公里，第一次被运营读到

## 起点

`accounts.CampusVerification` 里有三个时间戳/状态，写路径一直在写，但从没有任何一行代码读过它们的差值：

- `token_issued_at`——每一次「重新发送验证邮件」都会刷新它（`accounts/views.py` 的 `campus_verification` 视图，第 114 行）；
- `verified_at`——用户点开邮件里的链接、令牌通过校验的那一刻写上它（`verify_campus_email`，第 164 行）；
- `status`——`pending` → `verified`，另外两个取值 `unverified` 和 `rejected` 从未被任何代码写过。

`token_issued_at` 唯一的读者是 `verify_campus_email` 里的过期判断（24 小时）。`verified_at` 唯一的读者是 `is_verified` 属性和两处 `verified_at__isnull=False` 的筛选。**两个字段的差值——用户从收到邮件到点开链接花了多久——从来没有任何一行代码算过。**

运营侧现在能回答「有多少人认证成功了」（`transaction_safety.py` 只把 `status='verified'` 当成交易安全卡上的一条正面信号）。回答不了的是「认证这一步到底卡不卡」「卡在哪」「反复收不到邮件的那些人，最后放弃了还是换了个邮箱再试」。

而判断依据缺失的代价是实的：校园身份认证是这套系统里唯一一个「平台主动发一封邮件、然后等用户自己回来点链接」的闭环。它是可信交易的入口——交易安全卡上「发布者已完成校园身份认证」这条正面信号、公开资料页上的认证标识，全靠它。一个用户点了两次「重新发送验证邮件」还是没有认证成功，运营看到的是同一个 `pending`，和第一次发邮件的用户一模一样。

## 口径上的取舍

### 只算已经认证成功的样本

分母只收 `verified_at` 非空、且 `token_issued_at` 也非空的记录。还挂在 `pending` 上的认证没有完成时刻，谈不上花了多久——这是右删失样本，单独数出来，不丢也不混。

`unverified` 状态的记录压根没有发过邮件，`token_issued_at` 是空的；把它们算进去会让「平均耗时」凭空变长。

### 耗时按分钟和小时分档，不按秒

一次认证等待的时间尺度是分钟到小时。报「平均 3 分 12 秒」听起来很精确，但运营要动作的对象是「邮件到没到」「链接好不好找」，不是毫秒级的优化。分档按「十分钟内 / 一小时内 / 一天内 / 超过一天」走，每一档对应一个可动作的判断。

### 重发次数要单独报，且只当参照不当成分母

`token_issued_at` 会被重发覆盖，所以**记录里只留着最后一封邮件的发出时间**。用户如果点了三次「重新发送」，我们看得到最后一次是哪一刻，看不到前两次是什么时候。

**取舍**：重发次数只能从「认证成功时 `token_issued_at` 到 `verified_at` 的间隔」反推——间隔短于某个阈值的，多半是用户当场就点了，没有重发；间隔明显偏长的，可能重发过，也可能只是没看邮件。我们分不出这两者，所以重发这件事只作为耗时的参照写进报告，不单独计数、不做成排名。

### 不能做成「按用户分层报告个体耗时」

那是隐私面很大的东西，而运营要改的是邮件文案和链接位置，不是某个用户点了多久。按域名报总体就够了。

### 域名维度比用户维度有用

同一个学校的校园邮箱，收件速度、垃圾邮件策略、学生查邮件的习惯都是同一个量级。按 `domain_name` 分组报，运营能看出「是某一类的邮箱特别慢」还是「所有邮箱都慢」——前者是邮件服务商的问题，后者是我们自己的文案或链接问题。

## 不做什么

- **不重发邮件、不改过期时间、不发提醒。** 这是全项目统计模块一致的边界：统计模块只读，动作归动作。24 小时的过期窗口是安全约束，不该因为「平均耗时很短」就放宽。
- **不清理 `unverified` 和 `rejected` 的死记录。** 理由同上，清理是独立的写路径。
- **不把耗时做成「认证体验分」。** 耗时久不等于体验差——一个期末周的学生三天后才看到邮件，不是平台的错。报事实，不裁断。
- **不写 `rejected` 状态。** 没有任何路径产生它，加一个只读模块不会替它发明写路径。它继续作为 choices 里的一个占位，和现在一样。
