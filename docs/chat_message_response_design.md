# 一条私信隔了多久被打开，第一次被运营读到

## 起点

`PrivateMessage` 有六列：`sender`、`receiver`、`item`、`content`、`created_at`、
`is_read`。最后一列是 `BooleanField(default=False)`，没有任何时间戳伴随它。

全部写路径只有四处，全部只翻布尔值，没有任何一处记录「什么时候被读的」：

- `chat_messages/views.py` 的 `mark_message_read`：`save(update_fields=['is_read'])`。
- `mark_all_messages_read` 和 `mark_selected_messages_read`：`.update(is_read=True)`。
- `conversation`：打开会话时 `.update(is_read=True)`。
- `mark_conversation_read`：`.update(is_read=True)`。

于是 `is_read` 从 `False` 翻到 `True` 的那一刻被永久丢掉了。数据库里只剩一个
布尔值，回答「读没读」，而读读的时刻、从发来到被打开隔了多久、有多少信发出去
就再没被打开过——这三个数一行代码都没算过。

这不是新建一套统计。站内通知 `Notification` 已经有 `read_at`，且
`notification_response.py` 在拿它算各类通知的处理时效，`lifecycle_reminder_effect.py`
也在拿它区分「收到没看」和「看了没动」。私信是站内唯一一条「用户对用户」的
沟通渠道，也是唯一一条记录已读却不记录何时已读的渠道。同一个平台上，一边在量
通知的时效，一边把私信的时效扔掉。

## 为什么这是真缺口

站内私信是交易闭环里唯一一段平台看得见的对话。买家点「联系卖家」、卖家回一句
「还在吗」、双方约在图书馆东门——这些话平台都存着，但平台对这段时间的唯一了解
是「这条信已读」。

已经存在的四个读路径，没有一条留下时间证据：

1. **打开会话页**（`conversation`）：进页面就把这个会话的全部未读一次性标已读。
   用户可能真的读了，也可能只是点进去看了一眼列表就关掉。
2. **收件箱逐条标已读**（`mark_message_read`）：POST 一条，标一条。
3. **全部标已读 / 选中标已读**：一次 `.update()` 改一片。
4. **读完这个会话**（`mark_conversation_read`）：一次 `.update()` 改一片。

四条路径里只有第一条是真的「用户在读」，后三条是清理动作。现在它们在数据库里
长得完全一样：都是 `is_read=True`，没有任何一列能区分。

后果是实的。一件 30 元的教材，卖家平均 6 小时才看到买家的私信；而另一件 800 元的
显示器，买家发完私信 3 天没得到回复，转头去别处买了。平台现在既不知道前者慢，
也不知道后者在流失。卖家也不会被告知——没有人给他看过「你平均多久回一次私信」，
而回复速度恰恰是二手交易里最能影响成交的一件事。

更隐蔽的一层：私信未读数驱动着站内的未读提醒（`unread_summary`、导航栏角标）。
一个卖家把 40 条未读一次性标成已读，和一个卖家真的逐条读完 40 条，在后台看来
都是「未读清零」。前者可能是对噪音的投降，后者是认真在做生意。这两个卖家该得到
的运营关注完全相反，而现在无法区分。

## 口径上的取舍

### 加一列 `read_at`，不建新表

`Notification` 已经证明了 `read_at` 这个形状在站内是成立的：可空、`null=True`、
`blank=True`，只在已读时有值。私信照抄这个形状，不发明新结构。

新增一列的代价是迁移，收益是四条写路径各加一次赋值。不改任何现有行为，不引入
新表、新关系、新接口。老数据没有 `read_at`，全部按「读过但不知何时读的」处理，
在统计里单列一类，不拿零冒充。

### 「首次阅读」而不是「最后阅读」

一个 `is_read` 布尔值只能翻一次。一旦为真，后面对这条信的再访问不会再产生新
数据——所以 `read_at` 记录的是**第一次被标记为已读的时刻**，此后再标已读不覆盖它。

这和 `Notification.read_at` 的语义一致（`mark_notification_read` 里
`if not self.is_read` 才写 `read_at`），也让「从发来到被打开隔了多久」这个差
有唯一确定的定义。

### 批量 `.update()` 必须逐条补时间

三条路径用的是 `.update(is_read=True)`，一条 SQL 改一片。`read_at` 需要一个
确定的值，所以这三处要先查出目标主键，再按主键批量补时间。

这里**不取 `now()` 当数据库时间**。批量 `.update()` 发生在一次 HTTP 请求里，
请求的开始时间和 SQL 的执行时间相差几毫秒，对统计没有影响；但如果取
`timezone.now()` 在 Python 侧算，四条路径会各有一个略有差异的时刻，而它们
本该是同一个「用户动手的那一刻」。统一用同一个 Python 侧时间戳，让四条路径
口径一致。

反过来，逐条路径（`mark_message_read`）保持 `save(update_fields=[...])`，
不动它的写法。

### 只报「已读的样本」，不推断未读的

未读私信的 `read_at` 是 `NULL`。统计里：

- 「多久被打开」的分母只收 `read_at IS NOT NULL` 的信。
- 「发出去就没被打开过」的是另一类分母：`is_read=False` 且 `created_at` 已超过
  一个可配置的静默期。这不是「没读」，是「到现在还没读」，随时间是移动的。

两类不混。把未读的算进「多久被打开」会得到一堆假的短时延（全填 0），
这是最容易犯也最不该犯的错。

### 三个问题，三个分母

沿用项目里已经确立的写法（见 `docs/availability-watch-design.md`、`docs/first-viewed-design.md`），
每个问题单独报，不合成一个总分：

1. **从发来到被打开隔了多久。** 分母：`read_at IS NOT NULL`。报中位数与分布，
   不报均值——一封信躺了 40 天才被打开，会把「一般 6 小时」这个真相平均掉。
2. **有多少信发出去就再没被打开。** 分母：`is_read=False` 且年龄超过静默期。
   按发送人与接收人分别报，因为「卖家不回买家」和「买家不回卖家」是两件事。
3. **打开得多快，和交易有没有关系。** 分母：关联了 `item` 的已读私信，
   和这些会话后续是否产生了订单。回答「回得快是不是真的更容易成交」，
   而不是「回得快的人更好」。

第三个问题只做相关性描述，不做因果声明，也不给用户打任何分数。平台现在没有
能力证明「因为回得快所以成交了」，只能把两列放在一起让人看。

## 不做什么

- **不给用户加「回复速度分」并显示在个人主页。** 这是排名，会影响交易决策，
   而它建立在「打开会话页即算读完」这个非常弱的信号上。数据还不够诚实到能
   支撑一个公开的分数。
- **不自动提醒卖家回私信。** 未读私信已经有站内未读角标，再加推送会变成骚扰。
   本模块只把现状报给运营，不替用户决定该不该回。
- **不把 `read_at` 暴露给对话双方。** 「对方已读」会让二手交易里的沟通变形。
   这一列只给运营看板用。
- **不回填历史数据。** 老信没有 `read_at`，永远不会有。给它们填一个
   `updated_at` 之类的时间是伪造证据。

## 落地顺序

1. `PrivateMessage` 加 `read_at`（`null=True, blank=True`）与迁移，加
   `receiver, is_read, read_at` 复合索引。
2. 四条写路径补 `read_at`：逐条路径用 `save`，三条批量路径先取主键再批量补。
3. `chat_message_response.py`：三个问题的统计，含静默期配置。
4. 运营看板接一个「私信响应时效」面板，与现有通知时效面板并列。
5. 测试覆盖：四条写路径都留下 `read_at`；二次标记不覆盖；未读样本不进时延统计；
   静默期边界；无数据时不报 0。
