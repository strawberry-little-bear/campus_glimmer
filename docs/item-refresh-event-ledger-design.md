# 商品刷新事件台账设计

## 要解决的问题

`Item.refresh_count` 和 `Item.last_refreshed_at` 只能回答“这件商品现在刷新过几次、最近一次是什么时候”。它们不能回答“每个时间点到底发生过几次刷新”。最近时间戳会被下一次刷新覆盖，累计计数也无法还原事件序列，所以生命周期提醒的跨学期对比只能暂时排除刷新动作，避免把数据留存缺口伪装成效果下降。

这一轮补上逐次刷新事件台账：**每一次通过限流校验的真实刷新，都在同一事务里留下一条不可覆盖的事件**。它先服务数据事实，不急着把完整行动率判成好坏。

## 事实来源与写入边界

- 新增 `ItemRefreshEvent`，记录商品、卖家、刷新时间和这一次写入后的 `refresh_count_after`。
- 事件只由 `refresh_item` 的成功路径写入：
  - GET 请求不写；
  - 预检或行锁后的二次限流校验失败不写；
  - 商品计数器更新失败时，事件与计数器同事务回滚。
- 事件不替代现有字段。`refresh_count` 继续承担限流，`last_refreshed_at` 继续承担排序和新鲜度；台账提供可追溯历史。
- `seller` 是写入时的卖家事实快照；商品删除后事件随商品删除，本项目当前不引入匿名留存表。
- 唯一键使用 `(item, refresh_count_after)`，防止同一商品同一次计数被重复落两行。
- 不回填历史。现有 `refresh_count > 0` 但没有事件的商品代表台账上线前的旧动作，不能按最近时间戳伪造一串事件。

## 观察口径

- 周期内统计事件数、事件口径商品数、卖家数、首末事件时间。
- 按本地日期输出逐日事件、商品与卖家数，空日期补零，避免图表把无事件日折叠成不存在。
- 台账覆盖只比较同一商品的当前 `refresh_count` 与事件行数：
  - 事件行数等于计数：完整覆盖；
  - 事件行数小于计数：历史缺口，单列缺口次数；
  - 最新事件计数不等于当前计数，或事件序列存在缺口：台账不一致，需要人工核对。
- 事件时间超过容忍范围的未来时间单独列为数据质量信号。
- 面板只读事件与商品计数，不修改限流、不清零、不回填、不给卖家排名。

## 输出形态

- 运营看板新增“商品刷新事件台账”面板，展示周期规模、逐日形状、覆盖缺口与一致性信号。
- CSV 导出同名小节，字段与页面同构，包括设计边界说明。
- 面板与 CSV 都写明“历史缺口不是错误”；真正异常的是新台账上线后的序列不一致。

## 非目标

- 不把刷新事件直接判为提醒效果，也不在本轮修改跨学期行动方向。
- 不记录 IP、User-Agent 或设备信息。
- 不自动补历史事件、不自动修复不一致行。
- 不改变每月刷新上限、最小间隔和现有卖家提示。
