# 内容审核结果通知：开关、触达与沉默

## 问题

站内有 24 种站内通知，`NotificationPreference` 上有 26 个布尔开关。用户可以在设置页
一项一项关掉它们，`create_notification` 也会老实读这些开关：关了就 `return None`，
连一行 `Notification` 都不建。

这件事本身没问题。问题在于**这些开关从来没有和任何结果对照过**。

`notification_response` 报了各类通知的处理时效，`notification_aggregation_quality` 报了
聚合合并的质量，`notification_snooze_return` 报了延后通知的回归，
`notification_kind_coverage` 报了「选择项里有、库里没有」和「表单里有、选择项里没有」
的版图缺口。四个模块都在按 `kind` 读 `Notification` 表，但**没有一个模块读过
`NotificationPreference`**。

于是有一整类问题是回答不出来的：**用户把某一类通知关掉之后，发生了什么？**

`moderation_update`（内容审核结果）是这条线上最该被读的一类，理由有三层：

1. **它是站内唯一一条「平台自己判了你违规、然后通知你」的消息。** 其余 23 种讲的都是
   人和人之间的事——有人预约了你的商品、有人申请了你的免费商品、有人给你发了私信。
   只有这一种，说话的是平台自己。用户对这类通知的态度和对交易提醒的态度没有理由一致。

2. **它是唯一一条「关掉它没有任何交易后果」的通知。** 关掉 `order_status`，你可能错过
   订单推进；关掉 `message_received`，你可能错过买家的私信。而关掉 `moderation_update`，
   你在站内的行为能力一分不少——只是从此不知道自己的留言或私信被判过什么。一个开关的
   代价越低，它被关掉的概率越高，而这件事此前没有任何数字支撑。

3. **它是唯一一条「关掉它就再也收不到平台任何说明」的通知。** 复核结论走的是
   `chat_messages/views.py:442` 的 `create_notification(..., kind='moderation_update')`，
   没有站内信以外的第二条路径。举报处理更新（`report_update`）至少在后台处理页上还能
   看到状态，内容审核结果只有这一条通知。

而这个字段的读取路径只有两处：`forms.py:40` 的表单字段，和
`notifications.py:66` 的 `getattr(preference, kind, True)`。**被表单收集、被写入路径读取，
从来没被统计过。**

## 已有什么，缺什么

| 已有 | 读什么 | 不读什么 |
| --- | --- | --- |
| `notification_response` | `Notification.is_read` / `read_at`，按 kind 报时效 | 不读偏好开关 |
| `notification_aggregation_quality` | `occurrence_count` / `dedupe_key` | 不读偏好开关 |
| `notification_snooze_return` | `snoozed_until` | 不读偏好开关 |
| `notification_kind_coverage` | `KIND_CHOICES` 与表单字段的差集 | 不读任何一行 `NotificationPreference` 的**值** |
| `moderation_rule_quality` | `ModerationEvent` 的规则命中、误判、漏判 | 不读通知，不读偏好 |

`moderation_rule_quality` 已经回答了「规则判得准不准」，但那个模块的终点是
`ModerationEvent.status`（确认违规 / 误判放行）。**复核结论发出去之后，接收端发生了什么，
四个通知模块加一个审核规则模块，一处都没有接上。**

## 这个模块报什么

只读，不加迁移、不加字段、不改 `create_notification`、不改复核写入路径、
不自动给任何人打开开关。

### 一、这一类的触达：有多少人真的收到了

`ModerationEvent` 周期内被复核完的记录，按复核结论分成两组（确认违规 / 误判放行），
报每组里「作者收到了通知」「作者没收到通知」「作者压根不存在」各多少。

「没收到」必须拆开，不能合成一个数，因为三种情况的成因完全不同：

- **开关关着**：`NotificationPreference.moderation_update == False`，`create_notification`
  在 `notifications.py:66` 静默返回 `None`。这是用户主动选的。
- **免打扰时段**：`quiet_hours_active(recipient)` 为真。这是用户主动选的另一种东西，
  和「完全不要这类通知」不是一回事——免打扰是有时限的。
- **自己是自己内容的作者**：`create_notification` 第一行就有 `recipient.pk == actor.pk`
  的短路。复核人是内容作者本人的情况极少，但结构上存在。
- **`NotificationPreference` 行不存在**：`get_or_create` 会现建一行，默认全开，
  所以这一项只可能来自并发或手工删行，报出来是为了让分母诚实。

四种都不读成同一个「未送达」。合成一个未送达率，运营看到的数会随复核人是不是作者
这种人极少的情况抖动，而那和用户有没有关开关毫无关系。

### 二、关掉它的是谁

按「这个用户在周期内有没有被复核过内容」和「开关状态」交叉，报四格：
有内容被复核且开着、有内容被复核但关着、没内容被复核且开着、没内容被复核但关着。

**只报四格的人数，不报用户名，不排名。** 关掉一个通知偏好是用户的私事，
做成排行榜就是把设置页变成公开表态。

四格里真正有信息量的是第二格和第四格的对比，而这两个数不能直接比——
第三、四格的人没被复核过内容，他们关不关这个开关和「收到过审核结果」没有因果关系。
所以**只报四格的原始人数，不报任何两格之间的比值**。

### 三、关掉之后，人还在不在社区里说话

关掉 `moderation_update` 的用户，和开着它的用户，在关掉之后各自还有没有发言行为。
发言行为只报三个最粗的形状：周期内有没有新的商品留言、有没有新的私信、有没有新发布的
商品。**不报发言条数，不报内容，不报任何自由文本。**

这一节是全模块最容易被读歪的一节，所以口径卡得最死：

- 报的是**同期人群的对照形状**，不是因果。关掉通知不会让人不说话，收到一条
  「你违规了」也不会。两群人在发言率上的差，可能只是「常发言的人更在意审核结果」。
- 两群人都过 `MIN_BUCKET_SAMPLE` 才报差值和方向，不过就只报两群各自的人数。
- 方向只允许是「关组更高 / 开组更高 / 两组相同」三档，**不给百分比差**——
  一个 3 个百分点和一个 30 个百分点在看板上长一样，给的指引却完全相反。
- **不按任何用户维度排名。** 不报是谁，不报发言最多的前十个。

### 四、通知发出去之后，读没读

`moderation_update` 通知的已读率，按复核结论拆。确认违规和误判放行是两条情绪上
完全不同的消息：一条说你违规了，一条说我们搞错了。**它们的已读率没有理由相同。**

同时报一条对照：同期全部通知的整体已读率。少了这个分母，单看一类的已读率读不出
「这一类是不是特别没人看」。

**只报聚合已读率，不报任何一条通知的阅读时长分布**——`notification_response` 已经报了
全部 24 类的时效，这里重复一遍是把看板撑大，不是把看板变好。

## 明确不做的事

- **不加迁移、不加字段、不改模型。** 只读。
- **不改 `create_notification`。** 它的静默 `return None` 是这个模块要观测的对象，
  改掉它，观测对象就没了。
- **不给任何人自动打开开关。** 那是替用户做决定。
- **不读 `ModerationEvent.content`。** 被拦截的内容是自由文本，可能写着电话、微信、
  楼栋号。`moderation_rule_quality` 明确不读，这个模块也不读。
- **不读 `Notification.title` / `message`。** 同理。
- **不按用户排名，不报任何用户名。**
- **不重复 `notification_kind_coverage` 的版图结论。** 那个模块报的是「选择项和表单
  字段的差集」，这个模块报的是「值本身」。
- **不重复 `notification_response` 的时效结论。** 只报已读率这一项。
- **不重复 `moderation_rule_quality` 的规则质量结论。** 那个模块的终点是
  `ModerationEvent.status`，这个模块从 `status` 往后接一步。

## 门槛

- `MIN_BUCKET_SAMPLE = 12`：任何一类占比要给方向，至少 12 条样本。全站统一。
- `MIN_PREFERENCE_USERS = 12`：偏好四格要报差值，两群各自至少 12 人。
- 空分母报 `None`，模板显示「—」，不报 0。
