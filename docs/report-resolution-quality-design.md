# 商品举报处理得公不公平

## 起点

`Report` 是站内最早的治理队列：用户在商品详情页点「举报」，选一个原因、写一段补充说明，
这条记录就进队列等审核。它是 `governance_sla` 里四条治理队列之一，也是用户唯一一条
**不经过对方同意就能递到平台面前**的通道。

而 `governance_sla` 只报了它一件事：多久被处理。`analytics` 报了另两件事：周期内新增多少条、
此刻待处理多少条。这三个数加起来，运营知道这条队列**忙不忙**，不知道它**公不公平**：

- 哪一类举报更容易被驳回；
- 审核意见写了没有、写了多长；
- 被驳回的举报集中在哪些商品、哪些卖家身上；
- 举报的人是不是同一批人在反复举报。

这四个问题，`dispute_resolution_quality` 为**争议**做了全套（按 `reason` 拆驳回率、证据
提交间隔、处理意见填写率与长度、发起方向分布），而 `Report` 这张表——比争议更早、更日常、
离用户更近——**一处都没有被读过**。`review_note` 这个字段的全部读者只有两处：`admin.py`
的 `search_fields`（后台搜索框）和 `views.py:1608` 的写入路径（审核人填完保存）。
**一个字段被写、被搜索，从来没被统计过。**

## 为什么之前没被看见

因为 `Report` 看起来一直是「有数的」：`analytics` 里有 `new_reports` 和 `pending_reports`，
`governance_sla` 里有它的时效。两个模块各自都自洽，都回答了「这条队列健康吗」的一个侧面。
而「处理得公不公平」这个问题，需要把 `reason`、`status`、`review_note`、`reviewer`、
`item`、`reporter` 六个字段**连起来看**——单看任何一个字段都问不出这个问题。

更隐蔽的一层：`Report` 上有一个 `UniqueConstraint(fields=['item', 'reporter'])`。
一个用户对一件商品只能举报一次。所以「重复举报」在这张表上**不可能由同一个人对同一件商品
构成**——它只能由同一个人对**不同**商品构成。这个约束让「这人是不是在刷举报」这个问题
换了一个形状，而换过之后的形状此前没有人看过。

## 报什么

### 口径一：驳回率按 reason 拆

四种举报原因的举证难度完全不是一回事：

| 原因 | 用户要证明什么 |
| --- | --- |
| 疑似诈骗或虚假信息 | 对方收了钱不发货、描述与实际不符 |
| 重复发布或广告引流 | 同一件商品挂了多次、内容是广告 |
| 不当内容 | 图片或文字违规 |
| 其他问题 | —— |

把它们平均成一个总驳回率，这个数一旦波动，运营第一反应是去查处理人，而不是去查是哪一类
举报在涨。按 reason 拆开之后，「诈骗」类驳回率上升和「广告」类驳回率上升是两条完全不同
的线索：前者可能是用户在拿举报当谈判筹码，后者可能只是审核标准在变。

**已完结的举报才算进分母。** 分母只收 `status` 为 `resolved` 或 `rejected` 的。还挂在
`pending` / `reviewing` 的是右删失样本：举报还没判，谈不上被驳回还是被支持。这和争议模块
守的是同一条线。

### 口径二：审核意见写了没有、写了多长

`review_note` 报两件事：填写率，和长度分档。

**一个字符内容都不读。** 它是审核人写给举报人的一段自由文本，可能写着电话、微信、楼栋号，
也可能写着审核人的判断和情绪。这个模块只关心一件事：这段理由有没有被写下来。至于理由写
得好不好，那是复核人该看的，本模块不替代复核人——`dispute_resolution_quality` 为争议的
`resolution_note` 守的是同一条线。

**按结局拆填写率。** 已处理的举报和已驳回的举报，意见填写率可能不一样。一个被驳回的举报
如果普遍不写意见，用户收到的是一个没有理由的拒绝——这是这套治理里最伤人的一种体验，
而它此前没有任何数字。

**不报「长度和驳回率的关系」。** 长意见是不是更难被申诉，观测数据里分不开：意见写得长
可能只是这类举报本身复杂。只报形状，不给方向。

### 口径三：被驳回的举报集中在哪些商品、哪些卖家

被驳回的举报指向的商品，和未被驳回的举报指向的商品，是两批不同的东西。报：

- 被驳回的举报涉及多少件商品、多少位卖家；
- 其中有多少件商品本身已经不在售（`Item.status` 是 `reserved` / `sold` / `expired`，即 `available` 之外的状态）；
- 重复出现的商品（被多次举报且被驳回）有多少件。

**只报规模与集中度，不列商品名、不列卖家名。** 一份「被驳回举报最多的商品榜」是一份
公开处刑清单，不是看板。运营要的是「集中在少数几件上」还是「摊在一大片上」这个形状——
前者说明有几件商品有问题，后者说明举报标准可能有问题。

### 口径四：举报的人是不是同一批人

按 `reporter` 聚合：周期内发过举报的用户里，有多少只发了一条、多少发了多条、最多发了
几条。

**不排名、不报任何人的用户名。** 把「谁最爱举报」做成一张排行榜，平台就从仲裁者变成了
一个记录谁难相处的小本子。报的是分布形状：如果绝大多数用户只举报过一次，那这条通道是
**应急**性质的；如果有一批人反复在用，那它可能是某些用户的**常规**手段——这两种形状
对应完全不同的治理动作。

**受 `UniqueConstraint` 限制，不报「同一用户对同一商品的重复举报」**——那个数结构上恒为
0，报出来是一个永远为 0 的常数，没有信息量。

## 判据与门槛

- 一个 reason 的已完结样本至少要 `MIN_BUCKET_SAMPLE = 12` 条，才允许对它下「这一类
  更容易被驳回」的判断。和争议处理质量、通知类型版图同一个量级；
- 填写率对照两侧（已处理 / 已驳回）各至少 12 条才给方向，差值不满 8 个百分点视为噪声
  （`NOISE_POINTS = 8`，与争议模块同一个数）；
- 空平台（一条举报都没有）不报 0 条、不报 0%，报 `None`；
- 拿不到的分母（没有任何已完结举报）报 `None`，不报 0。

## 不做什么

**不加迁移、不改 `Report`、不改审核表单、不改 `views.py:1608` 的写入路径。**
`review_note` 没有设为必填是一个产品决定，本模块只报「实际有多少人填了」，不把填写率
变成强制。

**不判定任何一条举报成立或不成立。** 平台没有能力从现有字段判断一次举报是不是恶意举报，
本模块只报「它被驳回了」这个既成事实。

**不把驳回率和处理人挂钩。** 按 `reviewer` 拆驳回率是一份考官成绩单，本模块不报——
审核标准的松紧是运营该统一管的事，把它摊成个人数字只会让审核人挑软的处理。

**不读 `detail`（举报人的补充说明）和 `review_note`（审核意见）的任何内容。**
两处都是自由文本，可能写着电话、微信、楼栋号。

**不把「举报多」读成「用户爱找茬」。** 举报是用户唯一一条不经对方同意就能递到平台面前
的通道，用得多可能说明用户信任这条通道。本模块只报形状，不做人物评价。

## 交付之后

运营第一次能回答四个问题：

1. 哪一类举报更容易被驳回——按 reason 拆的驳回率；
2. 被驳回的用户收到了有理由的拒绝吗——按结局拆的意见填写率与长度；
3. 被驳回的举报集中在少数商品上还是摊成一片——规模与集中度；
4. 这条通道是应急用的还是常规用的——举报人的分布形状。

`Report` 从一条「只有计数和时效」的队列，变成一条**质量可读**的治理队列。它和
`dispute_resolution_quality` 并排放在看板上，站内两条用户申诉通道第一次用同一套口径
被读。
