# 商品举报结果回访设计

## 要解决的问题

举报人现在只会在管理员保存结论时收到一条状态通知，之后这条治理记录对他来说就消失了：没有“我的举报”页面，看不到历史提交，也没有一个轻量入口表达“这个结果我看得懂”或“我仍然不认同”。运营侧则只能读到驳回率和意见填写率，无法区分“结论已送达但用户不理解”和“结论确实被接受”。

这条迭代补的是举报结果的回访闭环：举报人可以在自己的举报列表里查看处理状态，并在举报完结后提交一次结构化反馈；运营侧把回访率、反馈分布和反馈时延并入举报处理质量面板。它不是申诉系统，也不改变任何审核结论。

## 用户流程

1. 举报人在商品页提交举报后，可以进入“我的举报”列表。
2. 列表只显示本人提交的举报，按提交时间倒序排列，展示商品、原因、状态、提交时间、处理时间和审核说明。
3. 举报仍是 `pending` / `reviewing` 时，只能查看进度，不能反馈。
4. 举报进入 `resolved` / `rejected` 后，页面展示三个固定选项：
   - **问题已处理**：结果解决了举报时担心的问题；
   - **结果看不懂**：状态或审核说明没有说明白；
   - **不认同结果**：看懂了，但不同意这个结论。
5. 每条举报只能提交一次结果反馈；提交后选项变为只读标签，不能修改。
6. 管理员保存审核结论时，通知跳转到“我的举报”，让举报人能直接进入回访入口。

三个选项只表达理解和接受程度，不代表平台承认审核错误，也不触发重新审核。

## 数据口径

- 新增 `ReportOutcomeFeedback`：
  - `report`：一对一关联 `Report`，举报删除时随之删除；
  - `choice`：固定三档枚举；
  - `created_at` / `updated_at`：提交与更新时间，实际业务一条举报只会写入一次。
- 不冗余保存举报人：所有权始终由 `report.reporter` 判断，避免同一事实两处存储。
- 不保存自由文本反馈。举报补充说明和审核说明已经包含大量敏感信息，回访只收结构化选择。
- 一次反馈的唯一性由数据库 `OneToOneField` 约束保证，写入路径捕获并发冲突并返回“已反馈”，不做更新覆盖。
- 反馈不写入 `Report`，不影响举报优先级，也不改变治理工作台的 SLA 排序。

## 权限与状态边界

- “我的举报”与反馈提交路径都在服务端校验 `request.user == report.reporter`。
- 只有 `resolved` / `rejected` 的举报接受反馈；处理中、未知状态或他人举报均拒绝。
- 管理员可以看见某条举报是否已有反馈及其选项，用于复核沟通质量，但反馈不作为改判依据。
- 不通知卖家，不公开反馈，不生成举报人、卖家或商品榜。

## 运营指标

指标并入现有“商品举报处理质量”面板，不另立看板：

- **回访率**：已完结举报中收到结果反馈的比例；分母是周期内创建且已完结的举报。
- **反馈分布**：三档各多少条、占比多少，并按 `resolved` / `rejected` 分开，避免把支持率和理解度混在一起。
- **反馈时延**：从 `reviewed_at` 到反馈 `created_at`，分为 1 小时内、1–24 小时、超过 24 小时；尚未反馈的是右删失样本，只进待回访数，不进时延分母。
- 样本不足时只显示计数，不给方向性结论；负数时延单独计为异常样本，不用 0 伪装时钟偏差。
- 指标只读结构化字段，不读取举报说明、审核说明和用户名。

## 非目标

- 不做申诉、复核工单或自动重开举报；用户选择“不认同结果”后仍需走现有联系管理员路径。
- 不根据反馈调整审核人绩效，不把回访率变成个人考核。
- 不做提醒轰炸：只在审核结论通知里携带一次入口，不额外定时催促。
- 不给“问题已处理”发积分或奖励，避免把回访变成表态激励。
- 不回填历史举报的反馈；只有功能上线后由举报人主动提交的反馈才入库。

## 验收

- 举报人能只看到自己的举报；他人访问返回 404。
- 未完结举报不能反馈；完结举报只能反馈一次。
- 并发重复提交不会产生第二条反馈。
- 审核结论通知跳转到“我的举报”。
- 举报队列与审核详情能看到回访标签，但优先级排序不变。
- 运营面板显示回访率、分布与时延，样本不足时明确降级。
- 数据库迁移、系统检查和相关测试全部通过。
