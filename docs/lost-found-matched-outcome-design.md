"""失物招领确认匹配之后，记录停在哪一种终局里。

## 已有什么，缺什么

`lost_found_lead_quality` 已经回答了这条链路的前四步：一条记录平均收到几条线索、
线索被确认的概率有多大（按 `post_type` 拆）、确认之后东西找回来了没有、没被确认的
线索是被拒了还是被撤回了。它甚至读了 `LostFoundPost.status == 'matched'`，报了一个
`matched_rate`。

但那一步之后就断了。`review_lost_found_lead` 的 `accept` 分支做四件事：把线索置为
`accepted`、把记录置为 `matched`、把关联的那条记录也置为 `matched` 并互填
`matched_post`、把同一条记录下其余 `pending` 的线索批量清成 `rejected`。**做完这四
件事，这条记录的状态就再也没有被任何东西读过。**

而 `matched` 在这个系统里是一个**单向门**。全站只有四处写 `LostFoundPost.status`：

- `review_lost_found_lead` 的 accept：`active` → `matched`；
- `close_lost_found`：`active` → `closed`；
- `expire_lost_found_posts`：`active` → `expired`；
- `edit_lost_found`：`expired` → `active`（编辑时把过期的救回来）。

四处里有三处的前置条件都是 `status == 'active'`。一条记录一旦变成 `matched`，
**发布者再也关不掉它，过期任务也再也不碰它。** 于是有一类记录会这样留在库里：
`expires_at` 早就过了，`status` 还是 `matched`，它不出现在公开列表里
（`_lost_found_queryset` 只放 `active`），却一直挂在发布者的「我的失物招领」里。

这不是一个理论上的边角。它是**这条链路唯一的出口被焊死**：确认匹配是失物招领的
成功结局，而成功结局没有自己的收尾路径。发布者能做的是继续编辑它
（`edit_lost_found` 只救 `expired`，不救 `matched`），或者什么都不做。

`lost_found_lead_quality` 的 `matched_rate` 报的是「有多少条记录走到了这里」，
它不报「走到这里之后，这些记录现在是什么样子」。后者才是运营能动手的地方：
如果一大批 `matched` 记录的 `expires_at` 已经过了一个月，说明发布者以为这事已经
结了，而系统里它还挂着一个没人收尾的状态。

## 这个模块报什么

只读，不加迁移、不加字段、不改模型、不改任何写入路径。

### 一、确认匹配的记录，此刻停在四种终局的哪一种

按 `status` 拆 `matched` 之后的记录，四种状态分开数：

- **仍标记已匹配**：`status == 'matched'`，发布者没再做任何操作。这是默认结局。
- **又被关掉了**：`status == 'closed'`。当前代码里做不到，所以这一档预期是空的——
  但它是**预期的空**，不是「没数据」。报出来，是为了让「单向门」这件事在看板上
  看得见：一栏永远是 0 的状态，比一段注释更难被忽略。
- **又过期了**：`status == 'expired'`。同样做不到，同样预期为空。
- **回到寻找中**：`status == 'active'`。编辑一条 `matched` 记录**不会**把它救回
  `active`（`edit_lost_found` 只救 `expired`），所以这一档也预期为空。

四档都报，`MIN_BUCKET_SAMPLE` 以下只报数字不给方向，空分母报「—」不报 0。

### 二、挂了一个月的「已匹配」：截止时间已过，状态还没动

这是本模块的核心一问。`matched` 记录里 `expires_at` 已经过了的，按「过期多久」分档
报。它回答的是「发布者以为这事结了，系统里却还挂着」有多普遍。

分档按天：0-7 天、7-30 天、30 天以上。理由和其余模块一致——失物招领的时间尺度是
天，报「19 小时」会让运营以为是小时级的问题。

**不报取消率，不报这批记录后来有没有被重新打开。** 一条 `matched` 记录挂着没动，
可能只是发布者忘了，也可能是他觉得没必要收尾。观测数据里分不开这两者，所以只报
「挂着」这个事实。

### 三、匹配是双向的，另一条记录跟上了吗

`accept` 会把关联记录也置为 `matched` 并互填 `matched_post`。但那条关联记录可能是
**发布者后来自己删了、或者它的 `matched_post` 指向了别处**。报「互为匹配」和
「单边匹配」两类：

- 互为匹配：`A.matched_post == B` 且 `B.matched_post == A`，两边都停在 `matched`；
- 单边匹配：只有一边填了 `matched_post`，或者另一边已经不在 `matched` 了。

单边匹配不是 bug——用户可能删掉了自己那条记录。但它是「这次匹配在两边眼里是不是
同一件事」的直接证据，而这件事此前没有任何读者。

**不报另一条记录的标题、不报发布者是谁。** 两边都是真实用户，一条失物招领的标题
可能写着「身份证  XXX」。

### 四、确认之后，反馈回来了没有，按终局拆

`lost_found_lead_quality` 已经报了 `accepted` 记录的反馈提交率。这里按**终局状态**
再拆一次：仍标记 `matched` 的、和其余终局的，各自提交反馈的比例。

为什么要拆：一条 `matched` 挂着没人收尾的记录，和一条已经 `closed` 的记录，
发布者回来填反馈的动机完全不同。混在一起报，会把「没收尾的记录也没人填反馈」
这个信号稀释掉。而这个信号正好指向同一件事——**收尾路径缺失**。

不重复那个模块的结论。它报的是反馈维度（提交率、完成率、标签），这里报的是终局
维度（哪种终局的记录更有人回来填）。

## 明确不做的事

- **不加迁移、不加字段、不改模型。** 只读。
- **不改 `close_lost_found` 的前置条件。** 它在 `status == 'active'` 时才允许关闭
  是对的——一条已匹配的记录该不该允许关闭，是产品决策，不是一个看板模块该替运营
  做的决定。本模块把这个决定的结果读出来，不替任何人做这个决定。
- **不自动替任何人收尾。** 不把过期的 `matched` 记录改成 `expired` 或 `closed`。
  自动改状态是替用户做决定，而且会抹掉本模块要观测的对象。
- **不改 `expire_lost_found_posts` 的过滤条件。** 它只扫 `active` 是有理由的：
  一条已匹配的记录不该被「过期」这个词描述。改掉它，观测对象就没了。
- **不报取消率、不报这批记录后来有没有被重新打开。** 见第二节。
- **不按用户排名、不报任何用户名、不列任何记录标题。** 谁在什么时候确认了哪条
  失物招领是用户的私事。记录 ID 可以报，它是数字不是身份；标题不报，因为标题是
  自由文本，可能写着证件号。
- **不重复 `lost_found_lead_quality` 的任何结论。** 那个模块报线索维度（收到几条、
  确认率、驳回分类、反馈提交率），本模块报终局维度（确认之后记录停在哪、挂了多久、
  匹配是不是双向的）。两处的 `matched` 口径不同：那个数「走到 matched 的记录有几
  条」，这个数「matched 之后的记录现在是什么样子」。

## 门槛

- `MIN_BUCKET_SAMPLE = 12`：一档要给方向，至少 12 条记录。全站统一量级。
- `MIN_MATCHED_POSTS = 12`：匹配记录总数低于此数时，整张表只报数字不给方向。
- 空分母报 `None`，模板显示「—」，不报 0。
- 右删失样本单独数：`expires_at` 为空的 `matched` 记录不计入「过期多久」的分布，
  单独数出来——没有截止时间的记录谈不上过期。
