# 失物招领的线索，有多少条走到了「已确认」

## 起点

`LostFoundPost` 是站内唯一一条「我丢了 / 我捡到了」的记录。模型有二十个字段，核心是这些：

- `reporter` —— 发布者。
- `post_type` —— `lost` 我丢失了 / `found` 我捡到了。**两条记录只有类型相反才可能匹配**，`LostFoundPost.clean()` 直接挡掉了同类型匹配。
- `title` / `description` / `identifying_features` —— 标题、详细描述、颜色与辨识特征。
- `category` / `location` / `occurred_at` —— 分类、地点、发生时间。这三个字段是 `score_lost_found_posts` 的打分依据。
- `status` —— `active` 寻找中 / `matched` 已匹配 / `closed` 已关闭 / `expired` 已过期。
- `matched_post` —— 指向另一条相反类型的记录。
- `expires_at` —— 信息截止时间，可空。
- `view_count` / `created_at` / `updated_at`。

`LostFoundLead` 是它的线索表，一条线索 = 一个人（`respondent`）看到一条记录后私下提交的联系方式：

- `post` —— 指向哪条记录，`ForeignKey`。
- `respondent` —— 线索提供者。
- `related_post` —— 这条线索带来的另一条记录（例如有人捡到了，顺手把自己手里那条也挂上来）。
- `message` —— 线索说明，`TextField`，必填。
- `status` —— `pending` 待确认 / `accepted` 已确认 / `rejected` 暂不匹配 / `withdrawn` 已撤回。
- `created_at` / `updated_at`。

约束有两条：`UniqueConstraint(fields=['post', 'respondent'])`（同一条记录、同一个人只有一条线索，可以改，不能重复提交），以及 `clean()` 挡掉「给自己发布记录提线索」。

写入路径有四条，全部在 `views.py`：

1. `lost_found_detail`（GET）—— 展示记录、它的匹配候选（`find_lost_found_matches`）、已收到的线索，以及给非发布者看的 `LostFoundLeadForm`。
2. `lost_found_detail`（POST，提线索）—— 非发布者可以提交，`LostFoundLead.objects.filter(post=post, respondent=request.user).first()` 取已存在的，所以是「提交或更新自己的那一条」，建完通知发布者。
3. `review_lost_found_lead`（POST，`accept` / `reject`）—— **仅发布者本人**。`accept` 做四件事：这条线索改成 `accepted`、`record_lost_found_lead_contribution` 记贡献、记录改成 `matched`、**同一条记录下其余 `pending` 的线索全部批量改成 `rejected`**；如果带了 `related_post`，那条也改成 `matched` 并互相挂上 `matched_post`。然后通知提供者。`reject` 只改这条线索的状态，也通知。
4. `submit_lost_found_feedback`（POST）—— 发布者对一条 `accepted` 的线索提交 `MutualAidFeedback`，一条线索只能提交一次（`OneToOneField`），`outcome` 是 `completed` / `unresolved` 二选一。

读取路径：详情页给发布者列自己收到的线索、给所有人列匹配候选；后台列给管理员；`mutual_aid_feedback_insights` 把已确认的线索并进「已确认互助」这个总数。

## 为什么这是真缺口

失物招领这条链路是站内**唯一一条「不经过交易就完成的互助」**。它没有 `Order`、没有价格、没有交付确认，走的是「发布 → 有人私下提线索 → 发布者确认 → 双方自己联系」四步。它的成败标准也很朴素：**发布者确认的那一条线索，是不是真的把东西找回来了。**

而这四步每一步都在写库，**没有任何一处把它们连起来看过。**

具体到四个答不上来的问题：

1. **一条记录平均收到几条线索。** `LostFoundLead` 有 `UniqueConstraint(fields=['post', 'respondent'])`，同一个人只能有一条；但一条记录可以被很多人提。一条记录收到几条线索，决定它是「没人看见」还是「看见了但不敢认」。现在这两个形状在总数上长得一模一样——都是 1 条记录、1 条线索。

2. **线索被确认的概率有多大，按记录类型拆。** `lost` 和 `found` 是两个完全不同的处境：丢东西的人发一条，等着捡到的人来；捡到的人发一条，等着丢东西的人来。哪一边更容易收到能确认的线索，现在没人知道。

3. **确认之后，东西找回来了没有。** `MutualAidFeedback` 的 `outcome` 是 `completed` / `unresolved`，而失物招领是它两个来源之一（另一个是 `DemandResponse`）。`mutual_aid_feedback_insights` 把两个来源**并进一个「已确认互助」的总数**里报完成率——一个失物招领的完成和一个求购响应的完成在那个面板里是同一个数字。而这两件事的难度天差地别：求购响应是「我手里正好有你要的」，失物招领是「我捡到的东西正好是你丢的」。

4. **没被确认的线索，是被拒了还是被撤回了。** `rejected` 是发布者说「暂不匹配」，`withdrawn` 是提供者自己撤的。这两件事对发布者的意义完全相反：前者说明线索质量有问题，后者说明有人本来想帮忙又改了主意。而现在它们都在 `status` 字段里，没有任何统计区分过。

更麻烦的是第五件事：**一条记录收到多条线索时，`review_lost_found_lead` 的 `accept` 会把其余 `pending` 的线索全部批量改成 `rejected`。** 这是正确的产品行为——一条失物确认匹配了，其余的候选自然就不再需要。但它意味着「被驳回的线索」里有很大一部分**不是发布者一条条看过之后拒绝的，而是被一条 `accept` 顺带清掉的**。把这两类混在一个「驳回率」里报，会得出「发布者很不认可大家提供的线索」这个完全错误的结论。**本模块要做的第一件事，就是把它们分开。**

## 口径上的取舍

### 确认率按 `post_type` 拆，不按总数报

`lost` 和 `found` 各算自己的：发了多少条、收到多少条线索、确认了多少条。

不报一个总的确认率。丢东西的人主动发一条，和捡到的人主动发一条，面对的候选池大小和认领意愿完全不同。合并成一个数之后，运营看到的是「失物招领整体确认率 42%」，而这个数无论往哪边动都无法定位问题。

### 分母是记录数，不是线索数

「一条记录收到几条线索」的分布，**分母是记录数**。一条收到三条线索的记录，在这个分布里只出现一次。

这和交易评价覆盖率、免费领取队列、有货关注集中度是同一个道理：按线索数走会让「3 条线索」那一档被同一批记录撑三次，而它其实只是几条记录的真实热度。

### 记录的类型不混：`lost` 和 `found` 分开报

同一条链路，两种处境。丢东西的人发的是「寻找」，捡到的人发的是「归还」。**匹配的候选池在两边是完全不同的**——一条「捡到校园卡」的记录可能收到十几条线索，一条「丢失校园卡」的记录可能一条都没有，因为捡到的人更倾向于直接发帖而不是私信丢卡的人。

### 被批量清掉的线索，单独数，不算「发布者拒绝」

`review_lost_found_lead` 的 `accept` 会把同一条记录下其余 `pending` 的线索 `update(status='rejected')`。**这些线索不是发布者拒绝的，是另一条线索被确认时顺带清掉的。**

本模块的做法：一条线索如果是 `rejected`，去看这条记录有没有 `accepted` 的线索。**有的话，这条 `rejected` 归「另一条被确认时顺带清掉」；没有的话，归「发布者看过之后拒绝」。** 两类单独报。

这不是抠字眼。如果失物招领的「发布者拒绝率」里有 80% 其实是批量清理造成的，那运营看到的「发布者不认可线索」是一个纯粹的技术副产物，而它会直接导致错误的动作——比如去提醒发布者多看看线索，或者给发布者加确认引导。而真实情况可能只是这个功能运转得很好：确认得很快，其余候选自然就没用了。

### 线索提交间隔按小时分档，不按天

一条失物招领的线索，时间尺度是小时到天。一条「丢失校园卡」的记录可能在发布当天下午就收到三条线索，也可能一周后还有人看到。

**分档按小时起步、按天封顶**：6 小时内、6-24 小时、1-3 天、3 天以上。只报发布者收到第一条线索的时刻——那是「这条记录有没有被看见」的第一个信号，后续的几条是热度，不是时效。

### 只报「写了没写」和长度，一个字符内容都不读

`LostFoundLead.message` 是自由文本，`TextField` 必填。它可能写着电话、微信、楼栋号，也可能写着「我在食堂三楼捡到一个黑色书包」。

本模块只报填写率（必填字段，理论上恒为 100%，但 `blank` 之外还有空字符串的可能，报出来是给数据质量兜底）和长度分档。**不切词、不聚类、不抽关键词。** `mutual_aid_feedback_notes.py` 已经为互助反馈的 `note` 做了切词，那是另一个字段、另一套约束，本模块不把它复制过来。

### 完成率只报失物招领自己的，不和求购响应合并

`MutualAidFeedback` 有两个来源，`lost_found_lead` 和 `demand_response`。本模块只读 `lost_found_lead__isnull=False` 的那批，单独报完成率。

**不和 `demand_response` 合并。** `mutual_aid_feedback_insights` 把它们并进一个「已确认互助」总数，那是那个模块的口径——它看的是互助反馈这个环节本身的运转。本模块看的是失物招领这条链路走通没有，合并会让两个难度完全不同的东西互相稀释。

### 没提交反馈的已确认线索，单独数

`submit_lost_found_feedback` 的入口只对 `accepted` 的线索开放，一条线索只能提交一次。**但提交反馈不是确认线索时的强制动作**——`review_lost_found_lead` 的 `accept` 分支里没有任何东西引导发布者之后去填反馈。

所以「已确认但没提交反馈」是一个真实存在的中间状态：东西可能找回来了，发布者只是没回来填；也可能没找回来，发布者觉得没必要填。本模块把它单独数出来，**不猜测是哪一种**。

### 不按用户聚合、不排名、不报任何人的名字

`respondent` 和 `reporter` 都只是用来判断方向的。**不报「谁提供的线索最多」、不报「谁的记录最多没人认领」、不报任何用户名。**

失物招领是站内信任浓度最高的一条链路，把它做成排行榜会直接毁掉它——一个「提供线索排行榜」会让帮忙变成刷分，一个「没人认领的记录排行榜」会让丢东西的人难堪。清单第一格只带记录标题和线索编号，那是运营要认出来的东西。

## 不做什么

- **不改 `review_lost_found_lead` 的批量清理逻辑。** 一条失物确认了，其余 `pending` 的线索确实不再需要，这个行为是对的。本模块只是把它的副作用读出来，不让它伪装成「发布者的判断」。
- **不改 `submit_lost_found_feedback` 的入口，不催反馈。** 催来的反馈不是反馈，是应付。
- **不读 `identifying_features`、`message`、`note` 的任何一个字符。** 颜色、品牌、贴纸、挂件这些特征字段是为了让双方核对的，不是为了被统计的；`message` 同理。
- **不改 `score_lost_found_posts` 的权重，不评价匹配质量。** 那个函数是给用户看的「为什么这条可能相关」，本模块看的是「确认这一步走成了没有」。匹配得好不好和确认不确认是两件事，混在一起会让两边都说不清。
- **不做「疑似骗线索」检测。** 短时间内给大量失物记录提线索是可疑的，但把一个具体的人标成「疑似骗线索」需要一个能站得住的判据，而本模块没有。宁可看不见，不可冤枉。
- **不改 `expires_at` 的默认值，不自动过期。** 过期是 `LostFoundPost` 模型层的事，本模块只报已过期的记录规模，不动它。
