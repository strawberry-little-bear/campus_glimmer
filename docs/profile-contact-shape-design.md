# 联系方式的形状：四个手写字段，第一次被数字读到

## 起点

`Profile` 上有四个由用户亲手填写的字段：

- `phone` —— 电话，`CharField(15)`，可空。
- `wechat` —— 微信，`CharField(50)`，可空。
- `bio` —— 个人简介，`TextField(500)`，可空。
- `student_id` —— 学号，`CharField(20)`，可空。

四个字段的写入路径只有一处：`ProfileUpdateForm`（`accounts/forms.py`）。四个都允许 `blank=True`，
四个都挂着 `max_length`——也就是说，**四个都有规则**。

## 为什么这是真缺口

四个字段在业务模块里的读者数为零。逐个核过模板，站内的展示面是这样的：

| 字段 | 采集上限 | 站内展示位置 |
| --- | --- | --- |
| `phone` | 15 字 | 会话侧栏「联系方式」块（`chat_messages/conversation.html`） |
| `wechat` | 50 字 | 同上 |
| `bio` | 500 字 | 资料页、公开资料页、会话侧栏、商品详情，共四个模板 |
| `student_id` | 20 字 | **只有自己的编辑表单**，全站零展示 |

也就是说：

1. **电话和微信只有一处曝光，而且要走到会话里才看得见。** 交易双方必须已经谈起一件事，
   才可能注意到对方留没留电话。
2. **`student_id` 被采集，然后没有任何一个页面、任何一个数字再读它。** 它甚至是四个字段里
   唯一一个采集了却连展示面都没有的。
3. **四个字段的长度上限，从来没有被任何一个数字度量过。** 一条 15 字的电话、一个 45 字的
   微信号、一段 450 字的简介、一个 18 字的学号——这些阈值在产品规则里写着，运营看不到
   有没有人在撞它们。

前两个问题的共同点是：**它们都是采集规则的效果，而这个效果从来没有被度量过。** 站内其它带
校验器或带上限的字段几乎都有读者——`borrow_days` 有 `borrow_days_shape`，押金档有
`borrow_risk`，5 MB 证据上限有 `dispute_evidence_shape`，积分等级有
`contribution_tier_shape`。唯独这一组字段，上线之后没有任何一个数字回答过「有多少人填了、
写得多长、留下联系方式的是谁」。

## 口径上的取舍

### 全量口径，不按周期切

联系方式是累计状态，不是流量。一个人三个月前留下的微信，这个月不会消失。按周期切会让「本期
新填」和「此刻留着的联系方式」混成同一个数，而运营问的是后者——此刻站内有多大比例的会话是
「看得见对方电话」的。

`days` 参数只为和看板其余面板的接口保持一致而收下，不做任何过滤。理由与
`contribution_tier_shape` 第一节相同：等级是累计量，联系方式也是。

### 分母是全部 Profile，不是有过交易的用户

按「有过交易的用户」当分母，会把「留不留联系方式」和「参不参与交易」焊死成一个问题，而第四节
正是要把它们拆开来看。所以前三节的分母一律是全部 `Profile` 行。

`create_user_profile` 信号给每个新建用户建一行 `Profile`，但历史上直接 `User.objects.create`
或 `createsuperuser` 造出来的用户可能没有。**没有的那一行不在分母里，也不摊派进任何一档**，
单独数成 `orphan_user_count`。一个数不上的分母比一个错的分母好。

### 空白算未填

`strip()` 之后为空串的一律算未填。一个只打了几个空格再保存的用户，事实是没有留联系方式。
不 strip 会让「留了联系方式」的人数被空格撑大，而空格在会话侧栏渲染出来是空的。

### 长度档位取各字段自己的 `max_length`，不取分位数

四档是 `max_length` 的固定比例：不足一成、一成到五成、五成到九成、贴上限（≥ 90%）。换算成
字符数，电话的九成是 14，微信是 45，简介是 450，学号是 18。

**不取分位数**：一个每月都会移动的分位边界什么也说明不了，而这个数要能回答「上限是不是该调」
「学号的 20 字是不是太短」——只有固定档能回答这个问题。档位互斥、左闭右开、全列，包括
0 样本档：「没有人的简介写到 450 字以上」本身是结论，不是表格的缺口。

**贴上限那一档用整数算术算阈值。** `math.ceil(50 * 0.9)` 会得到 46——0.9 在二进制浮点里比
自己大一点点，`50 * 0.9` 是 45.000000000000004。而长度为 45 本来正好压线。用
`-(-9 * max_length // 10)` 算，50 的九成就是 45。

### 长度节的分母是填了该字段的人

没填的人没有长度。把他们摊派进任何一档，都会把「不足一成」撑成一个假的多数。填写率在第一
节，长度形状在第三节，**两节分母不同**，这一点必须在面板上写明，否则读者会拿两个占比对账。

### 站外可触达只数 `phone` 和 `wechat`

「站外可触达」指的是交易双方可以绕开站内私信直接找到彼此。`bio` 是给人看的自我介绍，
`student_id` 站内没有任何地方读它——把这两个算进「可触达」，这一节回答的就不是它想问的
问题了。

### 参与三项分开报，不并集也不交集

「有过对话」「下过买入订单」「发布过商品」三项各自独立取数。合起来就看不见「只逛不谈」和
「只发不买」是不是同一批人。全量口径，不限周期。

### 只报相关性，不讲因果

第四节把「有没有站外联系方式」和「有没有对谈、下单、发布」放在同一张表上。这是两个变量在这批
用户里的共同变化，不是因果。

**「留了联系方式的人更可能交易」这句话本模块不说，也不暗示。** 可能是留了联系方式的人本来
就更认真，也可能是交易过的人更愿意留——两种都解释得通，本模块没有能力区分。反过来也不说：
没留联系方式的人可能只是不需要，不是不参与。

## 明确不做的事

- 不加迁移、不加字段、不改模型、不改任何一个 `max_length`。只读。
- 不输出任何字段值。不列用户名、不列手机号、不列微信号、不列学号。
- **不读 `bio` 的正文。** 它是自由文本，读它会牵出「谁写了什么」。本模块只报它的长度。
- 不按用户排名、不输出任何名单。
- 不判断「微信号是不是真的」「电话格式对不对」。`phone` 是 `CharField`，站内没有任何电话
  格式校验器，一个填到 15 字的用户只是刚好撞上 `max_length`，不代表那串数字能打通。本模块
  只报长度形状，不报有效性。
- 不报「改过几次」。`Profile` 上没有 `updated_at`，也没有字段变更历史表，这个数不知道，不编。
- 不自动补全、不提醒任何人填写、不因为某个字段填写率低就去改表单或改默认值。
- 不读 `avatar`。
- 不把「填写率低」读成「这个字段该删」。一个字段没人填，可能是不该问，也可能是问的时机不对；
  本模块只把现状读出来，删不删是另一个决定。

## 门槛

- `MIN_FIELD_SAMPLE = 12`：要给一个字段的填写率或某一长度档一个占比方向，至少 12 份资料。
  低于这个数，一个百分点的波动就是一个人。
- `MIN_GROUP_SAMPLE = 12`：要给一组（留了 / 没留站外联系方式）的参与率一个方向，至少 12 个
  用户。
- 空分母报 `None`，模板显示「—」，不报 0。分子 0、分母存在时报 `0.0`，两者不是一回事。
- 百分点差值不满 `NOISE_POINTS = 8` 视为噪声，不给方向。全站同一套。
