设计文档：一次交付安排被改了几次才定下来。

## 现象

`MeetingAppointment` 上有四个「时间」和一个「人」的字段（`models.py` 481-513 行）：

```python
proposed_by      = ForeignKey(User, related_name='proposed_appointments')
responded_by     = ForeignKey(User, null=True, related_name='responded_appointments')
responded_at     = DateTimeField('回应时间', null=True)
start_at         = DateTimeField('开始时间')
end_at            = DateTimeField('结束时间')
```

它同时是 `OneToOneField(order)`——一笔订单最多只有一条交付安排，摆在那里的时间
是「当前这一版」。运行时另有一条不可变事件链 `MeetingAppointmentEvent`，保存
上线后每一次提议、改期、接受、拒绝和订单取消。写入路径全在业务事务内：

- `propose_meeting` 第一次提交时 `get_or_create` 建成一条 `pending`，并写
  `proposed` 事件；
- 同一笔订单再次提交时，走的是 `if not created:` 这个分支——把 `proposed_by`、
  `start_at`、`end_at`、`location` 全部改写，`status` 打回 `pending`，
  `responded_by` / `responded_at` 清空，再写 `rescheduled` 事件和兼容用的订单备注；
- `respond_meeting` 把 `responded_by` / `responded_at` 写上，
  `status` 改成 `confirmed` 或 `declined`，再写一条
  `accepted` 或 `declined` 事件；
- `transition_order` 取消订单时，把预约同步改为 `cancelled` 并写 `cancelled` 事件；
  没有预约的订单取消不凭空生成预约事件。

`MeetingAppointmentEvent` 保存当次提议的起止时间、地点和名称、发起人、回应人、
回应时间、拒绝原因与前后状态快照，已保存记录不可修改。上线前的预约没有事件链，
迁移不回填，也不从 `OrderEvent` 自由文本伪造历史。

订单详情现在先显示当前待办：提议人等待对方回应，另一方看到「轮到你回应」；
接受后提示安排已确认，拒绝后允许重新提议，取消后停止协商。事件列表按真实发生
顺序展示每次提议及其回应所指向的同一版时间、地点快照。旧预约没有事件时只显示
当前安排；首条事件就是 `rescheduled` 时明确标为不完整记录，不把上线后的首个改期
当作首个提议。

当前读取路径集中在五处：`admin.py` 列给管理员看，
`templates/listings/orders/_appointment.html` 只向订单买卖双方展示当前回合与真实事件链，
`meeting_attendance.py` 读响应时长与到场，`meeting_reschedule.py` 读改期形状，
`meeting_scheduling.py` 读推荐。用户页面先提交订单参与者校验，再读取事件。

`meeting_attendance.py` 已经回答了两个问题：对方多久回应一个提议、约了时间的
订单里有几个人真的到了现场。它读的是「一条提议从交上去到被回应」这一段。
而这个模块要回答的是它前面那一段：**一条提议在定下来之前，被改过几次。**

## 为什么这件事值得做

「改期」是交付安排里唯一一个双方意见不一致的信号。一次谈成，说明第一次提议
就合适；改了三次才定，说明这个时间对其中一方一直不合适，而另一方一直在迁就。

平台现在完全看不见这件事。一个把全部预约都按「一次谈成」统计的看板，会以为
交付环节的协商成本是零的。而实际上：

- 如果三成订单要改两次以上，那「推荐时间」这件事就是在浪费双方的时间——
  平台给出一个谁都不满意的时间，然后让两个人来回磨；
- 如果改期集中在一小部分订单上（改了四、五次才定），那这些订单是交付异常的
  高发地，该在排期推荐之外单独看；
- 如果改期时地点也换了，说明不只是时间不合适，是「约在哪」这件事也没达成
  一致——而地点推荐（`meeting_scheduling.py`）和地点运营（`CampusLocation`）
  各自都以为自己在管这件事。

三件运营动作的方向完全不同，而现在一个数字都没有。

## 设计取舍

### 1. 完整事件链精确计数，旧备注另报兼容下界

完整事件链必须从首条 `proposed` 开始。该链中：

- `proposed` 是首条提议；
- 每个 `rescheduled` 是一次改期；
- `accepted` / `declined` 回应它之前的最近一条提议；
- 订单取消保留 `cancelled`，不伪装成一次接受或拒绝。

因此改期次数是 `rescheduled` 的条数。上线前就已经存在的预约，上线后首次动作
即使写下了 `rescheduled` 事件，也因为缺少首条 `proposed` 而不算完整链，仍归
旧快照组。旧组只把 `OrderEvent(note='更新了交付时间安排')` 当作下界：有备注能
证明至少改过，没有备注仍是“没有可核对痕迹”，不能说成一次谈成。

页面与 CSV 分别报完整链总数、旧快照总数、能由备注确认改过的旧样本和没有痕迹的
旧样本。两类样本不混算；迁移不回填旧预约，不伪造上线前历史。

### 2. 「一次谈成」只在完整链中定义

完整链从 `proposed` 开始、没有 `rescheduled`，才称为一次谈成。旧快照不能可靠
区分“一次提议就成”和“改过但没留痕迹”，所以旧组只报有痕迹的下界和缺失数量，
不产出“一次谈成率”。把未知硬算成一次谈成会让协商成本看起来比实际低。

### 3. 分母只收「已经有了一条安排」的订单

统计的对象是订单，不是预约。一个从没安排过交付的订单（下单后直接取消、
或者还在更早的阶段），谈不到「改了几次」，不进分母。它单独数出来——
这部分是「连一次交付都没约上」的规模，属于订单阶段流的领域，这里只报规模，
不展开。

### 4. 首次回应和一次谈成的对照只在完整链里做

`meeting_attendance.py` 的首次回应取首条提议到首个接受/拒绝，后续改期不会把
它覆盖。这个模块只报一个对照：改过一次以上的订单，对方回最初那一版花了多久；
一次谈成的订单花了多久。两组各自过样本门槛、差值超过噪声带才给方向，旧快照
的兼容时长不进入这项方向判断。

这不是因果。改期多的订单可能本来就是难谈的商品（便宜的热门货、描述含糊的
二手物），而不是改期本身让回应变慢。看板上标注为对照。

### 5. 逐轮比较相邻提议的地点

完整事件链保留了每一版地点。统计优先按地点外键比较相邻提议，地点被删除后使用
当时保存的名称；任一相邻版本缺地点就计入不可测量，不并进“没换”。这直接回答
“哪些改期同时换了地点”。“改时间”是「这个点我没空」，“改地点”是「这个点
我不去」，两者的运营动作不同。

### 6. 谁在改期，只按角色分，不按用户名

完整链里的每个 `rescheduled` 都保存当次提议人，可以按买家 / 卖家计数，并识别
同一订单是否由双方都改过；不按用户名、不排名、不列是谁。旧快照只另报“最后一版
归谁”，不能冒充历史次数。一份「谁在反复改期」的清单是考勤表，不是运营数据。

### 7. 样本门槛 12，噪声阈值 8 个百分点

和其余模块同一个量级。校园场景下一笔交付安排的改动次数是个位数，十几条样本
上几个百分点的差距是噪声。

### 8. 与 `meeting_attendance.py` 共用同一组事件语义

首次回应的定义、逐轮提议与回应配对都在 `meeting_events.py` 中共用，避免两个
看板各算一套。到场率、迟到分档和异常交叉核对仍归 `meeting_attendance.py`；
本模块只读同一事件链做改期对照。两边的分档上界如果有意不同，必须写出原因。

## 不做什么

- 不回填上线前的预约事件，不从旧备注伪造未记录的时间、地点或提议人。
- 不自动改任何一条交付安排，不自动重发通知，不新增提醒类型。
- 不按用户排名、不列用户名、不把改期次数写回任何记录。
- 不改 `meeting_scheduling.py` 的推荐逻辑——推荐时间准不准是它的领域，
  这里只提供「推荐完之后有没有被改」这个读数。
- 只对旧订单的固定备注做精确字符串匹配，不读取自由文本内容，也不把备注当作
  完整历史。
