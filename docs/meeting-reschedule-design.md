设计文档：一次交付安排被改了几次才定下来。

## 现象

`MeetingAppointment` 上有四个「时间」和一个「人」的字段（`models.py` 481-513 行）：

```python
proposed_by      = ForeignKey(User, related_name='proposed_appointments')
responded_by     = ForeignKey(User, null=True, related_name='responded_appointments')
responded_at     = DateTimeField('回应时间', null=True)
start_at         = DateTimeField('开始时间')
end_at            = DateTimeField('结束时间')
```

它同时是 `OneToOneField(order)`——一笔订单最多只有一条交付安排，摆在那里的时间
是「当前这一版」。写入路径有三条，全在 `listings/views.py`：

- `propose_meeting`（936 行起）第一次提交时 `get_or_create` 建成一条 `pending`；
- 同一笔订单再次提交时，走的是 `if not created:` 这个分支——把 `proposed_by`、
  `start_at`、`end_at`、`location` 全部改写，`status` 打回 `pending`，
  `responded_by` / `responded_at` 清空，并写一条
  `OrderEvent(note='更新了交付时间安排，等待对方确认')`；
- `respond_meeting`（1036 行起）把 `responded_by` / `responded_at` 写上，
  `status` 改成 `confirmed` 或 `declined`，再写一条
  `note='双方确认了交付时间安排'` 或 `note='暂未接受本次交付时间安排'`。

也就是说，改期这件事在库里是有痕迹的，但痕迹不在 `MeetingAppointment` 上——
一条 OneToOne 的行被原地覆盖，前几版的时间、地点、提议人全都不在了。痕迹在
`OrderEvent` 的备注里。

而读取路径只有四处，没有一条是统计：`admin.py` 列给管理员看，
`order_detail.html` 显示给本人看，`meeting_attendance.py` 读响应时长与到场，
`meeting_scheduling.py` 读推荐。

`meeting_attendance.py` 已经回答了两个问题：对方多久回应一个提议、约了时间的
订单里有几个人真的到了现场。它读的是「一条提议从交上去到被回应」这一段。
而这个模块要回答的是它前面那一段：**一条提议在定下来之前，被改过几次。**

## 为什么这件事值得做

「改期」是交付安排里唯一一个双方意见不一致的信号。一次谈成，说明第一次提议
就合适；改了三次才定，说明这个时间对其中一方一直不合适，而另一方一直在迁就。

平台现在完全看不见这件事。一个把全部预约都按「一次谈成」统计的看板，会以为
交付环节的协商成本是零的。而实际上：

- 如果三成订单要改两次以上，那「推荐时间」这件事就是在浪费双方的时间——
  平台给出一个谁都不满意的时间，然后让两个人来回磨；
- 如果改期集中在一小部分订单上（改了四、五次才定），那这些订单是交付异常的
  高发地，该在排期推荐之外单独看；
- 如果改期时地点也换了，说明不只是时间不合适，是「约在哪」这件事也没达成
  一致——而地点推荐（`meeting_scheduling.py`）和地点运营（`CampusLocation`）
  各自都以为自己在管这件事。

三件运营动作的方向完全不同，而现在一个数字都没有。

## 设计取舍

### 1. 改期次数从 `OrderEvent` 反推，报的是下界

`MeetingAppointment` 是 `OneToOneField(order)`，一条行被原地覆盖，没有版本表。
唯一能证明「改过」的是 `propose_meeting` 写下的那条事件备注
`更新了交付时间安排，等待对方确认`。所以：

- 改期次数 = 同一笔订单的这条备注的条数；
- 一次都没改过的订单，这条备注是 0 条，称为「一次谈成」。

这只能给出下界。两条丢失的情况要说清楚：

1. `OrderEvent` 是后来才有的表。如果一笔订单的安排是在它上线之前改的，
   痕迹不在，会被算成「一次谈成」；
2. 备注是自由文本，`note__contains='更新了交付时间安排'` 是按子串匹配的。
   如果将来有人把这句话改了，统计会静默地少算。

这和 `handoff_code_usage` 从站内通知反推确认码重新生成次数是同一个处境：
证据是间接的，报出来的数只能是下界。看板上如实写「报的是下界」，而不是给
一个看起来精确的次数。

### 2. 「一次谈成」的定义是 0 次改期，不是 1 次提议

一笔订单从没进过 `propose_meeting`，或者进了但一条事件都没留下，都算 0 次改期。
两者在统计上不可区分，也不必区分——平台关心的是「有没有人来回改」，
不是「有没有人提议过」。提议过但没留下痕迹的订单，归到「一次谈成」里去，
会让这个数偏大；这是宁可接受的偏差，因为反方向（把没改过的算成改过）需要
证据，而这里没有。

### 3. 分母只收「已经有了一条安排」的订单

统计的对象是订单，不是预约。一个从没安排过交付的订单（下单后直接取消、
或者还在更早的阶段），谈不到「改了几次」，不进分母。它单独数出来——
这部分是「连一次交付都没约上」的规模，属于订单阶段流的领域，这里只报规模，
不展开。

### 4. 改期之后的响应时长，和一次谈成的分开报

`meeting_attendance.py` 已经报过响应时长的总体中位数。这个模块不复述那个数，
只报一个对照：改过一次以上的订单，对方回应当初的那一版花了多久；一次谈成的
订单花了多久。两组各自的样本过门槛、差值超过噪声带才给方向。

这不是因果。改期多的订单可能本来就是难谈的商品（便宜的热门货、描述含糊的
二手物），而不是改期本身让回应变慢。看板上标注为对照。

### 5. 改期时的地点换没换，单独一节

`propose_meeting` 的 update 分支会连 `location` 一起改，`Order.meeting_location`
也会跟着同步。所以「改时间」和「改地点」在写入路径上是同一个动作，但读出来的
含义完全不同：改时间是「这个点我没空」，改地点是「这个点我不去」。

地点更换只能和「当前这一版」比——前几版的地点被原地覆盖了，库里没有。
所以这一节报的是「最后一次改期时，地点和现在这一版不一样」的订单占多少，
而不是「地点改过几次」。这个上界是硬的：平台没有存过历史地点。

### 6. 谁在改期，只按角色分，不按用户名

`proposed_by` 和 `responded_by` 都在。按角色（买家提的 / 卖家提的 / 双方都提
过）分组报，不按用户名、不排名、不列是谁。一份「谁在反复改期」的清单是考勤表，
不是运营数据；而且它最可能的用法是去找人，那正是这个看板不该做的事。

### 7. 样本门槛 12，噪声阈值 8 个百分点

和其余模块同一个量级。校园场景下一笔交付安排的改动次数是个位数，十几条样本
上几个百分点的差距是噪声。

### 8. 不碰 `meeting_attendance.py` 已经报过的数

响应时长的中位数、P90、到场率、迟到分档、异常交叉核对——这些都在
`meeting_attendance.py` 里，这个模块只引用它们的结论，不重算、不改口径。
两边的分档表如果对不上，运营会以为其中一个看板是错的。

## 不做什么

- 不改 `propose_meeting` 的 update 分支，不引入版本表，不加字段。
- 不自动改任何一条交付安排，不自动重发通知，不新增提醒类型。
- 不按用户排名、不列用户名、不把改期次数写回任何记录。
- 不改 `meeting_scheduling.py` 的推荐逻辑——推荐时间准不准是它的领域，
  这里只提供「推荐完之后有没有被改」这个读数。
- 不读任何自由文本的内容，只数字符串匹配的条数。
