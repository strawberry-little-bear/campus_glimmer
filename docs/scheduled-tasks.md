# 后台与定时任务

[返回 README](../README.md) · [功能手册](feature-handbook.md#78-任务台账七个定时命令过去跑得怎么样) · [Docker 与部署](../README.md#docker-与部署)

> 本文档集中维护定时命令、周期建议、幂等边界和运行台账。README 只保留启动入口与常用命令。

项目将需要周期执行的工作封装成 Django management command，便于接入 Windows 任务计划程序、cron、容器任务或其他调度系统。

### 预约超时处理

发送临近截止的提醒，并释放已经过期的预约：

```bash
python manage.py process_order_timeouts
python manage.py process_order_timeouts --reminder-hours 6
```

该命令同时检查限期借用订单：在预计归还时间临近时提醒借用双方，超过归还时间后发送逾期提醒；每个提醒阶段都带有幂等字段，重复运行不会重复刷屏。

同一次运行还会走一遍借用逾期催收阶梯：逾期满 1 天提醒借用方，满 3 天同时告知双方，满 7 天上报治理工作台。等级按「逾期了多久」推导，漏跑一次下一次会自动追上；同一笔订单两次催收至少隔一天；双方确认归还后记录立即闭环。

### 历史商品图片变体与展示宽高回填

新上传图片会在保存时生成最长边 480px 的列表缩略图；原图最长边超过 960px 时再生成 960px 大图预览，小图不重复落盘。历史图片不必停机一次性处理，可以用幂等命令分批补齐缩略图、预览图和宽高：

```bash
python manage.py backfill_item_thumbnails --dry-run
python manage.py backfill_item_thumbnails --limit 100
```

命令按 `id` 升序处理缺失变体或展示宽高的记录；已有缩略图的记录只补预览图或元数据，不重复生成文件。单张历史图片解码失败时只计入失败数并继续处理后续记录。每次运行都会写入 `TaskRun` 台账，保存检查数、补齐数、失败数和跳过数；剩余待处理量由命令输出，便于决定下一批的 `--limit`。它是上线辅助命令，不是周期任务；全部补齐完成后可以停止调度。

### 商品展示到期处理

将超过展示截止时间的在售商品自动下架，并向商品发布者发送一次到期提醒。该命令设计为幂等操作，可以安全地接入定时任务：

```bash
python manage.py expire_items
```

建议每天运行一次；即使命令没有及时执行，公开列表、推荐和创建订单时也会再次校验截止时间，避免过期商品继续被预约。

### 运营告警日报

按统计周期构建运营告警，并向符合条件的活跃管理员发送站内通知：

```bash
python manage.py send_operations_digest
python manage.py send_operations_digest --days 30
```

可选周期为 `7`、`30`、`90` 或 `365` 天。命令没有发现告警时不会生成空通知；同一天、同一周期重复运行时也不会向同一管理员重复投递。

### 互助机会摘要

向存在有效商品或失物招领记录、且当前确实有可响应机会的用户发送每日摘要：

```bash
python manage.py send_opportunity_digest
```

摘要只在存在匹配机会时生成，用户可以在通知偏好中关闭；同一用户在同一自然日重复运行命令不会收到重复通知。建议将命令接入每天一次的计划任务，并与站内通知未读提醒配合使用。

### 校园专题上新摘要

把用户主动订阅的校园专题新上架商品合并成一条站内摘要。加入专题本身不会自动订阅，只有用户在专题详情或“我的专题足迹”中明确打开提醒后才会进入候选：

```bash
python manage.py send_campaign_update_digest
python manage.py send_campaign_update_digest --frequency daily
python manage.py send_campaign_update_digest --frequency weekly
```

发送前会重新校验活跃报名、订阅开关、专题窗口、商品当前归属、可售状态和有效期；已售、已预订、已过期或已移出专题的命中只取消、不发送。同一用户在同一频率和同一周期内最多收到一条摘要，多个专题的命中会合并；每日与每周使用彼此独立的去重键。全局专题摘要偏好关闭或处于免打扰时段时，命中保留到后续运行，不提前回写为已发送。建议每日运行一次，每周摘要也由同一条命令覆盖；如果需要分开调度，使用 `--frequency` 指定。

### 关注搜索汇总提醒

把缓冲区里的关注搜索命中合并成一条通知，按用户和周期去重：

```bash
python manage.py send_saved_search_digest
python manage.py send_saved_search_digest --frequency daily
python manage.py send_saved_search_digest --frequency weekly
```

命令会回报发送、跳过、无命中和静默中的关注数量；处于静默期的关注只统计不发送，命中记录仍然保留。建议每日运行一次（或按需分别运行日订任务与周订任务，两者彻底独立，不会互相干扰）；重复运行安全且幂等。


### 商品生命周期提醒

把需要卖家处理的商品合并成一条站内通知，按冷却期控制节奏：

```bash
python manage.py send_lifecycle_reminders
python manage.py send_lifecycle_reminders --seller-id 12 --seller-id 34
python manage.py send_lifecycle_reminders --dry-run
```

命令会回报发送条数、两类提醒各覆盖多少卖家、回写了多少件商品的冷却时间、写入多少条事件台账，以及因关闭提醒、处于免打扰时段或缺少价格证据而跳过的卖家数。事件、合并通知与冷却字段在同一事务内写入；`--seller-id` 可重复传入，用于只补发某几个卖家；`--dry-run` 只统计，不写通知、事件或冷却字段，适合上线前确认影响范围。

去重键按“通知类型 + 日期 + 卖家”构成，同一天重复运行不会发出第二条，也不会重复回写冷却时间，因此可以直接接入系统计划任务。建议每日运行一次，与运营告警日报错开时间，避免同一批卖家在同一天收到多条长文通知。

提醒的触达与行动情况由运营看板的「生命周期提醒触达与行动」面板呈现：新发送优先读取事件台账，旧数据回退商品冷却时间戳，并单独标明事件、混合与旧时间戳口径，避免把覆盖差异误读为效果变化。

跨学期视角由「生命周期提醒的跨学期终态转化」面板呈现：它固定回看 420 天，只比较相邻学期的同一阶段；分母只读事件台账，方向只看提醒后 14 天内的订单终态动作，刷新时间因可被后续刷新覆盖而不参与纵向判断。

商品刷新事件台账已同步落地：只有通过限流的真实刷新才逐次落库，事件与累计计数同事务写入；台账上线前的历史缺口照实单列、不回填，完整行动史等覆盖稳定后再评估。

### 学期日历维护

学期日历本身不产生数据，它只是把已有记录按阶段重新聚合。因此只需要一个维护命令：

```bash
python manage.py sync_academic_calendar
```

命令做两件事：为启用中的学期补齐缺失的默认阶段，以及刷新各阶段的统计快照。默认两件事都做，也可以用 `--ensure-phases` 或 `--refresh-snapshots` 单独执行，或用 `--term-slug` 只处理某个学期。没有配置学时时命令会明确提示，不会静默失败。

建议在每学期开始前手工运行一次补齐阶段，之后按周刷新快照即可；阶段边界调整后同样需要重跑，否则看板仍会显示旧边界下的统计。

按周刷新留下的轨迹，现在可以在运营看板的「学期阶段快照质量」面板上读到。刷新出来的快照也不再是没人看的副本：看板对已结束的阶段直接读它，每一行都标着「读快照」或「实时算」。实时行还会继续拆开：阶段未结束是既定策略；已结束阶段缺行或区间不匹配则触发来源告警，说明当前只是实时兜底，并提示核对 `sync_academic_calendar` 与阶段边界，而不是自动补刷。要特别留一句：**改动学期的开始日期会让快照表留下成倍的孤儿行**——`AcademicPhase.start_date` 是算出来的属性，`starts_on` 一改，四个阶段的匹配键整体平移，旧行不会被更新而是被旁置，新键下另插一批新行。命令回报的“刷新阶段快照 N 条”不会有任何变化，只有面板能看出表从这一刻起多了一倍。阶段边界调整后重跑，同样建议顺手看一眼这块面板。

### 定时任务运行台账

九个带运行台账的管理命令过去都是「跑完就走」：各自打印一行摘要然后退出，发送了多少条、跳过了多少个卖家、有没有失败，只存在于进程返回值里。带来的两个后果是，看板回答不了「上周的提醒到底发出去没有」，而命令失败在项目内部也完全没有记录——只有调度器从退出码里知道出过事，排查一次漏跑只能去翻调度器日志。

现在每次运行都会留下一行 `TaskRun` 记录：

```bash
python manage.py send_lifecycle_reminders
python -X utf8 -c "from listings.models import TaskRun; [print(r.name, r.status, r.metrics, r.note) for r in TaskRun.objects.all()]"
```

接入方式对命令本身只增加一行上下文，返回值仍按原有方式打印，不影响任何现有输出：

```python
from listings.task_runs import normalise_metrics, record_task_run

with record_task_run('send_lifecycle_reminders') as run:
    result = send_lifecycle_reminders()
    run.metrics = normalise_metrics(result)
```

台账落库的数据进入运营看板的「定时任务运行台账与健康统计」面板，给出每个命令的运行次数、失败次数、最近状态、静默天数和连续失败次数，并汇总出需要优先处理的命令。看板还会先做一层台账完整性审计，确认时间、状态、备注和指标形状是否可读，再让读者进入健康度结论。
