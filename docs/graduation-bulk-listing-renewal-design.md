# 毕业季批量续期设计

## 要解决的问题

单件商品已经可以在编辑页把展示截止时间改到未来并重新上架；“我的商品”也能按生命周期识别即将到期和已过期的商品。但毕业季教材、宿舍用品这类短周期商品常常一次发布一整批，临近学期末时会同时到期。卖家现在只能逐件打开编辑页重复填写同一个截止时间，既容易漏改，也容易在多件商品之间填出不同的展示期限。

批量续期这一刀要把已经存在的单件续期能力扩展为批次操作：卖家在“我的商品”勾选多件本人商品，统一设置一个新的展示截止时间。系统先校验整批，全部合法才写入，避免出现“一半续期成功、一半没有变化”的半批状态。

## 目标

- 在“我的商品”的现有批量选择工具栏中增加“批量续期”动作，复用同一组商品勾选框，不另建选择机制。
- 批量续期必须填写明确的新展示截止时间；时间为必填。
- 新截止时间沿用商品编辑的同一时间口径：
  - 必须晚于当前时间；
  - 不能超过当前时间后 90 天。
- 只允许处理当前卖家自己的商品。
- 第一刀只允许两类商品续期：
  - 状态为“已过期”的商品；
  - 状态为“在售”且已有展示截止时间的商品。
- 已过期的商品在整批校验通过后恢复为“在售”；在售商品只更新展示截止时间。
- 服务端在事务中锁定所有请求商品并重新判断状态；只要存在不可续期、非本人或数量不匹配的商品，整批拒绝，不写入任何一行。
- 成功后提示续期数量与新的截止时间，并回到“我的商品”。
- 只更新展示截止时间、必要时的商品状态和 `updated_at`；不把批量续期伪装成主动刷新。

## 为什么整批失败而不是跳过

批量续期面向的是一次清理一批即将到期商品的场景。若跳过失败商品，卖家看到“已处理 8 件”时仍需要再逐件核对哪几件被跳过；后续把已售出或已预订商品误选进来的概率也会变高。整批失败让“这批没有生效”有明确信号，卖家可以先处理交易中的商品，再对剩余商品重新提交。

## 状态边界

- `expired`：允许。新时间合法时恢复 `available`，与现有单件编辑的重新上架语义保持一致。
- `available` 且已有 `expires_at`：允许。适合即将到期但仍在售的商品。
- `reserved`：第一刀不允许。商品可能处在预约或交易流程中，延长公开展示不应绕过订单状态。
- `sold`：不允许。交易已完成，续期没有业务含义。
- 长期展示商品（`expires_at` 为空）：不允许。它没有到期问题；“批量设置截止时间”是另一个语义，不混入本刀。
- 请求中不存在或属于他人的商品：不允许，并让整批失败。

## 明确不做

- 不做异步任务、排队和跨会话续期草稿。
- 不新增续期历史表；`updated_at` 只反映最近保存，不承诺还原每次续期轨迹。
- 不修改、重置或伪造 `last_refreshed_at` 与 `refresh_count`。
- 不触发主动刷新额度，也不写入商品刷新事件台账。
- 不触发保存搜索匹配、求购匹配、降价或生命周期提醒。
- 不把续期次数、批量规模或过期行为用于卖家标签、信用、排序或运营排名。
- 不处理“批量转长期展示”；续期必须给出新的明确截止时间。
- 不修改单件编辑页的既有行为。

## 验收口径

- 未登录访问跳转登录；GET 请求回到“我的商品”。
- 未勾选商品、缺少截止时间、时间已过去或超过 90 天时整批失败且数据库不变。
- 混入他人商品、已售出、已预订或长期展示商品时整批失败且数据库不变。
- 成功时本人在售且即将到期的商品更新截止时间，仍保持“在售”。
- 成功时本人已过期商品更新截止时间并恢复“在售”。
- `last_refreshed_at`、`refresh_count` 与商品刷新事件表不变。
- 匹配通知和生命周期提醒通知不新增。
- 页面继续使用同一组勾选框，批量专题与批量续期动作互不改变对方的表单提交。
