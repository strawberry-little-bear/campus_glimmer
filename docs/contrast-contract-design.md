# 文字对比度契约设计

## 问题

这个项目的界面大量使用「深绿渐变面板 + 浅色文字」和「米白底 + 暖色点缀」。这类配色有两个
共同点：单看任何一个色标都像是够深的，以及真正的对比度取决于若干层叠加之后的结果。深绿
面板的背景是一段多停止点线性渐变再叠两团径向高光，浏览器取到的颜色是逐层合成之后的那一
点；写样式时盯着最深的那个色标看会觉得余量很大，合成之后的最亮处却可能刚好跌到 4.5:1 以下。
DevTools 的点选取色抓不到这类问题——点中的那个像素恰好不是最亮处。

还有两种更隐蔽的形态。一种是半透明前景：`rgba(255,255,255,.76)` 不是「白字」，合成到深绿上
之后大约只剩 `#d2e0d8`，比值直接掉一整个档位，只看 `color` 声明会以为没问题。另一种是令牌
联动：`--muted` 被全站几百处引用，改一次就同时改掉所有次要文字，而它在暖色渐变面板上恰好
压在 4.5 的临界线上，差 0.01 就是不合格。

## 本轮范围

治理对象是「文字与它真正落在的底色」这一对，不是颜色本身好不好看。做法分两步。

第一步是用无头浏览器做真值审计：逐页把每个文字节点连同它合成出来的背景色一起读回来，
按 AA 公式复算。这一轮量完 53 个页面，从 463 处不达标降到 0。审计脚本不进仓库——它依赖
运行时环境和页面清单，留在仓库里只会腐烂；结论以契约测试的形式落下来。

第二步是把结论钉成静态断言，即 `campus_glimmer/test_contrast_contract.py`。它按与浏览器一致的
分层合成规则复算每个浅色文字位点的最坏背景：

- 一段多停止点渐变取「与前景比值最小的那个停止点」，即最坏情况；
- 半透明前景先按 alpha 合成到背景上，再算比值；
- 多层 `background` 从最外层祖先往里逐层合成；
- 选择器按逗号切开后逐个精确匹配，所以 `.contribution-page .account-hero-actions .btn-light`
  （白底深字）不会被误当成 `.account-hero-actions .btn-light`（深底透明白字）；
- 同特异性按文档顺序取最后胜出值，注释先剥掉。

具体钉住的位点分三类。位点类覆盖三块深绿面板（首页 hero、登录注册故事面板、账户中心 hero）
上的眼眉行、正文、信任条目、受益条目、提示胶囊、简介和次级按钮。令牌类覆盖 `--muted`、
`--primary`、`--primary-dark` 在所有浅色底面上的下限，以及全局 `code` 字色。规则类覆盖所有
局部改过 `code` 的规则：自己画了底板的，在自己的底板上算；只改字色的，按最坏情况拿最亮的
浅色底面试它。

## 为什么用静态契约而不是只留审计脚本

审计脚本给的是一个时间点的结论，契约测试给的是「以后每次改动都会重新检查」的保证。改渐变
色标、高光透明度、文字透明度或令牌值，测试会立刻变红，不必再为此起一轮浏览器审计。这一点
经过反向验证：把样式表换回治理前的两份备份，位点测试分别报 13 处和 8 处失败，令牌测试分别报 2 处和 3 处失败，没有一处漏过。

## 判据

- 这些位点的字号都小于 18.66px，一律按 4.5:1 要求，不吃大字豁免；
- `aria-hidden="true"` 的装饰性内容、禁用态控件和芯片里的序号属豁免范围，不进契约；
- 契约只覆盖浅色文字位点和会被大面积引用的令牌，不试图把全站每一条规则都搬进测试。

## 不做什么

- 不做全站 CSS 重写：只调整不达标的色标、透明度和令牌值，视觉方向不变；
- 不在测试里复刻整个层叠引擎：只覆盖已知会出问题的三类形状，剩余部分交给浏览器审计；
- 不把审计脚本收进仓库：它依赖运行时可复现性差，结论比脚本更值得留下；
- 不宣称「全站无障碍已完成」：键盘焦点顺序、窄屏布局和图片加载仍在逐页补齐，见[后续路线图](roadmap.md)。

## 验证

- 53 个页面的真实浏览器审计，`violations` 从 463 降到 0；
- `campus_glimmer.test_contrast_contract.py` 5 个测试全绿；
- 用治理前的两份样式表备份反向验证，契约确实会红；
- 完整测试集、`manage.py check`、迁移一致性检查与 `git diff --check` 均通过。
