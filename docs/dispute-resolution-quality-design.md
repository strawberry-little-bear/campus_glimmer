# 交易争议处理得公不公平，第一次被运营读到

## 起点

`OrderDispute` 是站内唯一一条「一笔交易走不下去，双方自己谈不拢，请平台介入」的记录。模型有十一个字段：

- `order` —— 哪一笔交易，`OneToOneField`，一笔订单最多一条争议。
- `opened_by` —— 谁发起的，买家或卖家。
- `reason` —— 争议类型，五种：`not_received` 未收到商品、`mismatch` 商品与描述不符、`payment` 价格或付款问题、`safety` 交易安全问题、`other` 其他争议。
- `detail` —— 争议说明，`TextField`，必填。
- `status` —— `open` 待处理 / `reviewing` 处理中 / `resolved` 已解决 / `rejected` 已驳回。
- `reviewer` —— 处理人，`SET_NULL`。
- `resolution_note` —— 处理意见，`TextField`，可空。
- `resolved_at` —— 处理时间，可空。
- `created_at` / `updated_at`。

写入路径有三处：`open_dispute`（双方均可，要求订单状态在 `confirmed` / `meeting` / `completed` / `borrowed` / `returned` 之一，要求这笔订单还没有争议，然后建记录、写 `OrderEvent`、通知对方）、`add_dispute_evidence`（双方均可，要求争议还在 `open` / `reviewing`，然后建 `OrderDisputeEvidence`、写 `OrderEvent`、通知对方）、`resolve_dispute`（仅 `is_staff`，写 `status` / `resolution_note` / `reviewer` / `resolved_at`，通知双方）。

`OrderDisputeEvidence` 是它的附件表：`dispute`、`uploaded_by`、`attachment`（限 5 MB、限 jpg / png / webp / pdf）、`note`（可空 300 字）、`created_at`。

## 为什么这是真缺口

`governance_sla.py` 已经把交易争议并进了治理队列，和商品举报、交付预约异常、借用逾期催收放在一张表里比时效。它回答的是「这条争议多久被处理」。

**它从来没有回答过另外三个问题，而这三个问题比时效更接近「治理公不公平」：**

1. **哪一类争议更容易被驳回。** 五种 `reason` 从来没有人分开比过。买家说「没收到商品」，卖家说「商品与描述不符」，这两类争议拿到的是同一个处理队列、同一个时限、同一个表单，但它们的举证难度完全不是一回事——「没收到」要看交付确认，「不符」要看聊天记录和实物照片。如果某一类争议被系统性驳回，那不是巧合，是举证责任在那一刻落在了更难举证的一方身上。而现在运营能看到的是总数：本期 12 条争议，9 条解决，3 条驳回。这三个驳回是哪一类，没人知道。

2. **证据提交得晚不晚。** `add_dispute_evidence` 的入口挂着，`open_dispute` 提交时 `detail` 已经必填。也就是说，**发起争议时说明是必须写的，附件是可选的**。一件争议从发起到处理完，中间补进来的附件是几点几分进来的，从来没有人算过。而附件进来的时刻，决定了处理人是带着材料判，还是先催材料再判——这直接影响 `governance_sla.py` 报的那个处理时长。两个模块报的是同一条争议的两端，却从来没有被放在一起看过。

3. **处理意见写了没有。** `resolution_note` 是可空的。`resolve_dispute` 把它和 `status` 一起写，但表单不强制——一个处理人可以只把状态从 `reviewing` 改成 `resolved`，一个字都不写，双方收到的通知里只有「商品 X 的争议已解决」。**争议是这个平台唯一一个「双方自己谈不拢、请第三方裁定」的环节，而裁定理由是可以留空的。** 一个只写了状态没写理由的解决，对双方来说和驳回没有区别：他们都不知道为什么。

更麻烦的是第二层：**从来没有人从「谁发起」这个方向看过争议。** `opened_by` 是买家还是卖家，一直只是数据里的一个字段。而它是这套治理里唯一的方向信号——一个只有买家发得起争议、发了总被驳回的流程，和买卖双方发起率相当、驳回率也相当的流程，在治理队列的总数上长得一模一样。

## 口径上的取舍

### 驳回率按 `reason` 拆，不按总数报

五种 `reason` 各算自己的：发起多少条、解决多少条、驳回多少条、还在处理中多少条。

**不报一个总的驳回率。** 总驳回率把五种举证难度完全不同的争议平均成一个数，而这个数一旦出现波动，运营第一反应是去查处理人，而不是去查是哪一类争议在涨。按 `reason` 拆开之后，「不符」类驳回率上升和「没收到」类驳回率上升是两条完全不同的线索。

### 证据只报「进来得多晚」，不读内容、不判充分性

按 `OrderDisputeEvidence.created_at` 减它所属争议的 `created_at` 算提交间隔，分档报。**只报进来了多少、进来得多晚、进来在什么状态下。**

不读 `note`（那是自由文本，可能写着电话、微信、楼栋号），不数附件个数，不判断「证据够不够」。平台没有能力判断一段聊天记录能不能证明「商品与描述不符」，这个判断只有处理人能做，而这个模块只是把处理人做过的事读出来。

也不按 `uploaded_by` 拆：谁传的附件本身不带方向，一条买家传的截图和一条卖家传的截图在统计上是对称的，拆开只会得到两个同样没有解释力的数。

### 「有没有附件」和「驳回不驳回」只做对照，不给因果

带至少一条附件的争议和不带附件的争议，各自算驳回率。

**只报对照，不给因果。** 一个发起时就附了截图的争议，可能本身事实更清楚、更容易被支持；一个什么附件都没有的争议，也可能只是用户不知道怎么上传。平台没有能力把「证据起了作用」和「这事本来就好判」分开。把它做成因果会直接变成对具体用户的负面标签——「你上次没传截图所以被驳回了」——那是这套治理最不该变成的东西。

两组各至少 8 条才给方向，差值不满 8 个百分点视为噪声。

### 发起方向只报「谁发起的」，不报任何人的名字

`opened_by` 是买家还是卖家，按比例报。**不按用户聚合、不排名、不报任何人的用户名。**

发起争议是一个人在一笔不顺利的交易里做的选择，把「谁最爱发起争议」做成一张排行榜，平台就从仲裁者变成了一个记录谁难相处的小本子。方向分布报的是流程本身是否对双方可用——如果只有一方发得起、发了总被驳，那流程就是偏的；如果双方发起率相当、驳回率也相当，那流程是中的。这是流程的性质，不是人的性质。

### 处理意见只报「写了没写」和长度，一个字符内容都不读

`resolution_note` 报填写率、长度分档。**不读内容、不切词、不聚类、不抽关键词。**

它是处理人写给双方的一段自由文本，可能写着电话、微信、楼栋号，也可能写着处理人的判断和情绪。这个模块只关心一件事：这段理由有没有被写下来。至于理由写得好不好，那是复核人该看的，而本模块不替代复核人。

### 已完结的争议才算进驳回率

分母只收 `status` 为 `resolved` 或 `rejected` 的争议。还挂在 `open` / `reviewing` 的是右删失样本：争议还没判，谈不上被驳回还是被支持，把它算进分母会让驳回率凭空变小。这部分单独数出规模，不丢也不混。

这和订单阶段流、归还握手、交易评价覆盖率是同一个道理。

### 处理时长只报「等材料花了多久」，不归因

一条争议从发起到结案，中间可能有一段是在等某一方补证据。本模块报两段：从发起到第一条附件进来隔了多久；从发起到结案隔了多久。

**不报「等材料花了多久」这个差值。** 一条争议结案慢，可能是材料来得晚，也可能是处理人忙，还可能是双方在谈。平台没有能力把这三件事分开，报一个差值等于把处理人的效率问题算成了用户的问题。两段各自单独报，运营自己判断。

## 不做什么

- **不改 `resolve_dispute` 的表单，不强制 `resolution_note` 必填。** 让它变成必填会让驳回率数字变好看，但会让处理人在没话说的时候写废话，而一段「经核实，情况属实」比空着更糟——它让双方以为理由已经给了。填写率是一个要被看见的数字，不是一个要被填满的格子。
- **不改 `add_dispute_evidence` 的开放状态。** 入口挂在 `open` / `reviewing` 两个状态下是正确的——一个人在争议提交三天后找到当时的聊天记录，比强制他在提交时一次性交齐更有价值。
- **不催证据、不催处理意见。** 催来的材料不是证据，是应付。
- **不按用户做任何聚合或排名。** 见「发起方向」一节。
- **不做「疑似滥诉」检测。** 短时间内集中发起争议是可疑的，但把一个具体的人标成「疑似滥诉」需要一个能站得住的判据，而本模块没有。宁可看不见，不可冤枉。
- **不改 `governance_sla.py` 的任何口径。** 那个模块报时效，本模块报质量，两边各报各的。本模块读的是它读的那批记录的另一半字段，不是它的替代品。
