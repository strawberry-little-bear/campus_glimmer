# 失物招领举报闭环设计

## 问题

失物招领这条链路此前的写路径只有三条：发布、编辑、提交线索。三条都由「想让东西回去的人」发起——
失主写自己丢了什么，拾获者写自己捡到了什么。但真实场景里还有第四种人：一个既没丢也没捡、只是看出来
这条记录不对劲的围观者。

常见的情况很具体。有人拿别人的失物信息当自己的发布，用来引流或约线下；有人在描述里写「看到联系
我」但不写地点，本质是套联系方式；有人反复发布同一条子虚乌有的信息占位置；还有人在详情里贴了别人的
校园卡和手机号，等于替陌生人公开了隐私。

这些情况此前只有一条出路：找管理员线下反映。问题是它不可见也没有痕迹——发布者不知道别人举报过
自己，运营不知道有多少条记录被举报过、处理到哪一步，举报人也看不到自己提的事有没有被处理。一个
治理动作如果没有记录，就等于没有发生过。

但给失物招领加举报的风险比商品侧高一个量级。商品举报针对的是「这个商品描述不实」，失物招领针对的
是「这个人是冒充的」，而失物招领天然包含「谁丢了东西」这个半公开事实。举报通道一旦做成公开的，
它会立刻变成一条新的攻击面：可以批量举报别人的记录让它在列表里显得可疑，也可以通过举报列表反推出
谁在关注哪条记录。

所以这是「该开、但必须把可见性收紧到只剩运营」的通道，不能照抄商品举报或求购反馈那一套就完事。

## 本轮范围

**一条记录对应一个独立举报表 `LostFoundReport`。** 举报对象是记录本身，不是它的发布者；一条记录
可以被多人举报，同一个人对同一条记录只能有一条（`UniqueConstraint(post, reporter)`）。举报人不允许
举报自己发布的记录，这在模型 `clean()` 和表单里都拦一道。

四个举报理由照实分成四类，第五类是「其他」：

| 理由 | 面向的情况 |
| --- | --- |
| 冒充失主或拾获者 | 发布者不是丢东西或捡东西的人 |
| 涉嫌诈骗 | 以认领、归还为名要钱或要敏感信息 |
| 侵犯隐私 | 描述或图片里出现他人的校园卡、证件、联系方式 |
| 信息不实 | 时间、地点、物品与事实不符，或重复发布 |
| 其他问题 | 上面四类都不成立 |

四个状态构成一条单向前进的线：`pending` → `reviewing` → `resolved` / `rejected`。`reviewing` 是
可选的中间态，进审核页默认落在它上面，用来区分「还没看」和「正在看」。

**四个入口，全部走既有路由风格。**

- `report_lost_found`：详情页侧栏的举报入口，表单只有理由和详情两栏；
- `my_lost_found_reports`：举报人回看自己提交过的举报和处理结论；
- `lost_found_report_list`：运营队列，按状态筛选、分页 20 条；
- `review_lost_found_report`：审核页，写结论并通知举报人。

**审核结论只有一条写路径。** `review_lost_found_report` 是唯一能改 `status` / `reviewer` /
`review_note` / `reviewed_at` 的地方，走 `select_for_update(of=('self',))` 锁主表行——不锁
`post` 和 `reporter` 这些外连接，否则在 PostgreSQL 上会因为可空外连接直接报错。后台
`LostFoundReportAdmin` 把这四个字段全部设为只读：后台能看、能改理由和详情，但结论只从运营页写。
这是为了让「谁在什么时候基于什么结论关掉了这条举报」只有一个答案。

**通知只发给举报人，复用既有 `report_update` kind。** 不加新 kind，`NotificationPreference`
因此不需要新迁移。通知标题是「你提交的举报有处理进展」，正文带记录标题和新状态；
`target_url` 指向举报人自己的列表，而不是审核页——举报人点进去看到的不该是别人的工作台。

**发布者什么都不知道。** 不发通知、不计数、不在详情页出现任何「你被举报过」的提示。举报的意义在于
让运营先看，而先看的结论可能是「这条记录没问题」。让发布者在结论落地前就知道自己被举报，等于把
一个尚未成立的怀疑变成一次公开的伤害，也会让下一个真的该举报的人选择沉默。

## 为什么这样切

**为什么举报人要能看到自己的举报结论，但不能看到别人的。** 「我提的事有没有被处理」决定一个人下次
还举不举报。看不到结论的举报通道，用三次就没人用了。而「别人举报了哪条记录」对举报人是纯风险：
既能反推出谁在关注这条记录，也能照着一个列表批量骚扰。所以列表页永远按 `reporter=request.user`
过滤，运营队列则按 `is_staff` 拦在门外。

**为什么审核页锁主表行而不锁整条 join。** PostgreSQL 不允许对包含可空外连接的查询整体加
`FOR UPDATE`，会直接报 `FOR UPDATE cannot be applied to the nullable side of an outer join`。
这条链路上 `reporter`、`reviewer` 都可空（`reviewer` 是 `SET_NULL`），整条 `select_related` 一起锁
必然踩到。锁 `of=('self',)` 拿的是举报行本身的排他锁，正好也是并发审核要守的那一行。

**为什么「其他」单独一类而不是让用户自由填空。** 自由填写的举报理由在队列里没法筛、没法统计
哪类问题在变多，运营只能一条条读原文。固定选项加详情文本，既能按 `reason` 聚合，又能保留具体情节。

**为什么举报不自动下架记录。** 一条举报是一个信号，不是判决。自动下架会让「批量举报」变成一条
零成本的删帖路径——而这恰好是失物招领这种强时效、难自证的场景最承受不起的。本轮只把信号送到
运营眼前，动作仍然由人决定。

## 判据

- 同一用户对同一条记录只能有一条举报，重复提交在数据库层被拦住，而不是只靠表单提示；
- 举报自己发布的记录被拒绝，匿名访问跳登录，非 staff 打不开队列和审核页；
- 审核页能写入结论、时间、审核人，且只通知举报人；发布者收不到任何通知；
- 审核结论、审核人、审核时间在后台只读，后台无法绕开运营页改结论；
- 举报人的「我的失物举报」只显示自己的记录，处理结论与运营队列一致；
- 举报不改变记录的状态、可见性、匹配关系和站内既有字段；
- 队列支持按状态筛选，分页参数与站内既有分页口径一致。
