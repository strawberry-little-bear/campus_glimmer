# 窄首列网格首格契约设计

## 背景

运营看板「提醒效果」分区里有一张三行小表，静态结构只有「标签 / 数量 / 单位」三项，却复用了订单生命周期那张四轨表格的 `grid-template-columns: 5.6rem 1fr 2.4rem 3rem`。两个后果同时出现：

1. 第四轨（3rem）永远空置，数字被推到中间的自适应轨里，和「件」脱节；
2. 「关闭了生命周期提醒」「缺少可引用的价格证据」这类九字标签在 89.6px 的首轨里折成两到三行，行高从 20px 涨到 39~59px，三行互相错位。

同一个根因还以另一种形态出现过：搜索洞察的小时图在 390px 上要 407px，容器只有 330px，最后几个小时被 `overflow-x: auto` 裁掉——高峰正好落在尾部时就整段看不见；聊天响应趋势的四张汇总卡每列只剩 73px，`<strong>` 和六字 `<span>` 双双溢出内容盒，卡片被撑到 147px 高。

这三处都在页面上一眼看不出病因：前两处是「这一行怎么突然高了」，第三处是「图表右边缺了一截」。浏览器审计抓得到，但代价是逐页逐宽度量，跑一轮以小时计，而且只有数据恰好渲染出那一行时才照得到。

## 更值得记下来的盲区

上一轮的全站溢出扫描漏掉了 47 个分区，原因是运营看板和搜索洞察的分区默认懒加载：`html.js` 下 `.ops-section[data-ops-deferred]:not(.is-revealed) > * { display: none }`，靠 IntersectionObserver 滚到才展开。扫描工具不显式去掉标记再补 `is-revealed`，量到的就是一屏空壳——34 个运营分区加 13 个搜索洞察分区，一次都没被测到。

这不是测试环境噪声，是方法缺陷：任何针对这两个页面的溢出审计，都必须先强制展开懒加载分区，否则结论无效。

## 目标

1. 把「窄首列 + 长内容」这一类缺陷变成可静态判定的契约，秒级跑完，能挂在每次提交上。
2. 覆盖渲染态检查照不到的分支：空状态、他人视角、`{% if %}` 分支、被 include 拆到另一个文件里的结构。
3. 让新增一条窄首列规则时必须先登记首格允许放什么，而不是等上线后由用户发现。
4. 把懒加载分区的审计前提固化成断言，防止下一个人再踩同一个盲区。

## 方案

在 `campus_glimmer/test_page_semantics.py` 新增 `GridFirstCellTests`，四类检查：

### 1. 注册表守卫

静态解析 `static/css/style.css`，抽出所有「首轨是固定长度（px / rem / em / pt，rem 与 em 按 16px 折算）且不超过 170px」的 `grid-template-columns` 规则，要求每条选择器都登记在契约表里。没登记就报错，消息给「选择器 + 首轨像素值」。

不报 CSS 行号：规则可能嵌在 `@media` 里，静态算出来的行号会漂，给了反而误导。

### 2. 内容契约

对登记过的选择器扫全部模板源，断言匹配元素的首个子元素落在允许集合里。允许条目同时约束行上的修饰类：

- `.activity-row` 的首格默认必须是 `<time>`；
- 首格可以是 `<span>`，但只在行同时带 `activity-row--wide-label`（该修饰类把首轨改成 `minmax(7em, auto)`）时成立。

第二条是这次真正起作用的约束：它把「换内容」和「改轨道」绑在一起，不允许只改一半。

模板源先内联 `{% include %}`。卖家工作台的 `.seller-desk-table--stacked` 挂在 `_my_items_table.html` 的 `<table>` 上，`.seller-desk-row td[data-label]` 却在被 include 的 `_my_item_row.html` 里；不内联的话这条选择器一条都匹配不到，契约会悄悄空转。

### 3. 伪元素契约

卖家工作台那张表窄屏时首格是 `::before { content: attr(data-label) }`，DOM 里根本没有子元素可查。改成反向约束属性文本长度：`data-label` 最多 4 个字（72px 首轨按 .65rem 字号放得下）。同时断言规则体里确实还有 `attr(data-label)`，哪天首格改回真实子元素，这条契约会提示换登记方式。

### 4. 懒加载分区守卫

断言 `operations_dashboard.html` 的 `data-ops-deferred` 和 `search_insights.html` 的 `data-si-deferred` 数量不为零、不超过各自分区总数，`main.js` 里仍有对应选择器，样式表里仍有 `html.js` 下的 `display: none` 规则。四条同时成立，才说明懒加载结构完好、审计前提仍然有效。

## 为什么不做成浏览器审计

浏览器审计是必要的补充，但不能当守门人：起服务、装驱动、逐页访问以小时计；只能点亮演示数据恰好命中的分支；而窄首列这类问题的根因在样式表和模板的静态组合里，本来就不需要渲染才能判断。反过来，浏览器审计该承担的「整体横向溢出、元素互相重叠」仍然由它承担，两者分工不重叠。

## 非目标

- 不覆盖 `grid-template-columns` 首轨是 `auto` / `minmax()` / `fr` / `repeat()` 的规则：这些轨道宽度由内容决定，不属于同一类缺陷。
- 不量真实像素宽度。契约判的是「首格是什么」，不是「首格有多宽」；后者留给浏览器审计。
- 不改动任何业务模板、样式或路由；本轮只加测试和文档。

## 验收标准

1. 四条检查全部通过，且跑完在秒级。
2. 变异测试：分别新增一条未登记的窄首列规则、把 `supply-lifecycle-level-label` 改成普通 `span`、把 `data-label` 改成六字、抹掉全部 `data-ops-deferred`，四条检查各自变红。
3. `manage.py check`、迁移一致性检查通过。
4. 运营看板与搜索洞察在 390px 下 `overflow=0`、无元素溢出容器、小时图 24 列完整收进内容盒。
5. 全量测试通过后才提交。

## 实施记录

1. 修复 `_lifecycle_reminders.html` 的「仍未真正收到的卖家」三行：新增 `.supply-lifecycle-level--compact` 三轨变体（`auto minmax(0, 1fr) auto`），首轨交给内容自适应，标签单行。选择器多带一层 `.supply-lifecycle-levels` 把特异性抬到 (0,2,0)，窄屏媒体查询里那条四轨规则不会误伤这个变体。
2. 搜索洞察小时图在 575px 以下把间距收到 2px、轨道下限放到 0，24 列收进 326px 内容盒；列上的计数与小时标签都是绝对定位，且标签每 3 小时才出一个，收窄后不相撞。
3. 聊天响应趋势汇总卡在 575px 以下从四列改两列，每列 130px 内容宽。
4. 新增 `GridFirstCellTests` 四类检查与两份契约表，模板源带 include 内联。
5. 用 Chrome headless 复核：40 个 URL 的全站扫描加上 12 个补充页面，390px 下全部 `overflow=0`、无元素溢出、无网格首格溢出。
