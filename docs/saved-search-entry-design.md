# 关注搜索的管理入口与命中回溯

## 起点

「关注搜索」这条链路早就是完整的：`saved_searches.py` 负责匹配与分流，
`SavedSearch` / `SavedSearchMatch` 两个模型把即时命中和待汇总命中都记了下来，
`saved_searches.html` 甚至已经写好了暂停、改节奏、删除的整套界面。
`send_saved_search_digest` 发出的每一条汇总通知，`target_url` 也都指向
`reverse('saved_search_list')`。

但全站没有任何一个模板链到 `saved_search_list`。用户在商品发现页保存了一组
筛选条件，看到的只是一条「已保存，有新商品匹配时会通知你」的提示，然后就
没有了——没有地方能看见自己存了什么、改节奏、暂停，或者临时静默。
真正收到汇总通知点进去的人，也是靠通知里的 `target_url` 才第一次见到这个页面。

一条只写了通知、没写入口的功能，对用户来说等于不存在。本轮补的就是这条断链。

## 补什么

### 1. 导航入口

放在用户下拉菜单里，和「最近浏览」「我的心愿单」这些个人化内容并列。
没有放进顶部一级导航：一级导航是全站共享的，而关注搜索是个人配置，
放在那里会挤占「发现好物」「求购广场」这些公共入口的位置。

### 2. 保存成功后的提示改成带链接

原来保存成功后只 `messages.success` 一句。现在这句话里带上通往管理页的链接，
保存动作和管理动作之间不再需要用户自己猜路径。

### 3. 卡片上的命中数改成可点的

`_attach_saved_search_stats` 已经在为每条关注搜索算两个数：
`pending_match_count`（待汇总的命中）和 `live_match_count`（当前仍满足条件的在售商品）。
这两个数此前只是展示。现在给它们各自一条链接，直接跳到商品列表页并带上这组筛选条件，
让「当前命中 5 条」这句话变成能点的。

## 命中回溯的两种口径

这两个数语义不同，回溯方式也必须不同，混用会误导用户：

- `live_match_count` 是**实时口径**，用 `matches_saved_search` 逐件比对当前在售商品得出的。
  点它应当跳到商品列表，让 Django 的那套筛选重新跑一遍——页面顶部会显示
  「已扩展匹配」和当前筛选条件，用户能确认自己看到的和数字是同一批。
- `pending_match_count` 是**缓冲口径**，数的是 `SavedSearchMatch` 里还没发出去的记录。
  这些命中可能已经过期、下架或卖掉了，点它不该装作它们还在售。

所以只有 `live_match_count` 做成可点的，`pending_match_count` 保持纯展示。
这不是偷懒：一个待汇总的缓冲数如果点了却跳不到对应商品，比不点更让人困惑。

## 链接怎么构造

`item_list` 的筛选走 query string：`q`、`category`、`location`、`condition`、
`min_price`、`max_price`。这正好和 `SavedSearch` 的字段一一对应，
所以链接就是把这几个字段原样拼起来，不引入新的匹配逻辑。

这里刻意**不复用** `matches_saved_search`：那个函数是 Python 侧的逐件比对，
只服务于「新商品发布时该通知谁」这一个写路径；而列表页的筛选是 ORM 侧的，
两边各自演进才不会互相绊住。真要校验，靠测试钉住「同一条关注搜索，
`live_match_count` 和列表页实际返回条数一致」。

`sort` 参数不写死。默认排序对「我刚保存的这个条件现在有什么」是最合适的，
把用户按死的排序强加过来没有收益。

## 工作台分页与操作回跳

关注搜索刚上线时，管理页会一次读取用户的全部记录，并对每条记录逐件扫描当前在售商品。
记录一多，页面响应就会被“展示所有卡片”和“重复计算所有命中”同时拖慢。现在列表按
`-is_active`、`-created_at`、`-pk` 排序并每页展示 8 条，只对当前页调用
`_attach_saved_search_stats`，因此全量计数仍准确，但命中计算量与页面大小保持有界。

暂停、保存提醒节奏和删除的表单都会带上当前 `request.get_full_path()`。视图只接受
通过 `url_has_allowed_host_and_scheme` 校验的同站地址，外部 `next` 会回退到管理页首页，
避免把表单变成开放重定向。删除最后一页的唯一记录后，`Paginator.get_page` 会自然收敛到
仍然存在的页面。

## 不做什么

- **不做未登录可见的入口。** 关注搜索是个人数据，`saved_search_list` 本身已有
  `@login_required`，入口也只挂在登录后的用户菜单里。
- **不给 `pending_match_count` 加跳转。** 理由见上一节，缓冲口径无法保证商品仍在。
- **不做单独的「命中记录」时间线。** `SavedSearchMatch` 是通知缓冲区而不是历史账本，
  把它渲染成历史会给用户「我错过的东西都在这儿」的错觉，实际汇总发完就清了。
- **不改变暂停、节奏、删除的业务语义。** 本轮只调整列表规模与回跳方式，操作仍由原视图完成。
