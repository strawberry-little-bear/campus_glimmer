# 商品图片缩略图与历史回填设计

## 背景

上一轮迭代已经把「新上传的过大图片」治理到最长边 1600 像素内。但列表场景并不需要 1600 像素：商品卡片、搜索结果、我的商品表格、同类商品和详情页的小缩略图都在用 `item.images.first.image.url` 读取同一张原图。

这意味着页面加载的瓶颈分成了两层：

1. 新图片已经适合详情页，但对列表页仍偏大。
2. 历史图片没有统一的小图版本，且不能为了页面提速一次性重写全部历史文件。

本设计补第二层：给每条 `ItemImage` 增加可选缩略图，新图入库时生成，历史图片通过可重复执行的管理命令回填；页面读取时永远保留原图回退。

## 目标

1. 新上传商品图片在保存记录时同步生成列表页缩略图。
2. 提供幂等回填命令，逐步为历史图片补缩略图，不要求一次性停机完成。
3. 商品卡片、搜索结果、我的商品、同类商品和详情缩略图优先读小图。
4. 缩略图缺失、历史图片未回填或生成失败时，页面回退原图，功能不中断。
5. 缩略图生成失败不影响主图保存，错误只记录异常类名，不记录路径、标题或用户。
6. 回填命令写入定时任务台账，便于运营确认它是否真的跑过。

## 缩略图口径

- **最长边 480 像素**，等比缩小；小于该尺寸的图片不放大。
- **输出 WebP，质量 80**。列表卡片和表格缩略图的显示尺寸显著小于 480 像素，这个规格在清晰度与体积之间足够。
- 生成前应用 EXIF 方向，保证详情原图和列表缩略图方向一致。
- 透明通道保留。
- 缩略图文件名使用服务端随机名，不使用用户上传名。

## 数据与存储

- `ItemImage` 新增 `thumbnail`：
  - `ImageField`
  - `upload_to='items/thumbnails/'`
  - 可为空
  - 不出现在表单中
- 原图字段和原图 URL 不变。
- `thumbnail` 为空表示「尚未生成」或「生成失败后暂时回退」，不把它解释成图片违规。
- 替换主图时重新生成缩略图；旧行已有缩略图但主图变化时，不能继续沿用旧小图。
- 不做存储层孤儿文件清理；删除记录后的文件治理需要单独设计。

## 回填命令

新增 `python manage.py backfill_item_thumbnails`：

- 默认处理所有缺失缩略图的记录，按 `id` 升序，保证多次执行时进度可预期。
- `--limit N` 限制本次最多处理 N 条，适合把回填拆成多批。
- `--dry-run` 只报告待处理数量，不写文件、不改数据库。
- 命令是幂等的：已有缩略图的记录直接跳过。
- 单张历史图片解码失败时记录失败数并继续处理后续记录；这类数据质量问题不阻断整批任务。
- 命令结果写入 `TaskRun`：
  - `marked`：本次检查的候选行数
  - `failed`：生成失败行数
  - `skipped`：已有缩略图或无需写入的行数
- 这是一次性迁移辅助命令，不加入周期任务健康面板的“已知周期命令”清单，避免把未调度的一次性任务误报为静默。

## 页面策略

- 详情页主图仍读原图；点击缩略图后也切换到原图，保证用户查看细节时不降质。
- 缩略图条、商品卡片、搜索结果、我的商品和同类商品优先读 `thumbnail`。
- 模板通过 `ItemImage.list_image_url` 取图：有缩略图用缩略图，否则回退原图。
- 回填期间页面会出现「部分小图、部分原图」的混合状态，这是预期；不为了统一显示而隐藏未回填商品。

## 非目标

- 不做 `srcset`、懒加载或 CDN；这些依赖布局和实际流量数据，后续单独评估。
- 不修改图片排序、主图选择规则，也不引入 `is_primary`。
- 不判断图片内容，不做违规识别。
- 不删除或重写历史原图。
- 不清理数据库行已删除但文件仍留在存储里的孤儿文件。
- 不把缩略图生成结果写进运营看板；任务台账只回答命令是否执行、处理多少、失败多少。

## 验证口径

1. 新保存的 `ItemImage` 自动生成 WebP 缩略图，最长边不超过 480。
2. 原图小于 480 时不放大。
3. EXIF 方向应用后，缩略图方向与原图展示方向一致。
4. 替换主图后缩略图会重建，不会继续使用旧图。
5. 缩略图生成失败时主图记录仍可保存，页面回退原图。
6. 回填命令能补历史行、重复执行不会重复生成，`--limit` 和 `--dry-run` 生效。
7. 坏的历史图片不会让整批命令失败，只计入失败数。
8. 列表相关模板输出缩略图 URL；缩略图缺失时输出原图 URL。
