# 关注搜索的命中时延，第一次被运营读到

## 起点

`SavedSearchMatch` 表里躺着两个时间戳，两个都一直在写：

- `matched_at`（`auto_now_add`）——这件商品命中这条关注条件的时刻，写在 `notify_saved_search_matches` 里；
- `notified_at`——这条命中被送达用户的时刻，写在 `send_saved_search_digest` 和 `deliver_buffered_saved_search_matches` 里。

写这两个字段的理由很直接：即时节奏不需要缓冲区，日度和周度节奏需要——否则一周的命中会变成几十条近乎重复的通知。写完之后，`notified_at` 被用来做「哪些还没发出去」的筛选条件，`matched_at` 只被用来给缓冲区排序。**两个字段的差值，从来没有任何一行代码算过。**

运营侧现在能回答的是「发了多少条」「还有多少条没发」。回答不了的是「一条命中从产生到送达，平均等了多久」「周度节奏是不是等得太久了」「这些等太久的命中，商品是不是早就卖掉了」。这三个问题恰好是判断汇总节奏该不该调整的全部依据。

而判断依据缺失的代价是实的：一个用户保存了「图书馆附近考研资料」这个条件，选了周度汇总，一周后收到一条「另有 7 条未展示」的通知——点进去发现三件已经下架。他不知道这是节奏问题还是自己条件太宽，运营也不知道。

## 口径上的取舍

### 只算已经送达的样本

分母只收 `notified_at` 非空的记录。还在缓冲区里躺着的命中没有送达时刻，谈不上等待多久——这是右删失样本，和 `return_handshake`、`handoff_code_usage` 是同一个道理。它单独数出来，不丢也不混。

### 等待时长按天分档，不按小时

一次汇总等待的时间尺度是天。报「平均等了 31 小时」对一个按周运转的节奏没有意义，而「平均等了 1.3 天」立刻能看出日度节奏是正常的、周度节奏是偏慢的。分档左闭右开，和其余模块一致。

### 日度和周度必须分开报

这两个节奏的等待时长天然不同，合成一个平均数会把两者的差异抹平。日度节奏等了两天是异常，周度节奏等了两天是正常。分开报，运营才能看出是哪一档该调。

分档阈值因此按节奏各设一套：日度看「有没有拖过一天」，周度看「有没有拖过一周」。

### 时延要按命中商品的最终状态对照

这是这个模块真正的价值所在。一条命中等了三周才送到，而商品第二天就卖掉了——用户收到的通知是无效的。反过来，一条命中当天就送到了，商品还挂了一周——这条通知是有效的。

所以统计要交叉两个维度：**时延** × **送达时商品是否还可交易**。这个交叉回答的是「汇总节奏的等待有没有真的让用户错过东西」，而不是「我们发得快不快」。

商品状态取 `Item.objects.available()` 之外的都算不可交易。注意这里看的是**送达那一刻**的状态还是**当前**状态：`notified_at` 之后商品仍可能被下架或卖出，用当前状态回看会让「发得很及时但商品后来卖掉了」被误判成错过。但反过来，历史状态没有记录。

**取舍**：用当前状态，但在报告里明确写出这个口径——「以下对照以当前在售状态回看，送达之后才下架的商品会被算成不可交易，因此这一栏是高估」。运营看到高估的数字会去核实，看到低估的数字会直接相信。宁可高估。

### 不做成「提醒用户商品已下架」

只报告，不改写。这是全项目统计模块一致的边界：统计模块只读，动作归动作。如果将来要做「失效命中清理」，那是一个独立的写路径，需要自己的设计和自己的约束，不该塞进一个只读的统计里。

## 不做什么

- **不算即时节奏的时延。** 即时节奏的 `matched_at` 和 `notified_at` 是同一笔写入的两个字段，差约等于零，报出来是噪声。只统计 `daily` 和 `weekly`。
- **不按用户分层报告个体时延。** 那是隐私面很大的东西，而运营要改的是节奏参数，不是某个用户的等待。按节奏报总体就够了。
- **不把等待时长做成「用户体验分」。** 等待久不等于体验差——一个选了周度汇总的人就是在主动选择少收通知。报事实，不裁断。
- **不清理失效命中。** 理由见上一节。
